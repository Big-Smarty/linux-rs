# Repository-local skills

## Contract and discovery

This repository ships **16 original local skills** under `.agents/skills/<name>/SKILL.md`. They are versioned, portable instructions for this kernel program, not implementation or certification. Their local paths and descriptions are the discovery interface. Read [AGENTS.md](../AGENTS.md), [contributor workflow](../CONTRIBUTING.md), [decisions](decisions.md), and the relevant skill bodies before a matching task; combine skills when a change crosses boundaries. Reading only this index is not activation of a skill's detailed procedure.

No particular agent vendor, global installation, network service, leaderboard, or external skill manager is required. If a client supports repository skill discovery, enable it deliberately for this checkout and inspect what it will load. If it does not, open the linked `SKILL.md` files directly and follow the same rules. Do not silently edit global configuration or copy these skills into a user's home directory. Skills do not grant authority to execute unsafe operations or override the task's no-gates instruction.

Global Rust skills can provide optional language/compiler assistance. They are **not portable project requirements**, may recommend unsuitable userspace/embedded allocation or C-backed FFI patterns, and never override Rust-only runtime/tools, Linux semantics, unsafe/concurrency, performance, licensing, or hardware rules here. Do not blind-install `npx`/external skills, execute downloaded skill scripts, or trust popularity as evidence of kernel fitness. Any external instruction/code proposal requires source/license/security review and explicit adoption. See [dependencies](dependencies.md).

## Format, adoption, and maintenance

The [Agent Skills specification](https://agentskills.io/specification) is the primary format reference. Each local skill has a `SKILL.md` with opening/closing `---` YAML frontmatter, a lowercase-hyphen `name` matching its directory, and a nonempty `description` describing purpose and activation triggers. Keep both required fields single-line scalars for the local auditor; follow the upstream name and length constraints, not only the subset the auditor can recognize. Instructions follow as Markdown with ordinary relative file links. Relative repository links inside `.agents/skills/<name>/SKILL.md` go up **three** parents, for example `../../../docs/verification.md`.

Names and paths above form the contractual set of 16. Renaming, adding, removing, or changing a trigger requires updating this index/matrix, dependent skills, [agent rules](../AGENTS.md), affected subsystem plans, and auditor expectations where applicable in one reviewed change. Optional referenced resources are loaded on demand; do not add implementation scripts in non-Rust languages merely because the general format permits them. New optional external skills are opt-in reviewed proposals, not hidden runtime prerequisites.

When baseline, ABI, architecture, dependency policy, threat model, hardware qualification, or performance gates change, update all affected skill procedures and primary citations with the relevant plan. Review for conflicts, stale shortcuts, unsupported completion claims, broken relative links, and whether the skill explains failure/recovery as well as success. Keep upstream facts distinct from proposed local mechanisms. Preserve provenance and license notices for copied/adapted material; these local skills are original project guidance, not a claim to have imported or vetted every external skill.

The integration owner's actual host checks are `cargo run -p xtask -- check` and `cargo run -p xtask -- status`, documented in [CONTRIBUTING](../CONTRIBUTING.md) and [project audit](project-audit.md). The auditor checks its documented metadata/link/source subset; it does not establish instruction quality, security, complete format conformance, kernel behavior, physical test results, or performance. Do not claim that audit passed before it actually runs. Required tests and observed execution are separate: use the artifact-bound [implementation record](implementation.md), not the presence of a skill, to establish what exists and ran.

## Current implementation, tooling and deployment scope

The earlier planning-only boundary is historical. `kernel/` now contains a real original Rust `no_std` x86_64 bootstrap using external Limine 12.9.3, base revision 5, UEFI OVMF/q35 and explicit four-level paging. [Implementation evidence](implementation.md) binds Rust paths and workstream routing to the frozen `target/kernel-first-boot/cell9/` artifacts: eight actual bounded QEMU cases (positive exit 33, seven negative exits 35), five production-parser host tests, and strict owned-crate Clippy for host tests and both freestanding release profiles. These are local ignored evidence artifacts, not a checked-in distribution or M1/full-Linux completion. No physical candidate boot/recovery or performance pass is claimed. Initial cell sequencing is engineering work; integration Clippy is repository verification, not an invented detailed user approval.

[Workstreams](../planning/workstreams.tsv) retain exactly five tab-separated columns: `id`, `upstream_prefix`, `plan`, `priority`, `status`. Only `not_started` and `in_progress` are allowed. The canonical [row-ID → Rust-path → revision-evidence table](implementation.md#routed-implementation-status) names all current `in_progress` owners; every other row remains `not_started`. Read that table before changing status. `in_progress` means genuine routed implementation, not a translated upstream prefix, completed workstream, compatibility claim or percentage. Do not add a completion state or change the schema to store test outcomes.

Host tools declare MSRV 1.88 as an engineering metadata baseline, not a user-specified Rust version. That is separate from the kernel manifest's 1.101 declaration and the actually qualified runtime compiler, `rustc 1.101.0-nightly` commit `5c543b0b8c73c7b72bc8284ced4fb22ead15734d` with LLVM 23.1.1 and matching `rust-src`/build-std `core` and `compiler_builtins`. Nightly kernel/parser tests do not establish host-tool qualification on 1.88. Any authorized 1.88 gate must select only host packages (`-p xtask -p baremetal`, or `--workspace --exclude kernel`), not a workspace build including `kernel`. A mutable `nightly` alias or stable host `core` is not the runtime identity. Use the exact [implementation commands and artifact inspection](implementation.md) and maintained [kernel tooling](kernel-tooling.md); do not label manual cell9 runs as harness executions.

The [current source record](implementation.md) adds independent matching kernel.org/GitHub objects and a local GPG “Good signature” for the pinned tag. Signer fingerprint `647F28654894E3BD457199BE38DBBDC86092693E` matches kernel.org HTTPS/WKD publication; GPG still reports `TRUST_UNDEFINED` / `[unknown]`, not Web-of-Trust or ultimate trust. Preserve the original GitHub-only retrieval history rather than retroactively claiming it used local verification.

In addition to the planning auditor, [the Rust bare-metal smoke suite](bare-metal-suite.md) provides actual bounded non-destructive Linux functional tests now. Read `kernel-verification`, `kernel-security`, `kernel-documentation`, and the affected mechanism skills when changing it. Its CLI is `cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>`; choose exactly one environment label. That label is an operator assertion, not hardware proof. Host-reference results exercise the runner and running host Linux only, not a new kernel, full Linux parity, broad hardware qualification, or performance.

Skills must follow the [exhaustive definition-of-done contract](definition-of-done.md), keeping bootstrap observations distinct from full-kernel completion. Only the current workstation is available; other hardware is explicitly blocked. Candidate installation/selection/boot is user-operated, never an agent reboot/install action. The existing `freestanding` diagnostic ELF permits planning an isolated, storage-free M1 trial on separate user-owned recoverable media with independent known-good recovery before rootfs/initramfs/userspace exists. It is not a Linux-replacement package, has not physically booted, and excludes QEMU-only COM1/debug-exit assumptions. Native Limine ELF is not systemd-boot EFI/PE/Linux-image compatibility. [Packaging](packaging.md) still requires real storage, durable filesystem, root/initramfs, init/userspace and the broader gates for a separate Arch-like Linux-replacement package, preserving the working kernel and recovery. The approved first userspace remains Arch/CachyOS without downstream CachyOS kernel patches, using a balanced server profile. Activate `kernel-release`, `kernel-dependencies`, `kernel-firmware`, and `kernel-architecture` for changes to that deployment contract.

The accepted architecture is modular monolithic Rust, with only unavoidable function-local `asm!`/`naked_asm!` under proof and no standalone/global assembly escape. Skills must enforce fixed upstream Linux 6.18.57 feature scope plus explicit reviewed security deltas; later feature-baseline changes require a separate decision. Security deltas need provenance, rationale, compatibility-impact review, and regression/security/performance evidence rather than silently weakened semantics. Complete module coverage means every **in-baseline** module's functionality; arbitrary third-party/proprietary out-of-tree additions require separately enumerated approval.
