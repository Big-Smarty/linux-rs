# Definition of done: planning history, bounded implementation and whole-kernel completion

## Authority and present state

**Latest delivery authority:** after publishing the bounded checkpoint, the user asked to continue with a first-userspace slice and a complete roadmap ([A18–A20](decisions.md)). This changes what this round delivers, not what complete Linux means. The previously published code wave was indexed memory003 plus corrected image inspection, preserving the008 CPU repair; [the publication checkpoint](implementation.md#publication-checkpoint) records its actual current commands, outcomes, source identities and remaining work. Historical cell9/eight-case/five-parser-test evidence is not the current proof. M0 retains unresolved gates; **M1–M8, full Linux6.18.57, physical qualification, replacement packaging and Linux-parity performance remain unclosed**.

The behavioral/source baseline is Linux **6.18.57**, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`, with exact inventory and authentication limitations in [coverage](coverage.md). First implementation priority is x86_64 QEMU plus early physical bring-up; first distribution userspace is Arch/CachyOS with a balanced server profile. Neither priority excludes other architectures, desktops, embedded/real-time operation, legacy hardware, filesystems, protocols, or configuration surfaces. CachyOS userspace does not add its downstream kernel patch set to the pinned baseline.

The accepted architecture is a **modular monolithic Rust kernel**. Feature scope remains fixed at that baseline; explicit reviewed security deltas require a recorded rationale, behavior/threat-model impact and regression evidence, rather than silently chasing a moving release. Later feature-baseline changes need a separate decision. Every in-baseline module's functionality needs a Rust replacement, but arbitrary proprietary/third-party out-of-tree modules are not implicitly added to this project: extra functionality must be separately enumerated and approved. Rejecting legacy C module loading does not reduce the in-baseline functionality obligation.

This document governs completion language alongside [architecture](architecture.md), [compatibility](compatibility.md), [verification](verification.md), [performance](performance.md), [bare metal](bare-metal.md), [packaging](packaging.md), and the [roadmap](roadmap.md). A narrower successful experiment can be reported precisely; it cannot be titled “the Linux port is complete.”

## Distinct deliverable boundaries

### Original planning/setup delivery contract

The original planning assignment required the following. These historical acceptance criteria remain useful for maintaining the plans and tools; they do not describe the current repository as kernel-free:

1. The immutable reference, full structural inventory, longest-component-prefix workstream ownership, provenance caveats, and all plans agree. Every reference tree/blob/gitlink is accounted for, including root metadata, licensing, documentation, samples, build machinery, architecture support and host tools. Structural counts are never implementation percentages.
2. Ordered mechanism-level plans identify dependencies, Linux compatibility traps, reusable/shared mechanisms, Rust dependency candidates and rejections, safe simplifications, invariants, security, improvements and observable tests for each workstream/subfamily. Missing implementation evidence is described as missing, not generated as a successful status.
3. Full-project completion, per-change completion, proof stages, exact compatibility oracles, hardware/performance obligations, packaging/recovery design and ongoing baseline maintenance are explicit. Unavailable hardware/toolchains and unauthenticated source provenance remain named gates, not invented passes.
4. Project-owned executable setup tools are Rust; local agent skills and instructions enforce the project constraints. The offline [project audit](project-audit.md) checks only its documented syntax/structural contracts, including negative fixtures. Its actual invocation/results must be reported by the integrating agent; this document is not an execution log.
5. A real, runnable dependency-free Rust [bounded smoke suite](bare-metal-suite.md) is delivered with CLI, exact-release checking, explicit environment assertion, new output-directory protection, bounded/time-limited non-destructive tests, individual pass/fail/skip/unavailable records and environment limitations. A reference-host execution validates the runner, not the replacement kernel. Actual exercised outcomes belong in the evidence record, not a prewritten claim here.
6. [Arch-style packaging](packaging.md) specifies genuine future artifacts, user-controlled install/entry/reboot, both boot-manager integrations and rollback. No placeholder kernel package, fabricated binary or untested install claimed as working is delivered.
7. All local links/callers/contracts affected by this delivery are consistent; the integrating agent runs the agreed setup checks once after all edits land. Remaining M0 decisions/authentication limitations are reported accurately, rather than erased to make the planning milestone appear unconditional.

Planning completion does **not** advance any kernel row to implemented, compiled, booted or qualified. The runner's bounded functional coverage does not implement the broad differential, destructive recovery, hardware or statistical performance suites required below.

These are progress labels, not the proof stages below, not whole-prefix completion and not percentages.

### Final whole-kernel project done

Final completion requires every reference obligation below implemented in Rust or correctly accounted for as non-executable/reference material, every applicable qualification gate passed, and no missing port hidden as deferred, unsupported, skipped, unavailable, excluded, or “later.” An unimplemented old driver still blocks full completion even when the initial server boots without it. A hardware shortage blocks its qualification; it does not remove that driver from scope.

The claim is finite and evidence-bounded: complete accounting of the pinned reference and its enumerated behavior/configuration/hardware obligations, backed by the stated proofs and tests. It is **not** a claim that a script or finite test suite mechanically proves every possible future input, physical fault, schedule or unknown Linux bug. Newly discovered baseline behavior creates a tracked obligation and can reopen qualification; a baseline update requires an explicit inventory/behavior delta, never silent scope drift.

## Obligation registry: what “everything” means

The existing [inventory](coverage.md) is structural only. Before any implementation-completeness claim, create and maintain reviewable, machine-checkable qualification registries linked to it. These are future required records, not tables already generated by the setup auditor. No row may be certified by a directory name, source-line count, stub symbol, enabled Kconfig option or mere test name.

Each lowest independently testable obligation records:

- Immutable upstream path/object and source range; function, type, macro, constant, exported symbol and generated-source origin as applicable. Many upstream items may map to a shared Rust implementation, but every caller, side effect and variant must be covered, with a reviewed semantic mapping.
- Owning workstream/subsystem and ordered implementation step; downstream paths/symbols; dependencies and all affected callers; reviewer; exact candidate revision/build digest.
- Relevant Kconfig symbols, types/defaults/dependencies/select/imply/choice interactions, architecture guards and generated values; applicable `y`/`m`/`n` behavior, failure-to-configure cases and build variants. A shared feature model may replace Kconfig internally only with a complete, tested mapping.
- Architecture, subarchitecture/CPU extensions, word/address/time widths, endian mode, page size, memory model/ordering, ABI/compat personality, SMP/UP, NUMA, MMU/no-MMU, firmware/platform and toolchain constraints. Only combinations genuinely invalid in the baseline may be marked not applicable, with source-backed proof and reviewer; an unavailable Rust target is a blocker, not invalid baseline support.
- Device bus IDs, revisions, subsystem IDs, firmware requirements, DT compatible strings/ACPI IDs, match tables, quirks, board/platform variants and hardware dependencies. “PCI driver ported” does not qualify every matching device or quirk.
- Syscall number/personality, ioctl command/layout, flags/errno, netlink family/attributes, proc/sysfs/debugfs fields and permissions, socket option/address family, protocol/state machine and wire format; on-disk filesystem/feature/version and recovery format; module, firmware and boot interfaces. Enumerate reserved/unknown inputs, not only happy paths.
- Source/license/provenance disposition; Rust implementation identity; unsafe/inline-assembly audit links; third-party dependencies and firmware records; functional, error/state, concurrency, recovery, QEMU, physical and performance evidence IDs with precise applicability and outstanding blockers.

Use separate dimensions rather than fabricating the full Cartesian product. Record constraints and equivalence classes, justify reductions, test boundaries/interactions, and review that every **valid** baseline combination has a disposition. Compilation may use dependency-aware covering sets where exhaustive combinations are infeasible; uncovered combinations remain unqualified until a sound reviewed argument or direct evidence closes them. A pairwise sample alone is not proof of all interactions. Registries must expose the residual, not suppress its denominator.

## Proof stages are distinct

Maintain these exact meanings for each obligation/configuration and candidate. Evidence stages can be represented as independent fields; passing a later narrow experiment does not fill missing earlier reviews or qualify a wider row.

| Stage | Required evidence | Does not establish |
| --- | --- | --- |
| `mapped` | Reference identified, ownership/dependencies/interfaces enumerated, Rust target and tests planned. Initial workstream `not_started` can have structural mapping. | Any executable port. |
| `ported` | Complete actual Rust behavior and caller migration, reference mapping reviewed, no substitute stubs/legacy runtime; tests authored and invariants documented. | Compilation or exercised correctness. |
| `compiled` | Reproducible build/link of the exact artifact for the named architecture/config/toolchain; warnings, generated ABI/layout checks and artifact identity reviewed. | Boot or functional behavior. |
| `QEMU-verified` | Exact virtual machine model/firmware/topology and kernel/userspace revisions, boot logs, oracle comparisons, individual tests, errors and recovery outcomes retained. | Real DMA, silicon timing, firmware, physical devices or performance parity. |
| `physical-qualified` | User/lab actually boots and tests the exact candidate on the identified physical platform/profile with recovery provision and recorded outcomes; all row-required hardware tests pass. | Any untested machine/device or Linux-performance qualification. |
| `performance-qualified` | Functional/security qualification plus matched-baseline statistical results meet the per-workload/per-hardware contract below; raw data and analysis reproducible. | Unmeasured workloads, architectures, devices or future versions. |

`blocked`, `failed`, `inconclusive`, `unavailable`, `skipped` and `not_started` remain explicit non-passing outcomes. `not_applicable` is permitted only for a demonstrably impossible/inapplicable baseline combination, with reviewed reason; it is not an escape hatch for missing hardware or effort. Successful artifacts expire/reopen when relevant code, configuration, compiler, dependencies, firmware or hardware changes. Impact analysis must identify which prior evidence remains applicable and why.

## Every implementation step and subsystem must meet this checklist

1. **Semantic contract:** name exact reference entry points, valid/invalid inputs, pre/postconditions, ownership/lifetimes, locking/order, interrupt/preemption/allocation context, externally visible state transitions and invariants. Resolve discrepancies by running the pinned Linux reference with matching configuration and retaining the reproducible fixture; standards/descriptions support but do not replace the behavioral oracle. Nondeterministic outputs require a predeclared allowed relation, not brittle byte equality or a retrospective waiver.
2. **Real implementation:** migrate every applicable callsite and remove obsolete implementation/shims. No fake return-success, no-op side effect, hard-coded demo output, panic/ENOSYS wall, C-backed kernel bridge, legacy C module, foreign-language runtime implementation or disabled security path may stand in for the required port. A real Linux-defined `ENOSYS`, `EOPNOTSUPP` or no-op is correct only where the matched reference/config/input actually requires it; attach that evidence.
3. **Oracle tests:** differential success values, errno and error precedence, short/partial I/O, restart/EINTR, timeout/cancellation, boundary/overflow/alignment/endian/compat inputs, invalid pointers/lengths/flags, observable data/layout and permissions. Include exact expected state after failure, resource release, refcount/lock accounting, object lifetime and cross-process effects. Record test implementation, fixture and reference result, not just “run LTP.”
4. **State/concurrency tests:** full transition coverage, competing close/unmount/hotplug/reset/shutdown, lost-wakeup/ABA/reordering hazards, SMP/weak memory, allocation failures and quota/OOM exhaustion, repeated stress/fuzzing with retained seeds and minimizations. Prove safety assumptions locally; a passing stress run alone does not prove race freedom.
5. **Durability/recovery:** for persistent effects, define acknowledgement/ordering/flush/FUA/fsync/rename/directory-sync promises against Linux, then check crash points, torn/failed/reordered writes, replay/idempotence, corrupted metadata and remount/recovery. Test surviving data, ownership, link counts and errors after each fault. Only disposable media/images and explicit destructive opt-in in an isolated lab; ordinary workstation smoke cannot satisfy this gate.
6. **Unsafe/assembly:** enumerate each unsafe block/interface, validity/aliasing/provenance/lifetime/pinning/ordering requirements, boundary validation and failure behavior, independent reviewers and exercised adversarial tests. Function-local `asm!` and `naked_asm!` are permitted only where unavoidable: explain why Rust/intrinsics cannot suffice; specify registers, memory/clobbers, stack/flags/privilege/interrupt assumptions, unwind and control-flow contract, and retain target disassembly checks. Naked functions additionally prove complete entry/exit, stack and calling-convention behavior without assuming a compiler-generated prologue/epilogue. No `global_asm!`, project standalone `.S`/`.s`, C/C++/Zig implementation or build-script escape.
7. **Dependencies/legal:** exact locked versions/features/targets, transitive/build/proc-macro/native-code audit, no hidden C build or unreviewed allocation/panic assumption in kernel context; provenance from original source through Rust mapping, SPDX/per-file exceptions/notices and GPL-compatible distribution under [licensing](licensing.md). Independently authenticate release sources before a release claim; GitHub's verification flag alone is not that proof.
8. **Qualification/integration:** affected unit/model/ABI/differential/adversarial/integration tests and applicable architecture/configuration compilation, QEMU, early physical and performance records pass. All caller/subsystem/deployment contracts, documentation, changelog and test expectations are updated. The agent implementing a slice names checks for the integrating owner rather than independently storming shared gates.
9. **Subsystem closure:** all child obligations, exports, Kconfig/device/ABI/format rows and dependency cycles resolved; aggregate evidence identifies each version/configuration. Passing the happy-path server workload cannot close its filesystem, network stack or architecture family by itself.

## At least Linux performance is a release gate

[Performance](performance.md) defines the measurement program. Every applicable workload/hardware/configuration row must be **at least the real pinned Linux baseline**, preserving equivalent functionality, correctness, security/mitigation settings and workload semantics. This includes throughput, latency and tails, CPU work/utilization, resident/peak memory, startup and power/energy where applicable; applicability must be justified before results, not chosen to discard a regression. A faster geometric mean cannot hide one failing row.

Control compiler/optimization comparability, userspace, data/cache state, storage, network peers, firmware/microcode, CPU topology/affinity, power/thermal policy and security configuration. Use independent repeated paired/interleaved runs, calibrated instruments, predeclared confidence methods/noise controls and raw logs. For a normalized candidate/reference benefit ratio (higher is better), require the confidence bound in the non-regressing direction to be at least 1 for every required metric; invert lower-is-better metrics. No arbitrary regression allowance or weakened security is permitted. A point estimate near equality, interval spanning regressions, insufficient repetitions, unstable hardware, unsupported metric or missing Linux comparison is **inconclusive/unqualified**, never a pass. Correlated metrics and comparisons require the declared statistical analysis, not cherry-picked seeds or precision.

Optimize only after preserving semantics/invariants: remove avoidable allocations, copies, computation, locking and contention with measured evidence; do not trade durability, compatibility or mitigation for benchmark scores. Broad unmeasurable hardware remains a named qualification blocker.

## Physical evidence, operator control and recovery

Bare metal starts with M1 alongside QEMU, not after M7. Only the current workstation is available now; other vendors, architectures, NUMA/IOMMU, real devices, power states and fault fixtures remain required named acquisition/access blockers under [bare metal](bare-metal.md). VM results do not fill these rows. The user personally controls package installation, entry selection, reboot and physical observations. Agents must not modify host boot state, mount/raw-write devices, flash firmware, elevate or reboot as part of setup.

The [smoke suite](bare-metal-suite.md) uses the operator's explicit environment label plus exact running release, not infallible hardware attestation. `--environment bare-metal` is an assertion to corroborate with operator console/platform records. Passing on stock Linux or in a VM cannot become replacement-kernel physical evidence. A successful candidate run qualifies only its bounded named cases and exact machine; no destructive storage, broad device, suspend, isolation/security, full ABI or benchmark certification follows from it.

Before an **isolated storage-free M1 diagnostic trial**, [packaging](packaging.md) requires the real reviewed diagnostic artifact and matching loader/platform contract, the applicable QEMU suite, a usable console, separate user-owned recoverable media, independent known-good manual recovery and the user's control of the trial. The candidate must not mount or access the workstation root disk. This path can precede storage, rootfs, initramfs, init and Linux userspace; it is not a Linux-replacement package or a physical pass. Native Limine ELF does not establish Linux boot protocol, native EFI/PE or systemd-boot support.

Before a **Linux-replacement package or root-storage trial**, all actual storage/controller, durable filesystem, partition/encryption/RAID/root dependencies, initramfs `/init`, init/userspace ABI and advertised boot-protocol/EFI prerequisites remain mandatory, together with non-overwriting artifacts, preserved stock recovery and user control. An early diagnostic trial waives none of them. Package install success does not prove boot, and boot does not prove safe root-storage semantics. No host installation, boot-state change, mounting/raw-device operation, firmware action, elevation or reboot is authorized for agents.

## Standing execution and reporting rule

Agents must continue all actionable work within the assigned scope, including reachable dependent edits/tests/docs required by the assignment. A phase boundary, finished subtask or uncertainty with discoverable information is not a stopping point. If an external prerequisite truly prevents further work, finish independent reachable work and report the precise missing hardware/tool/data/permission, affected obligations, evidence already obtained, failed acquisition attempts where relevant, and the exact condition needed to resume. Never fabricate an observation, repeatedly rerun a user-reported failure merely to reconfirm it, or relabel the partial result as final whole-kernel completion.

A final M8 release/completion statement therefore requires: every reference disposition and behavioral row closed; no outstanding port/qualification blockers; full applicable compile/QEMU/physical/per-workload performance gates; reproducible audited Rust-only project artifacts and legal provenance; real package install/upgrade/uninstall/rollback/boot-manager/security validation; and maintainable regression/security/update machinery. If any item is missing, the accurate deliverable is a specifically bounded implementation or evidence report, **not “everything ported.”**
