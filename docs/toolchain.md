# Rust-owned build and toolchain program

## Current state and explicit boundaries

The repository contains a real Rust `no_std` x86_64 bootstrap and linker script, built for the maintained `x86_64-unknown-none` target and booted through external Limine 12.9.3 on QEMU q35/OVMF UEFI64. [Implementation and evidence](implementation.md) preserves the historical manual cell9 self-test and diagnostic ELFs with their hashes, exact commands, eight bounded QEMU cases, five production-parser host tests, strict owned Clippy results and both-profile code-generation inspection. This is a limited bootstrap cell, not a closed M1, Linux-replacement package, physical qualification or reproducibility/performance result.

The same frozen diagnostic ELF was subsequently booted manually in QEMU with serial disabled and without `isa-debug-exit`; its framebuffer capture and QMP/HMP evidence are recorded in [implementation](implementation.md). That default-profile run is separate from the eight-case self-test manifest and from maintained-harness integration. QMP cleanup exit 0 is not a guest debug-exit pass, and no physical execution is implied.

Separate [maintained integration evidence](implementation.md#maintained-integration-and-retained-harness-failure) records actual `integrated-002`, `integrated-003` and final source-bound `integrated-004` runs, each returning 0 with all eight cases matched and a fresh default capture. The real `integrated-001` seven-of-eight CSI-framing failure remains retained. Under `target/kernel-tooling/integrated-004/`, `default-boot/director-visual-review.json` binds independent visual acceptance to the exact PNG/ELF, and `artifact-review/review.json` records the separate integration-owner runtime/provider inspection. These are bounded observations of the frozen sources and artifacts, not complete toolchain, kernel or release qualification.

Project-owned executable code is Rust. Host tools may use `std`; the kernel uses `#![no_std]`, with explicit context-aware fallible allocation where needed, not a blanket ban on heap allocation. External rustc/LLVM/linker, Limine, QEMU, reference Linux, external test suites, userspace, package/boot tools and provenance-recorded firmware may be non-Rust. Their permitted use does **not** authorize linking C/native libraries, a C kernel shim or legacy kernel modules into the kernel. `extern "C"` describes ABI; it does not prove or require a C implementation.

Actual unsigned `diagnostic-001` production used the Rust package producer with provenance-recorded external `bsdtar`, `zstd`, `sha256sum` and read-only `pacman` queries; their paths, versions and binary hashes are host-tool inputs, not admission of non-Rust kernel runtime. [Diagnostic handoff](diagnostic-handoff.md#evidence-status-do-not-substitute-old-results-for-this-package) identifies the immutable archive and `target/kernel-tooling/diagnostic-001/inspection/review.json`, `commands.json` and `extraction-commands.json`. Actual metadata/member inspection and fresh project-owned extraction passed their bounded checks without installation or host boot changes. `.BUILDINFO` describes the actual package-assembly environment separately from original kernel-build provenance; the consumed constant-only `PKGBUILD` is Rust-parsed data, not a shell implementation. Independent director archive review, signing, approved release SBOM and independent reproducibility remain unestablished.

The approved behavioral reference is Linux **6.18.57**, not the workstation's installed kernel and not downstream CachyOS patches. The first userspace is Arch/CachyOS with a balanced server performance profile. See [architecture](architecture.md), [compatibility](compatibility.md), [dependencies](dependencies.md), [licensing](licensing.md), [packaging](packaging.md) and the standing [definition of done](definition-of-done.md).

## Two deliverable tool classes

### Implemented planning and smoke tooling

The Rust 2024 host `xtask` (its only dependency is the vendored `serde_json` graph, see [dependencies](dependencies.md#host-tool-dependency-serde_json-for-the-vendor-gate)) owns structural planning checks/status. The host workspace MSRV is **1.88**, separate from the kernel manifest's **1.101** declaration and the exact nightly runtime compiler below; a declared floor alone is not an exercised minimum-version test. Actual host Rust 1.88 strict Clippy and46 tests in two suites passed. The separately exercised [final integrated gates](project-audit.md#current-integrated-evidence-and-final-gates) passed strict nightly workspace Clippy,51 tests in three suites, formatting and `check`/`status`. No nightly feature is required for the planning auditor. [Project audit](project-audit.md) defines exactly what `check`/`status` mean; those commands do not compile a kernel or certify dependencies.

Any Rust 1.88 minimum-version gate must select only the host packages `xtask` and `baremetal`, or explicitly exclude `kernel` from the workspace. The kernel's 1.101 manifest requirement and exact-nightly parser/runtime evidence cannot be qualified by a host-only gate, and nightly kernel results do not prove host 1.88 execution. The host floor is an engineering metadata choice, not a user-specified version.

A separate dependency-free Rust `std` executable is the [bounded functional suite](bare-metal-suite.md). Its operator-facing invocation is:

```text
cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>
```

The expected release must be the actual running OS release for a reference-runner smoke; writing `6.18.57` does not turn another host into the pinned baseline. The environment label is an operator assertion, not physical-machine attestation. The runner is not a kernel, privileged hardware exerciser, full qualification suite or performance proof. No third-party dependency/build script/native library is introduced by these project crates; normal host Rust `std` may itself use platform-native services.

### Kernel build orchestration and remaining integration

The maintained Rust-owned interfaces are described in [kernel tooling](kernel-tooling.md), with actual source-bound bootstrap runs, separate runtime/visual/package inspection, a successful same-host packaged-source rebuild and final integrated gates. Those observations are distinct from manual cell9 history and do not complete the broader build/release program. Preserve the following orchestration responsibilities without adding empty subcommands or inventing command/results:

1. Resolve the named board/architecture/configuration and exact compiler/tool inputs; reject unsupported combinations and implicit host settings.
2. Build the actual Rust kernel with target-specific flags isolated from host tools/proc macros. The current route uses external Limine, not a project Rust boot application; a future native Rust EFI application needs its own target/ABI and firmware-allocator lifetime proof.
3. Generate declarative linker/layout/configuration inputs deterministically from reviewed Rust logic; call a pinned external linker. Linker scripts and boot metadata are data, not a license to hide project-owned shell/assembly implementations.
4. Emit artifact manifest, source/dependency/firmware provenance, link map, undefined-symbol inventory, section/relocation metadata, assembly exceptions and reproducibility evidence.
5. Build disposable test disks/images using Rust orchestration and recorded external tools where needed; isolate output, refuse overwrites of host devices, and select only explicitly approved lab paths.
6. Invoke QEMU and capture serial/panic/result logs; prepare user-operated physical-machine test bundles from the same artifact, never silently install/reboot the workstation.
7. Prepare only genuine declared-scope artifacts. An isolated storage-free M1 diagnostic trial may use separate user-owned recoverable media before rootfs/initramfs/storage/userspace exists; it is not a Linux-replacement package. The later separate Arch-like replacement package and Limine/systemd-boot paths retain all [packaging](packaging.md) prerequisites. A native Limine ELF is not a systemd-boot EFI/PE image or Linux boot-protocol implementation.

Reuse the same build manifest/parser in all commands. Do not duplicate configuration interpretation in scripts or let image packaging alter code-generation/security settings. External commands are subprocesses with explicit arguments, working directory, environment, timeout and captured exit/result data, not opaque shell pipelines. Freeze all workspace member sources and selected compiler/runtime inputs through build and packaging; final004 binds those current executable inputs. A member-source change, including packaging code, requires a fresh build and corresponding evidence rather than reuse of the old manifest. The produced archive and creation-time pending review fields stay immutable; later identified reviews are separate records.

## Compiler selection and reproducible pinning

Prefer a tested stable compiler and built-in freestanding target when they meet the required contracts. The current exact nightly supplies matching-source `build-std` and non-error `extern "x86-interrupt"` entries. Its emitted hardware-error-code entry alignment was independently found defective and genuinely reproduced in integrated-007; those boundaries now use the minimal local assembly repair recorded in [implementation](implementation.md#error-code-entry-defect-reproduction-and-repair), with fresh008 consumer evidence. This is not an invented detailed user approval or a claim that all compiler ABI behavior is qualified. Do not install/update global toolchains or treat a floating alias as artifact identity.

The actual cell9 and maintained runtime compiler is **rustc 1.101.0-nightly**, full commit `5c543b0b8c73c7b72bc8284ced4fb22ead15734d`, LLVM **23.1.1**; Cargo is **1.101.0-nightly**, commit `3d7cf6e937d6127d0f49881bf689c560b36d35c4`. Matching installed `rust-src` rebuilt `core` and `compiler_builtins` with that compiler for `x86_64-unknown-none`. No target was installed globally, no host Linux `core` was substituted, and no stable-core/nightly mixture was used. The installed nightly alias is mutable: artifact qualification is bound to the exact compiler commit and inputs, not the alias or the kernel's numeric MSRV alone.

The current compiler record in [implementation](implementation.md) supplies bounded ABI/runtime/QEMU evidence; complete admission and release qualification still require:

- exact rustc/Cargo release or dated nightly, commit hash, host and rustup component manifests/checksums; `rust-src` revision when rebuilding core/alloc, LLVM revision, linker/LLVM tool versions and binary provenance;
- installed/built target libraries and their source/features, target specification bytes/hash, rustflags, custom cfgs, environment allowlist, host/target separation, linker script/configuration and CPU baseline;
- exact graph/feature lock and crate archive checksums, proc macros/build scripts, firmware/test-tool inputs, configuration and source revision, source path remapping and controlled timestamps;
- executed compiler regression, ABI, runtime closure, QEMU and recoverable bare-metal evidence. Record failures/known blockers; rollback to the last qualified toolchain must remain possible.

Only after this record passes should a project-local `rust-toolchain.toml` pin be introduced with exact components/targets; never silently mutate a user-wide override. Toolchain upgrades are reviewed changes: rerun affected codegen, unsafe/ABI, target, performance and reproducibility evidence before adopting. A compiler's newer version or a crate's stated MSRV is not qualification.

`Cargo.lock` is necessary but insufficient. Use locked/offline artifact builds after reviewed dependencies are fetched; preserve archive checksums, exact features and immutable source snapshots. Record Cargo resolver/config and every target-specific edge. Isolate build scripts/proc macros, deny incidental network/host-library search and capture emitted linker flags. See [Cargo build script semantics](https://doc.rust-lang.org/cargo/reference/build-scripts.html). Eliminate absolute source/output paths where appropriate; prove reproducibility using two independent clean build roots/environments, compare artifacts and explain any nonidentical metadata. Store signed release manifests separately from nondeterministic signatures. Do not equate `--locked`, a container image name or matching executable size with reproducibility.

## Target feasibility and architecture closure

The [Rust target-tier documentation](https://doc.rust-lang.org/rustc/platform-support.html) distinguishes guaranteed-build targets from tested targets and unsupported configurations. A target named `*-unknown-linux-*` is generally a **userspace** target with Linux ABI/runtime assumptions, not a kernel port. A freestanding target's existence likewise proves neither booting nor Linux compatibility nor security mitigations.

Physical boot/recovery, native EFI/Linux/PVH paths, broad ABI/CPU and mitigation qualification remain open. |

| riscv | Evaluate `riscv64imac-unknown-none-elf` and required RV32/RV64/extension configurations individually | ISA/ABI must match Linux baseline hardware; S-mode/SBI, trap entry, atomics, no hidden F/D/vector register use or unsupported extension assumptions, code model/relaxations and hardware tests. A no-F target alone does not establish all Linux architectures. |
| Remaining baseline arch families and variants | Per-architecture matrix from [architecture plan](subsystems/architectures.md); compare built-in target, reviewed custom specification, compiler/backend port or qualified alternate Rust backend | Need core/alloc, instruction/inline-asm or intrinsic availability, exact calling/data ABI, byte order/width, atomics, linker/relocations, privileged entry and physical test access. Built-in target defaults are starting evidence, not frozen properties. If a custom target is necessary, record the generated target specification from the selected compiler and a reviewed delta; pin it with the compiler. Target JSON schema is not a stable ABI. [Cargo `build-std`](https://doc.rust-lang.org/cargo/reference/unstable.html#build-std) was actually used here for matching `core,compiler_builtins` with `compiler-builtins-mem`; `alloc` joined the kernel build with the [kernel services foundation](implementation.md#kernel-services-foundation) (`-Zbuild-std=core,alloc,compiler_builtins`, `--cfg no_global_oom_handling`, see [kernel tooling](kernel-tooling.md#fallible-only-kernel-allocation)); the user `/init` still builds only `core,compiler_builtins`. Cargo's external `clippy` subcommand requires the `-Zbuild-std` flags **after** `clippy`; the native `rustc` command accepts the documented leading `-Z` form. Do not combine a freestanding application with host libc or a different compiler's core to patch missing runtime support.

## Runtime closure: compiler, linker and language items

“Rust-only source” does not imply “no C/assembly runtime in the final image.” LLVM can lower ordinary Rust to helper calls, memory routines and target runtime stubs. The following **must all be proved per exact target/profile** before M1 admission:

| Concern | Required design and observable acceptance |
| --- | --- |
| `core`/`alloc` and compiler builtins | Inventory archive members and linked symbols, map each to source/selected implementation/license, inspect actual machine code. The [compiler_builtins manifest](https://raw.githubusercontent.com/rust-lang/compiler-builtins/master/compiler-builtins/Cargo.toml) exposes optional `c` and default `arch`; do not enable C compiler-rt or assume architecture-selected routines meet the no-standalone-assembly rule. Prove supplied artifacts or build an audited Rust-only subset with required features; missing intrinsic on any architecture is a blocker, not a C fallback. Toolchain component licensing has its own LLVM exception and conjunctive expression, requiring [license review](licensing.md). |
| Libcalls and memory | Resolve `memcpy`, `memmove`, `memset`, `memcmp`/`bcmp`, integer division/multiplication/128-bit helpers, atomics/outline dispatch, stack probes and any software FP helper actually emitted. Provide reviewed Rust implementations or qualified builtins; verify overlap, zero length, alignment, page faults and no recursive lowering (e.g. a copy routine compiling into a call to itself). Reject unresolved symbols and host CRT/libc/libgcc/unwinder/OS syscalls/TLS imports. |
| Allocator | Explicit kernel allocation interface with context/GFP-like policy, fallible reservation and alignment/overflow behavior; `GlobalAlloc` alone cannot represent all contexts. Early boot arena/page ownership transfers exactly once. Every alloc-using dependency proves OOM propagation and no reclaim/lock recursion. No firmware allocator references after ExitBootServices and no host allocator in the image. |
| Panic and exceptions | Kernel panic handler, abort strategy and emergency reporting require no allocation, sleep or recursive locks; define per-CPU/NMI/panic ownership and reset/halt outcome. No unwinding across entry/FFI boundaries and no implicit personality/unwind runtime. Keep genuine error paths recoverable; panic is not acceptable for routine bad user input/OOM. Build/test profiles must not silently change panic semantics. |
| Link layout | Define boot entry, virtual/physical addresses, segment alignment, W^X/NX, read-only relocation phases, stack/per-CPU/TLS-like kernel storage, init reclamation, exception tables, retained metadata, KASLR/relocation and dynamic userloader separation. Linker assertions reject overflow/overlap, unexpected sections/orphans, executable stack, unexpected dependencies and missing entry. Preserve map/symbol/relocation evidence. No accidental host `main`/CRT entry or linker default script. |
| x86 red zone and ABI | Red zones disabled for **all** kernel code and relevant target libraries; default x86-none contract helps but is verified. Entry wrappers handle stack alignment, direction flag, red zone exclusion, callee/caller saved state, syscall register clobbers, user/kernel GS/FS state and all return paths. Firmware `efiapi` ABI is not SysV kernel ABI. |
| FP/SIMD/vector | Exclude FP/vector codegen from ordinary kernel and selected dependencies initially, inspect generated code including memory/hash/crypto routines. Any later accelerated scope requires explicit context-save/preemption/interrupt/NMI and feature-detection rules, traps and Linux-compatible security behavior. Softfloat names/feature flags alone are insufficient; inline asm and prebuilt builtins may bypass them. Never enable `target-cpu=native` for distributable baseline images. |
| Stack | Separate boot/kernel/IRQ/NMI/exception stacks, guard pages/canaries, overflow/double-fault recovery, bounded recursion/frames and stack probes with Rust providers. Test interrupt nesting, page-boundary growth, deep paths, compiler-generated spills and panic handling. Large fixed arrays are not “free” substitutes for fallible heap allocation. |
| Atomics and memory model | Every selected width/ISA has correct alignment and ordering, lock-free/fallback status, SMP/IRQ/NMI and MMIO/DMA barriers. No hidden native `libatomic` or unsupported hardware instructions. Model Rust memory-model/alias rules separately from Linux's hardware/RCU contracts; don't mechanically substitute orderings. |
| Mitigations and instrumentation | Kernel-compatible control-flow/branch/return protections, speculation barriers, stack protection, sanitizers and tracing hooks must be tied to CPU/ABI/entry rules. Compiler instrumentation providers must be Rust or outside the kernel artifact; no disabling required mitigations to pass performance tests. Debug/sanitized/release profiles all need explicit closure. |

The frozen manual cell9 self-test and diagnostic profiles were both inspected: ET_EXEC with RX/R/RW load segments, non-executable stack, no relocations or undefined symbols, and scalar-only inspected code. Actual inspection found the compiler-builtins architecture-selected `memset` using avoidable `rep stos*`; the final kernel instead supplies the needed scalar Rust `memset`, without unused memory-function stubs. The separate final004 `artifact-review/review.json` retains fresh both-profile symbol/layout/disassembly findings and map comparisons, including inspected Rust providers and default-profile exclusion of COM1/f4. [Implementation](implementation.md#maintained-integration-and-retained-harness-failure) owns the exact artifact hashes, raw outputs and review limits. These are per-artifact findings, not proof for all architectures, future builds, mitigations, independent security/legal review or reproducibility. Continue mapping linked bytes to audited source/build configuration and investigate unexpected instructions rather than filtering them away.

## Inline assembly exception register

Use normal Rust/intrinsics first. The accepted exception permits only function-local `asm!` and `naked_asm!`, where unavoidable and with the proofs below. **`global_asm!` is prohibited**, as are standalone `.S`/`.s`/assembly libraries and C entry shims; moving assembly into a dependency or generated source is not an escape. The [Rust inline assembly reference](https://doc.rust-lang.org/reference/inline-assembly.html) defines `asm!`, `naked_asm!`, clobbers and option contracts; compiler stability varies by target/version and must be checked for the selected pin.

Each unavoidable block requires: operation/architecture/CPU/privilege scope; why Rust/intrinsics cannot express it; precise entry/exit ABI; registers/flags/vector and memory/clobber effects; stack alignment/ownership; faults and exception recovery; barriers and compiler reordering; interrupt/preemption/SMP interaction; valid input/alias/provenance assumptions; permitted caller context; source license; reviewers; generated instruction/disassembly checks and negative/adversarial tests. `nomem`, `readonly`, `nostack`, `pure` and `preserves_flags` must be true, not optimization hints to guess. Naked entry wrappers must establish all Rust preconditions before calling compiled Rust, and cannot assume compiler prologue/epilogue. Review context-switch, trap, boot and return paths together.

For necessary operations such as privileged control-register access, trap return, context transfer, cache/TLB maintenance or halt, the exception should be narrow and reusable across callers. Pure arithmetic/memory copying is not automatically exempt merely because standalone assembly is faster; optimize qualified Rust/intrinsics and retain the at-least-Linux performance requirement.

## Ordered implementation and definition of done

1. **M0 (planning):** settle candidate compiler/target/boot contracts, reproducibility inputs, license/runtime provenance and physical recovery procedure. Documentation existence does not prove these contracts. Current auditor/suite evidence must be reported separately from kernel evidence.
2. **M1 (underway, not complete):** retain the real trusted entry, firmware decoding, physical-frame ownership, owned paging, exceptions, timer and bounded diagnostic evidence in [implementation](implementation.md). Pair QEMU bring-up with user-operated physical recovery planning; the diagnostic profile uses framebuffer reporting and excludes QEMU-only COM1/f4 paths. A safe storage-free trial can precede rootfs/initramfs/userspace, but physical execution and recovery remain unproved. No automated host install/reboot/firmware action is authorized; additional required vendors/architectures/platforms remain lab blockers.
3. **M2–M3:** prove SMP/interrupt/concurrency and process ABI with the exact compiler, Linux ELF/syscall/signal/vDSO behavior and actual Arch/CachyOS userspace. An unmodified userspace executable running on the reference host validates the test harness, not the new kernel.
4. **M4–M7:** integrate qualified subsystems and targets, gate each new dependency/assembly/backend and packaging configuration. Extend hardware coverage as [bare-metal](bare-metal.md) requires; unavailable physical targets stay unqualified.
5. **M8:** accept toolchain only when clean isolated builds reproduce, every linked runtime symbol has Rust-source/approved-asm/license provenance, all ABI/stack/FP/atomic/panic/link checks and affected adversarial/differential/hardware tests pass, package selection/rollback is exercised, and identical-security balanced-server [performance](performance.md) is at least pinned Linux on every required workload/hardware metric. Missing confidence/evidence is not a pass; no aggregate can hide individual regressions. Follow [verification](verification.md) and [definition of done](definition-of-done.md).

Historical origin: preparing the original planning design performed no kernel build, target installation, QEMU boot, physical boot, reproducibility comparison, performance measurement or kernel codegen inspection. Subsequent actual builds, manual cell9 and maintained QEMU runs, separate both-profile inspections, diagnostic archive production and a same-host packaged-source consumer build are recorded in [implementation](implementation.md) and [diagnostic handoff](diagnostic-handoff.md), not retroactively attributed to that design exercise. No global target installation, physical candidate boot, independent reproducibility or performance qualification is claimed now. Strict Clippy was integration verification under repository policy, not an additional detailed user approval; the inherited core soft-float future-incompatibility warning remains unsuppressed. The final nightly workspace51-test/strict-Clippy/format/check/status results are distinct from the host Rust1.88 checks and historical freestanding-profile Clippy.

## Accepted architecture and fixed scope

The architecture is an approved **modular monolithic Rust kernel**, not an unresolved alternative. Its feature baseline stays fixed at upstream Linux 6.18.57; necessary security deltas must be explicit and reviewed, and a later feature-baseline change requires a separate decision. Every in-baseline module's functionality needs a Rust replacement, but arbitrary third-party/proprietary out-of-tree module functionality is not implicitly included; additions require separately enumerated and approved scope. Compiler/runtime/dependency choices must enforce this boundary without reducing any in-baseline coverage.

### Concrete cross-architecture feasibility blocker: s390 compat

The pinned [s390 Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/s390/Kconfig) makes `COMPAT` (31-bit ESA syscall emulation) depend on `MULTIUSER` and `!CC_IS_CLANG && !LD_IS_LLD`. This is an observed limitation of the baseline build configuration, not proof that a Rust implementation is impossible. It is, however, a concrete blocker to assuming rustc/LLVM plus LLD provides complete baseline compat functionality merely because a freestanding s390x target exists. Investigate the exact backend/assembler/linker/ABI causes, use a qualified external linker where sufficient, and implement/test missing Rust/compiler support where needed. Preserve 31-bit compat in scope, with real syscall/ELF/ABI evidence; do not treat a successfully linked 64-bit image as closure.
