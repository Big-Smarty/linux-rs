# Verification and qualification program

## Present evidence is not future proof

**M1 bootstrap work is underway, not complete.** A real Rust `no_std` x86_64 kernel runs processes, threads and unmodified static and dynamic Linux programs on one CPU in QEMU; what passed at which commit is in the [current status](implementation.md#current-status), the open work and its acceptance tests are [next steps](next-steps.md), and [what each command establishes](#what-each-command-establishes) is below. History: [implementation](implementation.md) and [diagnostic handoff](diagnostic-handoff.md). Current [routed workstreams](implementation.md#routed-implementation-status) are `in_progress`, with all other rows `not_started`; each subsequent source revision needs its own evidence. The broader verification program remains required, not implicitly passed. The [planning auditor](project-audit.md) checks repository/metadata/link/source-policy rules only: its success cannot prove bootability, ABI parity, runtime provenance, memory safety, durability, performance or hardware compatibility. No physical candidate result, full Linux qualification or Linux-replacement package readiness is claimed.

The [compatibility contract](compatibility.md) defines the obligation denominator. [Performance](performance.md) and [bare-metal qualification](bare-metal.md) are mandatory from M1 planning onward, not optional late benchmarks. Arch/CachyOS userspace is the first deployment target; the semantic and performance oracle remains pinned upstream Linux 6.18.57, not whichever distribution kernel happens to be installed. User-reported physical observations are authoritative. Only the user's workstation is currently available: unavailable hardware remains blocked and cannot be substituted with VM evidence.

The separate Rust host/guest [bare-metal smoke suite](bare-metal-suite.md) tests only its bounded non-destructive operations on the **currently booted** kernel. A reference-host run validates that tool/environment only. Its environment label is an operator assertion, not physical attestation.

## Executable harness boundary

All project-owned runners, comparators, image/test orchestration, destructive-device guards, result parsers, and evidence exporters must be Rust. Existing external tests and unchanged applications may be C, C++, shell, Python, Go, or other languages. External compiler/linker/firmware tools are permitted under [toolchain](toolchain.md) and [licensing](licensing.md). This permits running LTP and syzkaller; it does not permit embedding their C kernel modules or C-backed implementation in this kernel. A project-authored adapter is Rust; an upstream suite kept with recorded revision/provenance is an external dependency.

The full runner must distinguish reference/candidate targets, bound timeouts, detect crash/hang, capture serial/logs, select by obligation, hash artifacts, retain explicit skip/fail/block outcomes and fail when a required selected case has not passed. Infrastructure errors, unknown IDs, empty selections, malformed logs, missing completion markers and disconnected consoles must not produce success. Deliberately failing fixtures are required alongside success cases. The maintained bootstrap interfaces in [kernel tooling](kernel-tooling.md) now have the actual source-bound runs and separate reviews above; their narrow bootstrap/package proof does not implement or qualify this complete program, and manual cell9 history remains separate.

A run record must contain source/artifact/config/image hashes, compiler/linker/target revisions and flags, full invocation, suite revision and patches, seed, machine/QEMU/accelerator details, firmware/microcode, topology/device IDs, user/namespace/cgroup/LSM state, boot parameters, start/end times, power state, expected obligations, per-test results, raw logs, crashes/captures, benchmark samples, reviewer, and relation to earlier runs. Preserve failing seeds and minimized reproducers. Hash manifests and artifacts together; retain original output rather than only a green summary. Redact secrets without removing diagnostic provenance, and record redactions.

## Linux-oracle differential execution

1. Reproduce the pinned upstream Linux reference with a recorded valid configuration and the same userspace/rootfs, virtual or physical devices, peers, credentials, limits, and initial storage image as the candidate. Keep the reference bootable and immutable. Reference generation is a real prerequisite, not assumed from source availability.
2. Derive independent tests from UAPI/source/manual obligations. Include raw syscall byte probes alongside glibc/musl and real application paths, so libc emulation does not hide missing kernel functionality. Build 32-bit/compat/time64 and endian fixtures where applicable rather than passing host-native structures to every target.
3. Start both targets from equivalent isolated state; execute deterministic sequences and controlled races; record returns/errors, output buffers including sentinels, descriptor/offset state, signals/register context, filesystem/proc/sysfs/netlink changes, packets, persistent writes, and permission effects. Cover operations that fail before and after partial commitment.
4. Compare using reviewed interface-specific permitted-behavior rules. Consistent identity renaming, bounded clock comparisons, or nondeterministic set/order comparisons require written justification. Never strip an errno difference, lost wakeup, accounting drift, missing field, unauthorized action, or tail-latency regression as noise.
5. When results differ, minimize the reproducer and run the exact reference cell again only as part of a new investigation, not to overwrite an authoritative user observation. Classify candidate defect, oracle/config mismatch, test defect, baseline bug, or genuine specified nondeterminism. Until supported by evidence, the cell fails or is blocked. A flaky test is not a pass.
6. Persist regressions and their causal obligations. A fix needs the original failing reproducer, relevant neighboring cases, full affected QEMU suite, and applicable physical/performance reruns. Do not remove a test because a feature is inconvenient.

For multi-error inputs test cross-products deliberately: bad descriptor plus bad pointer, denied capability plus malformed attributes, invalid flags plus missing path, full resource limit plus signal interruption. Assert the reference validation order, side effects, output mutation and rollback. Exercise user buffers spanning unmapped/read-only pages, unaligned and overflowing lengths, nested pointer changes, shared-memory races, zero sizes, huge sizes, reserved bytes, duplicate TLVs, and legacy variants. These are ABI and security obligations, not merely fuzz seeds.

## Memory, concurrency, and unsafe verification

Each unsafe boundary needs a documented invariant, caller obligations, lifetime/aliasing and synchronization proof, ownership transfer diagram where useful, failure cleanup path, and independent review. Test alloc/free, reference counts, pinning, usercopy, RCU/grace periods, wakeups, signal delivery, cancellation and teardown against concurrent mutation. Stress SMP/preemption/interrupt/softirq contexts, CPU and memory hotplug, NUMA migration, interrupt affinity, and work cancellation. Use lock-order checking, allocation poisoning/redzones, race detection and memory-error instrumentation where the Rust toolchain/target supports it; absent instrumentation is a recorded tooling gap. Existing Linux KASAN/KCSAN/lockdep support does not automatically exist in this kernel.

[Miri](https://github.com/rust-lang/miri/blob/master/README.md) interprets Rust and can catch alignment, initialization, bounds, aliasing and some race issues. It cannot generally execute inline assembly, MMIO, real DMA, firmware, a complete privileged kernel, or arbitrary platform/FFI APIs; a passing tested execution does not establish soundness. Do not replace real operations with fake successful ones and report a kernel test pass. Isolate pure mechanisms for Miri and retain separate hardware tests. Host tests with a mock device validate that model, not the silicon driver.

[Loom](https://github.com/tokio-rs/loom/blob/master/README.md) is a candidate for bounded Rust synchronization models, not an approved kernel dependency. Its README describes incomplete memory-model behavior; code must use its instrumented model primitives for exploration to apply. Neither finite bounded exploration nor a C11-style model proves architecture-specific barriers, cache coherence, interrupt exclusion, DMA ordering, speculative execution mitigations, or every schedule. Review target instructions and use actual weak-memory systems plus architecture litmus tests. Any other model checker must state state-space bounds, assumptions, unsupported constructs, and links between model and compiled code.

## Adversarial, recovery, and durability campaigns

- **Fuzzing:** structured mutations of syscall argument/state sequences, native/compat layouts, ELF/signal frames, ioctl/netlink/proc/configfs input, filesystem metadata, packets, firmware tables, and virtual-device descriptors. Retain validity-aware and malformed-input corpora. Exercise unprivileged and capability-restricted entry points, cross-namespace interactions, resource caps, concurrent removal, and cancellation. Verify no crash, hang, privilege gain, kernel memory disclosure, unauthorized persistent mutation, or resource leak.
- **Fault injection:** fail each relevant allocation and usercopy step, then I/O completion, mapping/IOMMU setup, interrupt delivery, timer expiry, module/driver registration, and firmware requests. Test delayed/reordered/duplicate completions, queue exhaustion, DMA mapping failure, device timeout/reset/disconnect and CPU/memory hotplug. The [Linux fault-injection inventory](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/fault-injection/fault-injection.rst) provides concrete baseline categories; Rust equivalents and external device injectors must be real, observable mechanisms rather than always-success hooks.
- **Leak/liveness stress:** repeated fork/exec/exit, mount/unmount, net namespace/container creation/destruction, memory pressure/reclaim/swap/OOM, reconnect, module load/unload, suspend/resume and hotplug while workload runs. Define forward-progress/watchdog bounds, check resource/accounting return to an explained baseline, and capture lock/wait/RCU state on timeout. A machine still responding to ping does not prove workload liveness.
- **Power failure:** enumerate persistence cut points around data, metadata, journal/log commits, flush/FUA, rename and directory fsync. Use write-log replay and emulated block faults first, then controlled physical power interruption only on consenting sacrificial media with recovery hardware. Verify acknowledged durability, permitted pre-crash outcomes, filesystem invariants and repair-tool output under both Linux and Rust replay. VM reset does not prove controller power-loss protection or device cache ordering.
- **Protocol faults:** packet loss/reordering/duplication, fragmentation, checksums, MTU changes, reconnect/failover, offload enable/disable, clock/time namespace changes, untrusted peers and malformed messages. Include wire capture and both endpoint states, not only throughput.
- **Security faults:** denied namespace joins, mount/LSM/seccomp/capability combinations, credential transitions, untrusted executable/filesystem/device input, malicious signals, invalid return frames, speculation controls, boot/module trust failure and rollback policy. Review permission-check ordering and side effects in failures.

Each campaign records seeds, durations/operation counts, schedules/cut points, enabled instrumentation, actual covered mechanisms, observed failures, and remaining gaps. Finite crash-free stress is evidence, not a universal guarantee. Campaign size and acceptance thresholds must be set before running based on obligations and risk, not shortened after failures.

## QEMU and physical-machine stages

### M1 co-development, not physical claims

Develop emulated boot and the real-workstation boot/recovery path together: machine inventory, firmware handoff assumptions, console path, independently selectable candidate entry, watchdog/panic capture, known-good Linux fallback, recovery media and data protection. No unavailable serial/BMC, spare disk, controlled power rig, vendor machine or IOMMU feature is assumed present. Record unknown workstation capabilities explicitly. Keep future multi-vendor/NUMA/other-architecture qualifications as blocked required cells.

QEMU sessions need explicit machine/CPU/accelerator/device models, bounded boot/completion markers and captured crash/hang logs. Preserve reproducible root images and disk snapshots when the tested cell uses storage/userspace; the current storage-free bootstrap instead uses its recorded Limine/OVMF inputs and private test images. Use TCG and accelerated paths where each exposes different assumptions. Required broader cases include UP/SMP, low/high memory and pressure, modeled NUMA, interrupt/timer changes, applicable IOMMU/device faults, compat execution and malformed inputs. QEMU success proves only the named configuration, not real hardware coverage.

### Full QEMU suite before a user-test package

An isolated **storage-free M1 diagnostic trial** is a different artifact class from the Linux-userspace/replacement package described below. It may precede rootfs/initramfs/storage/userspace, but requires the real diagnostic image, complete applicable bootstrap QEMU cases, declared limits, separate user-owned recoverable media and independently usable known-good recovery. The user alone controls boot selection; no host devices, boot configuration or firmware are modified by these tools. Native Limine ELF is not a systemd-boot EFI/PE image, Linux/PVH boot path or Linux userspace claim.

Before claiming a **Linux-replacement Arch/userspace package** is ready for the user to boot, run **the full suite for its declared candidate scope**, not a handpicked smoke subset: all mapped mandatory ABI/layout/error/restart/process/VM/filesystem/network/security/boot/deployment regressions; applicable external suites; unchanged Arch/CachyOS systemd/container/server workloads; fault/stress/recovery cases; balanced performance samples with uncertainty; package install/remove/upgrade/rollback and actual supported Limine/systemd-boot entry tests. Every applicable included feature must be implemented and pass; disabled options cannot hide obligations. Publish narrower-than-full-Linux scope until M8 closure. Infrastructure failure, required skip, missing output or unexplained differential discrepancy blocks this readiness claim. The separate storage-free diagnostic trial above does not claim or bypass these replacement-package capabilities.

“Full QEMU suite” does not mean QEMU supplies every final hardware proof. Publish the exact suite manifest and closed candidate-scope obligations plus all final-scope blocked cells. A package with known missing baseline families is explicitly an experimental scoped candidate, never a full-compatible kernel. A runnable installer or a real test runner by itself is also not a usable kernel package.

### User-operated bare-metal suite

The included [bare-metal smoke suite](bare-metal-suite.md) has this concrete CLI:

```text
cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>
```

The operator supplies the exact expected release and a new output directory; existing evidence must not be overwritten. This dependency-free Rust `std` executable runs bounded memory/thread, sandbox filesystem/sync/rename/link, TCP/UDP/Unix loopback with timeouts, process exec/wait/exit, and proc/sysfs visibility checks. It records separate outcomes and environment metadata without hardware serial IDs, reports failure nonzero and distinguishes unavailable checks. It does not mount filesystems, raw-write devices, alter settings, elevate privileges, reboot, update firmware, or launch destructive external suites. See its own documentation for the implemented outcomes and limits. A zero smoke exit cannot turn a skipped/unavailable required qualification obligation into a pass.

The **future full physical qualification program**, distinct from that smoke tool, must additionally tie booted artifact/config hashes to firmware/microcode, topology/device classes, bootloader and mitigation state, with privacy-aware collection. Required groups are boot/console/root mount and systemd/udev; native/compat/time/signal and ELF/vDSO probes; memory/SMP/timers/interrupts; filesystem and durability; isolated-peer physical NIC/offload behavior; containers/security; balanced workloads/performance; teardown; and recovery. Controlled suspend/resume/reboot and destructive storage/power/device fault tests belong only to separately designed, user-approved campaigns with verified recovery and dedicated safe media. The included smoke binary must not grow silent destructive defaults. Missing safe scratch space, peer, device or recovery path remains blocked. No full differential, physical, durability, power or performance certification is implied by having a runnable smoke suite.

The user personally selects the candidate in Limine or systemd-boot and runs the supported suite. The assistant must not claim or synthesize physical execution. The user's report identifies the exact artifact and observed outcome; logs substantiate scope when available, but a reported failure remains ground truth even without perfect logs. Record physical outcomes only after the user reports them. Preserve a separate known-good Linux entry and verified recovery instructions; never overwrite its kernel/initramfs or silently change the default boot target. A single workstation pass cannot qualify other device revisions, CPU vendors, NUMA machines or architectures.

## Definitions of done

These are conjunctive evidence-level summaries of the standing [definition of done](definition-of-done.md), not a points system or a reduction of its obligations. Implementation and evidence status remain separate; a file named after a subsystem is not an implementation. Package workflow details are owned by [packaging](packaging.md).

| Level | Done only when every applicable item is satisfied |
| --- | --- |
| Planning/tooling delivery | Reference provenance and inventory caveats recorded; ownership/plans/skills audited; runnable bounded Rust smoke suite supplied; actual positive/adversarial tool results reported at their revision; no kernel result inferred from those results. Current local fingerprint-pinned signature evidence and its trust limit are in [coverage](coverage.md); remaining provenance/review/toolchain/hardware gates stay explicit. |
| Individual ABI/interface obligation | Pinned behavior/layout/config/arch variants enumerated; real Rust implementation reachable; safe/unsafe and permission invariants reviewed; success, boundary, error precedence, partial effects, restart/race and malformed-input tests pass against Linux; no required skip; caller and documentation migration complete; concrete evidence artifacts tied to revisions. |
| Mechanism or driver | Every mapped obligation above, plus failure-unwind/lifetime/ordering review, adversarial input, SMP/concurrency where relevant, stress/leak/liveness, applicable fault injection and reset/hotplug/recovery, real device evidence for claimed hardware, and performance/security parity in its workload cells. Emulation is additional evidence, not replacement. |
| Filesystem/storage/protocol family | Every supported feature/configuration/format version and native/compat/wire variant accounted for; read/write interoperability both directions, tooling/admin workflows, error/recovery/durability or peer-state behavior, external suite gaps filled, real media/NIC and applicable fault/power evidence, no hidden optional-feature omissions. |
| Storage-free M1 diagnostic trial ready | Genuine diagnostic artifact and exact compiler/provenance/notices; full applicable bootstrap positive/negative QEMU evidence and reviewed handoff; no storage/userdata access; separate user-owned recoverable media and independent known-good recovery; bounded reporting, limits and user-operated procedure. No rootfs/initramfs/userspace requirement for this diagnostic class, and no physical, full-M1, Linux-replacement or performance claim. |
| Linux-userspace QEMU-qualified candidate | Bootable Rust artifact with provenance; complete declared-scope suite manifest; full mapped QEMU tests and real Arch/CachyOS workloads pass; package/bootloader/recovery rehearsals pass; no mandatory scoped gap; final-scope unqualified matrix published; no physical/full-Linux parity claim. |
| Linux-replacement user-test package ready | Linux-userspace QEMU-qualified candidate plus real storage/durable filesystem/root/initramfs/init/userspace, installable Arch artifact, checksums/signatures/source/provenance, actual supported independent boot entry, preserved known-good boot, runnable documented Rust-owned bare-metal suite and recovery/rollback instructions. Native Limine support does not supply systemd-boot EFI/PE compatibility. No physical pass until the user's report. |
| Workstation-qualified candidate | User-reported actual physical boot/suite/workload/recovery results for the exact artifact/config/device inventory; no unexplained failures or unqualified claimed device cells; physical performance/security evidence passes. The claim is limited to that recorded workstation/configuration, not every Linux machine. |
| Full compatibility release, M8 | Every baseline feature/architecture/ABI/config/hardware obligation is implemented and qualified or proven genuinely inapplicable; no blocked/not-run required cell; no unexplained differential or security failure; QEMU and real hardware evidence; at-least-Linux per-workload performance; reproducible/licensed/provenanced release and complete deployment/recovery gates; independently reviewed closure. |

For every level, an infrastructure error, missing artifact, unsupported feature, expected-failure label, waiver, manual assumption, or untested hardware cannot count as a pass. Valid reference-inapplicability must be substantiated and reviewed. A temporary preview may disclose unresolved cells but cannot use the higher-level done label. New regressions reopen affected qualifications, and a security-driven deviation remains visible rather than changing comparison rules to make it green.

## Ordered implementation of verification work

1. **M0:** specify obligations/results/artifact schema; pin suite revisions and reference build; classify destructive actions, missing hardware and tool limits. Integrate the present planning audit without conflating it with kernel testing.
2. **M1:** implement Rust-owned reference/QEMU/image/log orchestration, startup probes, ABI codec fixtures and the non-destructive workstation inventory/recovery design; establish performance collection and hardware blockers. Use existing standard host facilities rather than inventing a second job framework; future crate candidates need [dependency review](dependencies.md).
3. **M2–M3:** add native/compat/time64/error/restart/ELF/vDSO differential probes, bounded mechanism models, concurrency/memory stress, and unchanged loader/userland tests as their implementations become reachable.
4. **M4–M5:** integrate storage/network external suites, crash/replay/fault tests, real Arch/CachyOS services and containers, and balanced server performance. Bring the actual package and runnable safe physical suite to the readiness gate before asking the user to boot it.
5. **M6–M7:** expand security/virtualization/observability, all driver/filesystem/protocol/architecture/configuration cases, alternate hardware and rare/legacy paths. Fill external-suite omissions with independently reviewed Rust tests, not reduced scope.
6. **M8 and each release:** reproduce artifacts, run all affected and full qualification suites, evaluate every matrix cell, obtain actual user/physical evidence where required, close provenance/security/performance gaps and apply [maintenance release gates](maintenance.md). No execution of these future stages is asserted here.
