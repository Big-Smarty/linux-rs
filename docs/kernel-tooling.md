# Rust-owned x86_64 kernel build and QEMU tooling

## Scope and honest status

`xtask` keeps the existing offline `check` and `status` planning-audit commands and adds real Rust-owned `kernel-build`, `kernel-test` and `kernel-package` commands. They cover the current x86_64/UEFI/Limine bootstrap cell and separate unsigned diagnostic distribution only. They do not implement or qualify the Linux 6.18.57 kernel, establish physical boot support, Linux parity, security, performance, or any other architecture. The broader fixed Linux baseline remains in scope.

The implemented first boot cell uses QEMU `q35` with OVMF, Limine 12.9.3, and Limine protocol base revision 5. This is an engineering sequencing choice, not a newly attributed detailed user approval. Tool/firmware provenance and the independent Linux tag verification remain in `target/implementation-prereqs/{tooling-manifest.txt,upstream-verification.txt}`; the latter records `TRUST_UNDEFINED`, not Web-of-Trust certification.

This page specifies the maintained interface and acceptance rules. Actual `integrated-002`, `integrated-003` and final metadata-bound `integrated-004` runs each returned0 with eight matched cases and independently reviewed default captures; `integrated-001` remains retained failed evidence. Host Rust1.88 strict Clippy/46 tests and separate final nightly strict-Clippy/51-test/format/check/status gates passed. The genuine unsigned `diagnostic-001` archive received actual read-only metadata/member/extraction/hash inspection and independent director format/source acceptance; its documented build also succeeded from a new writable packaged-project copy, without whole-ELF/map identity or independent reproducibility claims. [Implementation](implementation.md) identifies exact hashes, comparisons and review limits. Historical manual `cell9` results are not relabelled as maintained-harness results. Newly captured screenshots always begin with human review pending.

## Commands

Run from the repository root on the Linux x86_64 host. The shared build/test/package output policy accepts only a fresh direct child of `target/kernel-tooling/`; it refuses reuse, parent traversal, symlink directory ancestors and special files. The run directory is created with mode `0700` (subject to a more restrictive umask). Each build owns an isolated Cargo target directory and map, so it does not read or overwrite `target/x86_64-unknown-none/release`, the kernel developer's work directory, a host disk, or a shared `target/kernel.map`.

```console
cargo +1.88.0 run --offline --locked -p xtask -- check
cargo +1.88.0 run --offline --locked -p xtask -- status
cargo +1.88.0 run --offline --locked -p xtask -- kernel-build --output target/kernel-tooling/build-001
cargo +1.88.0 run --offline --locked -p xtask -- kernel-test --output target/kernel-tooling/test-001
cargo +1.88.0 run --offline --locked -p xtask -- kernel-test --output target/kernel-tooling/test-002 --timeout-seconds 30
cargo +1.88.0 run --offline --locked -p xtask -- kernel-package --build-output target/kernel-tooling/test-002/freestanding-build --output target/kernel-tooling/package-001
cargo +1.88.0 run --offline --locked -p xtask -- baremetal-suite --output target/kernel-tooling/suite-001
```

`baremetal-suite` is the [kernel-run bare-metal suite](#kernel-run-bare-metal-suite-a21) builder: it produces the directory tree the user copies to a separate USB stick (it never writes to a block device) and boots that exact tree once in QEMU.

`--root PATH` may appear before or after a command and selects the project root; relative `--output` paths resolve under that root. Output names are 1–20 ASCII letters, digits, hyphens, or underscores. `--timeout-seconds` is valid only for `kernel-test`, from 1 through 300, and applies to each guest. Usage errors return 2; audit/build/test failures return 1; success returns 0. Existing `check`/`status` semantics and exit behavior remain unchanged.

### Generated initramfs fixtures

`kernel-test` has **no external input**: it builds `/init` itself and generates every boot module, so a fresh clone with the documented toolchain/firmware prerequisites is expected to reproduce the suite; observed so far only on one workstation (same host, user, toolchain installation and firmware, different checkout paths and `CARGO_HOME`), not on another machine or toolchain location (the earlier two ignored `target/linux-reference` CPIO files are gone, along with their hash constants).

1. **Init build.** After the two kernel profiles it builds `user/init` (package `linux-rs-init`, bin `init`, `--features freestanding`) into `init-build/` through the same `prepare_build`/`finish_build` path: exact nightly resolution, merged vendor `CARGO_HOME`, private target dir, source/runtime inventories, plus `-Crelocation-model=static -Cstrip=debuginfo -Clink-arg=--no-pie -Clink-arg=--no-undefined` (no linker script) and a linker map. The snapshot `init.elf` and its SHA-256 are in `init-build/build-manifest.tsv` (`init_elf_snapshot`, `sha256_init_elf_snapshot`) and the top manifest (`init_elf`, `sha256_init_elf`). The `elf` crate must report little-endian ELF64 x86-64 `ET_EXEC`, no `PT_INTERP`/`PT_DYNAMIC` and no undefined `.symtab` symbol; the executable `PT_LOAD` ranges and the undefined-symbol count are cross-checked against the captured `readelf -lW`/`-sW` text (`program-headers.txt`, `init-symbols.txt`), which stays the independent oracle.
2. **Archive.** `cpio::write_cpio` (only; `Writer::finish()` after a short write emits a corrupt entry) writes a deterministic `newc` archive: mtime 0, uid/gid 0, sequential inode numbers, `dev` (`040755`, nlink 2), `init` (`0100755`, the built ELF), `linuxrc` (`0120777`) -> `/init`, the oracle-test tree `TEST_FILES` (`fixture/`, `hello.txt` 0644 `hello, oracle\n`, `empty`, `noexec` 0755 text, `sub/nested.txt`, `link` -> `hello.txt`; see [Oracle syscall test suite](implementation.md#oracle-syscall-test-suite)), then `TRAILER!!!`. Unit tests walk the raw bytes (magic, header fields, name/data 4-byte padding, trailer) independently of the crate.
3. **Expected kernel record, by construction.** The `CHECK image inspected` tail is computed, not observed: `records=11 files=10 regular=5 symlinks=2 trailers=1 skipped=0 elf=1` (computed from `TEST_FILES`, not hard-coded), `loads` and `interpreters` from the `elf` crate's `PT_LOAD`/`PT_INTERP` count of the init, `bytes` the archive length and `reserved` that length rounded up to 4096 (a zero-byte module keeps one page). It is recorded as `expected_image_record` in the top manifest and compared field-for-field with the kernel's serial record; a mismatch fails the case.
4. **Per-case module layouts.** Every case's module 0 is the generated archive (`fixtures/initramfs.cpio`, hash bound at generation, again after the per-case snapshot copy and again after extraction from the FAT image). `empty-module` appends a genuinely empty second module (expected `reserved=4096 bytes=0`, epoch `modules=2`). `bad-module` is `fixtures/initramfs-corrupt.cpio` (deterministic garbage starting with the gzip magic `1f 8b`) as module 0 and the archive as module 1: the kernel must print exactly `WARN Initramfs unpacking failed: module=0 error=Archive { offset: 0, error: CompressionPending(Gzip) } skipped=true`, no `CHECK image inspected module=0`, the archive's record as `module=1`, epoch `modules=2`, then every success marker and exit 33 (Linux reports a bad initramfs and still boots). The success-marker list is `SUCCESS_MARKERS` in `xtask/src/kernel.rs`; per-module image records are validated in `validate_image_serial` because they depend on the layout.

**Fresh-clone procedure.** `git clone <repo> <dir-under-target-or-anywhere-with-space>` (not a small `tmpfs`: a run is several GiB), install nothing beyond the prerequisites above (exact nightly with `rust-src` for the kernel/init builds, Rust 1.88 for `xtask`, QEMU, OVMF, Limine 12.9.3, mtools/dosfstools, `sha256sum`, `readelf`, `setpriv`), then from the clone: `env PATH="/bin:$PATH" CARGO_HOME=<empty dir> CARGO_NET_OFFLINE=true cargo +1.88.0 run -p xtask --locked --offline -- kernel-test --output target/kernel-tooling/<new-name> --timeout-seconds 60`. Everything else (vendored crates, init, archive) comes from the clone; recorded in [implementation](implementation.md#generated-initramfs-fixtures-and-the-built-init).

Not asserted yet: any userspace execution (`CHECK userspace exec`, init output lines, the Linux "Attempted to kill init" panic). Those arrive with the kernel userspace work; the init is only inspected, never run, by the current kernel.

## Build profiles and compiler contract

Both profiles run Cargo from the project root with `--offline --locked`, fresh output-local `CARGO_HOME` and per-profile `--target-dir`. `rustup which --toolchain nightly`, with automatic installation disabled, resolves already-installed actual Cargo/rustc once; inherited host `CARGO` and proxy selection do not choose the runtime. Required Cargo commit `3d7cf6e937d6127d0f49881bf689c560b36d35c4` and rustc commit `5c543b0b8c73c7b72bc8284ced4fb22ead15734d` must share a sysroot. Absolute `RUSTC` and exact bundled `rust-lld` are bound through Cargo and explicit `-Clinker`. Host1.88 is separate. Pinning does not certify all compiler lowering: the [confirmed error-code ABI defect and local repair](implementation.md#error-code-entry-defect-reproduction-and-repair) require their own generated-code/consumer review.

Compiler executables and their installed `librustc_driver`/LLVM support libraries are hashed **before** the identity queries, checked against the pre-build inventory, and included in the post-build equality check. This closes ordinary alias/file drift; it is not a sandbox against a malicious tool or a same-user adversary changing bytes and restoring them between observations.

Every child starts with a cleared environment plus a minimal system `PATH`, `LC_ALL=C`, and explicitly constructed settings. The runner rejects nonempty `RUSTC`, compiler wrappers, Rust flags/bootstrap/target-path overrides, `LD_PRELOAD`, and Cargo build/target/profile/source/unstable overrides (including a redirected build directory). The build explicitly sets both wrapper variables and `RUSTFLAGS` to empty and sets `CARGO_ENCODED_RUSTFLAGS` to exactly three `--remap-path-prefix` flags (checkout -> `/src`, run directory -> `/out`, toolchain sysroot -> `/toolchain`) plus, for the kernel builds only, `--cfg=no_global_oom_handling` ([fallible-only allocation](#fallible-only-kernel-allocation); the user `/init` keeps exactly the three remaps; recorded as `cargo_encoded_rustflags` in the build manifest), so no host path reaches panic locations or debug info of any crate in the target build, `core` included; it does not rely on removal that could expose a Cargo-config fallback. Cargo's own inherited `LD_LIBRARY_PATH` is discarded rather than forwarded. Repository/ancestor `.cargo/config{,.toml}` files, including a home directory that is an ancestor, are refused; global Cargo configuration is not copied. There is no toolchain/target installation, network resolution, or global Cargo/Rustup mutation.

Shared target/compiler arguments are:

```text
-Zbuild-std=core,alloc,compiler_builtins      (kernel; the user /init build uses core,compiler_builtins)
-Zbuild-std-features=compiler-builtins-mem
rustc --offline --locked --target-dir <private-output>/cargo-target
-p kernel --bin linux-rs-kernel --target x86_64-unknown-none --release --no-default-features
-Crelocation-model=static
-Clinker=<actual-qualified-sysroot>/lib/rustlib/x86_64-unknown-linux-gnu/bin/rust-lld
-Clinker-flavor=gnu-lld
-Clink-arg=--no-pie
-Clink-arg=-Tkernel/linker.ld
-Clink-arg=--no-undefined
-Clink-arg=-Map=<this-run>/kernel.map
```

`kernel-build` uses only `--features freestanding`. `kernel-test` independently builds `--features qemu-self-test` (which includes `freestanding`) and `--features freestanding`, under `qemu-self-test-build/` and `freestanding-build/`, and then the user `/init` under `init-build/` ([generated fixtures](#generated-initramfs-fixtures)). The ELF snapshot, linker map, target specification and runtime archives are per-build. The source inventories must also agree across the three builds. Runtime archives are discovered recursively in the **fresh** target's release tree, including current Cargo's `release/build/{core,compiler_builtins}/<hash>/out/` layout, not assumed to live in `deps`. Both runtime providers must be present, plus `alloc` for the kernel builds (and no `alloc` in the init build); artifact symlinks/special files fail.

### Source and vendored standard-library binding

Before Cargo runs, the harness records every regular file in the current `kernel/`, `xtask/` (including every module and `package.rs`), `baremetal/` and `vendor/` trees, root `Cargo.toml`, `Cargo.lock`, `LICENSE`, `.cargo/config.toml`, and any root `rust-toolchain*` files. It separately records the complete selected installed `rust-src/library` tree, including `core`, compiler-builtins, workspace metadata, vendor files and checksum manifests; the Rust library copyright/license files; exact compiler/tool inputs; the running harness executable; and generated local Cargo configuration/target specification. Source symlinks and special files are refused.

Sorted path/SHA-256 inventories are saved as `source-inputs-{before,after}.tsv` and `runtime-inputs-{before,after}.tsv`. Hashing is batched and uses NUL-delimited filename records. After Cargo finishes, the source trees are re-enumerated and rehashed: additions, removals or byte changes fail the build, even if Cargo returned zero. Both successful and failed build directories are retained. These snapshots detect changes over the observed interval; they do not authenticate a pre-existing modified checkout or prove reproducibility.

The runner requires the matching installed Rust source distribution's own `library/vendor` and exact source-replacement configuration. It strictly parses the installed lock/checksum metadata, compares each locked vendor package checksum and each listed file digest with the pre-build inventory, and preserves those inputs. Only a generated **run-local** Cargo configuration points crates.io resolution at the [merged vendor directory](#vendored-dependencies-and-the-fresh-clone-build) (rust-src vendor plus the project `vendor/`). No global registry cache, reconstructed source-only cache, downloaded dependency, or fabricated `.cargo-checksum.json` is used. Cargo remains offline and enforces its normal source checks. The trust root is the installed qualified toolchain/rust-src distribution: checksum consistency is **not independent cryptographic authentication**.

The ELF must be x86-64 ET_EXEC with executable PT_LOAD ranges. Its immutable snapshot hash is checked when copied, before FAT staging, and after guests. The manifest explicitly says that xtask does **not** perform full symbol/disassembly/provider/unsafe/legal closure review. That review and reproducibility remain separate acceptance obligations.

### Fallible-only kernel allocation

The kernel links `alloc` (`-Zbuild-std=core,alloc,compiler_builtins`) rebuilt with `--cfg no_global_oom_handling`, the switch Rust-for-Linux uses: every `alloc` API that can abort when allocation fails (`Box::new`, `Vec::push`/`with_capacity`/`vec!`, `String::from`, `format!`, `Clone` of collections, ...) is compiled out, so kernel code can only use `try_reserve`, `Vec::push_within_capacity`, `Box::try_new` and similar. Observed on `rustc 1.101.0-nightly 5c543b0b8` with a probe crate built exactly this way: the fallible calls compile; `Box::new(1)` fails with `E0599 no associated function or constant named new found for struct Box`, and `Vec::push` with `E0599 no method named push`. The flag must reach the `alloc` build, so it is in the harness's `CARGO_ENCODED_RUSTFLAGS` (kernel only) and in every target Clippy command: `env CARGO_ENCODED_RUSTFLAGS=--cfg=no_global_oom_handling cargo +nightly clippy --config <run>/freestanding-build/cargo-home/config.toml -Zbuild-std=core,alloc,compiler_builtins -Zbuild-std-features=compiler-builtins-mem -p kernel --bin linux-rs-kernel --target x86_64-unknown-none ...` (a Clippy run without it would accept infallible calls that the maintained build rejects). The flag is recorded in `cargo_encoded_rustflags` of the build manifest, and a unit test pins the flag set and the build-std list. Third-party crates that call infallible `alloc` APIs fail to compile in this configuration (observed: `allocator-api2` 0.4.0 with feature `alloc`), which is part of the admission test for any crate ([dependencies](dependencies.md#kernel-heap-buddy_system_allocator)). The host library tests link the ordinary `alloc`, so the guarantee is the target build's, not the host unit tests'.

### Vendored dependencies and the fresh-clone build

Registry crates live in `vendor/` (committed, produced by `cargo vendor --locked --versioned-dirs`, never hand-edited) and the checked-in `.cargo/config.toml` replaces `crates-io` with it, so every `--locked --offline` host command (`check`, tests, Clippy, `kernel-build`) resolves from a clone with only the pinned toolchains installed: no network and no `~/.cargo` registry cache. Verified with an empty `CARGO_HOME`.

`kernel-build`/`kernel-test` use `-Zbuild-std`, and Cargo allows only one directory behind a replaced source, so the harness builds a per-run merged source: `<output>/cargo-home/vendor/` holds one symlink per rust-src `library/vendor` package and per project `vendor/` package (a name-version present in both, e.g. `memchr`, must have the same lock checksum and is linked once from rust-src; differing checksums fail), and `<output>/cargo-home/config.toml` points `crates-io` at it. The build command passes that file with `--config`, which has higher precedence than the checked-in host config, so the two never shadow each other. Before the build the harness verifies every project package against the root `Cargo.lock` (exact locked set, `.cargo-checksum.json` `package` equals the lock checksum, every listed file hash equals the file, **no unlisted file**, only the reviewed `build.rs` allowlist) and records them in `vendored-std-inputs.tsv`. `vendor/` and `.cargo/config.toml` are in the before/after source inventories, so a byte change during the build fails it. `reject_build_overrides` refuses every `.cargo/config*` in the root or an ancestor directory except `.cargo/config.toml` byte-identical to `PROJECT_CARGO_CONFIG` in `xtask/src/kernel.rs`, which is also accepted in an enclosing checkout (a worktree nested under the main checkout's `target/`). That is safe because the file's relative `vendor` resolves against its own directory, the deeper config wins for the same keys, and build-std builds override `crates-io` with the per-run `--config` file; a differing ancestor file, a legacy `.cargo/config` and a root with `vendor/` but no config of its own stay rejected (unit tests; a unit test also pins the checked-in file to the constant). The checksum chain is integrity consistency, not authentication of the crates.io bytes: `Cargo.lock`'s checksum covers the `.crate` archive, not the extracted tree, so a coordinated edit of a file and its `.cargo-checksum.json` entry is undetectable offline (re-run `cargo vendor --locked` and diff `vendor/` to authenticate). Build scripts and proc-macros are found by asking `cargo metadata --offline --locked --all-features` (see [project audit](project-audit.md#skills-and-rust-only-source-policy)), not by text matching; the host `xtask` therefore depends on the vendored `serde_json` ([record](dependencies.md#host-tool-dependency-serde_json-for-the-vendor-gate)). Because the check and the harness share the verifier, a root with its own `vendor/` must carry the reviewed `.cargo/config.toml` itself, even nested in a checkout that has one. Known limits: the host `cc`/linker is not hashed, the two reviewed build scripts and proc-macros run unsandboxed as the invoking user, the ambient-environment check is a denylist, and the merged-directory symlinks are not inventoried.

Update workflow: the checked-in config makes `cargo add`/`cargo vendor` run inside the repository look only at `vendor/`, so run them from a directory outside the repository with `--manifest-path` (e.g. `cd /tmp && cargo add --manifest-path <repo>/kernel/Cargo.toml x86_64@=0.15.5 ...`, then `cargo vendor --manifest-path <repo>/Cargo.toml --locked --versioned-dirs <repo>/vendor.new`), move `vendor.new` over `vendor/`, review the diff (unchanged crates must show no diff) and the new crate per the [admission record](dependencies.md#admission-record-one-crate-one-exact-configuration), add any new `build.rs` to `VENDOR_BUILD_SCRIPTS` only after reviewing it, and run `check`. A branch that adds a crate while another does too must re-run `cargo vendor` after the merge. Target-specific `cargo clippy -Zbuild-std ...` is not covered by the checked-in host config (it needs the merged source): append `--config target/kernel-tooling/<a kernel-build run>/cargo-home/config.toml` to it (and, for the kernel, `-Zbuild-std=core,alloc,compiler_builtins` with `CARGO_ENCODED_RUSTFLAGS=--cfg=no_global_oom_handling` in the environment, see [fallible-only allocation](#fallible-only-kernel-allocation)), as exercised in [implementation](implementation.md#cpu-layer-on-audited-crates).

### Bounded processes

Metadata/version/hash/git/ELF/target queries use bounded socket capture: 30 seconds and at most 16 MiB per stdout/stderr stream. Cargo has a 900-second deadline; filesystem-image commands have 30-second deadlines. No shell implements the harness. Ordinary commands run in a new Unix process group (`CommandExt::process_group(0)`) and the long-lived children (cargo, QEMU) are launched as `/usr/bin/setpriv --pdeathsig KILL -- <program>` (util-linux; it sets `PR_SET_PDEATHSIG` and execs in place, so pid and process group are unchanged). Ctrl-C, SIGTERM or an aborting panic of xtask therefore kills them instead of orphaning them. The signal follows the spawning thread, and every spawn happens on the thread that waits for the child. `setpriv` is a fixed absolute path whose version and SHA-256 are recorded in the manifests (and in the build runtime inputs). Not covered: grandchildren such as `rustc` (once cargo is dead they finish their current compilation unit and stop; observed gone within seconds), a parent dying between fork and `prctl` (no `getppid` recheck without `unsafe`), short-lived metadata/image tools, and the `kill` utility. A crate such as `rustix` was rejected: it needs `unsafe` `pre_exec` and its dependencies would enter the shared lock file that the isolated offline kernel build must vendor. On timeout/error, and when a direct child exits with descendants still present, the runner uses the fixed `/usr/bin/kill --signal KILL -- -<group>` utility, itself bounded to two seconds, and reaps its direct child. The shared helpers are also used by packaging. This controls the audited tools' inherited process trees, not a hostile process deliberately escaping its group.

## FAT image and firmware boundary

The runner creates regular image/evidence files and a private QMP socket in a fresh `0700` directory `$XDG_RUNTIME_DIR/linux-rs-qmp-<pid>-<run-name>` (falling back to `/tmp`; removed after the capture) because `sun_path` is too short for deep checkouts; its path is in the recorded `qemu_arguments`. It sizes a disposable FAT32 image with Rust filesystem calls, then invokes `mkfs.fat`, `mmd`, and `mcopy` with explicit argument vectors; there is no shell, mount, loop-device, raw-device write, privilege escalation, or network device. The image contains the real ELF at `/linux-rs-kernel`, Limine at `/EFI/BOOT/BOOTX64.EFI`, and a generated `limine.conf` with `timeout: 0`, `protocol: limine`, `path: boot():/linux-rs-kernel`, and `resolution: 1024x768x32`. The runner extracts the staged ELF and EFI application again, compares their actual payload digests to their inputs, and records those image-payload hashes rather than merely hashing unrelated source files.

QEMU uses x86_64 `q35`, TCG, one CPU, 512 MiB, no NIC, and OVMF. `OVMF_CODE.4m.fd` is read-only and the boot disk is attached `readonly=on` as a `virtio-blk-pci` device (QEMU rejects read-only `ide-hd`/AHCI disks; Limine/OVMF only read it); a fresh `OVMF_VARS.4m.fd` copy is created for every guest and retained after execution. Limine's EFI payload is retained as an image-verified extraction; Limine/OVMF notices are also copied. Limine's `--version` first line must be exactly `Limine 12.9.3`. Manifests retain tool identities, QEMU arguments, image/firmware digests, variable-store before/after digests, boot-disk `sha256_disk_image_initial`/`_after_run` digests (a difference fails the run) and observed outcomes. The guest serial log is read with a 4 MiB cap; an oversized, missing or non-UTF-8 log fails the case with that reason.

## Automated self-test cases

The self-test profile uses QEMU's explicitly supplied `isa-debug-exit` device. No exit code alone is accepted: success requires exit 33 **and** all required serial records; failures require exit 35 **and** the case-specific diagnostic, and must not contain `RESULT success`.

Current source has **thirty-two fixed cases** plus the [oracle-group cases](#oracle-group-cases) (one per landed syscall group): the twelve below, seven that exercise the first userspace slice (`init-segfault` with `-- fault`, `no-init` with an archive that has no `/init`, `unimplemented-syscall` with `-- io_uring`, `sse`, `rseq`, `demand` with `-- demand` (init takes its own ring-3 page faults; the required `CHECK user-faults ok handled=N` has N >= 1 there and is only required to be present in the other userspace cases), and `cpu-max` under `-cpu max` requiring `smep=true smap=true`) and seven interrupt-controller/time [platform cases](#platform-cases) and three that run the signal smoke (`user/init` mode `signals`, [record](implementation.md#signal-wiring)): `signals` under `qemu64`, `signals-nolapic` on the PIT-only clockevent (an `ITIMER_REAL` wake-up served by the periodic PIT) and `signals-kvm` on the KVM TSC-deadline clockevent, and three [scheduler cases](#scheduler-cases) (`sched-switch`, `sched-preempt`, `kstack-overflow`). The `signals*` cases are positive cases with the mode line `init: signals ok`; the mode exercises handler entry and `rt_sigreturn`, faults recovered by handlers, a timer interrupting a busy loop, `pause`, `rt_sigsuspend`, `rt_sigtimedwait`, the alternate stack, hostile `rt_sigreturn` frames (bad RIP, CS and SS; a compatibility RIP beyond 4 GiB where the CPU enforces the limit, i.e. not under TCG; a non-canonical RSP, which user mode resumes with), an unreadable `rt_sigreturn` frame (`bad frame in rt_sigreturn`), `getitimer`/`alarm`/a periodic timer and 300 microsecond-scale timers, TSC-based lower bounds on `pause`, `rt_sigtimedwait` and the periodic timer (calibrated by the 20 ms busy-loop timer), and the signals the VFS and memory lanes send (`SIGPIPE` with `EPIPE`, `SIGXFSZ` with `EFBIG` past `RLIMIT_FSIZE`, `SIGBUS`/`BUS_ADRERR` with the faulting address for a file page past `i_size`), and prints the same line on the pinned Linux 6.18.57 (TCG and KVM). The positive cases `success`, `empty-module`, `bad-module`, `sse`, `rseq` and `cpu-max` require, exactly once and in order, the isolation audit, `Run /init as init process`, `CHECK userspace exec path=/init entry=0x<AT_ENTRY> loads=<PT_LOAD count> sp=0x7fffffff... smep= smap=`, the exact `CHECK mm-usercopy ok fault_in=read,write short_write=4 hole=8 readonly=refused zero_page=shared range=refused unmap=restored` record ([memory-mapping wiring](implementation.md#memory-mapping-wiring)), init's first line, its summary line, an optional mode line, `init: ok`, the init-death panic with exit code 0 and `RESULT success`; the summary line is computed from the built init ELF (`AT_PHDR`, `AT_PHNUM`, `AT_ENTRY` via the `elf` crate) and the `qemu64` constants and equals the oracle's `vdso=0` line with its two `AT_RSEQ_*` entries removed (`target/linux-reference/init-reference-004`). `cpu-max` compares only the line's prefix because `AT_HWCAP` is model dependent. The failure cases check Linux's text in order: the segfault line shape, its `init[off,start+len]` bracket bound to the executable `PT_LOAD`'s file-backed extent (page-rounded `p_vaddr..p_vaddr+p_filesz`) and `exitcode=0x0000000b`; `no-init`'s `prepare_namespace` lines (observed on the pinned kernel, minus its configuration-dependent filesystem list) and `FAIL no-root`; `FAIL syscall unimplemented nr=425` (`io_uring_setup`; the case moved off `mmap` when the memory syscalls were implemented). The tenth genuine terminal-PF case retains failed0079/10/callee residue0 and corrected00810/10/residue8; positive cases require the unique returning-PF fifteen-GPR proof. The eleventh `empty-module` and twelfth `bad-module` cases are independently expected33 ([layouts](#generated-initramfs-fixtures)), not treated as negatives merely because their names differ from `success`. Historical008/003 source does not contain the new buddy/image/runtime consumer wave; [publication evidence](implementation.md#publication-checkpoint) separates current inputs and retained failures.

Serial captures retain the exact UART bytes, including firmware output before kernel entry. ### Oracle-group cases

`oracle_case!(<group>)` in `xtask/src/kernel.rs` adds one `DEBUG_CASES` entry named `oracle-<group>`: `qemu64`, command line `-- <group>` (one of the `user/init` oracle modes `mm ids time signal fs proc`), exit 33, the normal `SUCCESS_MARKERS`, the ordinary userspace record sequence (isolation audit, `Run /init`, exec record, hello line, the exact summary with `argc=2`, `init: ok`, init-death panic, `RESULT success`) and one more requirement, `validate_oracle`: of the serial records, exactly those starting with `init: test `, `init: tests ` or `init: info ` are compared with the rows of `xtask/oracle/expected.tsv` for that group, which are the lines the pinned Linux 6.18.57 printed for the same `/init`. They must be equal one for one, in order, with none missing, none extra, no `FAIL` line and the summary `init: tests <group> passed=<n> failed=0`; they must also lie between init's summary line and `init: ok`. Kernel `printk` lines and init's banner are ignored. `info` rows are recorded observations (for example tmpfs directory cookies), so only their `init: info <group>.<name>` key must match, not the value. Landing a group's syscalls therefore means adding one `oracle_case!(<group>)` line and raising the array length; the validator and its unit tests are shared (`oracle_case_requires_every_expected_line_exactly_in_order`, `oracle_info_rows_match_by_name_only`). Current oracle cases: `oracle-mm` (121 checks plus the summary), `oracle-ids` (157), `oracle-time` (118) and `oracle-fs` (284, the whole `fs` group including its file-backed `mmap` checks) and `oracle-signal` (201, the whole `signal` group, which needs the signal wiring together with the `ids`, `time`, `mm` and VFS syscalls); the [VFS spine](implementation.md#vfs-spine) and the [memory-mapping wiring](implementation.md#memory-mapping-wiring) are thereby compared with the recording.

Every case must also print `CHECK console ok framebuffers=N scrolled=true tail=true stale=false readback=true wrap=true` (exactly once, before `CHECKPOINT`) ([console record](implementation.md#framebuffer-console-on-real-hardware)): `N` is `DebugCase.framebuffers`, 2 for `success` (its QEMU adds `-device ramfb` so OVMF publishes a second GOP handle) and 1 elsewhere.

Each of the thirty-two fixed cases and every oracle-group case has a separate FAT image, QEMU process, copied variable store, serial log, QEMU stdout/stderr and `result.tsv`. Timeouts always fail; the runner kills the guest process group and reaps QEMU. It deliberately omits `-no-shutdown`, which would hide the debug-exit result. Port `0xf4` and assumed COM1 output are confined to the explicit QEMU self-test feature/device profile.

### Scheduler cases

All three exist only in `qemu-self-test` builds and run `ktask::selftest` between the user-image checks and the start of `/init` (`sched-preempt` also at `/init`'s death); the `test=` word may precede a `--` and `/init`'s arguments ([record](implementation.md#scheduler-core)).

* `sched-switch` (`test=sched-switch`, exit 33): a positive case with the normal success markers, the usual userspace sequence for `/init`, and exactly one `CHECK sched-switch ok threads=7 switches=ok regs=callee-saved first_run_abi=aligned fpu=isolated order=fifo timers=ordered wake=keyed,signal,spurious stacks=recycled pool=exhausted,reused guards=unmapped guard_fault=exact` record, compared whole by `named_case_failure` (a missing, altered or duplicated record fails). Behind it: seven kernel threads (two timed sleepers, a keyed and an unkeyed sleeper with the controller that wakes them through the wrong key, the empty key, a signal wake-up and the right key, and a ping-pong pair that alternates 256 rounds through `schedule()` while loading chosen callee-saved registers and XMM0 before each switch and checking them after, and checks the SysV alignment of its first Rust frame); the sleepers' timers fire in expiry order; 128 threads fill the stack pool, the 129th is refused, all exit, their `SchedId`s go stale and the slots are reused; every pool guard page is unmapped with its stack mapped, and a read of one faults at the exact instruction.
* `sched-preempt` (`test=sched-preempt -- signals`, exit 33): a positive case with the normal success sequence and the `signals` mode line, plus exactly one `CHECK sched-preempt ok kthread=ran user_return_preemption=interrupt init=resumed` record (compared whole by `named_case_failure`) printed when `/init` dies. A kernel thread kept runnable beside `/init` yields in a loop; the tick preempts `/init` at the return to ring 3 from the timer interrupt and the kernel switches to the thread inside the user-interrupt handler. The record is printed only if the thread ran at least twice and at least two such preemptions switched tasks (counted in `ktask::preempt_user`); `/init`'s `signals` output must still be complete and in order.
* `kstack-overflow` (`test=kstack-overflow`, exit 35): a negative case. A kernel thread recurses (6 KiB frames, larger than the 4 KiB guard page, so only per-page stack probes stop it before the guard is jumped) until its stack is gone; the fault on the unmapped guard page finds no room for the exception frame and becomes a #DF on its IST stack, and the kernel must print `FAIL kernel stack overflow slot=0 vector=8` (the record also carries `cr2=` inside the guard page) and never `RESULT success`.

Mutation evidence (changed code in a scratch worktree, same harness) is in [the record](implementation.md#scheduler-core).

### Platform cases

Every positive case now also proves which interrupt-controller and time path the kernel took ([design](implementation.md#interrupt-controllers-and-timekeeping)). `DebugCase` carries a `Platform` (QEMU `-machine` string, `kvm` flag, expected APIC mode, tick clockevent, IOAPIC-timer result, HPET presence, accepted TSC calibration sources); `validate_platform` requires exactly one `CHECK interrupt-controllers ok mode=<m> event=<e> ioapic_timer=<t>` of that value, a `CHECK tsc ok` whose `source` is allowed (and, for `source=pit`, `pit_tries` in 1..=3), `khz>=100000`, `rtc=true` and an `hpet_hz` that is non-zero iff the machine has an HPET, a `CHECK time-tables` agreeing with it, `CHECK madt ok` with one CPU and one IOAPIC, `CHECK apic ok` with the expected `mode` **and** `reason` (the decision, not just its result: `default`, `hypervisor`, `no-interrupt-remapping`, `nolapic`), `CHECK timer ok` with `tick16_ns` (16 ticks counted on the TSC) in 14..60 ms and `CHECK timekeeping ok` with a sleep of at least 20 ms (`slept_ns`; the kernel itself enforces `realtime_skew_ns=0` and monotonicity). Wrong-path mutations are unit tests. `result.tsv` records `machine` and `accel`. Base `Q35_TCG`: `-machine q35,accel=tcg`, `-cpu qemu64`, xAPIC, `reason=default`, one-shot LAPIC timer (this CPU model has no TSC-deadline), IOAPIC IRQ0 proven, HPET present, TSC from the PIT (`pit`) or, under host load, the HPET (`hpet`) refined against the HPET.

| Case | Machine / CPU / command line | Expected path |
|---|---|---|
| `hpet-off` | `q35,hpet=off` | as base, no HPET: **requires** `source=pit` (refined against the PM timer) |
| `pit-off` | `q35,pit=off` | HPET-only TSC calibration (`source=hpet`), `ioapic_timer=false` (no IRQ0 source), LAPIC timer still ticks |
| `nolapic` | `nolapic` | `legacy-pic`, `reason=nolapic`, `pit-periodic` tick through the 8259 (the only place the PIT drives the tick); **requires** `source=pit` |
| `noapic` | `noapic` | xAPIC + LAPIC timer, no IOAPIC programmed, `ioapic_timer=n/a` |
| `x2apic-forced` | `-cpu qemu64,+x2apic`, `test=force-x2apic` | x2APIC register (MSR) backend with the one-shot timer, `reason=hypervisor`; the mutation stands in for Linux's KVM `x2apic_available()`, which TCG cannot signal |
| `x2apic-firmware` | `-cpu qemu64,+x2apic`, `test=firmware-x2apic` | the kernel sets `IA32_APIC_BASE.EXTD` first, simulating firmware that enabled x2APIC; Linux's no-IR rule switches back to xAPIC: `mode=xapic` with `reason=no-interrupt-remapping`, which is what proves the transition ran |
| `kvm` | `q35,accel=kvm`, `-cpu host` | KVM detected: x2APIC enabled (`reason=hypervisor`), TSC-deadline clockevent, `source` `pit` or `hpet`, SMEP/SMAP in init |

| `signals-kvm` | `q35,accel=kvm`, `-cpu host`, `-- signals` | as `kvm`, running the signal smoke on the TSC-deadline clockevent; SMEP/SMAP in init; mode line `init: signals ok` |

`cpu-max` (`-cpu max`) keeps the base expectations: this QEMU's TCG model offers no TSC-deadline timer. `test=firmware-x2apic` and `test=force-x2apic` exist only in `qemu-self-test` builds. **The `kvm` and `signals-kvm` cases need a usable `/dev/kvm`.** Without one the case is recorded as `unavailable` (`case_kvm_status unavailable`, `automated_cases_unavailable`, a `UNAVAILABLE (not run, not a pass)` line in the summary): not matched, not counted as a failure, so the suite exits 0 on a host without KVM but never reports 28/28 there, and the package evidence (which requires every case matched) refuses it.

**Quick-PIT retry.** The quick PIT calibration is timing sensitive and correctly falls back to the HPET/PM timer under heavy host load. A case whose only mismatch is the TSC *source* is therefore run once more in `<case>-retry`; both logs stay, the second result decides, and its diagnostic names the first failure. This is what lets `hpet-off` and `nolapic` require `source=pit` without a flaky gate.


## Kernel-run bare-metal suite (A21)

The user-run bare-metal suite ([procedure and meaning of every check](bare-metal-suite.md#kernel-run-suite-a21), [design record](implementation.md#kernel-run-bare-metal-suite-a21)) is a third kernel profile, `baremetal-suite` (implies `freestanding` and the shared `boot-proofs`; no `qemu-self-test`, so no COM1 or debug-exit port). `Target::Kernel { qemu_self_test, suite }` selects four feature sets: `freestanding`, `qemu-self-test`, `baremetal-suite` (the physical artifact) and `qemu-self-test,baremetal-suite` (the composed build the harness validates; serial and debug-exit are added, nothing else). The suite builds set `LINUX_RS_BUILD_ID` (the short source commit, `+dirty` when the tree has uncommitted changes), which the summary screen prints.

**`xtask baremetal-suite --output target/kernel-tooling/<new-directory>`** builds `/init` and the physical suite kernel (private target directories, the same `prepare_build`/`finish_build` binding as every other build), generates the initramfs fixtures, then lays out `usb/`: `EFI/BOOT/BOOTX64.EFI` (copy of `/usr/share/limine/BOOTX64.EFI`, Limine 12.9.3 required), `limine.conf` (`timeout: 5`, one entry, protocol `limine`, `path: boot():/linux-rs-kernel`, `module_path: boot():/initramfs.cpio`, no `resolution:` line, no `cmdline:`), `linux-rs-kernel`, `initramfs.cpio`, `SHA256SUMS` and `README.txt` (the exact user steps and the build id the screen will print). It then makes a FAT32 image of exactly those files with `mkfs.fat`/`mmd`/`mcopy` inside the output directory, verifies every file by copying it back out and comparing hashes, and boots it in QEMU (`q35` TCG `qemu64`, 512 MiB, OVMF, std VGA, **no** serial and **no** debug-exit: the physical profile) while polling QMP for the kernel's terminal `HLT` state. On the way it saves a screendump about every four seconds (`tree-boot/page-NN.ppm`: the replay pages) and at the halt `tree-boot/summary-screen.png`. A premature QEMU exit, a timeout, a changed disk image or a kernel file that differs from the build snapshot fails the command. The screens are **not** OCR'd: `manifest.tsv` records `visual_review pending`.

**`kernel-test` suite cases** (`SUITE_CASES`; counted and reported apart from the 26+ debug-exit cases because `kernel-package` stages exactly `debug_case_catalog()` from the self-test build): the composed build `baremetal-suite-build/` is built beside the others and four cases run it with `suite_pause_ms=50` (the page pause of the replay): `baremetal-suite` (`qemu64` TCG), `baremetal-suite-two-displays` (a second `ramfb` display: the machine has two GPUs), `baremetal-suite-kvm` (`-cpu host`, `unavailable` without `/dev/kvm`) and `baremetal-suite-stops` (`suite_timeout_s=1 suite_groups=fault,io_uring,spin,ids`: a SIGSEGV, an unimplemented syscall and an `/init` that arms a 2 ms `ITIMER_REAL` and loops forever (ended by the one-second group bound, `FAIL group timeout after 1 s`, cause `timeout`) must end only their own group, the next group must still run and pass, the suite must report failure and exit 35). `suite::validate` requires, on top of the ordinary platform/console/image/success validators: every boot proof once as `PROOF <name> PASS` and none failing; each group's `SUITE group <g> start uptime_s=<n>` and `result=` record with the right verdict and cause (`init exit 0`, `init signal 11`, `kernel stop`, `timeout`); for a passing group `matched == expected == observed > 0`, no mismatches **and** the host harness's own `validate_oracle` over the group's serial lines (an independent comparison against `expected.tsv`); `SUITE complete ok=... groups=p/n proofs=23/23`; the summary heading, `RESULT:` line, footer and final line in order; and the 16-digit log digest on the heading and footer equal to the FNV-1a of the serial transcript between the kernel banner and the summary heading, recomputed by the host. Every case takes a separate FAT image and QEMU process like any other; the timeout is at least 180 seconds (the suite runs every group and the whole-RAM exhaustion walk under TCG).

## Default freestanding framebuffer capture

The default ELF boots with **no** `qemu-self-test`, debug-exit device, serial port or COM1 assumption. QMP `query-cpus-fast` supplies CPU identity, not halt evidence. The runner polls QMP's HMP `info registers` and requires `HLT=1`, EFLAGS.IF clear, and RIP inside an executable PT_LOAD of the exact built ELF. This excludes a firmware/menu halt and an STI/HLT timer loop, but can still represent a kernel failure halt: human framebuffer inspection remains essential. Socket readiness, bounded QMP messages and screenshot requests share the guest deadline; reads/writes are additionally bounded to two seconds and each response line to 1 MiB. The runner retains raw QMP/HMP state and requests PNG, falling back to PPM if unavailable while preserving the failed PNG attempt. It then requests QMP `quit`; exit zero within three seconds is required. Timeout, premature exit, failed cleanup or a changed ELF snapshot fails the command rather than producing a pass.

A valid image header and QMP state are checked, but **the screenshot contents are not OCR'd or otherwise programmatically certified**. The run report labels the capture `pending` human visual review, and `kernel-test` prints its exact path. A director must inspect `default-boot/framebuffer.png` (or `.ppm`) and confirm the complete checkpoint; an image file existing by itself is not a visual pass.

## Retained output

Each `kernel-build` retains `cargo.stdout.log`, `cargo.stderr.log`, the isolated target tree and runtime libraries, `readelf-header.txt`, `program-headers.txt`, `linux-rs-kernel.elf`, `kernel.map`, `target-spec.json`, tool versions, before/after source/runtime inventories and `build-manifest.tsv`. A failed top-level build writes `failure.tsv` when possible; a failed test writes a failure `manifest.tsv`. Partial files and logs are never overwritten by a subsequent run.

Each `kernel-test` also retains `init-build/` (a full build directory: `init.elf` snapshot, `init.map`, `init-symbols.txt`, manifests and inventories), `fixtures/` (the generated archive and corrupt module) and per-case images, configuration, image-verified ELF/EFI payloads, variable stores, serial/QEMU logs, notices and results. Default capture retains `qmp.log`, `qmp-cpus.jsonl`, `qmp-registers.jsonl`, `qmp-status.jsonl` and the framebuffer. The top-level manifest separates automated case matches from **pending** human visual review; case count is recorded, not inferred from an old run.

The separate experimental `kernel-package --build-output <existing-default-build-dir> --output target/kernel-tooling/<fresh-name>` interface consumes a real default-profile build without rebuilding a self-test profile into the package. Its scope, ALPM inspection and user-operated recovery restrictions are documented in [diagnostic handoff](diagnostic-handoff.md). It does not install anything or qualify a Linux-replacement package.

Execution and package evidence now share one case-name/expected-exit catalog. The package validator checks the current catalog count and every case receipt, then copies all case evidence. It no longer keeps a separate eight-case list, count or success-versus-failure exit assumption. The consumer regression uses actual fixture validation/copy/hash operations and a fresh staging destination for failed-receipt rejection, so duplicate-output errors cannot mask a missing status check. ## Five design checks

1. **Crates:** the host runner uses three vetted crates instead of hand-rolled code ([`cpio` and `elf`](dependencies.md#host-tool-dependencies-cpio-and-elf-for-the-generated-test-fixtures) for the fixtures and ELF decoding, `serde_json` for the vendor gate and the QMP client), still invoking audited external tools; the kernel's vendored crates and the two reviewed vendored build scripts they bring are described in [Vendored dependencies](#vendored-dependencies-and-the-fresh-clone-build).
2. **Bundle:** both build profiles share the same compiler/target/linker argument construction, per-run manifest, file hashing, process timeout/reaping, and FAT image staging; only the explicit feature set and QEMU evidence differ.
3. **Simplify:** one Limine/OVMF x86_64 QEMU cell is implemented first. It does not narrow the required Linux architecture, device, ABI, filesystem, protocol, or deployment scope.
4. **Security:** outputs are fresh regular files under `target/kernel-tooling`; external commands use argument vectors, no shell, network, mount, raw device, privilege or global configuration writes. QEMU networking is disabled. Debug-exit is confined to the explicit test-feature build; default capture uses no serial/debug-exit assumption. Tool and firmware inputs are hashed and notices retained.
5. **Improve:** immutable per-run ELF snapshots and separate profile caches prevent cross-build races; real allocation-failure, exception, interrupt and timer cases expose regressions. The framebuffer screenshot improves observability without claiming automated visual correctness or physical qualification.
