# Decisions register

## Authority, state and change control

This register separates **accepted user decisions/requirements**, **observed facts**, **recorded implementation decisions**, and **unresolved design recommendations**. A recommended default is not user-approved merely because another document explains it or an engineer implements it. Before implementing a blocking choice, record the chosen alternative, rationale, decision authority, affected source/configuration/ABI/hardware scope, evidence and superseded recommendation. Update all callers, plans, tests and provenance together; do not leave compatibility aliases or undocumented contradictory defaults.

The original delivery was planning/setup, a Rust project audit and a bounded nondestructive Rust smoke suite. The later implementation request has produced the real Rust `no_std` x86_64 bootstrap, immutable integration/package checkpoint and subsequent foundation work in [implementation](implementation.md). **M1 is in progress, not complete**; the canonical routing table names current `in_progress` owners, with all other rows `not_started`. Full Linux 6.18.57 scope, M2–M8, independent reviews, physical qualification, Linux-replacement packaging and performance parity remain open. M0 stays conditional on its remaining evidence/review/access obligations. Historical approvals below remain intact; the implementation choices that follow are not invented detailed user approvals.

The actual suite interface is documented in [bare-metal suite](bare-metal-suite.md):

```text
cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>
```

The environment label is an operator assertion; output directory must be new. The reference host observed by the integration owner runs `7.2.10-1-cachyos`, **not** the selected upstream `6.18.57` oracle. Do not convert a current-host smoke into baseline/candidate evidence.

## Observed baseline facts and limitations

- kernel.org release metadata observed 2026-10-19 listed 6.18.57 LTS, released 2026-10-15. [Release metadata](https://www.kernel.org/releases.json) is mutable; preserve retrieved evidence.
- [Annotated tag object](https://api.github.com/repos/gregkh/linux/git/tags/c05de972ca192e22ce318dd70ce8e990b9466f6d) `c05de972ca192e22ce318dd70ce8e990b9466f6d` resolves to commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`, tree `911d5155c230d7d778ac38585e01e8ab46d75a90`. The original GitHub inventory recorded the service's verified report without independent local verification. Subsequently, local kernel.org/GitHub fetches matched these objects and isolated GPG `verify-tag` produced a **good signature** from primary fingerprint `647F28654894E3BD457199BE38DBBDC86092693E`, authenticated by matching kernel.org HTTPS signature-page and WKD/TLS fingerprints. GPG explicitly reported `TRUST_UNDEFINED`/`[unknown]`; no Web-of-Trust or ultimate trust was established. Raw evidence is `target/implementation-prereqs/upstream-verification.txt`, indexed in [implementation](implementation.md#pinned-source-and-specification-map); [reference.tsv](../planning/reference.tsv) records current status without rewriting retrieval history.
- [Linux ABI guidance](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/ABI/README) does not promise stable Kconfig/internal symbols. [Internal driver guidance](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-api-nonsense.rst) explicitly rejects stable internal source/binary driver ABI. Preserve external behavior, not C internals by default.
- [License rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/license-rules.rst) establish overall GPLv2 and separate per-file expressions/UAPI exceptions. Direct-source translation requires [licensing](licensing.md), not merely a root license file.
- [Rust target tiers](https://doc.rust-lang.org/rustc/platform-support.html) offer differing build/runtime guarantees. A target name, host compiler installation or successful host `cargo` command does not establish kernel/backend/assembly support for every baseline architecture.

## Blocker disposition rules

1. Scope and behavior choices come from the approved decisions or a recorded resolution, not convenience. No row becomes accepted merely because an implementer starts coding.
2. Tool/repo/source-provided facts must be investigated rather than asked of the user. User-only approvals and physical operations remain explicit user actions; do not fabricate them.
3. An unresolved choice blocks only work that truly depends on it, but blocks that milestone's relevant exit. Continue independent research/implementation without calling the blocked gate complete.
4. Unavailable physical devices remain in scope with named access blockers. Host-reference or VM evidence is separately useful but cannot replace real hardware.
5. No accepted simplification can weaken Linux-visible semantics, final architecture/family coverage, security or performance. Any actual scope reduction requires explicit user approval and updates across inventory, plans and qualification claims.
6. Evidence of a flaw overrides a convenient proposal. Fix the mechanism, update every affected caller and regression case, then requalify; do not suppress the test or special-case a benchmark.
