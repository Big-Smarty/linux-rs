# Dependency candidate catalog and admission policy

## State and boundaries

**This is a candidate catalog, not blanket kernel dependency admission.** The real bootstrap in [implementation](implementation.md) links only the vendored kernel crates recorded in [admitted exact configurations](#admitted-exact-configurations) (`syscalls` there is for the userspace `user/init` only) (the host `xtask` additionally uses `serde_json`); every other catalog candidate remains unadmitted. Its matching-source compiler runtime, selected Limine protocol definitions and external loader/firmware are actual inputs with bounded evidence, described below. The dependency-free host `xtask` auditor and its `std`/compiler/platform runtime are separate from target-runtime closure. See [toolchain](toolchain.md), [licensing](licensing.md), [project audit](project-audit.md), and [architecture](architecture.md).

Evidence below was read on 2026-10-19 from upstream manifests/documentation. Moving `main`/`master` links identify research candidates, **not reproducible dependency pins**. Versions shown are observed source-manifest versions, sometimes unreleased, not recommendations or tested releases. No popularity, badge, `no_std` category, “pure Rust” description, repository language percentage, or empty advisory result proves kernel suitability. Source, archive, complete feature-resolved graph, build outputs and final machine code must all be reviewed at admission.

Approved policy: modular monolithic Rust kernel and Rust-owned executable project tools; no C kernel shim, C-backed runtime, legacy C modules, standalone assembly implementation, `global_asm!`, C/C++/Zig implementation or bindgen-backed native runtime. Rust `extern` ABI declarations and `repr(C)` are permitted layout mechanisms, not evidence of a C implementation. Only unavoidable function-local `asm!`/`naked_asm!` may qualify under the [toolchain proof](toolchain.md). External compilers/linkers, emulators, Linux reference, test tools, user programs and documented firmware may be non-Rust. That exception does not allow their runtime code to be linked into the kernel.

### First userspace program (`user/init`): one admitted crate, two rejections

- **Admitted exact configuration: `syscalls` 0.8.1** (crates.io checksum `81c645a4de0d803ced6ef0388a2646aa1ef8467173b5d59a2c33c88de4ab76e7`), `default-features = false`, `features = ["x86_64"]`, pinned `=0.8.1`. Need: issue raw `syscall` instructions with deliberately invalid pointers (the EFAULT/EBADF/ENOSYS differential checks) without Rust UB, and reuse a maintained Linux `Sysno`/`Errno` table instead of hand-copied numbers; its tables match pinned 6.18.57 for the numbers used. Licence **BSD-2-Clause**, GPL-2.0-only compatible; the duty is to retain the copyright notice (Jason White 2020-2021; Trustees of Indiana University and Ryan Newton 2018-2019), the conditions and the disclaimer in source redistribution and to reproduce them in documentation or other materials accompanying a binary distribution, which a future initramfs/package of `init` must do (the crate's `LICENSE` is kept in `vendor/syscalls-0.8.1/`, shipped in the package's corresponding-source `vendor/`). With these features it has **zero dependencies** (`std`, `serde` and every other architecture are off; `Cargo.lock` gains only this package). It is vendored byte-identically in `vendor/syscalls-0.8.1/` (produced by `cargo vendor --locked --versioned-dirs`, checksum-verified by `xtask check`). Its `build.rs` was read in full: it only prints `rerun-if-changed` and sets a `thumb-mode` cfg for ARM targets, with no process, network or file access, and `("syscalls-0.8.1", "build.rs")` is the third entry of the auditor's `VENDOR_BUILD_SCRIPTS` allow-list with that justification; there is no `links`, proc macro, `*-sys` or native code. It contains one inline-assembly construct per arity in `src/syscall/x86_64.rs`: a bare `syscall` with `inlateout("rax")`, argument registers `rdi rsi rdx r10 r8 r9`, `rcx`/`r11` clobbered, `nostack, preserves_flags` and the default memory clobber. `user/init` calls `syscalls::{syscall0, syscall1, syscall3}`, `raw::syscall0` (unknown syscall number 100000) and the `Sysno`/`Errno` tables; the other wrappers are unused. No allocation, no `unsafe` beyond the documented `# Safety` contract of the syscall functions. This admission covers only the userspace test program, not any kernel crate; the maintenance/advisory review (item 8 above) was not performed beyond reading the 0.8.1 source, so it is `reviewed exact configuration` for this test program only.
- **Rejected: `origin` 0.26.2 and `rustix`.** They would supply `_start` and syscalls, but their lock graph pulls target-cfg crates (`windows-sys`, `libc`, `errno`) into the shared `Cargo.lock` (about 62 MB to vendor for the isolated harness), `rustix` 1.1.5 does not work with `origin` 0.26.2 (it needs a `=1.1.4` pin), and `origin`'s `nightly` feature adds unwinding and `gimli`. That is disproportionate for a three-instruction entry point, so `_start` is a local `naked_asm!` function with its proof in [implementation](implementation.md#first-userspace-program).

## Admission record: one crate, one exact configuration

Proposed mandatory record, retained with the dependency change and release evidence:

1. **Need and owner:** subsystem, exact reused mechanism, alternatives (including a small local implementation or direct Linux-to-Rust port), Linux behavior not provided, and removal/replacement cost.
2. **Identity and provenance:** package/version, crates.io archive checksum, upstream immutable commit/tag, source URL, archive-to-source differences, maintainer identity/release history, fork policy and named project owner. Check yanks, ownership changes, unresolved soundness/security issues, maintenance response and release cadence; no candidate below has passed this review.
3. **Entire graph:** target, host, build, proc-macro and relevant test/fuzz dependencies separately; exact feature union and target cfgs, default features explicitly disabled where appropriate, feature reasons and target-specific edges. Cargo features are additive; one transitive request can re-enable `std`, allocation, assembly or native backends. A `Cargo.lock` alone does not record the chosen feature set. See the [Cargo features reference](https://doc.rust-lang.org/cargo/reference/features.html).
4. **Execution/build audit:** all build scripts (including custom `package.build` paths), proc macros, generated code, `links`, `cc`, `cmake`, `pkg-config`, `*-sys`, bundled archives, `include_bytes!`, network/file/process access and linker directives. `build.rs` being Rust says nothing about what it builds. Cargo documents [native compilation and link directives](https://doc.rust-lang.org/cargo/reference/build-scripts.html). Run future builds isolated, offline and with recorded inputs; review generated Rust and objects, not just checked-in `.rs` files.
5. **Kernel semantics:** actual `#![no_std]` path; `alloc` use; each infallible `Box`/`Vec`/map growth, formatter, clone, destructor and error path; fallible/context-aware allocation; reclaim/reentrancy; sleepability; interrupt/NMI context; lock order, preemption, SMP, DMA/cache coherency; endianness/alignment/32-bit widths; resource ceilings and stack usage; no host clocks, OS syscalls, threads, entropy, TLS, unwinding or libc assumptions. An allocator adapter cannot make an infallible internal growth operation fallible after the fact.
6. **Unsafe/assembly proof:** exact unsafe interfaces and invariants, aliasing/provenance, initialization, pinning, lifetimes, `Send`/`Sync`, packed accesses, volatile versus atomics, target instructions and runtime CPU dispatch; register/FP use and libcalls. Review every selected architecture path, not only x86_64. Disable unneeded optimized paths initially; do not discard mandatory checks to improve benchmarks.
7. **License:** per-file licenses/notices and every dependency, selected branch of `OR`, exceptions, generated artifacts and patent obligations; counsel review for ambiguity. MIT selection in one package does not fix an Apache-only transitive package. See [licensing](licensing.md).
8. **Security and correctness:** check the [RustSec advisory database](https://github.com/RustSec/advisory-db) and upstream issues/releases for the exact graph, record database revision/date and dispositions; fuzz hostile formats and allocation failure, test unsafe abstractions in host models, differential Linux behavior and adversarial resource limits. Audit scope/version must accompany any third-party security-audit claim; no blanket “RustCrypto audited” or “no unsafe” assurance.
9. **Qualification and maintenance:** compiler/targets, feature matrix, generated-code review, panic/OOM paths, QEMU and initial bare-metal tests where applicable, performance/resource comparison, reproducible artifacts and update rollback. Follow [verification](verification.md), [performance](performance.md), [bare-metal](bare-metal.md) and [maintenance](maintenance.md). Failed or missing mandatory evidence blocks admission, not merely a warning.

Catalog admission dispositions are `candidate` → `reviewed exact configuration` → `admitted exact configuration`; rejected and host-only candidates are separate. These are descriptive dependency decisions, not additions to the five-column workstream status schema. None of the catalog candidates has reached the second disposition; the bounded compiler/protocol inputs above have their own exact-role evidence. Each upgraded archive, enabled feature, target or toolchain change reopens the affected proof. Vendoring, if adopted after review, preserves notices and checksums; it does not itself improve source trust.

## Disqualified kernel configurations and host-only tools

- **Native C runtime behind Rust bindings:** `bindgen` generates declarations, not implementations; [its requirements](https://rust-lang.github.io/rust-bindgen/requirements.html) include libclang. ACPICA/uACPI C runtime adapters, `libfdt` bindings, `libc`, native littlefs implementations, OpenSSL/BoringSSL/aws-lc, native zlib/zstd/lzma and embedded native archives do not become Rust by disabling dynamic linkage. Reject configurations requiring those implementations. A host-side, provenance-recorded header/ABI extraction experiment may use external tooling; generated declarations still require independent ABI/layout/license review and must not introduce kernel C symbol providers.
- **ACPICA and libfdt:** [ACPICA](https://github.com/open-acpica/acpica) and [dtc/libfdt](https://github.com/dgibson/dtc) are reference implementations/external tooling candidates only. Port required behavior to Rust or qualify a Rust implementation; do not weaken ACPI/DT scope to avoid porting missing pieces.
- **OpenSSL:** [openssl-sys manifest](https://raw.githubusercontent.com/sfackler/rust-openssl/master/openssl-sys/Cargo.toml) declares FFI, `links`, `cc`, pkg-config/vcpkg and optional bundled/native providers. A Rust wrapper's MIT license and vendored mode do not satisfy the Rust-only kernel boundary.
- **ring:** [manifest](https://raw.githubusercontent.com/briansmith/ring/main/Cargo.toml) includes C files, standalone `.S`, generated assembly inputs, `cc` and `links`; license expression is conjunctive Apache-2.0 AND ISC, not a generic MIT alternative. Reject as kernel runtime; `default-features = false` is not a pure-Rust switch. This is not a claim that ring is insecure.
- **Compiler builtins:** [compiler_builtins features](https://raw.githubusercontent.com/rust-lang/compiler-builtins/master/compiler-builtins/Cargo.toml) offer a `c` feature and architecture-specific `arch` implementations. Current exact-input selection and scalar `memset` replacement are recorded above; this does not qualify every compiler-supplied object or architecture. [Toolchain](toolchain.md) defines continuing closure proof and [licensing](licensing.md) preserves exception/conjunctive-term review.
- **Hosted frameworks:** Tokio, std thread locks, generic userspace networking/filesystem/KVM/BPF loaders and host allocator/entropy facilities cannot implement kernel scheduling/IRQ/driver semantics. Proc-macro/build crates are host executables, not target runtime, but remain trusted build inputs.
- **Audit tools:** `cargo metadata`, `cargo tree`, `cargo vendor`, RustSec/cargo-audit, cargo-deny and cargo-vet are external review aids, not workspace dependencies or proof of machine-code purity. `xtask`'s offline audit subcommands make only their documented structural checks; maintained bootstrap build/run/package interfaces have separate [integration and evidence requirements](kernel-tooling.md).

## Ordered dependency work and exhaustive definition of done

The bootstrap has begun the bounded runtime work above; the broader admission and qualification stages remain outstanding:

1. **M0:** maintain the admission record, license/provenance disposition and per-target evidence repository. Resolve exact candidate releases only when a mechanism is needed; archive manifests/source/advisories. Keep the unadmitted research catalog separate from the current exact compiler/protocol/external-input record.
2. **M1:** prove Rust runtime closure, target ABI, boot transfer, panic/stack/allocator constraints before admitting architecture/boot/parser utilities. Execute the same primitive checks in QEMU and the initial recoverable physical lab; unavailable required hardware is a blocker.
3. **M2–M5:** admit narrow collections/parsers/drivers only after owning allocator/locking/DMA contracts exist; test fallible failure paths and differential Linux behavior, not only crate upstream tests. One adapter layer per shared mechanism, no duplicate hidden runtimes.
4. **M6–M7:** close every unqualified architecture/backend and subsystem feature, including obscure formats/protocols and devices; replace/reimplement unsuitable candidates rather than dropping scope. Re-evaluate CPU acceleration and feature additions with identical mitigations and configuration.
5. **M8 and updates:** an exact dependency configuration is done only when identity/license/full graph/host scripts/generated code/unsafe+asm/runtime closure/resource+OOM/panic/target matrix/security issues/semantic adversarial tests/QEMU+applicable real hardware/performance/reproducibility/owner+update rollback evidence are all accepted. Each mandatory dimension needs a reproducible command or lab procedure, retained input and raw result, reviewer and explicit pass criteria. Missing/unexecuted evidence is not a pass. The complete kernel is done only under the project-wide [verification](verification.md) and [roadmap](roadmap.md), not because its dependencies passed admission.

Safe simplification means fewer wrappers, bounded parsing, caller-owned buffers, shared representation code and deferred optional acceleration **without changing required behavior**. It never means a reduced ABI, silently smaller resource limits, unsupported real hardware relabeled as supported, or mean-only benchmarks hiding regressions. No kernel test or performance result was produced by this research catalog.

## Standing completion rule and runnable smoke tool

The exhaustive [definition of done](definition-of-done.md) remains the rule for the whole kernel; the current bootstrap does not satisfy it. The separate Rust-owned, dependency-free [bounded functional smoke suite](bare-metal-suite.md) uses the running host/guest's `std` platform services and does not establish target-runtime provenance. Its CLI requires an exact running release, new output directory and operator-asserted `reference`, `qemu` or `bare-metal` environment. Reference-host smoke qualifies the runner only; the bootstrap has no userspace ABI to run it yet. Full driver/hardware/performance/parity evidence remains outstanding.

The initial userspace is Arch/CachyOS, without importing downstream CachyOS kernel patches; the approved performance profile is balanced server. Only the current workstation is physically available, with user-operated boot selection and independent recovery. A storage-free M1 diagnostic trial is distinct from the later Linux-replacement [package](packaging.md), which retains root/initramfs/storage/userspace prerequisites and independently selectable Limine/systemd-boot paths. No candidate crate, smoke result or package plan itself proves a bootable artifact, and no required architecture/vendor/platform is waived because hardware is unavailable.
