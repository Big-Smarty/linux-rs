# Linux compatibility contract

## Status, scope, and meaning of full compatibility

**Standing compatibility contract; bounded bootstrap implementation is underway, not Linux-compatible completion.** The reference remains Linux **6.18.57 LTS**, tag `v6.18.57`, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`. [Coverage](coverage.md) records structural inventory and current/historical source authentication. [Implementation](implementation.md) separates the real x86_64 Rust bootstrap's historical cell9 evidence, maintained integration/package checkpoint and subsequent foundation revisions. Its canonical routing table identifies `in_progress` owners; no tested bootstrap cell, compiled host tool or structural audit establishes whole-prefix translation, M1 completion or Linux ABI parity.

Full compatibility means preservation of the pinned Linux kernel's externally observable behavior across every applicable architecture, userspace ABI, configuration capability, hardware/device family, persistent format, and protocol in that baseline. It includes old, uncommon, optional, and obsolete-but-present facilities, not only server/container workloads. Removed historical facilities absent from the pinned baseline are not silently added to scope. Arch/CachyOS userspace is the first deployment target; balanced server/container workloads and x86_64/QEMU-first debugging determine order, not the final denominator. Bare-metal design and recovery are required from M1; physical evidence remains blocked until actual user-reported runs under [bare-metal qualification](bare-metal.md). At-least-baseline performance, with unchanged security and semantics, is an additional release condition under [performance](performance.md).

This is an approved **modular monolithic Rust kernel** direct source-port program, not a Linux-in-Linux wrapper. Kernel and project-owned executable tools must be Rust; kernel code is `no_std`. No C-backed kernel runtime, legacy C kernel module execution, standalone assembly implementation, or `global_asm!` escape is permitted. Function-local `asm!` and `naked_asm!` are permitted only where unavoidable, with the operation, alternatives rejected, privilege/register/memory/clobber contracts, reviewers, and disassembly evidence recorded. Existing non-Rust userspace, external test suites, compiler/linker tools, and explicitly recorded firmware/microcode are allowed. See [architecture](architecture.md), [licensing](licensing.md), and [toolchain](toolchain.md).

“Full” is not a mathematical claim that finite tests exhaust every possible execution. It is a release claim conditional on a closed, reviewable obligation set, implementation traceability, all required evidence gates, no unexplained differential failures, and no unqualified required matrix cells. A newly found baseline obligation expands that set and can invalidate a prior claim. No present delivery makes this claim.

Only the user's workstation is available; no multi-vendor lab or physical result is invented. An isolated storage-free M1 diagnostic trial may precede rootfs/initramfs/storage/userspace, but needs actual declared-scope QEMU evidence, separate user-owned recoverable media and independent known-good recovery. It is not a Linux-replacement package. The latter retains full applicable QEMU/userspace/storage/deployment gates, independently selectable actual supported boot entries and rollback instructions. Native Limine ELF does not implement systemd-boot EFI/PE, native EFI, Linux or PVH boot paths. User-reported physical outcomes remain authoritative; other devices/vendors/architectures and power-failure facilities remain blockers, not VM passes. The semantic/performance oracle stays pinned upstream Linux, not the installed CachyOS kernel.

The completion requirement remains exhaustive; the initial bootstrap is not the completed port. Apply [definition of done](definition-of-done.md), [packaging](packaging.md) and [verification evidence levels](verification.md). The runnable [bare-metal smoke tool](bare-metal-suite.md) is bounded host/guest tooling; its existence, a reference-host run or an asserted environment label is not physical candidate qualification. The candidate has not been shown to host that runner: it needs sockets, which the declared configuration leaves off ([matrix below](#current-support-matrix)).

## Current support matrix

This section is **present support**, kept short and separate: what the kernel does today, how much of it, and which executable evidence applies. It is not a compatibility percentage, it is not evidence of the unexercised remainder, and every row is limited to the declared configuration and to x86_64 on one CPU in QEMU. Evidence kinds are those of [verification](verification.md#what-each-command-establishes); an "oracle group" is a `user/init` mode whose serial output equals the lines the pinned Linux 6.18.57 printed for the same program (`xtask/oracle/expected.tsv`), and the groups that need KVM, AVX-512 or pinned host programs report `unavailable` elsewhere. **Supported configuration** ([`kernel/src/config.rs`](../kernel/src/config.rs), 16 declared options, each tied to pinned source): x86_64, 4 KiB pages, four-level paging, one CPU, `CONFIG_PREEMPT_VOLUNTARY`; boot-parameter equivalents `norandmaps` (no address randomization), `vdso=0` (no vDSO, no `AT_SYSINFO_EHDR`), `ia32_emulation=0` (no 32-bit entry points), `nofsgsbase`; `CONFIG_RSEQ=n`, `CONFIG_NET=n`, `CONFIG_SECURITY_LANDLOCK=n`, `CONFIG_UPROBES=n`, user shadow stacks off and the x32 ABI off (the corresponding syscalls answer `-ENOSYS` exactly as the pinned reference build does); the console is the 8250 `ttyS0` at 9600n8; XSAVE with AVX-512 and `PKRU` where the CPU has them (`noxsave` selects FXSAVE-only). ## Reference authority and observable equivalence

1. Record the exact reference source, build configuration, compiler/toolchain, boot command line, userspace image, firmware, hardware, privileges, namespaces, resource limits, and test revision. A distribution kernel with extra patches is a different oracle unless its delta is explicitly part of the experiment.
2. Use pinned UAPI definitions, architecture entry/compat code, and actual reference executions together. Manuals explain intent; current online manuals can describe later releases or removed architectures and cannot override pinned source. Conflicts become reviewed obligations with minimal reproductions, not implementation guesses.
3. Compare success and failure values, output bytes/layout, state changes, visibility, permission checks, lifecycle, and event ordering. Match required behavior, not incidental allocator addresses, private object layout, identical instruction sequences, or one arbitrary scheduler interleaving.
4. Nondeterministic outputs need a **per-interface** normalization justified by Linux's allowed behavior: for example, consistently renaming allocated PIDs across all related records, rather than deleting identity checks. Randomness, address randomization, clock precision, packet timing, and scheduling retain their required distributions, invariants, and bounds. Never normalize away a security or performance regression.
5. A Linux defect is not automatically a required vulnerability. Any security-driven behavioral deviation must identify the baseline behavior, affected callers, exploit risk, intended replacement, and review decision. It is reported as a deviation, not passed parity. Updating the pinned baseline requires an explicit decision and complete delta review, never an unannounced moving oracle.

Upstream distinguishes stable/testing/obsolete/removed userspace ABIs and explicitly excludes Kconfig symbols and kernel-internal symbols from stability promises: [pinned ABI policy](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/ABI/README). That distinction is not permission to drop baseline functionality or administrator workflows.

## ABI obligations

### Syscall identity, entry, and representation

Maintain a separate obligation for every architecture/ABI syscall table entry, alias, historical multiplexor, reserved hole, and configuration dependency. Numbers, audit architecture identifiers, entry instruction/register conventions, argument extension/truncation, split 64-bit argument ordering, second return registers, error flags, and return-to-userspace state must match that ABI. Do not use x86_64 syscall numbers or generic errno constants globally. Raw syscall callers and libc callers are separate tests: libc may translate errors, retry, or emulate an absent syscall.

The pinned [x86 table](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/x86/entry/syscalls/syscall_64.tbl) explicitly distinguishes common, 64, and x32 entries. The [syscall manual](https://man7.org/linux/man-pages/man2/syscall.2.html) documents register and x32 differences but is a live supplementary reference, not the baseline inventory. Architecture-specific tables and UAPI in the pinned tree determine the rest.

For each exported structure, record byte size, alignment, field offsets/widths, signedness, padding, packing, union discriminator, array count, pointer encoding, byte order, flag meanings, and extension/size rules. `repr(C)` alone does not prove the right userspace ABI. Never reinterpret a user byte buffer directly as a Rust enum, reference, `bool`, pointer-bearing internal object, or arbitrary aligned structure. Use explicit checked decoding and initialized output encoding; preserve defined padding behavior without leaking uninitialized kernel memory. Compile-time layout checks and independent byte fixtures are both required.

Native 32-bit execution, 32-bit userspace on applicable 64-bit kernels, x32 where present, architecture-specific personalities, and little-/big-endian variants remain separate obligations. Account for 31-bit pointers on s390 compat, i386 64-bit field alignment, architecture-specific `stat`/`statfs`/`siginfo`/`flock` layouts, native-word masks and fd sets, IPC legacy forms, socket ancillary data, and compat ioctls. An architecture having a rustc target does not prove kernel support, ABI support, or hardware qualification.

Preserve both old-time and time64 interfaces, including syscall numbering, `timespec`/`timeval` variants, timeout clock selection, absolute/relative behavior, overflow/error behavior, timestamp updates, and compat conversion. Test negative times, invalid nanoseconds, 2038 boundaries, large future dates, time namespaces, clock adjustment, suspend, and restart-related remaining time. [Pinned time types](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/include/uapi/linux/time_types.h) distinguish `__kernel_timespec`, old timespec/timeval, and socket time values; do not substitute host libc types.

### Errors, validation order, interruption, and partial effects

Every operation needs a decision table covering valid and invalid combinations, unknown flags, invalid descriptors, missing objects, inaccessible user pages, insufficient permission, resource exhaustion, interrupted waits, and concurrent deletion. Match the pinned operation's **validation order**, errno value/encoding, and committed side effects when multiple conditions fail. Do not impose a single global “permission first” or “pointer first” rule. Error output buffers, short I/O, partial usercopy, count updates, timeout mutations, file offsets, and resource rollback are observable. Preserve architecture errno numbering and distinctions such as `ENOTTY`, `EOPNOTSUPP`, `ENOSYS`, `EINVAL`, `EFAULT`, and `EINTR` where the reference does.

Internal restart codes are not public errno values. Reproduce interrupt/restart behavior with and without `SA_RESTART`, signal handlers, stop/continue, restart blocks, ptrace, seccomp, and completed partial I/O. Test handler-visible register state and repeated timeout accounting, not only eventual success. The pinned [x86 signal path](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/x86/kernel/signal.c) treats restart classes differently; this is architecture-sensitive code to port, not a generic retry loop.

Returning `ENOSYS` is correct only for the matched baseline's absent/disabled syscall in the tested cell. It is not an implementation of an enabled syscall. Similarly, matching a disabled Linux configuration proves only that disabled behavior, never implementation of the enabled feature.

### Processes, signals, executable loading, and vDSO

Preserve process/thread identity and inheritance, clone flag interactions, exec transitions, credentials, descriptor sharing/close-on-exec, wait/reaping, futex/robust-list/rseq behavior, job control, ptrace, core dumps, and observable `/proc` state. Signals require per-thread/process pending rules, real-time queuing, masks and ordering, altstack, restorer/trampoline ABI, `siginfo` and `ucontext` bytes, FPU/vector state, signal-frame validation, handler entry state, and `sigreturn` security checks. An application launching once does not qualify these paths.

ELF execution covers supported class/machine/endianness, `ET_EXEC`/`ET_DYN`, interpreter lookup, segment permissions/zero-fill/alignment, stack layout and auxiliary vectors, TLS setup, ASLR, GNU properties and architecture features, credentials/secure exec, scripts and other baseline binary handlers where configured, malformed binaries, and exec failure/point-of-no-return semantics. The dynamic linker remains userspace: do not accidentally turn the kernel into a general ELF shared-library linker. Use the pinned [ELF loader](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/fs/binfmt_elf.c) as behavioral evidence and [process plan](subsystems/process.md) for implementation.

The vDSO is a userspace-facing ELF ABI implemented in Rust here, not imported C object code. Preserve applicable symbol names **and symbol versions**, calling conventions, auxv discovery, data-page consistency, clock fallbacks, compat variants, and historical helper/vsyscall behavior where baseline configuration requires them. Test libc fast paths and direct symbol resolution, as well as forced syscall fallback. A syscall trace alone misses vDSO calls; see [vDSO manual](https://man7.org/linux/man-pages/man7/vdso.7.html). Helper ABI obligations must be pinned from each architecture, not copied from the live manual's historical architecture list.

## Isolation, security, storage, and protocols

Namespaces include every baseline-supported type and interaction: creation/join, ownership, capability scope, ID maps, nested PID identity, mount propagation, network state, time offsets, namespace handles, lifetime, and cross-namespace permission checks. Cgroups include v1 and v2, controller availability, hierarchy/delegation/thread modes, limits, accounting, events, pressure, migration, charging ownership, reclaim/OOM and device control. A container starting with restrictions disabled is not a container-compatibility pass. [Cgroup v2's authoritative reference](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/admin-guide/cgroup-v2.rst) covers more than directory naming. Mechanisms belong to [process](subsystems/process.md), [memory](subsystems/memory.md), and [security](subsystems/security.md).

Security parity covers DAC/ACLs, capability sets and namespaces, credentials and securebits, LSM policies and stacking where applicable, seccomp filter/action/notification semantics, audit, keyrings, integrity/appraisal, module/firmware trust, lockdown, executable memory protections, mitigations, and their userspace controls. Rust memory safety cannot replace authorization or side-channel defenses. Preserve defined rejection behavior and prevent privilege escalation, information leaks, confused-deputy paths, and cross-tenant accounting escapes. Security posture must be equal for performance comparisons.

On-disk compatibility includes every baseline filesystem and storage format, feature flags, checksums, endian rules, metadata semantics, xattrs/ACLs, quotas, sparse files, reflinks, locking/leases, fsync/fdatasync/directory durability, journal/log replay, error handling, mount options, repair interoperability, discard/zoning, RAID/device-mapper/crypto and network filesystem behavior where applicable. Require Linux-created media to be safely read/written by Rust and Rust-created/updated media to be safely read/recovered by Linux, including crash cycles. A matching file's contents after clean unmount is insufficient. Unsupported feature flags must reject safely but remain unimplemented obligations, not parity passes. See [filesystems](subsystems/filesystems.md) and [storage](subsystems/storage.md).

Network compatibility includes socket semantics/options/errors/ancillary data, readiness, routing and policy, firewall/conntrack, tunnels, congestion/retransmission/PMTU, timeouts, offloads, multicast, legacy families, RDMA and network filesystems/protocols in scope. Both standards interoperability and Linux-specific baseline behavior matter; standards compliance alone is not Linux parity. Packet bytes, state transitions, loss/reordering/duplication, peer behavior, namespace visibility, and physical-NIC/offload paths need tests. See [networking](subsystems/networking.md) and [IPC](subsystems/ipc.md).

## Modules, boot, configuration, and deployment

Linux does not promise a stable internal driver API/ABI: [upstream explanation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-api-nonsense.rst). This project consequently does **not** promise binary execution compatibility with existing C `.ko` objects. That explicit implementation restriction must appear on release claims; do not advertise unrestricted drop-in compatibility with arbitrary out-of-tree kernel binaries. Port all baseline module-provided **functionality** into Rust. Cover load/unload dependencies, parameters, aliases, autoload, reference pinning, signatures/policy, sysfs visibility and failure semantics for Rust replacements, or record the absent behavior as an open obligation. Never silently execute, reinterpret, or claim to have loaded a C object. Existing module-management userspace needs a tested Rust-module packaging/metadata workflow; changing module names or requiring administrator migration is a disclosed deployment difference, not an invisible success. See [extensions](subsystems/extensions.md).

The required module-functionality universe is the pinned upstream baseline, not arbitrary proprietary or third-party out-of-tree modules. Such external functionality is not implicitly promised; each addition needs separately enumerated and approved scope. This does not remove any in-baseline module functionality from the Rust replacement obligations. The feature baseline remains fixed at 6.18.57 with explicitly reviewed security deltas; adding later feature baselines requires a separate decision.

Match each applicable architecture's boot image/handoff, entry state, memory map/reservations, firmware tables/device trees, initrd/initramfs, command-line parsing/effects, root discovery, init launch, console, emergency recovery, reboot/poweroff, kexec/crash handling, and secure/measured boot chain. The [x86 boot protocol](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/x86/boot.rst) is only one architecture's contract. QEMU-specific boot shortcuts do not qualify firmware/bootloader handoffs on hardware. UEFI/BIOS/other architecture paths and recovery begin with the M1 lab plan, not after M7.

Kconfig names and build-system implementation are not themselves a stable UAPI, but every baseline capability, dependency, architecture restriction, built-in/module/disabled mode, and administrator-visible effect must map explicitly to the Rust build/deployment configuration. Do not replace all configurations with one small defconfig and call that full Linux. Preserve meaningful boot parameters and feature discovery; if a build/configuration command is intentionally different, document it separately from runtime parity. Kernel-owned build/orchestration programs are Rust, while external compiler/linker/build infrastructure may be used under the toolchain contract. Packaging, initramfs hooks, bootloader integration, firmware installation, headers for unchanged userspace, updates, rollback, and recovery require runnable deployment tests on both emulation and real machines.

## Per-feature matrix and evidence ledger

The upstream-path TSV is structural routing only. **Proposed future qualification ledger**, not a claimed current audit feature: expand each routed source workstream into named externally observable features, then create applicable cells with these fields:

| --- | --- |

| ABI | Architecture, CPU variant, word size, userspace ABI/personality, endianness, page-size choice, compat/time variants |
| Configuration | Full reference/Rust config digests and capability mapping; relevant y/m/n states; dependency constraints; boot parameters; LSM/mitigations; module/firmware policy |

| Gaps | Unimplemented cases; failures; skipped/unavailable hardware/tests; mismatch reproducer; applicability rationale; upstream/security deltas; remediation owner |

The workstream TSV retains exactly five columns and only `not_started`/`in_progress`. The canonical [Rust-path/revision-evidence table](implementation.md#routed-implementation-status) names every `in_progress` owner; all other rows remain `not_started`. Neither status means qualification or completion. Separately, qualification outcomes are **pass, fail, blocked, not_run, or not_applicable**, not workstream status values or a blanket “supported” flag. `not_applicable` needs evidence that the pinned feature cannot exist in that architecture/configuration/hardware cell plus reviewer approval. Missing Rust support, hardware, harness, an upstream skip, disabled optional feature or unknown outcome is **blocked/not_run**, never pass or automatic inapplicability.

An applicable disabled-configuration cell may pass its disabled-behavior tests, but separate enabled and module-mode obligations remain mandatory wherever the baseline permits them. Mutually exclusive features are separate valid configurations, not an impossible all-yes build. Enumerate valid choices, boundary configs, and interaction obligations; pairwise config sampling helps discover bugs but does not prove every valid combination. Unexercised combinations remain unqualified. No aggregate percentage may hide missing architectures/devices or convert structural file coverage into behavioral proof.

## Ordered closure and acceptance

1. **M0:** pin provenance, enumerate interfaces/configuration constraints and applicability, map owners, identify unavailable oracle toolchains/hardware. Curated research is in [research](research.md); completeness requires subsequent per-interface work.
2. **M1:** establish Rust-only toolchain/image evidence, ABI layout fixtures, reproducible reference/QEMU boot, and physical-workstation boot/console/recovery design. Physical boot/console/recovery and paired startup/power/timing evidence are mandatory when a safely packaged candidate is available under [bare metal](bare-metal.md) and [performance](performance.md); until the user reports actual runs, mark them blocked, not passed or postponed out of scope.
3. **M2–M3:** qualify MM/SMP/process/entry and failure boundaries before broad userspace; run raw ABI, compat/time64, signal/restart/ELF/vDSO tests, then unchanged libc and service workloads.
4. **M4–M5:** close persistent/wire interfaces through differential, crash, and real storage/NIC tests; qualify a complete server/container deployment without disabling isolation requirements.
5. **M6–M7:** expand to security/observability/virtualization and every baseline architecture, driver, filesystem, protocol and optional facility. Earlier milestones are previews with a published unqualified matrix, not “full compatibility.”
6. **M8:** apply every evidence gate in [verification](verification.md), [performance](performance.md), [bare metal](bare-metal.md), and [maintenance](maintenance.md). Full qualification is blocked by any open required cell, unexplained discrepancy, untriaged security delta, missing physical evidence, unproved performance comparison, or provenance/license blocker.

Safe simplification is limited to private Rust internals: share checked ABI codecs, capability checks, accounting and wait mechanisms where behavior is identical; use architecture adapters where it is not. Reuse vetted `no_std` primitives only after [dependency review](dependencies.md); do not select a userspace libc ABI crate as the authoritative kernel-wide layout table. Do not unify away legacy ABI quirks, omit rare paths, fabricate output, or relax security to simplify implementation.
