# Firmware, boot interfaces, AML and platform trust

## Scope, implementation boundary and sources

**`ws-drivers-acpi` is `in_progress` for checked immutable table discovery in the initial bootstrap.** Remaining firmware facilities are `not_started`; no complete ACPI/AML, native EFI runtime, physical firmware or performance qualification is claimed. The architecture is a **modular monolithic Rust kernel**, directly porting GPL Linux **6.18.57** source with preserved per-file provenance. Fixed baseline functionality includes firmware-facing behavior, platform quirks and all in-baseline modules; later feature expansion requires a separate decision, while security deltas must be explicit and reviewed. There is no promise to execute arbitrary out-of-tree C modules.

Project-owned kernel/runtime and executable tooling are Rust only. Existing platform firmware, CPU microcode and device firmware may be externally supplied binaries under the approved exception. **Permitted external firmware is not a Rust implementation** and does not permit linking C ACPICA, uACPI, libfdt, a C boot stub, a vendor SDK runtime, libc, a C firmware service shim or C startup into the kernel. Calls across documented UEFI/SMCCC/SBI/PROM/PAL/hypervisor ABIs are a trust boundary, not C code ownership. Firmware may continue executing outside the kernel at a higher privilege level; record that dependence and its consequences honestly.

Primary observed Linux sources: [firmware tree](https://github.com/gregkh/linux/tree/v6.18.57/drivers/firmware), [ACPI tree](https://github.com/gregkh/linux/tree/v6.18.57/drivers/acpi), [OF/devicetree tree](https://github.com/gregkh/linux/tree/v6.18.57/drivers/of), [ACPI namespace mapping](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/firmware-guide/acpi/namespace.rst), [EFI stub behavior](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/admin-guide/efi-stub.rst), [firmware request API](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/driver-api/firmware/request_firmware.rst), [x86 microcode loader](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/x86/microcode.rst), [AArch64 boot](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/arm64/booting.rst), and [RISC-V boot](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/riscv/boot.rst). Exact source paths are tracked in [coverage](../coverage.md). Some implementation belongs under `arch/`, `drivers/base/firmware_loader`, `security/`, TPM, remoteproc and device drivers rather than `drivers/firmware`; directory boundaries cannot be scope boundaries.

Normative sources: [UEFI 2.11](https://uefi.org/specs/UEFI/2.11/), [ACPI 6.6](https://uefi.org/specs/ACPI/6.6), [Devicetree specification](https://devicetree-specification.readthedocs.io/en/stable/devicetree-basics.html), and [DMTF SMBIOS versions](https://www.dmtf.org/dsp/DSP0134) including its published [3.10.0 specification](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.10.0.pdf). These specification versions are research references, not automatic additions to Linux 6.18.57 feature scope. The UEFI Forum HTML reader returned HTTP 403 during research; search-indexed primary pages identify the specification versions, but no full-spec inspection is claimed. Before implementation, archive the exact permitted normative documents and relevant errata and compare to the pinned Linux behavior; source quirks can intentionally differ from an idealized spec.

### Current routed bootstrap and evidence

`ws-drivers-acpi` routes to [checked immutable firmware discovery](../../kernel/src/firmware.rs) and the [narrow boot/table boundary](../../kernel/src/boot.rs). The initial engineering path is native Limine base5 through external Limine 12.9.3 and q35/OVMF UEFI64. The loader exits boot services; the kernel validates required responses and uses a bounded immutable RSDP/XSDT/SDT/MADT traversal, with explicit trusted initialization/stability and reserved-memory lifetime assumptions. It does not create an all-firmware static slice or claim ownership of mutable FACS/NVS data.

[Cell9 QEMU observations and five host production-parser tests](../implementation.md) record actual OVMF discovery and malformed map/table rejection. [Strict owned Clippy and artifact inspection](../implementation.md#final-owned-strict-lint-gate) are integration evidence, not independent firmware/security approval. The translated Limine protocol layouts preserve 0BSD notices with original GPL-2.0-only code; external loader/firmware artifacts, hashes and license/trust limits are separately recorded in [source provenance](../implementation.md#pinned-source-and-specification-map). Local Linux-tag verification has a kernel.org HTTPS/WKD-pinned good signature with `TRUST_UNDEFINED`; it does not authenticate every external firmware binary or close release review.

This limited discovery does not implement AML/ACPICA, runtime services, device enumeration, ACPI power/interrupt routing, microcode loading or the remaining table families. Native Linux/PVH/EFI/PE/systemd-boot and other architecture handoffs remain required. The storage-free framebuffer diagnostic can precede rootfs/initramfs/userspace only through the [user-operated isolated-media/recovery path](../packaging.md); no workstation boot, firmware action, physical recovery or M1 pass is recorded.


## Ordered milestones and dependencies

1. **M0 evidence:** inventory every baseline handoff, firmware service, table/binding, opcode/method, update/loading path, version/quirk and binary dependency. Record provenance/license/hash and trust for external firmware. Reuse the exact Linux source, not a reduced hobby-kernel boot tutorial. Pin toolchain and candidate crate revisions before admission.
2. **M1 boot and real workstation together:** implement the selected architecture handoff with checked boot-information ownership, early diagnostics and memory reservations; the initial cell consumes the external Limine/UEFI exit contract rather than supplying a native EFI stub. Native Rust EFI/Linux image paths, secure image policy, initrd/command-line discovery and remaining boot-service transitions retain their own implementation obligations. User selects a candidate only after the corresponding [isolated diagnostic or replacement-package](../packaging.md) safety and recovery requirements exist. QEMU/OVMF is the first debug environment, not the sole gate. Existing working kernel/default entries remain untouched.
3. **M1–M2 early hardware:** immutable ACPI/DT topology for CPUs, interrupt controllers, console, timers, PCI windows, IOMMU and reserved regions; implement PSCI/SBI/PAL/PROM/PDC/OPAL interfaces for their architecture lane. Apply boot-time microcode at the required stage and reflect changed CPU features before secondary startup/mitigation selection. Bare-metal boot must validate actual firmware maps and interrupt routing.
4. **M2–M3 dynamic firmware mechanisms:** complete Rust AML interpreter and operating-system services, address-space handlers, EC/GPE/events, dynamic device discovery, DT graph/provider links and runtime-service serialization. A static table parser is not ACPI completion. CPU bring-up, PM and device dependencies must have real Rust implementations before dynamic methods can operate safely.
5. **M4–M5 userspace and I/O:** firmware loading/cache and Linux-visible attributes, efivarfs, DMI interfaces, secure-boot/lockdown measurement, platform transports and device firmware. First userspace is Arch/CachyOS userspace, without importing CachyOS kernel patches. Durable physical storage and NIC bring-up consume these services; do not satisfy them with firmware boot handles after boot services ended.
6. **M6–M7 breadth and power:** full suspend/resume/wake, hotplug, thermal/battery/processor policy, platform-specific firmware RPCs, RAS/APEI, firmware update interfaces and legacy firmware variants. Physical testing continues each phase; updates/flashing/power failures require separately approved isolated fixtures, never default workstation tests.
7. **M8 closure:** every baseline firmware path/configuration and actual machine cell has semantic/security/recovery evidence and at-least-reference performance/power. Missing firmware keys, manuals, legal redistributable images, interpreter features or devices remain named blockers. No failing AML method becomes a silent success.

Local `asm!` and `naked_asm!` are permitted only when an intrinsic or ordinary Rust cannot express the necessary operation, with privilege/register/memory/clobber/stack/fault contracts, reviewer signoff and disassembly/hardware checks. No `global_asm!` or standalone-assembly escape. Firmware tables and protocols should use checked byte parsing and explicit widths/endian conversions, not unsafe packed references to arbitrary physical memory.

## UEFI, bootloaders and handoff

### Implementation steps

1. Read firmware system-table signature/revision/size and validate all pointers against the memory map; establish bounded mapping/copy rules and architecture-correct UEFI calling conventions. Own command-line/initrd/ACPI/DT/SMBIOS pointers before reclaiming boot memory. Handle variable-length descriptors and descriptor-version differences, not `sizeof` assumptions.
2. Extend the initial native-Limine x86_64 ELF with the separately implemented Rust PE/COFF UEFI entry and Linux-compatible image needed for the replacement package's Limine/systemd-boot contracts. The current loader handoff is an engineering first step, not a substitute for any advertised baseline handoff. Cover x86 real/protected/long-mode and mixed-width handoffs only through explicit target/entry feasibility proof. Architecture profiles retain non-UEFI and legacy loader paths.
3. Allocate/place/decompress/relocate kernel and initrds with checked arithmetic and memory ownership. Parse command-line encoding and limits consistently; record original boot information losslessly before normalizing it. Handle fragmented memory maps, reserved holes, memory encryption/confidential state, framebuffer pitch/formats and boot entropy without logging secrets.
4. Take a final map key and call `ExitBootServices` with correct retry behavior if the map changed; stop using console/allocator/protocol references belonging to boot services. A Rust type/lifetime boundary should make the state transition one-way. The [uefi-rs boot-stage documentation](https://raw.githubusercontent.com/rust-osdev/uefi-rs/main/book/src/concepts/boot_stages.md) explicitly distinguishes boot services from runtime. Do not continue firmware file/network I/O as a permanent driver substitute.
5. Preserve/map only runtime regions with firmware-required cache/permission attributes and implement supported virtual-address transition/calling/serialization/context rules. Port runtime variables, time, reset, capsule/query interfaces and architecture-specific quirks; allocate/translate buffers safely and respect non-reentrancy and failure status. Runtime firmware code is an external dependency with a failure/containment policy, not memory-safe merely because the caller is Rust.
6. Preserve secure-boot trust state, verified kernel/initrd/module policy and TPM measurement/event-log semantics; UKI/PE signing and package hashes must reflect actual artifacts. Separate image verification, measured boot and remote attestation: one does not imply the others. Preserve privileged-variable and lockdown behavior.
7. Integrate with the device model and eventual efivarfs/sysfs/proc behavior; test permissions, persistence, unavailable services, firmware bugs and failure to update variables. Boot-menu installation and firmware-variable writes are user-operated separate operations, never part of the default smoke runner.

### Reuse and simplification

Candidate [uefi/uefi-raw](https://github.com/rust-osdev/uefi-rs) provides Rust wrappers/types with MIT/Apache license choices; admit only a pinned compatible choice after [dependency/legal review](../dependencies.md). Its existence does not prove Linux EFI stub, mixed-mode runtime, efivarfs, security policy or all architecture parity. External Limine/systemd-boot, OVMF/EDK2, U-Boot or platform ROM firmware may be non-Rust under the external-tool/firmware boundary; project-owned loader/stub code remains Rust. Do not import C/assembly bootloader example source into project runtime.

Bundle one immutable boot-record owner and checked address-range allocator across handoffs; simplify internal representation without discarding source records, quirk flags, firmware revisions or reserved ranges. Optimize boot allocations and table copies only after lifetime/ownership proof; cache stable tables but serialize actual runtime calls. Measure cold-boot time, service latency/tails, memory and idle power against the same Linux/firmware configuration; never omit verification to win boot-time comparisons.

### Proof and blockers

Host fuzz malformed tables/maps/device paths; QEMU test map-key changes, absent services and image rejection; physical workstation test actual UEFI/boot-menu handoff and recovery from M1. Later physical Intel/AMD and other architecture firmware generations must cover differing maps, 32/64 mixed-mode where baseline permits, secure boot, reserved runtime regions, real devices after boot-services exit and suspend/wake. Variable/capsule tests need safe fixtures and explicit authorization; test failure paths without flashing the workstation. Missing signing keys, recovery console, protocol support and alternate firmware are blockers. Completion requires every advertised baseline handoff and runtime/UAPI path, not one successful PE image.

## ACPI static tables and full Rust AML

### Static tables and namespace construction

1. Safely locate/validate RSDP/RSDT/XSDT and table headers/checksums/lengths with mapped-range limits, address-width conversions, duplicate/overlapping tables and firmware quirks. Parse FADT/FACS, MADT, MCFG, HPET, SPCR, BGRT and all source-used tables. Do not infer ordering or completeness from an idealized diagram.
2. Expand topology/memory/device tables: SRAT/SLIT/HMAT/PPTT, NFIT, CEDT, VIOT/IORT/RIMT/DMAR/IVRS as enabled by architecture, processor/performance and RAS tables. Connect them to MM/NUMA/cache, PCI, IOMMU, CXL, NVDIMM, perf and [RAS](drivers.md). Table presence is not permission to access reserved memory or unsupported hardware.
3. Load DSDT and SSDT definition blocks into a shared, versioned namespace with correct names/scopes/aliases and dynamic loading/unloading semantics. Track definition ownership so unload/hotplug cannot leave dangling handles. Keep per-device ACPI companions and Linux sysfs/modalias identity consistent with [the pinned namespace documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/firmware-guide/acpi/namespace.rst).

### AML interpreter work register

A complete **Rust** interpreter is required. A candidate parser's successful `_HID` evaluation is not a complete ACPI subsystem. Direct-port `drivers/acpi/acpica` semantic behavior or prove candidate equivalence; no linked C ACPICA/uACPI and no `extern` shim hiding it. Every opcode, supported table revision, predefined object/method and baseline firmware quirk needs a case register.

### Candidate feasibility, security and completion

The current [rust-osdev/acpi repository](https://github.com/rust-osdev/acpi) integrates static parsing plus an allocator-backed AML interpreter; its default features and API differ from the older standalone [published `aml` crate](https://docs.rs/aml/latest/aml). Treat these as separate revisioned candidates, not two interchangeable complete ACPICA replacements. Screen opcode/method coverage, operation regions, synchronization, events, predefined repair quirks, no_std/fallible/context allocation, unsafe mappings, thread-safety and Linux behavior. Use the permissive **MIT** choice only after file-specific review under the GPL-2.0-only project; Apache-only material needs separate legal disposition. No crate is admitted here. Candidate gaps requiring a direct Rust semantic port are first-class blockers, especially AML scheduling/regions/quirks and platform sleep.

An internal property representation may unify ACPI/DT consumers, but must retain source identity, type/length/endianness and dynamic lifetime. Never replace full ACPI with static DT generated on one machine; never hard-code a workstation's DSDT as universal support. AML can control physical memory, PCI, power, clocks and actuators; memory-safe parsing is necessary but not a sandbox. Every operation-region binding needs resource authorization and platform policy. A compromised firmware/secure monitor may exceed kernel authority; document residual risk instead of claiming Rust repairs it.

Host corpus uses ACPICA/`iasl` or reference Linux as **external test oracle**, not linked kernel runtime. Separate interpreter outputs and I/O traces from irreversible hardware writes. Every baseline ACPICA semantic path and all Linux ACPI integration files need direct mapping and regression tests. Physical multi-vendor laptops/servers and arm64/RISC-V ACPI systems require independent boot, PCI routing, power, EC/GPE, thermal, hotplug and failure evidence. Only the current workstation is presently available, so broader acquisition and safe instrumentation are named blockers. Dynamic ACPI completion and its performance/power parity cannot be inferred from this plan.

## Device tree and OF

1. Parse FDT header/version, total-size/reservation map/structure/strings blocks with checked bounds, alignment and big-endian cells. Respect that firmware-provided DT memory may be reclaimed or modified; establish ownership before exposing references. The [DT specification](https://devicetree-specification.readthedocs.io/en/stable/devicetree-basics.html) defines a hardware description passed from a boot program, not automatic driver discovery for every bus.
2. Implement node/property traversal, aliases/chosen/stdout, compatible ordering, status, `#address-cells`/`#size-cells`, `ranges`/`dma-ranges`, reserved-memory/no-map/reusable and architecture CPU/memory handoff. Convert bus addresses correctly across nested bridges; absent/empty `ranges` meanings cannot be collapsed.
3. Resolve phandles and provider arguments for interrupts/interrupt-map/domains, MSI/IOMMU, clocks, resets, power, regulators, GPIO/pinctrl, graph endpoints and memory/interconnect. Share the device dependency graph, deferred probe and lifetime handles with ACPI/platform, while preserving OF-specific binding behavior.
4. Port live-tree changes, overlays/fixups/symbols and notifier/device creation/removal, including pinned references and failure rollback. Runtime overlays are not merely a parser option. Overlay removal cannot free properties still used by an active driver. Keep binding schema and DTS source compatibility in scope.
5. Preserve Linux-visible `/proc/device-tree`, sysfs, modalias, user overlay interfaces and architecture-specific firmware nodes as baseline enables; associate property provenance and version with driver probes.

Candidate [repnop/fdt](https://github.com/repnop/fdt) advertises a pure-Rust no_std parser but uses **MPL-2.0**, not MIT/Apache. Evaluate exact license notices, secondary-license eligibility and GPL compatibility before any reuse; use direct GPL source translation if admission is not justified. Parsing alone does not supply dynamic overlays, providers, drivers or all binding quirks. **C libfdt is rejected as a runtime implementation**, even through Rust wrappers. External `dtc`/schema validators can act as development/reference tools under the external-tool exception; project-owned executable tooling remains Rust.

Bundle checked cell/byte parsing, indexed phandles and shared property access; safe simplification is one reference/lifetime system and typed decoded values. Do not erase distinction between absent property and zero, source endianness and CPU endianness, or firmware address and DMA address. Optimize immutable-node indexing and zero-copy borrowed views only while backing memory is owned/alive. Security tests fuzz totalsize, recursion, strings, cycles, overlays and integer wrap; semantic tests compare generated DTBs and Linux interpretation. Physical DT platforms must exercise real reserved memory, IRQ/IOMMU translations, overlays and hot-remove across multiple architectures. Current absence of boards is a blocker, not an excuse to delete bindings.

## SMBIOS/DMI and boot metadata

1. Discover 32/64-bit SMBIOS entry points and legacy DMI paths according to architecture/firmware; validate anchors/checksums/entry size/table bounds and version-specific lengths. Scan structures with bounded string termination and end-of-table handling.
2. Decode typed records with revision-compatible short structures, unknown fields/types retained as opaque validated bytes, handle lookup and Linux DMI matching/quirks. Type/model strings influence board workarounds but are not cryptographic identity. Do not turn arbitrary firmware strings into unchecked format strings or filesystem names.
3. Port DMI sysfs/raw-table/device interfaces and permissions, preserving restricted serial/UUID/key-like fields. Ordinary reports should redact serial identifiers. Connect machine quirks to exact model/version/source evidence; fuzz duplicated handles, bad string indices, truncated tables and missing terminators.
4. Cover related EDD, iBFT, firmware memory-map, framebuffer/sysfb and coreboot/VPD/CBMEM handoff data. Boot storage/network secrets from iBFT must remain privileged; framebuffer pitch/length/address validation precedes mapping, and takeover by native graphics must release/hand off ownership cleanly.

A Rust SMBIOS parser may be evaluated through [dependency admission](../dependencies.md), but none is selected; direct port of pinned `dmi_scan`, DMI exposure and quirk logic is the baseline mechanism. Share checked firmware-record iterators and immutable string views; do not simplify by trusting only newest SMBIOS records. Build a validated handle index once and avoid redundant string copies. Host differential parsing with external `dmidecode` and raw table fixtures plus actual workstation discovery starts early; multi-vendor/generation and legacy firmware remain separate physical gates. SMBIOS 3.10 availability does not require implementing post-baseline behavior unrelated to the pinned kernel.

| QEMU `fw_cfg` | Selector/data and DMA transport → directory/files → sysfs/handoff consumers; share checked blob ownership. | Host-provided lengths/names and DMA ranges; cache immutable entries, bound reads. | Emulator malformed/large files and DMA transport tests; physical-host QEMU labelled emulated, not proof of UEFI or real firmware. |
| DMI/EDD/iBFT/memmap/sysfb | Entry discovery → checked records → Linux-visible interfaces → native-driver takeover; share validated immutable views. | Privacy, boot credentials, address ranges and reserved memory; avoid copies only while memory owned. | P actual firmware generations and boot devices, malformed corpus, permission and takeover races. |
| Architecture firmware: SBI, OPAL/RTAS, PROM/Open Firmware, PDC, SRM/PAL, PS3/IBM Z services | Each ABI/version/feature → early entry → topology/CPU/I/O/power/error services → full source-enabled runtime interfaces; share typed register/result and reserved-memory contracts, not one universal calling convention. | Higher-privilege firmware, register clobbers, call context and machine quirks; cache discovery and batch only where protocol permits. | P every architecture/platform family per [architecture plan](architectures.md), including partition mediation; compiler/backend/manual/hardware absence remains blocker. |

A source family may include several unrelated protocols. Its row is a workstream decomposition requirement, not blanket permission to use one generic "firmware RPC" implementation. Source paths such as `drivers/firmware/microchip/mpfs-auto-update.c`, `drivers/firmware/thead,th1520-aon.c` and `drivers/firmware/samsung/` remain in the register even if less common than UEFI. Exact source children, revisions, behavior and client dependencies must be expanded before closure.

## Device firmware loading, microcode and update trust

### Device images and loader semantics

Port the full Linux firmware-request API, not just a filesystem read: synchronous/direct/no-warning/platform/into-buffer requests, asynchronous lifetime/cancellation, fallback/lookup/cache behavior, initrd/built-in/external image provenance, suspend/resume/reboot retention and device-specific upload. [The pinned API documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/driver-api/firmware/request_firmware.rst) explicitly says asynchronous requests cannot be called in atomic contexts and describes firmware retention for resume. Match errors and lookup behavior; missing mandatory firmware must remain visible rather than a fake successful device.

One shared Rust firmware-object owner can serve NIC/Wi-Fi/GPU/audio/DSP/FPGA/remoteproc consumers, with driver-specific validation/signature and upload protocol. Share lookup, immutable bytes, hash/provenance records, release and caching where policy matches; do not share authenticated-memory ownership or device reset state by filename alone. Eliminate repeated file copies where lifetime and DMA rules permit; account cached images and reclaim under pressure without breaking resume. Firmware version changes invalidate applicable tests and performance comparisons.

External image register fields: supplier/source URL; exact image/hash/version/device revision; license and redistribution/use constraints; cryptographic signing/key authority or explicit absence; hardware verification behavior; parser/upload path; expected privilege/DMA reach; update/rollback policy; legal availability; supported device/firmware matrix; known vulnerabilities and isolation limits. Signed firmware can still be buggy or maliciously privileged; hashes identify images, not their safety. Do not redistribute images whose license forbids it or claim Rust covers their instruction stream.

### CPU microcode

Implement a Rust parser/selector for the pinned early-initrd archive and vendor container formats, with signature/revision/CPU/platform-ID/bounds validation. Apply correct early BSP/AP ordering, cache the selected patch for secondary/resume/hotplug paths, verify installed revision and refresh feature/erratum/mitigation discovery at the appropriate point. Intel and AMD formats and update mechanisms are separate. The [Linux microcode documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/x86/microcode.rst) documents early BSP load, AP application and cached resume patches; arbitrary late updates are not an equivalent substitute.

Late-loading behavior, CPU rendezvous/safety and source-enabled restrictions need direct evidence; never assume all patches are safe to apply while other CPUs execute. Microcode is permitted **external binary firmware**, not Rust kernel code. Do not disassemble/reimplement licensed patches as an invented substitute. Privileged update writes may need minimal inline assembly/intrinsics under the strict operation contract. Optimize parsing and immutable patch reuse, never delay required security fixes for startup speed. Physical Intel/AMD CPU families, SMP/hotplug/suspend and installed-revision/mitigation checks are independent gates; current workstation provides at most its actual CPU cell. No firmware or microcode updates are performed by this planning task or default smoke suite.

### Updates, rollback and recovery

Port existing baseline update interfaces (UEFI capsule, firmware-upload/fwctl and platform-specific mechanisms) in Rust with exact authorization, status/error, staging, power and lifetime behavior. External `fwupd` or vendor tools may be workloads/oracles, not hidden kernel implementations. Define authorized key rotation and rollback policy per device; do not invent guaranteed rollback where hardware lacks it. Preserve working boot entry, known-good firmware recovery instructions and independent control; flash only explicitly approved sacrificial fixtures. Image integrity fuzzing and simulated rejection can run without ever flashing hardware.

## Physical execution, performance and exhaustive definition of done

The only currently available physical system is the user's workstation. The user will personally install/select/boot future candidate artifacts using [separate package/recovery design](../packaging.md). Do not install, reboot, mount, raw-write disks, alter firmware variables/settings, flash, overheat or power-cut that workstation as an assistant action. QEMU/OVMF, reference Linux and external test tools remain useful separate environments. Additional vendors, legacy firmware, DT boards, secure-service platforms, serial/remote power infrastructure, sacrificial firmware devices and measurement instruments are **unavailable qualification resources**, not assumed present.

The delivered [bounded Rust suite](../bare-metal-suite.md) is runnable now on an existing compatible Linux environment:

```text
cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>
```

Choose a single environment value. It records a user assertion, not proof of physical hardware. Proc/sysfs visibility can provide read-only context, but this suite does not evaluate AML, exercise firmware runtime calls, load microcode, modify boot variables, suspend/reboot, flash, inject hardware faults or prove firmware/performance parity. Running on the reference OS validates the runner/current OS only. The bootstrap cannot run this Linux userspace suite; broader firmware tests below remain unimplemented qualification requirements, separate from the bounded discovery evidence above.

For **every firmware subfamily/mechanism above**, apply [global definition of done](../definition-of-done.md) plus:

1. **Exact scope closure:** enumerate all pinned source/configuration paths, table/binding/opcode/service versions, architecture handoffs and machine quirks, including legacy/error/debug/update paths. Map each to Rust implementation, upstream provenance, ABI fixtures and test evidence. No opcode/device/firmware function silently returns success, no C interpreter/libfdt runtime and no out-of-scope proprietary module promise.
2. **Semantic closure:** parser validity/bounds/checksums; valid/invalid service responses; exact Linux errors, names/attributes/permissions and compat rules; dynamic loading/unloading, notifications and resource ownership; every supported boot path, operation region and control-method semantic; device firmware lookup/cache/unavailable cases. Differential traces against pinned Linux/ACPICA/external specifications are reproducible, not merely hand-selected happy paths.
3. **Concurrency/lifecycle closure:** all allocation failures and context constraints, interrupts/reentrancy, AML lock levels, hotplug, table/overlay removal, runtime serialization, device reset, CPU on/off, suspend/resume/wake, reboot and firmware crash/timeout. Memory and hardware resources remain safe after every failed transition; timers/watchdogs diagnose hangs without inventing successful operation.
4. **Security/purity closure:** independent review of unsafe memory/inline assembly and firmware privilege transitions; authorized operation regions/DMA; verified or explicitly unverified image trust; boot measurement and lockdown/efivar/update permissions; privacy/secret handling and residual SMM/secure-world/device-firmware trust. No weakening baseline mitigations/security to make firmware or performance tests pass; reviewed security deltas tracked separately.
5. **Physical closure beginning M1:** user-operated genuine boot with logs/recovery, real firmware maps/IRQ routing, EC/thermal/power/wake/hotplug and device firmware on each claimed platform/firmware version. External timing/power/rail/interrupt instrumentation where needed; safe sacrificial update/recovery fixtures. An emulator, firmware table corpus, guest or one vendor's laptop cannot qualify another physical cell. Missing hardware/keys/manuals/legal images are named blockers.
6. **At-least-Linux performance closure:** same firmware/microcode/device revisions, security configuration, power profile, hardware and test parameters; compare cold boot/startup, AML/service/event and resume latency/tails, CPU, memory and power as well as dependent I/O workloads. Repeated runs, uncertainty and noise controls per [performance](../performance.md); no geometric mean hides regressions and no absent/inconclusive result passes. Optimize table indexing, fallible frame pools, RPC batching and copies only after semantics/security proof.
7. **Operational closure:** published exact supported matrix, Rust-only link/dependency evidence, reproducible artifacts, separate selectable boot package and safe user recovery instructions, approved external firmware licenses/trust records and regression fixtures retained. Runtime firmware updates and security deltas invalidate affected evidence and require requalification.
