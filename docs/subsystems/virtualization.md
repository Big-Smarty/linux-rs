# Virtualization, hypervisor interfaces and device assignment

## Status, supported scope and dependency contract

**All virtualization implementation proposed here remains `not_started`.** This is a Linux **6.18.57** Rust-only porting plan, not a hypervisor. QEMU is the first debug environment, not a replacement for physical hardware; native boot, guest execution and host execution are distinct qualification axes. Early M1 native/guest platform initialization and physical workstation preparation proceed together, with physical execution still gated. Host virtualization depends on M2 MM/SMP, M3 processes/fds/signals, M4 memory-backed storage and M5 networking/security; common KVM and vendor backends develop in M6 and all baseline facilities/architectures close in M7 before M8 qualification.

Accepted design is a **modular monolithic Rust kernel** with fixed 6.18.57 feature scope and reviewed security deltas. Only function-local `asm!`/`naked_asm!` are allowed where unavoidable with explicit proofs and machine-code review; no `global_asm!`, standalone assembly or C runtime escape. All in-baseline virtualization module functionality remains required as Rust replacements; third-party/out-of-tree additions need separate scope approval.

Links: [architectures](architectures.md), [memory and MMU invalidation](memory.md), [process and containers](process.md), [drivers/DMA](drivers.md), [networking](networking.md), [storage](storage.md), [firmware](firmware.md), [security](security.md), [BPF/modules](extensions.md), [observability](observability.md), [dependencies](../dependencies.md), [performance](../performance.md), [physical lab](../bare-metal.md), [runnable smoke](../bare-metal-suite.md), [definition of done](../definition-of-done.md), and [packaging](../packaging.md).

**Release definition of done for every family:** exact pinned architecture/configuration/capability/ioctl/guest-interface matrix, complete implementation and negative paths, existing userspace/guest interoperability, migration/state roundtrip, isolation and adversarial tests, vendor/architecture-specific physical evidence, and at-least-reference performance for every required workload. `KVM_CHECK_EXTENSION` or other feature negotiation advertises only implemented qualified functionality; zero/unavailable during staged development is honest staging, not permission to drop the feature from final scope. A generic VM boot does not qualify nested virtualization, confidential guests, passthrough, live migration or another architecture. No virtualization-facility result is claimed; the [bootstrap's](../implementation.md) use of QEMU does not implement a hypervisor or Linux virtualization interfaces.

The pinned backend directories and their Kconfig files identify **x86, arm64, PowerPC, s390, MIPS, RISC-V and LoongArch** KVM implementations; a Rust target triple or documentation index alone does not establish support. In particular MIPS VZ and older PowerPC backends must not disappear because they are harder to test.

## 1. Common KVM userspace ABI and VM/vCPU lifetime

**Primary contracts:** [KVM API](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/kvm/api.rst), [locking](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/kvm/locking.rst), [vCPU request ordering](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/kvm/vcpu-requests.rst), and [KVM review/test requirements](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/kvm/review-checklist.rst). API version 12 does not remove capability-specific negotiation or architecture differences. VM resources persist until the final relevant fd reference, not simply creator process exit.

### Ordered implementation

1. Inventory every system/VM/vCPU/device ioctl, structure size/alignment/compat layout, capability number and return/error rule from the pinned UAPI and implementations. Tag which host/guest architecture, configuration and required hardware exposes it. Record vCPU fd thread/migration restrictions and memory mappings.
2. Implement `/dev/kvm`, VM/vCPU/device fds and owned state; create/destroy, `dup`/fork/close lifetime, mmap shared run state, `KVM_RUN` exits, signal interruptions/immediate exit, ioctls and capability enable/query. Preserve process/address-space restrictions and exact reserved-field/unknown-flag handling.
3. Port memory slots, guest physical mapping, MMU notifier invalidation, dirty bitmap/ring logging, readonly/huge mappings, guest memory fds/private mappings where supported, TLB/shadow/stage-2 synchronization and fault handling. Coordinate userspace backing changes, reclaim, COW, hotplug, huge pages and device DMA rather than treating a host address as a permanent Rust slice.
4. Implement VM/vCPU requests, kick/wait/barrier ordering and entry/exit mode transitions; interrupt routing/irqfd/ioeventfd/eventfd, timers, in-kernel device creation, coalesced I/O and async faults as applicable. A successful request must be observed before unsafe guest reentry; “atomic bit set” without the paired ordering is insufficient.
5. Add statistics, guest debugging/perf state, save/restore and migration data for **every** exposed state feature, with backend-specific support below. Run established QEMU/libvirt and Rust VMM clients without replacing Linux ioctls with a project-only API.

### Crates, common foundations and limits

The KVM core/backend is project-owned. [rust-vmm KVM wrappers](https://github.com/rust-vmm/kvm-ioctls) are userspace bindings/clients, not a hypervisor implementation; their repository currently redirects to the archived KVM workspace and points to rust-vmm/rust-vmm. Evaluate exact version/location/licenses when selecting external Rust validation clients. UAPI bindings can inform layout tests but do not replace per-architecture ABI extraction. Reject linking Linux KVM C objects or a host `kvm-ioctls` crate into kernel control flow.

Share VM fd ownership, MMU invalidation epochs, RCU/SRCU-like readers, scheduler accounting, eventfd, credentials, memcg, signal delivery and interrupt-controller infrastructure. Keep a written lock/context ordering model matching actual ownership, not an `Arc<Mutex<Everything>>`. Fallible allocation and no sleeping in guest-entry/IRQ-incompatible regions are mandatory.

Typed states and immutable slot generations simplify internals; they cannot erase asynchronous invalidation, rare ioctls, compat layouts, device APIs or fd semantics. Common architecture-neutral code is preferred where true semantics agree; do not force x86 CPUID/register conventions onto other architectures. Reject permissive guest-state fallback or fabricated zero state.

### Security, optimization and done tests

A guest is hostile. Validate guest-controlled indices, register values, emulated instruction lengths, interrupt routing and exit payloads; never expose host pointers/uninitialized padding. Stop in-flight guest execution and DMA before freeing memory. Keep tenant PMU/FPU/SIMD/debug/speculation state isolated. CPU migration/hotplug and invalidation require proof beyond `Send`/`Sync`.

After equivalence, optimize exits, fast faults, read-mostly memory slots, TLB shootdowns, dirty logging and per-vCPU allocation; avoid avoidable copies/global locks without weakening invalidation or migration state. Port the exact host/guest mitigation policy, not benchmark with speculation barriers disabled.

Done requires pinned `tools/testing/selftests/kvm`, kvm-unit-tests, QEMU functional guest boots and real userspace lifecycle/migration workloads; randomized ioctl/state sequences, fuzzed emulation, invalidation races/OOM, concurrent run/close/unmap/dirty logging and repeated create/destroy must fail safely. Physical hosts measure VM create/boot time, exit/entry cycles and p99/p999 latency, fault/dirty-log throughput, guest server/network/storage performance, vCPU scalability, memory/CPU and power. Nested QEMU-KVM testing is useful but not physical backend evidence.

## 2. Architecture and vendor KVM backends

Every backend below follows the common ioctl/security/state acceptance contract but requires its own mechanism tests and physical qualification. **Crate policy for each:** project-owned backend over common KVM/MM/IRQ foundations; register/bitfield crates may be considered after exact source/license/no_std review, none is a prequalified virtualization implementation. Required privileged operations use Rust/intrinsics or minimal documented inline assembly with entry/exit register, memory, clobber and mitigation contracts. No imported `.S`, C transition stub or legacy kernel module.

### 2.1 x86: Intel VMX and AMD SVM

**Authority:** [pinned backend Makefile](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/x86/kvm/Makefile) lists distinct VMX/SVM, nested, PMU, posted-interrupt/AVIC, Hyper-V, Xen, SMM, SEV and TDX paths.

**Steps:** (1) feature/erratum/MSR/CPUID and host state model; (2) separate VMCS/VMX and VMCB/SVM entry/exit, intercepts, register/FPU/debug/interrupt windows; (3) instruction emulator and mode/segment/paging, EPT/NPT plus shadow MMU, APIC/PIC/PIT/IOAPIC and timers; (4) PMU, MSRs, SMM, nested VMX/SVM state/validation, APIC virtualization/posted interrupts/AVIC, passthrough and enlightened interfaces; (5) every capability's save/restore/migration and confidential features in section 5.

**Shared/simplification:** share x86 emulator and common MMU model only with correct vendor distinctions, 32-bit/compat guest modes and nested controls. Typed VMCS/VMCB transactions can simplify field validation; do not remove shadow paging, SMM, nested virtualization or exposed legacy devices to avoid complexity. CPU unavailable feature reporting must remain honest.

**Security/optimization/tests:** prevent host MSR/state leakage, validate nested control pages and instruction faults, execute mandatory speculation/L1/SMT mitigations. Optimize proven TDP fault handling and hardware interrupt assists, not guest-state checks. Run VMX/SVM-specific unit/selftests, nested L1/L2, real Linux and other baseline-supported guest workloads, migration across compatible CPU generations and device/PMU interactions. Physical **both Intel and AMD** hosts are mandatory; record VM-exit cycles, nested overhead, interrupt tails, memory/fault/dirty-log rates and full guest workload CPU/memory/power. Only one currently available workstation cannot qualify both vendors unless separate actual evidence is obtained.

### 2.2 arm64: EL2, VHE/nVHE and protected paths

**Authority:** [pinned arm64 Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/arm64/kvm/Kconfig), [Arm KVM documentation](https://github.com/gregkh/linux/tree/v6.18.57/Documentation/virt/kvm/arm). Exact supported protected/nested modes come from implementation/configuration, not future architecture announcements.

**Steps:** (1) host EL2 availability, exception vectors and VHE/nVHE world-switch contracts; (2) stage-2 MMU, register/system-register traps, virtual timer, VGIC and PSCI; (3) CPU feature negotiation/ID registers, FP/SIMD/SVE/SME and debug/PMU state as pinned, reset/interrupt/one-reg APIs; (4) supported protected nVHE ownership transitions and supported nested features, device assignment and migration state.

**Shared/crates/limits:** use common slot/invalidation plus Arm exception/GIC/SMMU foundations; no ready-made EL2 crate is selected. Distinct typed host/hyp/private page ownership can simplify checks, but a shared Rust allocator across security domains without transfer validation is not safe. No omission of nVHE because VHE is easier or advertisement of nonexistent protected confidentiality.

**Invariants/improvement/tests:** no EL1/EL2 mapping or vector state leak, correct cache/TLB barrier domains and DMA ownership. Optimize stage-2 block mappings/interrupt injection after split/invalidation tests. Test VHE/nVHE/protected configuration matrices, vCPU migration/reset, vector lengths, GIC/timer races and compatible save/restore. Real Arm systems with the required EL2/GIC/SMMU capabilities are blockers until acquired; measure entry/exit/fault/IRQ tails, guest server throughput, memory, CPU and energy, not just emulated boot.

### 2.3 PowerPC: Book3S and BookE

**Authority:** [pinned PowerPC Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/powerpc/kvm/Kconfig) retains Book3S32, Book3S64 PR/HV and E500v2/E500MC/E5500/E6500 variants, plus XICS/XIVE/MPIC support subject to dependencies.

**Steps:** (1) inventory each selectable PR/HV/BookE mode and CPU/MMU restrictions; (2) port problem-state instruction emulation versus real hypervisor world switches and hash/radix/BookE MMU mechanisms supported per backend; (3) register/VSX/FPU/PMU, timebase and hypercalls, XICS/XIVE/MPIC and TCE/DMA semantics; (4) nested/secure facilities present in baseline and state/migration/endianness/32-bit guest handling.

**Shared/crates/limits:** project backend, common KVM lifecycle and PPC exception/TCE providers; no crate approval beyond reviewed register helpers. Separate state machines can share instruction records; do not conflate PR with HV or erase E500/32-bit limitations, hash modes or endian ABIs. Preserve the actual supported combinations rather than promising every mode on every POWER CPU.

**Invariants/improvement/tests:** host problem/hypervisor state, guest TLB/TCE and interrupt mappings remain isolated; nested PMU workaround/errata cannot be optimized away. Optimize interrupt/MMU paths per backend and compare real guest correctness under both endian/word-size cases where supported. Physical POWER PR/HV plus relevant BookE hardware and platform access are distinct blockers. Report each backend's exits, TLB/interrupt latency, guest throughput/tails, migration time, CPU/memory and power; one modern POWER server is not evidence for every BookE mode.

### 2.4 s390: SIE and protected virtualization

**Authority:** [pinned s390 Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/s390/kvm/Kconfig) selects SIE-based virtualization and optional userspace-controlled VMs; [s390 KVM docs](https://github.com/gregkh/linux/tree/v6.18.57/Documentation/virt/kvm/s390).

**Steps:** (1) SIE control block, interception and host/guest register/storage-key/protection model; (2) address translation, async faults, timers, floating/local interrupts and channel/I/O integration; (3) facility/one-reg/device APIs, userspace-control mode with exact capabilities and save/restore; (4) Ultravisor/protected guest lifecycle, shared/private pages, cleanup and migration capabilities as actually supported.

**Shared/crates/limits:** project SIE adapter over common VM/fd/MM and s390 channel/firmware abstractions; no existing Rust crate substitutes for architecture semantics. Typed control-block layouts can reduce unsafe spread, but do not remove storage keys, channel facilities, protected guests or userspace-control mode. Never infer z-machine state from an x86 generic KVM structure.

**Invariants/improvement/tests:** guest control blocks/facility state cannot alter host memory; secret pages and Ultravisor handles have explicit cleanup/zeroization contracts. Optimize validated interception and page-fault paths. Real authorized s390 hardware/LPAR and protected facilities are required; QEMU TCG coverage is partial. Test interrupt/channel I/O, state restore, storage protection, protected lifecycle and failure teardown, measuring interception tails, guest workload throughput, paging costs, resident memory and energy where hardware permits; unavailable power instrumentation remains explicit.

### 2.5 MIPS VZ

**Authority:** [pinned MIPS Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/mips/kvm/Kconfig) requires CPU VZ and floating-point support. This is existing pinned scope, not obsolete functionality to omit.

**Steps:** (1) VZ root/guest mode and CP0/register/TLB state; (2) trapped instruction/MMIO emulation, guest timer/count and interrupt injection; (3) FP/SIMD features as supported, endianness/32/64-bit ABI and one-reg/reset APIs; (4) MMU invalidation, migration state and device integration. Follow exact supported CPU/machine combinations, not a claim all MIPS machines can host KVM.

**Shared/crates/limits:** project backend on common KVM/IRQ/memory and MIPS exception foundations; no selected crate. Typed guest CP0 access and explicit ASID ownership can simplify internals without dropping guest modes or count/timer semantics. Do not substitute user-mode emulation for KVM VZ compatibility.

**Invariants/optimization/tests:** preserve root/guest TLB separation and state across CPU migration; validate fault/CP0 transitions. Optimize exit decode/interrupt and TLB work only after endian/alias tests. VZ-capable physical hardware is an explicit unavailable-lab prerequisite; run pinned applicable selftests/unit guests, timer/FP/TLB stress and real Linux guests, then measure exit/IRQ latency, guest throughput, memory/CPU and energy per qualified system.

### 2.6 RISC-V

**Authority:** [pinned RISC-V Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/riscv/kvm/Kconfig), with SBI/MMU dependencies; runtime H-extension and interrupt capabilities require exact implementation checks.

**Steps:** (1) HS/VS state and trap/entry contract, SBI emulation/forwarding; (2) stage-2 translation, fences, timers and virtual interrupts; (3) ISA extension/one-reg negotiation, vector/FP/PMU state and AIA device support as configured; (4) guest MMIO, reset, migration/state and passthrough. Inventory actual baseline extensions and error rules rather than advertising all current ISA documents.

**Shared/crates/limits:** project backend using common KVM and RISC-V fence/IRQ/SBI abstractions; register crates require review, not assumed hypervisor correctness. Generated CSR fields simplify representation; they cannot erase extension state or change supported guest ABI. No H-less emulator advertised as hardware KVM.

**Invariants/optimization/tests:** stage-2 guest memory ownership and remote fence completion must hold through migration/hotplug; validate malicious SBI/CSR requests. Optimize safe fence batching and interrupt assists. Test timers, vectors, AIA where supported, SBI errors, memory invalidation and restore on actual H-capable RISC-V systems, recording exit/fence/IRQ tails, guest workload rate, memory/CPU/power. QEMU is an important test target but not physical H-extension evidence.

### 2.7 LoongArch

**Authority:** [pinned LoongArch Kconfig](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/loongarch/kvm/Kconfig) selects LVZ-dependent virtualization, dirty ring and IRQ mechanisms.

**Steps:** (1) host virtualization-extension discovery and CSR/register entry/exit state; (2) guest TLB/stage-2 mappings, interrupt/timer/IPI and emulated MMIO; (3) FP/vector, feature negotiation, one-reg/IRQ chip/routing and dirty-ring behavior; (4) save/restore, migration and supported device/PMU integration with exact pinned constraints.

**Shared/crates/limits:** project backend on common KVM/dirty logging and LoongArch exception/TLB foundations; no suitable hypervisor crate assumed. Typed CSRs and common slot generation logic simplify unsafe boundaries; do not remove dirty ring, guest vector state or interrupt routing to obtain basic boot.

**Invariants/optimization/tests:** prevent stale host/guest CSR/TLB/vector state and validate all guest-controlled exit data. Optimize mapping/dirty logging and interrupt paths only after race/state equivalence tests. Physical LVZ-capable LoongArch hardware is required; test guest reboot/multi-vCPU/IRQ/IPI/TLB/vector/dirty migration with Linux guests and applicable selftests. Measure exits, page faults, interrupts, dirty logging, full guest server tails, CPU/memory and energy; unavailable hardware is not qualified by target compilation.

## 3. Guest-facing hypervisor interfaces and paravirtual operation

**Authorities:** [paravirt_ops](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/paravirt_ops.rst), [Hyper-V facilities](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/hyperv/index.rst), [virt tree](https://github.com/gregkh/linux/tree/v6.18.57/virt) and architecture guest implementations. Upstream describes assembly pv_ops; the port must instead implement the required contracts in Rust/minimal inline assembly and measure the resulting code.

1. Inventory host-detection and per-architecture guest interfaces across KVM, Xen PV/PVH/HVM, Hyper-V/VMBus/enlightened clocks/vPCI/suspend, VMware/backdoor/hypercalls, ACRN, Jailhouse, bhyve/other pinned platforms, PowerVM/pSeries, s390/zVM and architecture SBI/PSCI/firmware. A detection branch or vendor string is not full support. Include pinned Nitro Enclaves, SEV/SNP/TDX/other confidential guest interfaces under section 5, and UML host ABI under [architectures](architectures.md).
2. Implement native-versus-paravirtual CPU/MMU/interrupt/time operations, shared pages/hypercalls, pvclock/steal time, PV spinlocks, async faults, memory balloon/hotplug, event channels/grants and suspend/resume/migration appropriate to each hypervisor. Do not assume a Xen grant is ordinary DMA memory or a host-provided clock is trustworthy monotonic wall time.
3. Integrate hypervisor buses/storage/network/input/console and virtio transports with [drivers](drivers.md). Support virtio legacy/modern/pci/mmio/CCW and other baseline transports and split/packed queues where upstream supports them. These are distinct guest-device interfaces, not only QEMU defaults.
4. Preserve one native-capable binary where configured and dispatch/patch optimized paravirtual paths safely; verify native boot after every guest-specific change and vice versa. Respect feature negotiation and host/device capability mismatch errors.

**Crates/shared:** project guest architecture/bus adapters. `virtio-drivers`-style crates may be evaluated for narrow device/transport components but no crate is assumed to cover Linux's transport, legacy, hotplug, suspend and failure semantics; no Linux C paravirt shim. Share register/exception access, clocks, event channels, DMA ownership, executable patch service and firmware records, not a giant hypervisor string switch in every hot path.

**Simplification/security:** typed hypercall parameters and queue ownership simplify unsafe code; preserve feature bits, queue barriers, migration and descriptor-chain bounds. Host-originated configuration, clocks and buffers can be malicious or inconsistent; snapshot/validate shared metadata and avoid retaining Rust references across untrusted mutation. Confidential guests have stronger host-distrust requirements than ordinary guests. Do not delete legacy interfaces because modern virtio boots more easily.

**Optimization/test/done:** minimize hypercalls, safely batch TLB/notification work, suppress negotiated redundant kicks and use validated paravirtual clock reads. For **each named hypervisor family**, boot the actual guest environment, exercise devices, SMP, memory pressure, live migration/suspend/time adjustments and host-disconnect/fault paths; compare ABI traces and normal native boot. Physical hosted tests require actual hypervisor/CPU combinations and authorized platform access; only the current workstation is available now. Record clock drift/monotonicity, hypercall/interrupt tails, guest boot/startup, server/storage/network throughput, balloon/migration pause, CPU/memory/power. Nested emulation is not a substitute for proprietary/platform facilities that are absent.

## 4. vhost/vDPA, VFIO and IOMMU assignment

### 4.1 vhost, virtqueues and accelerated backends

**Authorities:** [pinned vhost implementation](https://github.com/gregkh/linux/tree/v6.18.57/drivers/vhost), [virtio implementation](https://github.com/gregkh/linux/tree/v6.18.57/drivers/virtio), and [rust-vmm vhost](https://github.com/rust-vmm/vhost) for candidate userspace protocol tooling. A userspace vhost-user server is not the kernel vhost ioctl/device implementation.

**Steps:** (1) exact vhost device ioctl/feature/memory/log/eventfd/ring ABI and owner/reset lifecycle; (2) split/packed queues and descriptor/IOTLB translation, barriers, notification suppression and dirty logging; (3) net/SCSI/vsock/vDPA and all pinned backend devices with networking/storage owners; (4) worker affinity, cgroup accounting, migration, reset and device unplug/failure. Inventory per-backend supported features rather than declaring all virtio features common.

**Crate/shared decision:** project kernel vhost/vDPA; evaluate rust-vmm `vhost`, `virtio-queue` and guest-memory crates as userspace differential clients or narrowly reusable reviewed algorithms, not evidence of kernel compatibility. Share bounded virtqueue parsing, eventfd, DMA/IOMMU and buffer lifetime; callbacks belong to kernel scheduling contexts, not a host async runtime.

**Simplification/invariants:** one checked descriptor walker may serve transports if endian/indirect/event-index/packed semantics are represented; never trust guest next pointers, lengths, wrap counters or writable flags. Teardown must stop worker/device access before releasing mappings. No bypassing IOTLB checks for performance or disabling migration logging to win throughput.

**Optimize/test/done:** scatter-gather ownership, batching, negotiated notification suppression and zero-copy only with pinning/accounting/cancellation correctness. Test QEMU/vhost userspace interoperability, invalid/cyclic/indirect descriptors, reset/unplug while active, IOTLB misses, dirty migration and OOM. Real NIC/vDPA/offload hardware and real storage/vsock workloads qualify separately; measure packet/IOPS/bytes/s, p99/p999 latency, wakeups/copies, dirty-log cost, CPU/memory/power per backend. Zero-copy that fails cancellation/security or increases unreported memory pins fails.

### 4.2 VFIO/IOMMUFD, mediated devices and isolation

**Authorities:** [VFIO](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/driver-api/vfio.rst) identifies groups as isolation units and explains topology/ACS limitations; [IOMMUFD](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/userspace-api/iommufd.rst) defines IOAS/HWPT/device/fault/vIOMMU objects and nesting. IOMMU translation alone does not prove an assigned device cannot reach another device through a bypass path.

1. Coordinate with [drivers](drivers.md) to port IOMMU domains, groups, DMA pin/accounting, invalidation, interrupt remapping and platform backends (Intel/AMD/Arm SMMU/POWER and all pinned others), including IOVA width, reserved ranges, noncoherent devices and peer DMA.
2. Implement legacy VFIO container/group/device APIs **and** device cdev/IOMMUFD forms: regions/mmap/IRQ/config access, IOAS mappings, HWPT paging/nesting, fault/PRI response queues, virtual device/IOMMU/event objects supported by pinned baseline and ownership changes. Preserve compat structures/error negotiation.
3. Implement reset/FLR/bus dependencies, PCI quirks/MSI-X, dirty tracking and migration state machines, mediated devices and platform/device-specific VFIO backends as present. Feature availability depends on actual hardware/driver support; never advertise migration for a device without a real state protocol.
4. Synchronize bind/unbind, DMA stop/drain, map/unmap, process exit, mm invalidation and hot-unplug before unpin/reuse. Validate PASID/ATS/PRI/SVA/nested translation where supported against process/address-space lifecycle and confidential page sharing.

**Crates/shared:** project VFIO/IOMMUFD and IOMMU drivers. Rust userspace vfio/ioctl wrappers are test clients only; no crate is assumed to implement hardware isolation. Share DMA ownership, page pins, interval maps, mm notifiers, eventfd, security checks and device reset transaction authorities. Preserve clear division between an IOVA mapping and host virtual/physical references.

**Simplification/security limits:** typed ownership tokens and one IOAS map representation may simplify bookkeeping, not override physical group boundaries or assume ACS. Preserve baseline supported no-IOMMU modes only as explicitly unsafe opt-in with matching permission/taint behavior and ledger/security documentation; never use them as evidence of secure passthrough. Do not invent a forced-ACS override to make a test pass. DMA/speculation/firmware flaws remain possible with Rust.

**Optimization/test/done:** batch map/unmap/invalidation within specified completion semantics, share page tables only where isolation permits, use large I/O mappings without violating pin granularity. Test reference QEMU/libvirt VFIO, all API generations, malicious ioctl/fault responses, overlapping/unmapped IOVAs, concurrent DMA/unmap/reset/exit, interrupt storms, migration/dirty tracking and denied group ownership. Physical VT-d and AMD-Vi plus Arm/POWER/other supported IOMMUs, actual group topologies, NIC/NVMe/accelerator/mdev devices and sacrificial lab isolation are required. Measure IOMMU map/unmap tails, translation faults, invalidation completion, guest IOPS/packet rate/latency, migration pause, pinned/page-table memory, CPU/power. The workstation's hardware inventory must be measured; absent devices/platforms remain blockers.

## 5. Confidential guests, host backends and attestation boundaries

**Primary authority:** [SNP/TDX threat model](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/security/snp-tdx-threat-model.rst) explicitly adds a potentially malicious host and distinct trusted security manager/platform; pinned [x86 KVM paths](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/arch/x86/kvm/Makefile) include SEV and TDX. [Security](security.md) owns crypto/key policy and residual side-channel analysis; this plan owns VM transitions and guest/host protocol mechanics.

Optimize acceptance and shared I/O only after leakage/ordering tests. | Arm protected KVM and other pinned Arm confidential interfaces | Port only pinned supported EL2 protected ownership/guest interfaces and firmware mechanisms; stage host/guest/DMA transitions and feature discovery before any attestation claim. | Project Arm world-switch/ownership code over section 2.2; do not equate pKVM with every future Arm CCA/Realm capability or invent unsupported baseline scope. A new shared transfer abstraction must represent actual host/hyp trust. | Private mappings must never remain accessible through host or device aliases; host-controlled device input is validated. Real protected-mode platforms and transfer/hotplug/reset negative tests; measure conversion, protected entry/exit and guest workloads. New facilities outside 6.18.57 are tracked future changes, not asserted baseline support. |
| s390 protected virtualization and PowerPC secure guests | Enumerate pinned Ultravisor/secure monitor interfaces and exact modes, then protected VM/CPU/page creation, memory export/import/sharing, error recovery and available report/measurement APIs. | Project architecture adapters; share state-transition review and secret-handling policy, never x86-specific wire assumptions. Retain normal non-protected guest paths. | Secure-monitor handles/page ownership survive failure teardown; never “retry” an ownership operation with unknown completion without the protocol's rule. Physical platform access and protected lifecycle/failed export/import/interrupt/device tests; measure startup, page transitions, guest throughput/tails and memory. |
| Hyper-V confidential guest/enclave interfaces and other pinned isolation devices | Inventory Hyper-V CoCo and Nitro Enclave or other actual baseline device/host interfaces, implement request/response, shared memory and lifecycle, then supported attestation communication and host-service error cases. | Project transport/device adapters plus security-reviewed bounded codecs; external guest userspace services are clients. Do not treat a hypervisor vendor string as attestation or add nonexistent hardware support. | Untrusted host responses cannot drive unchecked memory access; secret transport and report binding are verified by the proper relying party. Real platform-backed environments and bad-host response/lifecycle tests; compare shared I/O, launch, latency and memory independently. |

Each row is its own `not_started` workstream. Implementation inventory resolves the exact pinned support; unsupported newer extensions are neither silently imported nor falsely advertised. No report from a hardware feature automatically proves an application trustworthy, supply-chain integrity, freshness, identity, or freedom from side channels. Define measurement/reference values, nonce/freshness, report-to-session binding, revocation/TCB version, relying party and secret release policy explicitly. Denial of service by the host and physical/microarchitectural attacks may remain outside a technology's guarantee; state the residual model rather than claiming universal confidentiality.

Common release tests include malicious virtio/device/hypercall responses, repeated/shared buffer mutation, bounce-buffer bounds, private/shared conversion races, memory hotplug, guest crash/reset, firmware rejection and resource exhaustion, alongside genuine attestation verification against trusted vendor chains. Signatures/crypto must use reviewed implementations, not homebrew. Physical required hardware is currently unprovided; ordinary QEMU cannot produce qualifying confidential-computing evidence. Security fixes/changed restrictions are recorded in the [delta ledger](../compatibility.md), never hidden as “safer Rust.”

## 6. Execution program and measurable qualification

1. **M1 onward physical coexistence:** user personally selects a candidate under the distinct isolated-diagnostic or later Linux-replacement [packaging paths](../packaging.md), retaining the working kernel and independent known-good console/recovery. This plan never authorizes host reconfiguration or reboot by an assistant. Determine workstation CPU virtualization/IOMMU/firmware features from observed inventory, not assumptions; an early diagnostic does not qualify virtualization.
2. **Available bounded smoke:** on compatible reference Linux, or after a future candidate implements and boots the required Linux userspace environment, use `cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>`, choosing one actual environment. [Suite documentation](../bare-metal-suite.md) defines coverage: ordinary memory/thread/filesystem/loopback/process/proc/sysfs smoke, not KVM/VFIO/confidential performance certification and not proof that an environment label is physical hardware.
3. **Full external KVM campaign:** build pinned selftests outside project source; a concrete entrypoint is `make -C <pinned-linux>/tools/testing/selftests TARGETS=kvm run_tests` after matching toolchain/kernel preparation. Also run kvm-unit-tests with the explicit backend/capability manifest and QEMU functional workloads as required by the [upstream checklist](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/virt/kvm/review-checklist.rst). Existing external C/assembly guest tests are allowed oracles; project-owned tests/tools remain Rust. Record every skip, not only exit status.
4. **Real workload matrix:** Arch/CachyOS userspace and balanced server profile first: container services inside guests, database/network/storage loads, memory pressure, multiple vCPUs and NUMA, dirty logging/migration, nested guests and device assignment. Retain desktop/legacy/other OS/architecture cases required by final baseline compatibility rather than declaring server success global completion.
5. **Performance gate:** follow [performance](../performance.md) per workload/hardware/backend for throughput, p50/p99/p999 latency, CPU, resident/pinned/page-table memory, create/boot/migration startup and energy. Same host/guest configuration, vCPU topology, memory pages, I/O path, firmware/microcode, mitigations/security, PMU/watchdog reservations and compiler optimization settings; repeated runs/confidence intervals/noise controls. No arbitrary allowed regression, geometric-mean cover-up, disabled security or missing-hardware pass.
6. **Closure artifacts:** pinned source/ABI manifest, machine/firmware identity, guest images/licenses, tool and config versions, raw ioctl traces, state migration records, serial logs, isolation/fuzz cases and measurements. An architecture/device capability without its full artifact set remains unqualified. Root privileges, passthrough resets, firmware/TPM changes and fault injection require an isolated lab and explicit operator approval; never execute them on the current host as part of normal smoke.
