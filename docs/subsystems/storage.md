# Storage and block I/O porting program

## Scope, baseline, and present state

**Status: `not_started`.** This is a proposed implementation and qualification program, not a block implementation, runnable kernel, data-safety certificate, or measured performance result. The behavioral baseline is Linux **6.18.57**, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`. M4 requires an explicitly selected baseline filesystem that is usable, writable and crash-recoverable on virtual **and sacrificial physical** storage; a read-only image browser or toy filesystem does not satisfy it. Ext4/JBD2 is the proposed M4 choice, pending unresolved [decision Q12](../decisions.md); the initial filesystem, mount options and devices are not approved. Full ext4 parity remains required at baseline closure even if another filesystem is selected first. Server/container priority changes ordering, never final device, filesystem, or architecture scope.

Upstream facts below are anchored to pinned source/documentation; design choices and gates are proposals. The complete source routing is in [coverage](../coverage.md), not this document's family list. Filesystem transactions, VFS and application-visible durability are in [filesystems](filesystems.md); device enumeration, buses and individual controller ports are in [drivers](drivers.md); page ownership and writeback integrate with [memory](memory.md). Follow [verification](../verification.md), [performance](../performance.md), and [bare-metal qualification](../bare-metal.md). All project-owned kernel implementation and executable orchestration must be Rust; upstream C and external userspace tests are reference/oracle inputs, not linked kernel shims.

The accepted architecture is a **modular monolithic Rust kernel**: storage components are Rust kernel subsystems, not a C compatibility runtime or a mandatory userspace microkernel service. Feature scope stays fixed at upstream 6.18.57 with explicit reviewed security deltas; later feature-baseline changes and arbitrary proprietary/out-of-tree module functionality require separately enumerated approval. Every in-baseline module's functionality remains required as a Rust replacement. Architecture-owned function-local `asm!`/`naked_asm!` is allowed only where unavoidable with documented proofs; no `global_asm!` or standalone assembly escape is permitted.

### Primary observations that constrain the design

- [blk-mq](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/block/blk-mq.rst) separates software staging and hardware dispatch queues, supports tags and merging/scheduling, and explicitly does **not** promise completion ordering. Rust ownership cannot manufacture an ordering guarantee the device does not have.
- [Cache control](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/block/writeback_cache_control.rst) defines `REQ_PREFLUSH`, `REQ_FUA`, write-cache/FUA capability advertisement and fallback sequences. Completion of a cached write is not persistence; remapping drivers must propagate FUA and implement flush across their backing devices.
- The pinned [block build manifest](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/block/Makefile) includes mq-deadline, Kyber, BFQ, cgroup/QoS, integrity, zoning, inline encryption, power management, partitions and ioctl facilities. None is removed because the first QEMU disk uses a simpler path.
- [DMA rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/core-api/dma-api-howto.rst) distinguish CPU virtual, physical and device bus addresses; noncoherent caches, IOMMUs, mapping failures and address masks are real constraints, not optional hardware polish.
- [Block operations and flags](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/include/linux/blk_types.h) include discard, secure erase, write zeroes, zone operations, NOWAIT, polled, atomic, swap, integrity and P2PDMA requests. Their exact validation, limits and failure behavior must be ported, not mapped indiscriminately to ordinary writes.

## Ordered implementation and dependency gates

Each stage below remains `not_started`. A stage can begin experimentally once dependencies exist, but promotion requires its gates on the named targets. M7 closes every remaining baseline family; M8 qualifies the complete promised configuration rather than declaring success from structural inventory.

1. **M1–M2, hardware safety substrate:** establish per-architecture MMIO ordering, interrupt/MSI-X lifecycle, pinned pages, fallible allocation/reclaim contexts, timers, workqueues, CPU hotplug and DMA/IOMMU abstractions with the hardware/memory owners. On physical x86_64, enumerate a dedicated controller without writes, capture serial logs and recover through a known-good boot entry. Have an Intel and AMD platform lane from initial bring-up; unavailable equipment is a named blocked lane, not a VM pass.
2. **M2–M3, request and device objects:** port disk/partition registration, open/claim/holder lifetime, capacity and media-change handling, reference counts, queue limits, sector arithmetic, `bio` vectors, split/clone/chaining and completion/error aggregation. Build a Rust memory-backed fault-injection device that actually stores bytes; a null-completion benchmark is not a data test. Gate exact-once completion and no references released before DMA stops.
3. **M3–M4, real asynchronous queues:** port blk-mq contexts, tag allocation, reserved tags, dispatch/requeue, freeze/quiesce, timeout/reset and queue teardown; bind virtio-blk plus at least one physical NVMe and one SATA/SCSI path. Queue depth one is a debugging mode, not the permanent server architecture. Gate SMP, queue saturation, cancellation/reset races and hot removal before writable filesystem promotion.
4. **M4, durable base:** port flush/FUA sequencing and capability negotiation, physical/logical sector geometry, short/failed I/O, write-zeroes/discard and writeback-error propagation; connect the writable, crash-recoverable baseline filesystem explicitly selected under Q12. Ext4/JBD2 is proposed, not accepted; if selected, its detailed [durability gates](filesystems.md#proposed-ext4-m4-durability-implementation-gate-in-detail) apply at M4. Any other selection must meet equivalent application-visible durability and recovery gates with its own format-specific implementation and tests. Exercise devices with volatile cache and without power-loss protection as well as a PLP device. Require independent reread after controlled power loss and Linux recovery of the same image. Do not claim writable durability from graceful QEMU shutdown.
5. **M4–M5, isolation and server throughput:** port mq-deadline, Kyber and BFQ, scheduler switching, plugging/merging, ioprio, request-QoS, writeback throttling, blkcg throttling/weights/latency/cost, cgroup writeback association and pressure/accounting interfaces. Close buffered/direct/io_uring/polled and NUMA interactions with VFS and memory. Gate concurrent database WAL, container filesystem and backup jobs without starvation.
6. **M5–M6, stacked storage:** port DM core/table/ioctl and simple targets, then persistent-data users, crypt/integrity/verity, thin/cache/snapshot/RAID/multipath and every remaining target; port MD personalities, bitmap/resync/recovery and bcache. First prove each target alone, then compose it under ext4 and other filesystems. Gate power-fail and degraded recovery of metadata as well as data.
7. **M6–M7, breadth:** close zoned, DIF/DIX, reservations, atomic I/O, DAX/pmem, all transports, all block virtualizers and per-driver quirks, suspend/resume and storage fabrics. Tape/optical/sg interfaces retain their own semantics and are not forced into an ordinary disk abstraction. Run architecture-specific DMA and endian lanes.
8. **M8, release:** satisfy all definitions of done below and the per-hardware non-inferiority requirements. Preserve a bootable reference Linux recovery lane and export every image, trace, controller firmware identity, failure seed and benchmark record required to reproduce qualification.

## Shared mechanisms and safety contracts

### `bio`, requests and completion ownership

**Proposed design:** distinguish byte counts, Linux 512-byte sector units, logical blocks and physical alignment in internal types; checked arithmetic at parsing and aggregation boundaries; enforce driver-specific limits before descriptor construction. Own each page pin, DMA mapping, integrity payload and crypt context across a finite submitted/completing/retired lifecycle. Split bios carry offsets and operation flags without accidental duplication of flushes or loss of integrity seed adjustment. Clones do not own borrowed buffers unless the original's lifetime is extended. A request may complete in pieces and bios may aggregate multiple request outcomes; preserve Linux's residual/error rules and do not report success after any required child fails.

Define the exact IRQ/process/reclaim context of each callback. Never sleep under spinlocks, allocate unboundedly in interrupt completion, invoke filesystem callbacks while holding incompatible queue locks, or depend on an executor that requires the same blocked worker. Reserve forward-progress resources for swap, writeback, stacked-device metadata and reclaim; an allocator failure is an I/O failure, not a kernel panic. Teardown first prevents new submission, drains or safely terminates outstanding DMA, then retires tags and storage; dropping a Rust owner is not permission to free memory still owned by hardware.

**Port gate:** property/model tests for split/merge offsets, page-boundary vectors, generation-tag reuse, 32/64-bit overflow and exact-once completions; stress request failures during allocation, submit, timeout, reset, completion, CPU offline and unbind. Compare errno, residual bytes, read data, queue states and resource accounting with the pinned kernel.

### Multiqueue and scheduling

Preserve per-CPU/software and hardware queue mapping, tag-set sharing, reserved requests, stopped/restarted queues, dispatch budgets, queue-runnable ordering and starvation prevention. Maintain different resource/device/transport failure classes and baseline retry ownership. Do not add a generic retry that replays a possibly committed write or indefinitely holds an unmount. Queue freeze/quiesce and runtime scheduler changes must have explicit ordering against device removal and in-flight submission.

**Optimization proposal:** CPU/NUMA-local request caches, compact tag-indexed completion, batch dispatch/completion and validated adjacent-vector merging; avoid per-I/O heap allocation and buffer cloning where ownership permits. Measure cross-socket traffic and tail latency before introducing lock-free algorithms. Keep mq-deadline expiration/read-write fairness, Kyber latency-token policy and BFQ service/weight accounting distinct behind shared queue primitives; a FIFO renamed as each scheduler is incompatible. First use `none` only as an explicitly limited bring-up configuration, never as a substitute for baseline choices.

**Gate:** differential scheduler/sysfs and ioprio tests; mixed sequential/random/read/write workloads at depth 1 through saturation; fair shares and bounded progress under cgroup and reclaim pressure; SMT/CPU-hotplug/NUMA migration. Release cannot hide a BFQ or HDD regression behind NVMe average throughput.

### Persistence and operation semantics

The flush state machine must implement empty preflush, preflush+payload, FUA+payload and combined preflush/FUA, including FUA emulation when needed; report downstream failure to every dependent waiter. A device without a volatile write cache is a distinct capability case, not a license to strip durability flags everywhere. Each stacked device computes limits/capabilities from every relevant lower device, preserves ordering across stripes/mirrors/cache metadata, and propagates failures. Linux-compatible configurable unsafe options must remain explicit opt-ins with the same reporting; never silently default to disabling barriers.

`fsync`, `fdatasync`, `syncfs`, `O_SYNC`/`O_DSYNC`, journal commit and directory durability depend on this layer but are not identical operations. A CPU memory barrier, DMA sync, controller command completion, cache flush and persistent-memory drain each solve different problems. DAX additionally requires architecture cache-line writeback/drain, poisoned-memory handling, mapping/truncation exclusion and application persistence contracts; it is not an ordinary successful bio or an `mmap` optimization shortcut.

Discard/TRIM is not guaranteed zeroing or secure erasure. Implement queue alignment/maxima, partial-device capabilities, deallocation versus `NOUNMAP`, secure erase authorization and all error paths. Validate atomic-write unit/size/boundary constraints through the complete stack; never split a request advertised as atomic into independently durable pieces. Failed or unsupported atomic/NOWAIT/polled requests follow the baseline ABI, not silent weaker fallback.

**Gate:** record issue/ack/persist ordering in a fault model; replay every relevant crash cut, reordered/dropped/torn write and failed flush. Reread on a different boot and compare acknowledged durability obligations, not only successful mount. Check cache settings against identify/log output and known device quirks. A hardware controller that lies about flush remains an explicitly unqualified configuration until an upstream-compatible mitigation is demonstrated.

### DMA, integrity and encryption

Use the shared [driver DMA substrate](drivers.md), not a storage-only physical-address cast. Keep streaming/coherent mappings, direction, synchronization, scatterlist coalescing, bounce buffers, DMA masks, IOMMU mappings, peer-memory permissions and cache-line sharing in the ownership contract. Reset paths must fence DMA before freeing or reusing tags; malicious/buggy completions cannot index unchecked tables or expose another tenant's pages.

[Integrity documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/block/data-integrity.rst) describes integrity payloads attached to bios and separate data/metadata scatterlists. Port T10 protection interval, guard/reference/application tags, generation/verification, remap/split/merge and protocol-specific representation exactly. Integrity failure is not an ordinary success or zero-filled read. Inline crypto must preserve keyslot eviction/reset and data-unit numbering across splits, stacked remaps and concurrent keys. Crypto implementation and key lifecycle are shared with [security](security.md); checksums do not establish authenticity.

**Optimization proposal:** reuse mapped descriptors where the mapping contract permits, batch IOMMU operations safely, choose reviewed checksum/crypto acceleration by CPU capability while retaining the same polynomial, byte order and constant-time guarantees. Test noncoherent architectures and bounce paths as first-class M7 gates; x86 cache coherence does not prove them.

All prospective reuse must meet [dependency and licensing review](../dependencies.md), use a pinned reviewed revision/feature closure, `no_std` and context-aware fallible allocation, and pass the row's observable gates.

### Crate evidence and adoption boundaries

Observed candidate evidence, not adoption:

- [virtio-drivers upstream README](https://github.com/rcore-os/virtio-drivers) describes `no_std` guest drivers and block support but lists unsupported/incomplete feature areas including packed queues/platform ordering in the reviewed README. Review the exact pinned revision, HAL safety contract, DMA mapping and flush/error paths. Its existence does not supply blk-mq, Linux sysfs/ioctl, all negotiated features or physical-controller coverage.
- [rust-fatfs](https://github.com/rafalh/rust-fatfs) exposes FAT12/16/32 read/write and basic `no_std`, not block-layer lifetime, Linux FAT mount options or device durability. [ext4-view](https://github.com/nicholasbishop/ext4-view-rs) explicitly excludes write support. These are format-parser/harness candidates only for storage-layer purposes; filesystem-specific evaluation is in [filesystems](filesystems.md).
- [littlefs2](https://docs.rs/littlefs2/latest/littlefs2/) explicitly builds on `littlefs2-sys` and a C backend; reject it from the Rust-only runtime, independent of whether it is `no_std`. A new unrelated disk format cannot replace a baseline Linux format.
- No kernel dependency is approved by these documents. Cryptographic/checksum primitives require licensing, feature-closure, unsafe, allocation-context, timing and architecture reviews through [dependencies](../dependencies.md) and [security](security.md). A crate's popularity or benchmark is not an exception to crash-recovery qualification.

## Real-media-safe test suite specification

The repository's actual bounded, non-destructive [bare-metal smoke suite](../bare-metal-suite.md) is separate from the future full qualification matrix below. Its CLI is `cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>`. Run only on the operator-selected already-booted compatible Linux system; the environment label is an assertion, not proof of bare metal. It tests a self-created filesystem sandbox and functional facilities, never mounts, raw-writes devices, changes boot configuration, reboots or invokes the destructive tests below. A reference-host result validates the runner, not candidate-kernel storage behavior.

ST-01 through ST-09 are **future qualification procedures**, not executed evidence or functionality of that smoke suite. The [bootstrap](../implementation.md) has no storage stack to exercise them. Future Rust lab orchestration must execute and record these cases against both the storage-capable Rust kernel and pinned reference Linux; external binaries/suites may be non-Rust. Every proposed storage implementation workstream remains `not_started`, with missing hardware recorded as a separate qualification blocker. The standing [definition of done](../definition-of-done.md) forbids treating smoke success as parity.

### Mandatory destructive-test interlock

Before any write, require a dedicated DUT booted independently of its scratch controller, serial/BMC access and a verified known-good recovery entry. Provision distinct TEST/SCRATCH media using an explicit recorded destructive authorization. Resolve device serial/WWN/namespace UUID, controller PCI identity, firmware, capacity, full parent/child dependency graph and mounted/swap/holders state against an allowlist; do not select by unstable `/dev/sdX` names. Refuse the system disk, a disk with host/user data, any ancestor/descendant of mounted root/boot/swap, conflicting multipath identities, ambiguous identity, existing unapproved MD/DM members, and targets passed through from a live host filesystem. A namespace on a shared production NVMe controller is not safe for controller-reset, sanitize or power-cut tests.

Disconnect non-test drives where possible. Dedicated power switching must affect the sacrificial drive/controller or DUT, not a shared host, storage array or network switch. Maintain byte-for-byte seed images and expected application histories off-DUT; archive failed media images read-only before repair. Recovery/fsck is not run on the only failing image. Secure erase, firmware update and destructive namespace management require separate authorization from ordinary write testing. Isolated fabrics must have no route to production storage. If these preconditions or the hardware are missing, the destructive lane is blocked.

Physical firmware and recovery manuals must be attached to the lab record before ST-06. M1 read-only bring-up and M4 writable physical lanes co-evolve with QEMU; they are not deferred to M8. Flash wear, temperature, cache warmup, background GC, SSD preconditioning, device capacity used, power policy and thermal throttling are controlled and reported. Cold-start and steady-state are separate results.

## Exhaustive definition of done for this workstream

“Exhaustive” here means **every applicable record** in the pinned inventory, protocol operation, target configuration and qualification matrix has an explicit result; a prose family table or successful boot is not proof of exhaustive behavior. All conditions are conjunctive:

1. Every baseline block source path, operation/flag, ioctl/compat structure, sysfs/proc/debugfs interface, partition parser, scheduler, QoS/cgroup policy, DM target, MD personality, virtual block frontend and storage driver has a Rust implementation mapping and versioned behavioral tests, or remains an open blocker preventing full-parity release. No “other/legacy” bucket can silently count as complete.
2. Each exposed capability is truthful through every supported stacking combination; all limits, flush/FUA/atomic/integrity/crypto/zoned semantics, permissions, errors and failure recovery agree with pinned Linux. Every caller and userspace administrative tool path is covered; no C kernel/module runtime or FFI-backed implementation remains.
3. All data and integrity tests pass on virtual disks and qualified sacrificial physical storage; all crash-cut classes, reboot/replay, corruption, lost-member/path, timeout/reset, ENOSPC and memory-pressure cases have reproducible histories and verified on-media outcomes. A mount succeeding after recovery is insufficient.
4. Request/page/DMA/tag/key/holder lifetimes and concurrent transitions have documented invariants, lock/context proofs, unsafe review and model/stress evidence across SMP, hotplug, suspend/resume and every supported architecture. No known unbounded hang, stale DMA, double completion or unreported writeback failure remains.
5. Exact device/controller/firmware/topology/feature/security combinations are recorded. Required but unavailable physical platforms, zoning, integrity, pmem or fabrics are named blockers; VM evidence never substitutes for physical qualification. Real-media destructive interlocks and serial recovery are exercised before qualification.
6. ST-01 through ST-09 plus per-family driver/target tests have actual archived results. Every skip is capability-justified against the reference; flaky failures are unresolved failures, not removed tests. External suite versions and commands are reproducible.
7. Every promised workload/hardware meets the at-least-Linux performance requirement for throughput, latency/tails, CPU, memory, startup and power with controlled paired measurements and confidence intervals. Unproven non-inferiority is not a pass. Avoidable hot-path allocation/copy/contention has been measured and addressed without changing semantics or security.
8. User/admin documentation, provenance/licenses, configuration defaults, regression corpus, crash images, recovery instructions and maintenance ownership are current and reproducible through the project audit. Until these conditions hold, the honest state is partial implementation or blocked qualification—not “Linux-compatible storage complete.”

## Current blockers and assumptions

No block layer, storage driver or kernel storage-qualification execution exists. Only the current workstation is available; the user personally installs/selects/boots future candidates, with existing kernel and recovery entries preserved under the distinct diagnostic/replacement [packaging paths](../packaging.md). A storage-free M1 diagnostic trial does not waive any storage, durable filesystem or root-stack prerequisite for the later Linux-replacement package. Do not run boot/install/reboot/firmware/destructive-disk actions on that workstation. Other-vendor systems, dedicated sacrificial controllers/media, power switching, zoned/PI/pmem equipment and cross-architecture DMA laboratories are named missing prerequisites, not promised available resources. Storage crate candidates have not been pinned/adopted or audited. First userspace is Arch/CachyOS with the balanced server performance profile, not downstream CachyOS kernel patches. The plan assumes pinned Linux remains available as a read/write recovery and differential oracle; reference-kernel defects must be recorded rather than copied into Rust unsoundness or silently redefined as success.
