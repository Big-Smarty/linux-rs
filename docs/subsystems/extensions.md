# Rust modules, BPF and extensible kernel interfaces

## Status, language boundary and acceptance contract

**The extension-facility workstreams in this document remain `not_started`.** This is a proposed Linux **6.18.57** direct Rust port with no C kernel shim or C-backed incremental runtime, separate from the bounded [bootstrap](../implementation.md). Infrastructure starts with M1–M3 executable memory, exceptions, MM, RCU, credentials and fd lifetimes; module/device replacement progresses with subsystem bring-up; BPF and broad extension facilities develop through M6; every pinned architecture/helper/map/backend/configuration closes in M7 before M8 qualification. Built-in-only or interpreter-first milestones are staging, not final scope cuts.

Accepted design is **modular monolithic**, with feature scope fixed to 6.18.57 and reviewed security deltas rather than silent feature-baseline expansion. Only function-local `asm!`/`naked_asm!` are allowed where unavoidable with reviewed proofs; `global_asm!` and standalone assembly are prohibited. Every in-baseline module's functionality must have a Rust replacement; arbitrary proprietary/out-of-tree modules require separately enumerated approved scope.

Related plans: [architecture](../architecture.md), [dependencies](../dependencies.md), [toolchain](../toolchain.md), [licensing](../licensing.md), [security](security.md), [memory](memory.md), [process](process.md), [drivers](drivers.md), [networking](networking.md), [storage](storage.md), [filesystems/io_uring](filesystems.md), [observability and metadata](observability.md), [virtualization](virtualization.md), [compatibility ledger](../compatibility.md), [verification](../verification.md), [performance](../performance.md), [physical lab](../bare-metal.md), [smoke suite](../bare-metal-suite.md), [definition of done](../definition-of-done.md), and [packaging](../packaging.md).

### What “Rust-only” means here

| Artifact | Rule and compatibility consequence |
|---|---|
| Project kernel, built-in drivers, modules, verifier/interpreter/JIT/helpers, loaders and project-owned executable tools | Authored implementation is Rust; kernel code `no_std`, context-aware fallible allocation. Only function-local `asm!`/`naked_asm!` when unavoidable with explicit operation/register/memory/clobber/privilege and machine-code-review contracts. No `global_asm!`, C/C++/Zig, standalone assembly or imported C runtime. `repr(C)` and `extern` ABI syntax do not constitute C implementation. |
| Linux C `.ko` or old C livepatch binary | **Not loadable.** Every in-baseline module's functionality, bus/device aliases, policy and operational behavior requires a genuine Rust replacement, including obscure or legacy baseline code. There is no blanket promise to implement arbitrary third-party/proprietary out-of-tree modules; any addition must be separately enumerated and approved. |
| New Rust replacement module object | Allowed only through the project module contract below, bound to compatible kernel/build/ABI and provenance. A suffix, `rustc` symbol or caller-supplied license string cannot prove source language or safety. No stable Rust compiler ABI is assumed. |
| User-supplied eBPF/cBPF instructions | Linux-facing **input bytecode**, potentially generated by existing non-Rust userspace compilers/programs. Accept compatible permitted bytecode independent of original source language. Project-owned BPF programs/tests/tools are Rust; external reference suites may contain C. Rejecting external bytecode merely because it originated from C would be an unauthorized compatibility loss. |
| Native instructions produced by the kernel's Rust JIT | Runtime generated code representing validated bytecode, not a project-authored `.S`/C implementation. Require verifier/JIT equivalence, bounds, executable mapping policy and cache/mitigation handling. “Generated” is not an exemption from executable-memory review. |
| External compiler/linker/QEMU/reference Linux/existing userspace or test suite | Allowed external tools/workloads with provenance and license records; cannot be linked as a hidden kernel C runtime. Firmware/microcode remain explicitly external trusted/untrusted artifacts, not claimed as Rust. |

**Definition of done per subfamily:** complete pinned ABI/operation/configuration/architecture matrix; all successful, denied, malformed, OOM and teardown behaviors implemented; existing tools and legitimate workloads interoperate; threat-model/unsafe/provenance review and adversarial/differential tests have evidence; physical backends/devices qualify separately from QEMU; all required workloads achieve at-least-reference performance with equivalent security. A deny-all loader, a tiny verifier, a map dictionary or a single x86 JIT is not completion. Approved artifact differences and every security fix appear transparently in the central ledger; no unsupported audit claim.

## 1. Rust replacement module format and lifecycle

### 1.1 Build identity, module discovery and userspace behavior

**Authorities:** the pinned [module implementation](https://github.com/gregkh/linux/tree/v6.18.57/kernel/module), [signature facility](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/admin-guide/module-signing.rst), [license rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/license-rules.rst) and [lack of stable internal driver ABI](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-api-nonsense.rst). Stable userspace interfaces do not imply a stable internal Rust module ABI.

1. Inventory pinned module syscalls, flags, metadata sections, `/proc/modules`, sysfs module/parameter/holder/reference state, aliases, dependencies, autoload requests, taints, compressed formats, namespace imports and symbol license/version checks, plus userspace modprobe/udev/depmod consumers.
2. Specify the Rust module build contract: same compatible compiler/kernel feature/layout/ABI generation and build identity, exported symbol namespace/signature metadata, init/exit/parameter descriptions, unwind/BTF/ftrace/exception tables, license/provenance and a language/source-closure manifest covering all linked objects/dependencies. Exact manifest/version design is an implementation decision requiring format review; no fake current artifact is supplied.
3. Implement Linux-facing `init_module`, `finit_module`, `delete_module`, flags/error ordering, identity checks and corresponding sysfs/proc/uevent visibility for valid replacement artifacts. Preserve metadata needed for ordinary autoload by logical driver aliases; produce real dependency metadata using Rust project tools or compatible external tools without project shell implementations.
4. Migrate subsystem modules to genuine Rust equivalents and update every caller/alias/dependency; maintain an explicit old-functionality→replacement→test mapping. Do not keep an unused legacy export shim or silently map missing functionality to success. Resolve Arch userspace/mkinitcpio/modprobe packaging with [packaging](../packaging.md) before declaring operational compatibility.

**Crates/shared:** project module ABI/manifest/lifecycle. ELF codecs such as [object](https://github.com/gimli-rs/object) are candidates for trusted build tooling, not an approved adversarial kernel loader: upstream explicitly documents trusted-input focus and limited DoS defenses. Evaluate a bounded runtime parser separately against pinned structures and resource constraints. Reuse credentials, security hooks, keyrings, VFS read snapshots, symbol registry, allocation contexts and [toolchain](../toolchain.md) identity records.

**Simplification and invariants:** typed metadata can eliminate C macro/type hazards internally; Linux-visible names, parameters, dependencies and taints still require compatibility. Restricting accepted artifacts to new Rust replacements is an approved explicit delta, not a reason to remove module syscalls. A provenance/signature trust policy is needed because machine code alone cannot certify Rust-only construction; claimed Rust origin still does not certify safe behavior. Administrator loading policy and lockdown remain independent of source language.

**Optimization/test/done:** index static aliases/symbols and parse metadata once after validation; avoid hot-path manifest allocations after load. Test legitimate signed/unsigned-as-policy-permits Rust replacements with existing modprobe/udev flows, aliases/dependency cycles/version mismatch/unknown symbols, all syscall flags, proc/sysfs metadata and malformed compressed input. Test rejected legacy artifacts as the documented boundary rather than expecting C module passes. On real hotpluggable devices measure discovery-to-probe/load time, module bytes/memory, dependency resolution and userspace startup tails; a renamed `.ko` without functionality fails.

### 1.2 ELF relocation, executable memory and initialization rollback

1. Parse immutable snapshotted artifact bytes with checked offsets/counts/overflow/alignment; validate ELF class/endian/machine/sections/symbol bindings and relevant architecture relocation types. Inventory **every pinned architecture** relocation implementation, REL/RELA, branch ranges/stubs/TOC/GOT/per-CPU references and compiler-generated special sections rather than supporting only x86_64 `R_*_64`.
2. Allocate code/RO/data/per-CPU/init regions with correct alignment, accounting and addressability; resolve approved exported symbols and dependencies, apply checked relocations and required instruction/cache/barrier operations, then validate exception/unwind/BTF/ftrace tables before exposure.
3. Publish executable pages only after relocation/verification and strict code/data permissions; serialize any temporary patching through the shared W^X-aware service. Install constructors/init callbacks with defined Rust panic/error behavior; all failed phases unwind dependency refs, registered handlers and mappings in reverse order without publishing partial functionality.
4. Release init-only memory only after no CPU/callback/unwind table can refer to it; register symbols and metadata atomically with correct observable module states.

**Crate/shared decision:** project architecture relocation adapters using reviewed bounded ELF readers; generic object parsing does not implement loader relocation policy. Share executable mapping and text-patch transactions with BPF/kprobes/ftrace/livepatch, shared architecture cache/TLB primitives and namespace/license symbol lookup. No host dynamic linker, `libloading`, C `dlopen` runtime or whole LLVM runtime in kernel.

**Safe simplification/security:** a single typed relocation dispatcher per architecture reduces duplication, but unknown relocations need correct rejection and final support closure, not permissive truncation or architecture abandonment. Bound decompression/section/relocation work and total memory before allocating; protect against duplicate/overlapping mappings and signed-addend overflow. Rust bounds checks cannot validate instruction target privilege or physical executable mapping correctness.

**Optimization and done:** use validated offset views and in-place relocation of private staging regions; pre-index exports and batch architecture cache operations only with equivalent publication. Generate Rust relocation fixtures covering each compiler/backend output and negative boundary, compare mapped symbols/results with reference semantics for matching constructs, fuzz ELF/compression/relocation tables and inject allocation/init failures at every step. On each physical architecture load/unload functional drivers with IRQ/DMA activity and verify W^X, cache coherence and exception/unwind correctness. Measure load/relocation time by artifact size, init latency, code/data/init/per-CPU memory and CPU/cache costs; compiler support and unavailable hardware remain explicit blockers.

### 1.3 Signing, trust, unload and runtime replacement

**Authority:** [pinned signing rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/admin-guide/module-signing.rst) distinguish permissive/restrictive trust and reject unparseable signature blocks even in permissive mode. A signature authenticates an artifact, not its semantic safety.

1. Preserve baseline appended signature parsing/algorithm/trust behavior for the new module artifact where format compatibility applies; enforce configured trust roots, revocation, blacklist, lockdown, integrity/IMA/LoadPin, taints and disabled-loading policy. Add authenticated Rust build/provenance binding without calling filename validation language enforcement; document all artifact-format differences in the ledger.
2. Use [security](security.md) reviewed ASN.1/X.509/CMS/PKCS#7 and signature/hash providers; preserve baseline supported algorithms/modes. RustCrypto format/signature families are **candidates** after per-version primitive/algorithm/feature/license/DoS review, not evidence that the project or crate is audited. No homebrew signatures or C-backed OpenSSL runtime.
3. Model load/init/live/going/failure states, module refs and dependent exports; prevent new entries while unregistering. Drain IRQs, work/timers/tasklets, file/device callbacks, sysfs/proc readers, network/offload/DMA, RCU/SRCU, perf/probes/BPF attachments and all module-owned objects before reclamation.
4. Port normal and configured force-unload behavior, taint/error outcomes and permanent-module constraints, including the baseline risks. Do not silently remove force semantics under a safety slogan; if a vulnerability requires a changed policy, approve and test a specific ledger delta. Couple livepatch lifecycle with [observability](observability.md) rather than an independent unload shortcut.

**Bundling/simplification:** one trust verification service shared by module/firmware/kexec/IMA, but context-specific allowed keys and policy remain distinct. Owned registration guards and explicit unload dependency graphs simplify cleanup; `Drop` alone cannot synchronously prove DMA/NMI/RCU quiescence. Module object lifetimes cannot be equated with Rust strong-reference counts when external callbacks exist.

**Optimization/test/done:** cache validated immutable key material only across correct revocation/policy generations; batch callback unregister where supported. Test valid/bad/truncated signatures, revoked/unknown keys, permissive taints, restrictive policy, compressed/signed artifact boundaries and loading-disabled/lockdown. Race load/unload with IRQ/DMA/open files/probes/BPF/livepatch/hotplug, duplicate names, dependent modules, OOM and failed init. Physical storage/NIC replacement cycles must show no stale callbacks/mappings and correct recovery; measure unload quiescence p50/p99/worst-case, retained memory, load/signature overhead and service interruption. No allocator-only unload test qualifies real hardware lifetime.

## 2. BPF syscall, object model and privilege

**Authorities:** [BPF design](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/bpf_design_QA.rst), [map API](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/maps.rst), [licensing](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/bpf_licensing.rst), pinned [BPF UAPI](https://github.com/gregkh/linux/blob/v6.18.57/include/uapi/linux/bpf.h) and [kernel implementation](https://github.com/gregkh/linux/tree/v6.18.57/kernel/bpf). Narrative pages contain historical statements (including loop support); exact 6.18.57 implementation/selftests arbitrate current semantics.

1. Extract every `bpf` command/attribute/size/flag, program/map/attach/link type, feature probe, object info field, statistics/token/delegation control and privileged/unprivileged error rule. Include compat pointer widths, unknown trailing fields, log-buffer behavior and resource accounting. Enumeration from headers is structural coverage, not behavioral completion.
2. Implement program/map/BTF/link/token IDs and fds, refs/pins/bpffs, get-by-ID/info/query, freeze/update/batch APIs, link replacement/detach and namespace/cgroup ownership. Teardown is reference/RCU safe across processes, mounts and attachments.
3. Preserve `CAP_BPF`, `CAP_PERFMON`, `CAP_NET_ADMIN`, relevant legacy capabilities, user namespace scope, LSM/lockdown and unprivileged-BPF policy; token delegation can convey only pinned authority, not generic host privilege. Preserve GPL-only helper/kfunc/program restrictions and license-string handling without claiming that a supplied license is verified legal provenance.
4. Integrate complete production attachment contexts under their owners: networking/XDP/TC/LWT/socket/reuseport/flow dissector/netfilter, cgroup socket/address/options/device/sysctl, perf/kprobe/uprobe/tracepoint/raw trace/fentry/fexit/fmod_ret, LSM, iterators/syscall/extension/freplace, `struct_ops` including scheduler/TCP consumers where baseline supports them, and all remaining pinned types. No invented always-success attachment to an unimplemented hook.

**Crate/shared decision:** project BPF object/security core. [Aya](https://github.com/aya-rs/aya) is a Rust userspace loader/BTF/CO-RE client and program ecosystem, not a kernel verifier/JIT/helper implementation. It can be an external differential client; no assumption its internal parsers are kernel-hardened. Share fd/anon-inode/bpffs lifetime, credentials, memcg, RCU, cgroup/network/task object models, audit and monotonic time.

**Limits/invariants/optimization:** interned descriptors and static dispatch tables simplify ID and command handling; preserve all supported commands and attachment modes, not merely XDP/hash maps. No stale ID reuse reference, leaked host address, uninitialized info padding, unlimited verifier work or use-after-unpin. Optimize read-mostly registries and avoid global object locks for per-CPU operations without altering coherent info/query results.

**Done tests:** pinned BPF syscall/selftests and bpftool/libbpf/Aya userspace, ID/pin/link/token permissions and lifecycle, cgroup/netns/LSM interactions, fd transfer, malformed attributes and resource exhaustion. Physical multi-core/NUMA attach/detach/update stress must report object creation/lookup/load/startup times, memory per object, lock contention and application tail impact; compare access denials and audit to reference, not just a successful `bpf()` return.

## 3. Verifier: abstract interpretation and proof obligations

**Authority:** [pinned verifier documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/verifier.rst) explains register/stack state, pointer tracking, helper prototypes and bounds; actual pinned `kernel/bpf/verifier.c` and tests determine supported loops and newer object rules. Do not copy its early “disallow loops” prose as the modern implementation contract.

### Ordered implementation

1. Port instruction/control-flow validation, subprogram/call graph, branch/jump targets, wide instruction pairing and per-program-type legal opcodes; reject malformed/undefined encodings with reference behavior. Separate verifier internal resource limits from userspace instruction limits and privileged differences.
2. Port abstract scalar signed/unsigned 32/64-bit intervals, known/unknown bits and precision tracking; ALU32 zero/sign-extension, overflow, shifts, division/modulo and branch refinements. Arithmetic is BPF-defined, not Rust debug-overflow or host machine undefined behavior.
3. Model initialized/uninitialized registers and byte-granular stack spills, pointer identities/nullability/provenance, packet/data_end, map values, context offsets, dynptrs, object references, RCU/trusted pointers and pointer arithmetic. Check load/store alignment, size, atomic operations and access conversion.
4. Implement state pruning/equivalence, liveness/precision propagation, bounded loops/callbacks/iterators, tail-call/stack-depth accounting, BPF-to-BPF/global calls and return/ref ownership. Avoid unsound state merges that discard necessary bounds or obligation state. Bounds on work/memory must preserve the baseline acceptance envelope for safe programs, subject to transparently approved security fixes.
5. Validate helper/kfunc per-program-type prototypes, sleepable/non-sleepable/RCU/locking context, reference acquire/release, map-internal locks, timers/task-work, exception/callback paths and specialized subsystem rules. Verify rewrites/fixups, speculation sanitization and context conversion; execution consumes precisely the validated transformed program.
6. Preserve verifier logging, error/size negotiation and diagnostic behavior needed by loaders/tests; exact full prose text need not be invented as ABI where upstream does not guarantee it, but classify differences and preserve actionable diagnostics. Commit object references only after complete success; unwind every failure.

### Crates and bundling

Project direct port of pinned abstract semantics; [rbpf](https://github.com/qmonnet/rbpf) explicitly describes its verifier as very simple and “nothing close” to Linux's, so reject it as a kernel verifier/security boundary. Generic SMT/abstract-interpretation libraries may support **host-side independent tests/proofs** after review; none is assumed `no_std`, allocation/context-compatible or Linux-acceptance-equivalent. Do not replace Linux compatibility with a deliberately tiny accepted subset or assume Rust-authored BPF is automatically safe.

Share instruction decoder/semantics tables with interpreter and JIT, but keep independent test models so one shared bug does not validate itself. Share helper/kfunc signatures, BTF type identity, pointer/object lifetime and context rules with actual subsystem consumers; duplicate hand-maintained prototypes are a source of unsoundness.

### Simplifications, invariants and optimization

Typed register/object states and fallible arena-backed analysis can simplify memory ownership; no collapse of scalar signedness, pointer IDs, nullable states, per-byte initialization or reference obligations. Safety requires both a sound verifier **and** correct helpers/JIT/attachment context. Prevent speculative out-of-bounds access and address disclosure according to baseline policy, not only architectural bounds. Verifier rejection of a known-safe accepted program is a compatibility regression until resolved or explicitly approved; unsafe acceptance is a security defect and blocks release.

Optimize validated state deduplication, worklist locality, sparse state copying and cached immutable metadata only after soundness/equivalence tests; avoiding redundant allocation is desirable but not a reason to drop proof state. Analysis caches need exact program/configuration/BTF/helper/policy keys and invalidation.

**Done tests:** every pinned verifier accept/reject test and regression reproducer, arithmetic/pointer/stack/call/ref/lock/sleepable/loop/iterator paths, privileged/unprivileged policy, adversarial state explosion and OOM. Differentially fuzz loader decisions and interpreter results against reference; independently generate small bounded programs and check abstract transfers/rewrites against a concrete model. Historical vulnerable programs require approved safe deltas rather than faithfully reintroducing flaws. Measure verification p50/p99/worst-case time, explored states, peak/retained memory and concurrent load scalability on physical CPUs/NUMA, with malicious workloads unable to cause unbounded host starvation. No proof or audit is claimed before these artifacts exist.

## 4. Interpreter, classic BPF and execution semantics

1. Define precise BPF instruction semantics for all pinned widths/endian/ALU/atomic/load/store/jump/call/tail-call/exception behavior, independent of Rust host integer overflow and ABI quirks. Port register/stack frame setup, helper call conventions, context translation and return handling.
2. Implement the non-JIT execution path where baseline configuration supports it, verifier-produced fixups and BPF-to-BPF/tail calls, instruction counters and bounds; kernel configuration may require JIT on particular architectures, which is not permission to fake a fallback there.
3. Implement cBPF socket-filter and seccomp paths, conversions and ancillary/context-specific loads; share opcode decoding only where restrictions match. [Security](security.md) owns seccomp action/TSYNC/notification semantics; a socket filter and seccomp filter have different legal memory and return behavior.
4. Integrate `BPF_PROG_RUN`/test-run context copying and program-type behavior. [Pinned test-run documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/bpf_prog_run.rst) explicitly distinguishes ordinary test execution from live XDP frames; do not assume a “test” syscall can never send packets or cause side effects.

**Crate/shared decision:** project interpreter over reviewed instruction tables; rbpf may be a restricted external semantic cross-check but is not selected as complete interpreter/verifier/helper compatibility. Reuse bounded program storage, validated helper dispatch and map/object lifetime; no C interpreter runtime. A Rust function ABI adapter can implement required C-style BPF calling conventions without C source.

**Simplification/invariants:** one explicit register machine supports deterministic testing; do not map BPF pointer integers directly to arbitrary Rust references or use host arithmetic that panics/has incorrect overflow. The transformed verified program, helper prototypes and execution bytecode must agree. Enforce no uninitialized stack exposure and the correct call/frame/tail limits; budget/safety mechanisms cannot silently change valid program semantics.

**Optimization/test/done:** dispatch optimization and eliminating redundant checks need a proof of equivalence to validated execution; preserve non-JIT behavior. Compare accepted-program outputs/state/map side effects across reference interpreter, port interpreter and every JIT; cover 32/64-bit/endian arithmetic, atomics, faults, special loads, tail/call limits and helper callbacks. Run socket tcpdump/filter and seccomp workloads on physical machines and applicable big-endian/32-bit targets. Measure cycles/instruction, program startup/stack memory, packet/syscall throughput and tails with interpretation enabled; interpreter-first is not release-level JIT performance evidence.

## 5. Per-architecture JITs, trampolines and generated native code

**Authorities:** [BPF design/calling convention](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/bpf_design_QA.rst), [upstream BPF runtime/license scope](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/bpf_licensing.rst), and pinned per-architecture `net`/`bpf` implementation/configuration paths from the coverage inventory. A supported Rust target is not evidence its JIT exists.

1. Enumerate each pinned `HAVE_EBPF_JIT`/classic JIT and trampoline capability, architecture/word size/endian variant, mandatory JIT configuration, atomics and calling convention; tie each to [architectures](architectures.md). x86_64 first is scheduling only: x86_32, arm/arm64, MIPS, PowerPC, s390, RISC-V, LoongArch, SPARC, PA-RISC and every other **actually configured pinned backend** remain explicit inventory closure, not claims of identical support.
2. Port architecture instruction selection, register allocation/spills, prologue/epilogue, exception tables, immediate materialization, endian/ALU32 operations, atomics, BPF-to-BPF/kfunc/helper calls, tail calls, long branches and iterative code sizing/relaxation. Correct host ABI/FPU/stack/return protections must hold at every entry/exit.
3. Implement fentry/fexit/fmod_ret/extension/LSM/struct_ops and other required trampolines with register-preservation, sleepable/RCU context, patch collision, unwind/BTF/line info and callback lifetime. Shared text-patch service arbitrates ftrace/kprobes/livepatch/JIT rather than independent writers.
4. Allocate staging code non-executable, validate ranges/relocations and finalize RX plus RO metadata, synchronize instruction/TLB/cache state and publish atomically. Port constant blinding/hardening, randomization and speculation mitigations with exact policy/architecture differences. No writable-executable permanent alias or unaccounted executable memory.
5. Export introspection/disassembly/JIT symbols only with baseline privilege/address-disclosure rules; update/unload waits for execution and tracing readers before reclamation. An offline debug artifact does not confer runtime authority.

**Crate/shared:** project JIT backends; generic [rbpf](https://github.com/qmonnet/rbpf) x86 userspace JIT is not Linux kernel backend coverage. `dynasm`/Cranelift-style generators are not assumed suitable: evaluate source/native-code, architecture coverage, allocation, code size, latency, mitigation and kernel-context constraints before any adoption; no crate is selected here. Share exact verified IR/semantics, executable memory, architecture encoding helpers, symbol tables and helper ABI descriptions. A large runtime compiler is not a default substitute for a direct port.

**Simplification/invariants:** per-ISA typed instruction emitters and one checked relocation service simplify maintenance, not semantic choices. A Rust-generated instruction stream can still be wrong/unsafe; verifier correctness does not prove JIT correctness. No truncating long branches, missing atomics/barriers, wrong sign extension, host stack overwrite or stale code cache. Every assembly-like runtime encoding remains reviewable executable output; source-language rule does not waive disassembly checks.

**Optimization/test/done:** after exhaustive semantic tests, optimize peepholes, constant propagation, branch relaxation, register/stack layout, direct helper dispatch and trampoline reuse without changing verifier assumptions. Differential corpus on interpreter/reference/port JITs includes boundary immediates, ALU32, division/shift/endian, atomic litmus, branches at range boundaries, spills/calls/tail calls, exceptions and hardening on/off as valid configurations. Random valid-program generation, malicious accepted programs and concurrent unload/patch/hotplug are mandatory. Physical hardware **for every pinned JIT backend** must inspect/run actual output under mitigations; QEMU has independent useful coverage but is not physical timing/cache/atomic evidence. Measure compile time/peak memory, code size, cycles/instruction/helper/trampoline, XDP/TC/tracing/LSM/scheduler workloads, p99/p999 overhead and power. Do not claim parity from one JIT microbenchmark.

## 6. Helpers, kfuncs and subsystem contexts

**Authority:** [kfunc documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/kfuncs.rst) explicitly says kfuncs are not stable across kernel releases and defines contextual/size/constant/nullable/uninitialized annotations. Baseline helper IDs/prototypes come from pinned UAPI and per-program-type implementations. [LSM BPF](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/prog_lsm.rst) demonstrates composition with prior hook return state.

1. Inventory every helper ID/kfunc set, program/attach-type eligibility, GPL/capability restrictions and side effects. Annotate argument/return ownership, sizes/nullability, trusted/RCU references, initialized memory, sleepability, preemption, lock/IRQ context and verifier invalidation after calls.
2. Implement helpers against actual Rust subsystem interfaces: maps/ring output, time/random/identity, packet/socket redirects and checksum changes, user/kernel probe reads, task/cgroup/storage access, timers/work callbacks, dynptr/refcount/list/tree objects, iterators and all baseline families. Network mutation can invalidate packet pointers; acquisition/release must match verifier obligations.
3. Expose kfunc/BTF IDs and annotations truthfully, with generated Rust adapters where needed for the prescribed calling convention. Do not expose Rust internal objects by unchecked pointer casting or generic `extern` signatures that mask missing lifetime/context rules.
4. Wire hook ordering and return interpretation across networking, tracing/perf, cgroups, security, scheduling, filesystem and other consumers. BPF-LSM cannot erase a prior denial where the hook composition contract forbids it. `struct_ops` callbacks must obey the scheduler/network ownership and failure model; safe Rust alone does not make arbitrary policy live-lock-free.

**Crate/shared:** project helpers/kfunc adapters, no universal helper crate. Generate decoder/verifier/execution prototype tables from one reviewed source, sharing object refs and context descriptors with owners; separately test actual behavior so metadata cannot simply assert itself correct. Aya helpers are program-side declarations, not kernel helper implementations.

**Simplification/security:** reduce duplicate adapter boilerplate, not program-type eligibility checks or semantic differences; don't replace unsupported helpers with no-op/zero results. Fault-safe reads, bounded output, namespace-correct identities, no sleeping in forbidden contexts and no leaked uninitialized/padding data are mandatory. Helpers can introduce logic, DMA or speculation flaws even when implementation is memory-safe.

**Optimize/test/done:** direct dispatch/JIT inlining and borrowed scatter-gather only where helper contract permits, never bypass security decisions. Tests cover every helper/kfunc × supported context, argument boundaries, ref/RCU/lock leaks, nullable/faulting reads, callbacks/races, policy chaining and rejected contexts; include pinned network/LSM/tracing/sched-ext/struct_ops suites as applicable. On real NICs/CPUs/NUMA, measure cycles/helper, hook throughput, callback tail and retained memory along with full server/scheduler workloads. Each untested context or hardware offload is a named blocker, not inferred support.

## 7. Maps, links, ring buffers and retained kernel objects

**Authority:** [map API/index](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/maps.rst), [BPF ringbuf](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/ringbuf.rst) and pinned UAPI/map implementations. The index explains that types differ, including operations they do not support.

### Ordered map-family workstreams

## 8. BTF, CO-RE and Rust/Linux type interoperability

**Authorities:** [BTF kernel and ELF contracts](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/btf.rst), [LLVM relocations](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/llvm_reloc.rst), [LSM BPF example](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/bpf/prog_lsm.rst) and [Aya BTF/CO-RE client](https://github.com/aya-rs/aya). `CO-RE` is compile-once/run-everywhere relocation **within supported type/feature contracts**, not a guarantee arbitrary C-internal fields exist in a rewritten Rust kernel.

1. Implement kernel BTF load/query/info and validation of every pinned kind, sizes, strings, type graphs, qualifiers/tags, enums/bitfields, functions/line data and split/module BTF relationships; maintain IDs/lifetimes through module/program unload. Bound cycles/depth/complexity without rejecting legitimate baseline inputs unnecessarily.
2. With [observability](observability.md), produce truthful Rust kernel/module BTF and accurate exported Linux-facing semantic views for tool-consumed types/hooks. Resolve rustc DWARF→BTF representation before claiming usable metadata. A C-style generated header for an external user program is data describing an ABI, not a C kernel implementation.
3. Preserve the loader/kernel division: ordinary ELF/.BTF.ext CO-RE relocations are largely handled by libbpf/Aya userspace against kernel BTF; kernel validates the resulting program/BTF/context accesses and implements kernel-side typed access/attach semantics. Do not move all ELF loading into the kernel or treat a user's relocation output as trusted.
4. Inventory exact existing workloads accessing `task_struct`, socket, scheduler, VFS, MM and security fields/functions. Provide a truthful, semantics-preserving view/adapter where needed, tested down to size/offset/access semantics; arbitrary Rust internal layout is not compatible simply because field names resemble Linux. If a view requires verified access conversion rather than actual raw layout, explicitly model it and restrict accesses according to pinned program rules.
5. Test field/type/enum existence/value/size/signedness/bitfield relocation, flavored names, module split types, kfunc prototypes and attach target matching; preserve errors/feature negotiation. Stable helper IDs and unstable kfunc/internal-type contracts need different maintenance expectations, but pinned compatibility still requires planned evidence rather than blanket dropping of unstable consumers.

**Crates/shared:** project hardened BTF validator/type registry. `aya-obj`/Aya are evaluation candidates for userspace parsing/relocation tests, not assumed kernel hardened or blanket layout generators. `gimli`/`object` candidates apply mainly to offline trusted artifact work with separate resource hardening. Share one type/symbol registry across perf/ftrace/LSM/modules/BPF; no invented duplicate type ID worlds.

**Simplification/invariants:** deduplicate immutable validated types and generate adapter metadata from reviewed definitions. Never fabricate offsets, publish a C-compatible pointer to differently laid-out Rust memory, expose internal references with invalid aliasing, or return empty BTF to claim the feature is present. Unresolved C-layout/semantic view coverage is a real implementation/toolchain blocker; “CO-RE handles it” is not a solution.

**Optimization/test/done:** hash/intern type shapes and cache relocation queries with generation-safe module lifetime; avoid repeated full type graph scans. Run actual libbpf/bpftool/Aya CO-RE test corpora and production tracing/security programs, cross-version supported relocation and bytecode load tests, malformed BTF/line offsets, module unload/reload and kfunc mismatch. Physical different-endian/word-size backends require actual output/runtime validation; measure BTF bytes/resident memory, parse/load/relocate/attach time, type-query p99 and compiler/conversion startup. No blanket audit or universal portability claim.

## 9. io_uring and other asynchronous trust crossovers

[Filesystems](filesystems.md) owns the complete io_uring ABI, buffer/ring mechanics and operation completion; [storage](storage.md) owns underlying block operation semantics and [security](security.md) owns authorization policy. This extension plan owns consistency with BPF/module/file lifetimes and extension attach contexts.

1. Enumerate every pinned io_uring registration, opcode, SQE flag, restriction/personality/credential interface, registered files/buffers, worker mode, cancellation and command extension touching security or extensible providers. Support only actual baseline BPF/io_uring interactions; do not invent newer hook types.
2. Associate submitted operations with the pinned subjective credential/personality, file and namespace snapshots; preserve LSM/capability/audit checks at required submission/issue/retry/completion points. Deferred workers cannot silently acquire worker-thread or host-root identity, and retained authority must not be spuriously dropped on a valid passed descriptor.
3. Keep map/program/module/device refs alive for asynchronous callbacks, command handlers, timers/task work and completion queues; cancellation and teardown need exactly-once resource release even if completion races close, exec, cgroup teardown, device removal or module unload.
4. Review seccomp boundary truth: filtering `io_uring_enter` is not filtering each SQE as a separate syscall. Preserve pinned ring restrictions and object checks; document approved hardening deltas transparently rather than disabling all rings or forbidding an opcode because its lifecycle is difficult.

**Crate/shared:** no io_uring userspace crate supplies kernel security semantics. Project adapters reuse request ownership, credentials, cancellation, RCU/module refs, audit and VFS/device security entrypoints; project helper metadata is generated with actual provider constraints.

**Simplification/security/optimization:** typed submit/issue/completing/cancelled states and shared ref guards reduce duplicated cleanup; they do not permit assuming a request belongs to one thread or one lifetime. Avoid metadata copies only with stable snapshots/pins; untrusted shared rings remain concurrently mutable. An authorization check over a mutable path/pointer cannot be cached indefinitely.

**Done tests:** per-opcode security differential tests through synchronous and SQPOLL/worker/registered modes as applicable, restricted rings, personality changes, sandbox/namespace/FD transfer, cancellation/retry/timeout and module/device teardown; adversarial ring metadata and OOM. Real NVMe/NIC and physical multi-core workloads measure IOPS/packets/bytes, p99/p999 completion and cancellation latency, copies/allocations, pinned memory, CPU and power. No throughput result qualifies a mode with wrong credentials, leaked refs or suppressed audit.

## 10. Concrete qualification execution and present blockers

The [actual bounded Rust smoke CLI](../bare-metal-suite.md) can run after the user manually boots a reference or future candidate:

```text
cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>
```

Choose one environment; the label is operator-provided, not proof of native hardware. That suite checks only its documented non-destructive userspace functions and identity. It does **not** load modules, install probes, enable unprivileged BPF, arm watchdogs, mutate host policy or prove JIT/verifier/CO-RE/driver parity. Preserve current working kernel/recovery entries and follow [packaging](../packaging.md). The bootstrap has neither Linux userspace support for this suite nor the extension implementations required by these future campaigns.

For the future full campaign, a concrete external entrypoint is `make -C <pinned-linux>/tools/testing/selftests TARGETS=bpf run_tests` after separately preparing matching external suite dependencies/configuration; invoke individual verifier, maps, helpers, CO-RE, attach, networking/LSM/struct_ops and architecture programs with their explicit manifests. Existing external suites may compile C/assembly user BPF and execute returned JIT bytes without becoming project-authored kernel languages. Record each executed test and skipped/unavailable case; external test build success or aggregate exit zero does not prove all programs ran. Module-signature/load/unload/relocation tests need real Rust replacement fixtures and per-architecture driver hardware, not legacy C kernel modules or no-op modules substituted for production functionality.

Only the current workstation is physically available. Unknown CPU/device capabilities must be inventoried; missing second x86 vendor, weak-ordering/big-endian/32-bit architectures, offload NICs and hotpluggable DMA devices are named qualification blockers until supplied. KVM/QEMU evidence and mathematical/host models complement but do not replace physical execution. Full tests require security-isolated lab networks, disposable filesystem targets and recovery consoles; no privileged mutation or destructive host action is authorized by this plan.

Performance release gates use [the shared methodology](../performance.md): same workload/hardware/firmware/compiler settings/security mitigations and configs; repeated measurements and confidence intervals for each program/map/helper/JIT/backend, not geometric-mean-only summaries. Report throughput and p50/p99/p999 latency, CPU, memory/code size, startup/verification/compile/load/unload and energy. Every case must be at least the pinned Linux baseline; inconclusive/missing results are not passes, and unsafe “faster” modes cannot substitute. Preserve input acceptance and output/security semantics before optimizing copies/allocations/dispatch/locking.

Open implementation prerequisites include full operation matrices, a reviewed Rust module ABI/provenance contract, compiler instrumentation/BTF compatibility views, a sound full verifier, every required JIT/helper/map/backend and the physical hardware matrix. These are explicit `not_started` work, not delivered scaffolding or assumed audited dependencies. Every security rejection/acceptance change, source provenance and unsupported-artifact boundary belongs in the central [compatibility ledger](../compatibility.md) and release evidence.
