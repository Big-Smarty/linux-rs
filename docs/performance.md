# Performance floor and optimization program

## Status, scope, and non-negotiable floor

**Performance qualification remains unexecuted; bootstrap implementation is underway.** The real x86_64 Rust bootstrap has bounded [cell9 QEMU, host-parser, lint and code-generation evidence](implementation.md), not a benchmark campaign. QEMU case durations, PIT correctness checks and artifact inspection do not establish Linux performance. The behavioral/performance reference remains upstream Linux **6.18.57**, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`, not installed CachyOS. Arch/CachyOS is first userspace; a patched-kernel comparison must be separately labelled. The initial **balanced server** profile keeps throughput, latency, fairness, memory, startup and energy as independent requirements.

The release requirement is at least the reference Linux performance in every required, measured workload/configuration/platform/metric cell. There is **no permitted regression margin** and no security-off exemption. This is an empirical qualification requirement, not a mathematical guarantee over all possible programs, future devices, or inputs. Expanding the workload/device inventory remains necessary throughout maintenance. An untested cell, statistically inconclusive comparison, unsupported measurement, or missing physical machine is **not a pass**. A microbenchmark win cannot establish Linux parity.

The accepted architecture is a modular monolithic Rust kernel, with fixed upstream 6.18.57 feature scope plus explicit reviewed security deltas. Later feature-baseline changes require a separate decision; arbitrary third-party/proprietary out-of-tree modules are not implicitly added, while every in-baseline module's functionality remains required as a Rust replacement. Security deltas must be identified in the experiment manifest and protection-equivalence review; they cannot become an undocumented benchmark exemption. Unavoidable function-local `asm!`/`naked_asm!` requires documented correctness contracts and disassembly review; standalone assembly and `global_asm!` are not optimization escape routes.

Read with [verification](verification.md), [physical development](bare-metal.md), [operator suite](bare-metal-suite.md), [packaging](packaging.md), [standing definition of done](definition-of-done.md), [toolchains](toolchain.md), [coverage](coverage.md), and [roadmap](roadmap.md). The current workstation is the only authorized physical target; extra lab systems below are proposals, not acquired assets. The user personally selects and boots a future candidate package and returns evidence. Nothing in this plan authorizes host installation, reboot, disk destruction, or firmware changes. The actual bounded Rust smoke runner validates only its exercised functional cases; it does not implement this performance campaign or certify the floor.

## Five design answers

1. **Which existing Rust crates can be reused?** Start project-owned host analysis/orchestration with `std`; `hdrhistogram` and `statrs` are evaluation-only host candidates, subject to the [dependency review](dependencies.md), numerical-method review and independent oracle comparison described below, not kernel dependencies. `criterion` cannot be the sole end-to-end qualification tool. Existing external `perf`, fio, iperf3, netperf, rt-tests, schbench, lmbench, application binaries and reference Linux are separately permitted non-Rust test dependencies; pin their provenance, versions, build flags, licenses and hashes. Project-owned executables remain Rust; candidate functionality must not secretly delegate to a Linux/C kernel runtime.
2. **What should be bundled or shared?** Share experiment manifests, clock calibration, topology discovery, histogram formats, immutable artifact storage, statistical analysis, and regression attribution across subsystem owners. Keep workload-specific setup explicit; a single synthetic score is not a shared correctness oracle.
3. **What can be simplified safely?** Begin with a fixed x86_64 balanced-server configuration and deterministic datasets. Limit the first measurement campaign, not final compatibility scope. Use external wall-clock/load-generator instrumentation before the candidate PMU interface exists, but leave the missing PMU metric blocked. Do not simplify by skipping mitigation, fsync, cgroup, error, NUMA, or tail-latency behavior.
4. **How is security preserved?** Require semantic, isolation, adversarial and recovery gates before timing; compare actual protection equivalence for mitigations, IOMMU, privilege/LSM/seccomp and integrity settings, not command-line spelling. Record approved security deltas and rebaseline affected campaigns. Diagnostic and release-equivalent builds retain required protections; security regressions disqualify a candidate before performance analysis, and debug overhead never justifies deleting required correctness instrumentation.
5. **What can be improved?** Profile first, then remove avoidable allocations, copies, cache misses, global contention, unnecessary wakeups, and I/O round trips while retaining safety and Linux behavior. Every change must improve its target without failing any required cell. Unsafe shortcuts, unlimited pinning, or busy-polling that trades away energy/fairness do not qualify merely because one throughput number rises.

**Additional direct-port obligation:** preserve Linux-visible scheduler/futex/timer semantics, accounting, reclaim/OOM behavior, filesystem durability, network ordering/backpressure, cgroup isolation, and mitigation policy. Performance work cannot replace these with cheaper incompatible behavior. Port the necessary PMU/perf and accounting interfaces as real Rust subsystems, not fabricated counters or C wrappers.

## Correctness and security precede timing

A workload is eligible only after its dependency slice passes semantic differential/regression, isolation, race/stress, recovery, and adversarial checks in [verification](verification.md). Required results include exact completed-work accounting, output/checksum correctness, no lost requests or hidden retries, correct errors and signals, fair resource control, and durability after acknowledged flushes. Faster error returns, skipped packets, failed allocations, dropped transactions, stale reads, or delayed accounting are not speedups.

Use diagnostic builds for fault finding and release-equivalent builds for the floor; both must implement the same semantics and required security policy. Disable debug instrumentation equally only when it is not part of the shipped protection contract, and preserve separate instrumented evidence. Sanitizer overhead is not an excuse for deleting instrumentation from correctness campaigns. Security regressions disqualify a candidate before performance analysis, even if all timing cells appear faster.

At each load point report the whole vector: throughput; p50/p95/p99/p99.9 and observed maximum latency; jitter/deadline misses where relevant; user/system/total CPU time; cycles and instructions per unit useful work; peak/steady-state kernel memory and userspace RSS; achieved data/memory bandwidth and traffic per work where measurable; boot/startup time; idle power and energy per useful work. Do not count a lower traffic volume as better bandwidth, or higher throughput as lower CPU cost without normalization. Metrics genuinely unrelated to a workload can attach to its platform campaign instead, with a recorded rationale; they cannot vanish from platform qualification.

Choose offered-load points in advance from reference calibration: idle/light, moderate, near the reference saturation knee, and overload. Preserve absolute offered rates for both kernels; do not compare each kernel only at its own best point. Sweep CPU count and queue depth at fixed predefined points and record both affinity-controlled and ordinary scheduler-placement cases. Balanced mode retains normal idle and power management for its primary profile; a separately labelled fixed-frequency diagnostic profile does not certify it.

## Repeated measurements and zero-margin decision rule

The following is the proposed enforceable analysis policy, not a claim that a chosen sample count guarantees adequate precision.

1. **Preregister.** Freeze required cells, load points, metric definitions/directions, primary analysis, expected relevant effect sizes, noise thresholds, invalidation rules, and sample plan before examining candidate comparisons. Use a reference-only pilot to estimate variance and determine power. Start with at least 30 paired observations across at least five independent boot blocks per kernel for ordinary qualification; extend the preregistered design where pilot power/tail counts require more. Long destructive/boot tests need their own justified independent-run design, not an unrecorded reduction.
2. **Pair and randomize.** Alternate/randomize reference and candidate order within blocks, balance order across the campaign, and record seeds. Restore the same dataset and precondition device state, warmup, thermal state, power policy, and cache regime each time. Multiple samples in a single boot are correlated, not independent reboot replicates. Cold and warm caches are separate cells; clearing caches alone does not restore device or filesystem state.
3. **Control noise.** Isolate unrelated tasks without masking realistic workload interference, fix peer load, and monitor temperature, frequency, throttling, interrupts, background services, storage wear/GC and link health. Keep noisy-neighbor stress deliberate and symmetric. If conditions drift or control/reference repeatability fails a predeclared limit, mark the block invalid, retain it with reasons, and rerun a whole balanced block. Never discard slow candidate points as outliers merely for being slow.
4. **Retain raw data.** Archive every run, histogram/time series, request count, error, start/end marker, boot log, kernel warning, exit status, environmental observation, and tool version. Record timeouts/crashes as failed correctness/availability cells, not samples omitted from a mean. Preserve the worst observations and distribution shape.
5. **Estimate benefit.** For positive-valued higher-is-better metrics use log(candidate/reference); for positive-valued lower-is-better metrics use log(reference/candidate). Thus zero is exact parity and positive is improvement. Zero-valued reference metrics (for example no deadline misses) need a preregistered absolute-difference/count analysis and must not divide by zero. Any forbidden event remains a failure regardless of statistics.
6. **Respect dependence.** Derive one-sided confidence bounds for each predefined estimator, using paired block/boot-level resampling or another justified model; do not bootstrap millions of correlated requests as millions of independent kernel trials. For tails, preserve per-run histograms/counts and use quantile uncertainty methods with enough observations beyond the target quantile. A short run with no meaningful p99.9 resolution is inconclusive; maximum observed latency is reported but is not a proof of a population worst-case bound.
7. **Correct multiplicity.** Use a preregistered one-sided **99% familywise** confidence level over all release-required comparisons (for example Bonferroni allocation `0.01 / K` across the frozen `K` comparisons with valid individual intervals). Record method, assumptions, estimator, sample counts and actual interval bounds. Do not add benchmarks post hoc without defining a new multiplicity-controlled family/campaign. Optional exploratory findings are labelled exploratory.
8. **Classify strictly.** A metric passes only when its simultaneous lower confidence bound on benefit is at least zero and all correctness/security gates pass. A bound crossing zero is **inconclusive**, even if the point estimate is faster or a difference test is nonsignificant. An upper bound below zero demonstrates regression; a negative point estimate without sufficient precision is still not a pass. Measurement systematic uncertainty belongs in the bound; if it prevents the zero-margin conclusion the cell stays inconclusive. Equality can be difficult to establish with finite noisy measurements; do not solve that difficulty by adding an arbitrary tolerated slowdown.
9. **Conjoin, never conceal.** Every required metric, load point, ABI, device, filesystem and physical platform must pass independently. Geometric means and aggregate scores may summarize, never override, a failing/inconclusive cell. A faster Intel host cannot offset a slower AMD host; throughput cannot buy a worse p99.9, memory footprint, security policy or energy cost.
10. **No optional stopping.** Use the frozen fixed sample plan, or a preregistered sequential procedure with valid error control and stopping boundaries. Repeatedly collecting until an ordinary interval first becomes favorable is invalid. If power/noise is insufficient, record inconclusive and design a new campaign, retaining prior data and decisions.

Linux `perf stat` supports repetitions, per-CPU output and machine-readable fields, but its average/stddev output is not this qualification rule. PMU multiplexing, event availability, counter scaling, privilege filters, overflow and observer overhead must be recorded. Prefer nonmultiplexed small event groups in separate matched diagnostic runs; validate PMU counts against external clocks/completed work. PMU names and semantics are model-specific: never compare raw counts across different machines as a kernel speed ratio. See [upstream perf-stat](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/tools/perf/Documentation/perf-stat.txt).

Energy measurements use the same calibrated external meter and integration boundary where possible; package energy counters supplement rather than replace whole-system energy. Account for counter wrap and sensor resolution; do not sum nested power domains twice. Kernel powercap documents `energy_uj` and `max_energy_range_uj`, and explicitly notes that Intel RAPL does not expose instantaneous power through that interface: [powercap](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/power/powercap/powercap.rst). No meter or supported counter means blocked energy evidence, not zero watts.

## Ordered implementation and baseline capture

1. **M0: specification and baseline.** Name workload/performance and platform owners, freeze balanced-server manifests and baseline build recipes, establish source provenance and analysis review, and register missing sensors/hardware/tools. Gather upstream Linux reference data first when the user authorizes a matching reference boot; installed-kernel data is only exploratory if it is not 6.18.57. This delivery captures no such data.
2. **M1: instrumented bring-up co-design.** Extend the current bounded bootstrap markers/timer evidence into reviewed clocks, boot IDs, external timeout/recovery and log collection alongside workstation safety design. Distinguish firmware-to-ready, kernel-entry-to-ready and application-ready boundaries; no application readiness exists yet. A storage-free diagnostic trial may precede rootfs/initramfs/storage/userspace on separate user-owned recoverable media with independent known-good recovery, applicable QEMU gates and explicit user execution. This is not a replacement-package or performance pass.
3. **M2–M4: component measurement.** After semantic gates, bring scheduler/MM/IPC/storage cases online with real accounting. Validate timing instrumentation, perf event capabilities and memory ownership. Run reference/candidate paired campaigns on available hardware; mark unsupported interfaces and absent physical evidence blocked.
4. **M5: first workload qualification.** Run unmodified Arch/CachyOS userspace services and container workloads on the physical workstation, with isolated sacrificial storage and test networking only where available/authorized. No synthetic workload may stand in for durable application/container I/O. Qualify only the exact observed configuration, never every Arch package or all x86 hardware.
5. **M6–M7: expansion.** Instantiate additional families, ABIs, vendors, NUMA, firmware, power and error conditions as their implementations and physical resources become available. Keep the all-architecture matrix in [bare metal](bare-metal.md) open. Missing resources block those cells, not correctness work that can proceed safely elsewhere.
6. **M8 and maintenance: independent review.** Reproduce all required floor decisions from immutable artifacts, have subsystem/security/platform owners sign exact scope, publish regressions and blocked cells, and refuse unrestricted Linux-parity release until the required closure exists. Rerun affected and cross-subsystem guardrail cells after changes to toolchain, mitigations, firmware or shared mechanisms.

Do not introduce a new crate merely to pursue a hypothesis. The initial analysis/orchestration design can use Rust standard-library facilities; statistics/histogram crates such as `hdrhistogram` or `statrs` are **evaluation candidates only**, subject to [dependency review](dependencies.md), numerical-method review and independent oracle comparison before selection. They are host-analysis candidates, not a proposed kernel dependency. Reject `criterion` as the sole end-to-end kernel qualification tool: isolated Rust microbenchmarks cannot cover physical boot, userspace ABI, durability or cross-kernel paired campaigns. Reject C FFI wrappers and Linux-module instrumentation as candidate-kernel implementation shortcuts; external reference tooling remains allowed. No crate or tool is an evidence substitute.

## Regression attribution and bisection

On any observed regression, freeze candidate/reference manifests and raw evidence, first check identical successful work and security/firmware/configuration, and reproduce using the same blinded paired design. Do not dismiss a user-reported failure by rerunning solely to disprove it. Classify source, compiler, firmware, workload or environment differences; retain environmental invalidations with reasons. Compare against both the pinned Linux floor and the last qualified Rust build.

When a performance-qualified baseline and suitable implementation history exist, bisect source changes with immutable build manifests and the same workload cells; an inconclusive revision stays inconclusive. Include compiler/flag/dependency bisection when source is unchanged. Confirm the suspected change using its parent and a narrowly reverted/fixed build, then rerun cross-subsystem guardrails. Repair the mechanism or revert the optimization; never lower the floor, trim workloads, disable mitigations or relax confidence. The current retained bootstrap failure/success history is real, but no performance bisection or qualified baseline is claimed.

## Explicit definition of done

A performance workstream is done only when all of the following hold for its declared scope, and whole-kernel performance remains incomplete until every required workstream/platform scope closes:

- The pinned reference and candidate are real, provenance-recorded binaries; root image, workload, compiler policy, device configuration and security equivalence are reviewable and reproducible.
- The workload inventory includes realistic applications, boundary/load/tail cases and each affected ABI/device/configuration, with exclusions justified in advance and no unsupported feature labelled pass.
- Semantic, stress, adversarial, isolation, durability/recovery and security prerequisites pass with actual artifacts; useful completed work matches the reference.
- All required throughput, tail/jitter, CPU/cycles, memory, bandwidth, boot/startup and power/energy cells have adequate independently structured observations and uncertainty analysis on each required platform.
- The zero-margin, multiplicity-controlled decision passes every required cell; no failed/inconclusive cell is concealed by an aggregate or tuning asymmetry.
- Physical evidence is actually available from user-operated runs for the workstation and from authorized operators for any later lab additions; QEMU evidence is separately labelled.
- Regressions are resolved and independently reviewed, optimization invariants documented, raw artifacts retained, and rerun/bisection procedures exercised as appropriate.
- Missing hardware, sensors, counters and measurements are explicit blockers. Real cell9 bootstrap artifacts exist, but no paired pinned-Linux baseline campaign, physical user report or performance-qualified artifact is recorded. The functional/codegen evidence does not satisfy these performance criteria.

## Primary measurement evidence

The documents below establish tool behavior and hardware interfaces, not results for this project. Moving external documentation must be resolved to a pinned tool revision before an experiment.
