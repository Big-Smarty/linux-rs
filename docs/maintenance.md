## Upstream change intake without a moving oracle

1. Monitor the 6.18 stable branch/releases, relevant mainline fixes and security announcements, subsystem lists, Rust/LLVM/toolchain advisories, crate advisories, firmware/microcode updates and external test suite changes. Intake must not depend only on CVE labels or commit messages containing “security.” The [upstream stable rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-kernel-rules.rst) describe real-bug fixes, dependency/backport requirements and a separate security path; they do not promise every important bug has a CVE.
2. Record each candidate delta with upstream commit(s)/release, affected source paths/symbols and ABI/config/arch/hardware cells, dependency chain, vulnerability or correctness/performance impact, applicability evidence, Rust analogue, responsible reviewer and disposition. File-based inventory routing is the starting point, not sufficient proof that a rewritten equivalent mechanism is unaffected.
3. Classify as required equivalent fix, already fixed with proof, architecture/configuration-inapplicable with proof, additional feature outside current pinned baseline, or unresolved. Unported mechanisms remain tracked: “not yet implemented” does not close a future security obligation. Uncertain impact is open, not not-applicable.
4. Port semantics and invariants, not blindly translate C edits or cherry-pick line ranges. Review integer widths, lifetime/aliasing, memory ordering, authorization, error ordering, state visibility, cancellation, rollback and crash consistency. A Rust rewrite may eliminate one C memory hazard while retaining the logic flaw or introducing a different one.
5. Add the upstream reproducer/test where usable plus Rust-specific tests, preserve the pre-fix result, run the affected differential/security/fault suites and full required candidate suite, then update evidence cells. Requalify hardware and performance affected by mitigations. A high-risk emergency fix can be shipped only with explicit limited evidence and unqualified status; it does not magically meet full-release gates.
6. Keep the exact 6.18.57 oracle immutable for historical comparisons. A security-fix overlay is separately identified by all commit hashes and behavior changes. Moving to a newer stable point or release requires a reviewed baseline decision, full tree/ABI/config inventory delta, regenerated reference artifacts, updated tests, regression comparisons against both old and new baselines, and revised performance/hardware evidence. Never silently relabel a modified reference as pristine 6.18.57.

Maintain an actionable per-delta disposition register rather than relying on a version string or cumulative “up to date” badge. A release with unresolved applicable security deltas cannot claim full security parity. No guaranteed response SLA is invented here: actual maintainers, secure contact, coverage hours and support commitments must exist before advertising a supported release.

## Security response and disclosure

Create a functioning private report channel with access-limited storage, on-call ownership, backup reviewers and a publication path before accepting production users. Reports need affected artifact/config/hardware, impact, minimal reproducer, logs and proposed mitigation where available; never require exploit publication as a condition of action. Acknowledge and investigate according to a published service policy once staffed; do not pretend these organizational resources exist now.

Use the upstream [security-bug process](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/security-bugs.rst) for relevant Linux-origin issues and coordinate with upstream when affected. Distinguish Linux's disclosure rules from this project's own service commitments and from distribution coordination. Preserve reporter confidentiality and embargo controls; do not put private exploit material into public test artifacts or unrestricted CI. CVE references are useful identifiers, not a completeness argument or proof of exploitability.

For each incident: reproduce safely; contain availability/data/security risk; identify all Rust and inherited mechanisms; review fix dependencies; create exploit/regression evidence under access controls; test negative permission paths and failure unwind; assess supported variants and firmware/toolchain interactions; package/sign and publish; provide rollback guidance and any filesystem/protocol migration constraints; disclose affected/fixed versions and evidence limits; then revisit threat models, fuzz corpora and missed review assumptions. User observations of failure remain ground truth; missing perfect logs does not erase them.

## Reproducible inputs and outputs

Reproducibility is a gate on specific artifacts, not the statement “Cargo.lock exists.” Record:

- Exact upstream tag, tag object, commit and tree; authenticated retrieval and independent signature/key verification state; Rust port provenance and preserved notices/per-file exceptions.
- Downstream source revision and source archive hash; submodules/vendor bytes if any; dependency graph/lockfile/checksums; registry/index snapshots and offline inputs; build scripts/proc macros and their executed code; external build tools and licenses.
- rustc/Cargo/LLVM/linker versions and hashes, compiler source/bootstrap provenance where required, target specification, flags, codegen/LTO/panic/relocation settings, CPU features, configuration and security-mitigation choices.
- Generated ABI tables/bindings and generator input/output hashes, image/linker metadata, initramfs contents/order/timestamps, firmware/microcode hashes/licenses/trust policy, test userspace/rootfs and external suite revisions.
- Locale/timezone/environment, source epoch, path remapping, user/host normalization, deterministic archive ordering, build salts/seeds and randomness policy, symbol/debug paths and strip/compression settings. Randomizing runtime mitigations must not be disabled to make builds deterministic.

The pinned [Linux reproducible-builds guide](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/kbuild/reproducible-builds.rst) identifies timestamps, user/host names, absolute paths, generated inputs, signatures, randomization seeds and vDSO debug collisions. Apply equivalent controls to the Rust image pipeline; do not assume Linux Kbuild variables configure a new Rust build automatically. Signing keys never belong in source or public build containers. Separate deterministic unsigned payload reproduction from detached signing/envelope steps; document any nondeterministic signature metadata rather than excluding arbitrary payload bytes from comparison.

Rebuild in two independently provisioned clean environments using the same declared inputs, compare all intended reproducible payloads byte-for-byte, retain hashes/logs, and explain any mismatch before release. Independently provisioned is stronger than rerunning the same compromised build worker; it still does not prove compiler trust or absence of malicious source. Reproducibility, signatures, review and behavioral testing are complementary evidence, not substitutes. Offline/restricted builds should expose undeclared network fetches or missing dependencies as failures.

## SBOM and provenance

Publish a machine-readable SPDX or CycloneDX SBOM with the chosen schema/version and a corresponding human-readable release inventory. Kernel payload, Rust modules, project-owned tools, external runtime firmware/microcode, build-only tools, external suites and test userspace have separate relationships and scopes. Include component name/version/revision/source/hash, license expression/notices, direct/transitive dependency edges, vendored/modified status, patch provenance and included/excluded artifact mapping. A Rust crate-only listing misses compiler runtimes, intrinsics, embedded blobs, generated tables and firmware; a list of upstream directories misses the actual binary contents.

Primary format authorities are the [SPDX specifications](https://spdx.dev/use/specifications/) and [CycloneDX specification overview](https://cyclonedx.org/specification/overview/). Choose and pin an actual schema before implementation; neither specification makes an incomplete generated inventory complete.

The concrete SBOM generator is an implementation choice pending [dependency review](dependencies.md), not an invented existing tool. Project-owned executable logic must be Rust. Validate schema and completeness against the actual artifact graph, inspect unexpected native build steps and machine code, and preserve per-file exceptions and GPL compliance material. License compatibility or source availability must not be inferred solely from a registry label.

Release provenance must link authenticated source inputs, build recipe/configuration/toolchain, builder identity and isolation, payload hashes, reproducibility results, SBOM, test/evidence manifests, signing identity, release approval and published downloads. Use signed attestations with a pinned documented format, trust root and rotation/revocation policy; merely writing “SLSA” does not confer a maturity level. Record bootloader/firmware trust separately from source/build signatures. Verify downloaded payloads before install and retain enough information to diagnose supply-chain compromise without exposing keys or machine serials.

## Configuration and support lifecycle

Maintain release matrices by architecture/userspace ABI, capability configuration, kernel/module modes, devices/firmware and deployment profile. The applicable universe comes from [compatibility](compatibility.md), not whichever cases CI currently owns. Separate experimental, qualified and no-longer-maintained releases; experimental does not mean passed. Removing a profile from advertised support must not erase an unresolved final-scope Linux obligation. Missing maintainers or hardware blocks new qualification and is published honestly.

A config change can invalidate more than its immediate subsystem: changing page size, preemption, allocator, mitigation, LSM, IOMMU, compiler optimization, scheduler or firmware may require broader ABI/security/performance/hardware reruns. Keep boot parameters, feature discovery, headers, module metadata and userspace tools coherent with the actual build. Preserve baseline-enabled, disabled and valid mutually exclusive configurations, rather than relying on one all-purpose defconfig.

## Arch deployment, updates, and rollback

Concrete artifact and boot-entry requirements are in [packaging](packaging.md). Historical manual cell9 ELFs remain intact; the maintained [build/package harness](kernel-tooling.md) produced source-bound final004 QEMU/default-profile evidence and the actual unsigned `diagnostic-001` archive. Separate visual/provider reviews, archive command/hash/mtree records and independent director format/source acceptance are identified in [diagnostic handoff](diagnostic-handoff.md#retained-historical-evidence-withdrawn001-and-earlier-cells). Read-only inspection, project-owned extraction and the successful new-copy packaged-source build did not install a package or change host boot/toolchain state. The source-hash freeze and immutable package remain binding: changed member/compiler inputs require fresh corresponding evidence, and later reviews append records rather than rewriting creation-time pending manifests. A storage-free M1 diagnostic trial may use separate user-owned recoverable media and independent known-good recovery before rootfs/initramfs/storage/userspace; it is not a Linux replacement. The later replacement package needs its own real kernel/initramfs/root/storage/userspace/modules/metadata and tested supported boot entries. Native Limine ELF does not supply systemd-boot EFI/PE or Linux boot compatibility. Preserve the installed known-good kernel/default/recovery; no automatic overwrite, default-switch or firmware change. Project-owned packaging remains Rust; external package/boot tools are separate inputs. The inspected archive is not signed, independently reproduced, an approved release SBOM, or completion of the release gates below.

Before a declared-scope user trial is ready, its complete applicable QEMU cases, artifact/provenance review, safe boot selection and independent recovery prerequisites must hold. A Linux-replacement package additionally requires install/remove/upgrade/rollback and real userspace/storage rehearsals; those gates are not waived by the diagnostic trial. The user personally boots and supplies physical observations. The [bare-metal smoke suite](bare-metal-suite.md) has not been run on the candidate kernel by a physical test and needs sockets that the declared configuration leaves off (see the [current support matrix](compatibility.md#current-support-matrix)); its environment label is not physical proof. No assistant-run installation, reboot, host firmware/device/mount change or destructive storage action is authorized.

Updates must account for disk feature flags, journal format, encryption/key availability, module/version mismatch, initramfs dependencies, bootloader discovery, secure-boot signatures, userspace compatibility and rollback behavior. Test interrupted download/install/update and recovery without corrupting the known-good slot. A new on-disk feature that old Linux cannot mount makes rollback nontrivial; do not promise it is safe merely because an older kernel entry remains. Migration requires explicit compatibility policy and recoverable data backups.

## Release gates and honest labels

All gates are conjunctive for the claim being made; [verification](verification.md) and [definition of done](definition-of-done.md) define the exact evidence levels.

| Gate | Required release evidence; failure disposition |
| --- | --- |
| Identity/provenance | Pinned baseline and all overlays; source/license notices; authentic input verification state; reproducible payload and validated SBOM/provenance; unresolved trust/license mismatch blocks a qualified release. |
| Implementation completeness | Every claimed obligation maps to reachable Rust implementation with reviewed invariants and caller/config migration. Every final-scope obligation remains visible. No stubs, fake success, C module execution, directory-count proxy, or unsupported-as-pass shortcut. |
| Behavioral correctness | Full applicable QEMU suite, Linux differential/layout/error/race/negative cases, appropriate LTP/kselftest/fstests/blktests/packetdrill and real Arch/CachyOS workloads. Required skip/not-run/unknown outcome blocks the corresponding qualification. |
| Security | Applicable stable/security/toolchain/firmware deltas dispositioned; authorization/unsafe/concurrency review; adversarial/fuzz/fault results; mitigations and boot/module trust exercised. A CVE-free search or crash-free interval alone is insufficient. |
| Persistence/recovery | Applicable crash/durability/interoperability/error paths and deployment rollback demonstrated; sacrificial physical-media evidence where required. VM resets alone cannot close physical power-loss obligations. |
| Physical platform | Actual user-reported boot/workloads/device/recovery evidence for the exact artifact and workstation; all additional required hardware cells remain blocked until genuinely available and exercised. Never relabel QEMU as physical proof. |
| Performance | Per-workload/per-hardware throughput, latency/tails, CPU, memory, startup and power meet pinned Linux under equivalent configurations/security and controlled repeated measurements. Uncertain/unproven non-inferiority or hidden individual regressions blocks the pass. See [performance](performance.md). |
| Packaging/operations | Actual separate replacement artifacts, tested supported Limine/systemd-boot paths, preserved known-good boot, complete source/checksum/signature/evidence publication and verified update/recovery. The current bootstrap ELF is real but does not satisfy these Linux-replacement gates; a storage-free diagnostic handoff has a separate limited scope. |
| Claim review | Reviewers approve exact scope and evidence level, publish failures/unqualified cells and known differences, and verify no tooling smoke/audit is reported as kernel proof. Full Linux claim requires M8 closure, not merely a testable preview. |
