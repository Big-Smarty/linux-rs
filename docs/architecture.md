# Architecture and engineering program

## Status, authority, and reference

This document specifies the **accepted modular monolithic kernel direction**, its remaining proposed mechanisms, and the bounded implementation now underway. A real Rust `no_std` x86_64 bootstrap exists in `kernel/`; [implementation and evidence](implementation.md) separates frozen historical artifacts from subsequent source revisions and actual results. **M1 is in progress, not complete**; M2–M8 and full Linux compatibility remain open. The canonical [routing table](implementation.md#routed-implementation-status) identifies `in_progress` workstreams, not completed ports; all other workstreams remain `not_started`. M0 is not automatically complete because documents or a boot exist. Approved constraints, engineering choices and unresolved obligations are separated in the [decision register](decisions.md); implementation order is in the [roadmap](roadmap.md).

The exact initial behavioral reference is upstream Linux **6.18.57**, tag `v6.18.57`, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`. The [reference metadata](../planning/reference.tsv) preserves object identity and authentication status. The original inventory relied on GitHub-reported verification; subsequent local kernel.org/GitHub fetches matched, and isolated GPG verification produced a good signature from fingerprint `647F28654894E3BD457199BE38DBBDC86092693E`, pinned through kernel.org HTTPS/WKD. GPG reported `TRUST_UNDEFINED`/`[unknown]`, not Web-of-Trust or ultimate trust. [Source evidence](implementation.md#pinned-source-and-specification-map) does not discharge independent review or release provenance obligations. The userspace target starts with **Arch/CachyOS userspace**, not CachyOS kernel patches. The initial performance profile is **balanced server**; other workloads and architectures remain in scope.

Approved decisions include a GPL-2.0-only direct-source port, Rust-only kernel/project executables, provenance-controlled external firmware, and no legacy C kernel module loading or C-backed kernel runtime. See [licensing](licensing.md). Baseline source is evidence to translate and test, not permission to copy unidentified or incompatible code.

The initial engineering cell uses the maintained `x86_64-unknown-none` target, Limine base revision5 with explicit four-level paging, external Limine12.9.3 and q35/OVMF UEFI64, one executing BSP and4KiB pages. Checked firmware discovery, frame ownership, owned CR3, guarded stacks, exception and PIT/PIC consumers exist; they are not full Linux subsystem ports. Non-error entries retain the compiler ABI; the independently confirmed hardware-error-code lowering defect now has a [minimal local-assembly repair and genuine before/after proof](implementation.md#error-code-entry-defect-reproduction-and-repair). The old artifacts remain physically withdrawn. QEMU self-test adds serial/debug-exit; the separate diagnostic excludes COM1/f4. Exact evidence and outstanding review delimit every claim; no userspace, storage, physical or performance parity is implied.

## End state and compatibility boundary

The intended end state includes every baseline architecture, supported device/driver family, filesystem, protocol, kernel facility, userspace ABI, build/configuration mechanism, documentation and test workstream. The [coverage inventory](coverage.md) assigns pinned source paths to plans, but a path assignment is not per-device or per-ABI completion. All such units need downstream implementation, failure-path, security, test and maintenance evidence before closure.

The user-approved feature/behavior inventory is fixed to upstream 6.18.57, with explicitly reviewed security deltas recorded against the immutable oracle and affected cells requalified. Later feature-baseline changes need a separate decision; release cadence, staffing/resources, delta approval workflow and version naming remain unresolved. Every in-baseline module's functionality must become a Rust replacement with no legacy C execution. Arbitrary third-party/proprietary out-of-tree module functionality requires separate enumeration and approval, not an automatic scope commitment.

The compatibility surface includes:

- Architecture-specific syscall numbering/calling conventions, compat ABIs, errno and restart behavior, registers, alignment, endian and time representations, signal frames, vDSO and auxiliary vectors.
- ELF execution, dynamic loading prerequisites, process/thread lifecycle, scheduling and resource limits, futexes, signals, timers, memory mapping, shared memory, pipes and other IPC.
- VFS pathname and permission semantics, mount propagation, pseudo filesystems, file locking, mmap/writeback, ioctls, device nodes and stable storage ordering/recovery.
- Networking families/protocols, sockets, netlink and ioctls, routing, filtering, traffic control, namespaces, device configuration and legacy behaviors still present in the baseline.
- Credentials, capabilities, LSM policy hooks, integrity, cryptographic interfaces, seccomp, audit, resource controls, namespaces and cgroups; server/container isolation is not just launching a shell.
- Device/firmware lifecycle, DMA/IOMMU, interrupts, hotplug, power, suspend/resume, accelerators, graphics/audio/input, embedded and real-time operation, host/guest virtualization, tracing/perf/debug/crash and extension interfaces.

[Linux ABI documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/ABI/README) distinguishes stable/testing/obsolete/removed interfaces and explicitly excludes Kconfig and internal symbols from stable ABI. [Linux internal driver guidance](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-api-nonsense.rst) likewise distinguishes userspace compatibility from internal implementation interfaces. Therefore the proposal preserves observable behavior, not C object layouts or an internal binary module ABI. A narrow server boot does not satisfy full scope; unsupported return-code stubs are not implementations.

## Conservative kernel shape

**Accepted by the user:** a modular monolithic Rust kernel with a single privileged runtime and explicit subsystem boundaries. The detailed design recommendation is to keep Linux's proven behavioral model and port mechanisms conservatively before redesigning algorithms. This minimizes new IPC/ABI translation and failure-mode complexity relative to a microkernel or userspace-service rewrite; it does not itself prove performance or soundness. Internal Rust APIs may change in a single coordinated cutover when all callers and evidence are migrated.

Start with built-in Rust drivers and facilities to reduce bring-up variables. Implement loadable **Rust** modules later without weakening the no-legacy-C-module decision. A module depends on the exact kernel build/configuration/toolchain contract; no stable third-party Rust compiler ABI is assumed. Load, unload, symbol resolution, policy, signing and userspace-visible module behavior require real design and tests, not a permanent all-built-in escape hatch. See [extensions](subsystems/extensions.md).

A global async executor is not the scheduler. Core process scheduling, IRQ completion, wait queues and worker execution must have explicit Linux-compatible semantics. Ordinary host runtimes such as Tokio, `std::thread`, host mutexes or the upstream C-backed Rust-for-Linux abstractions are not a kernel runtime. Their use in host tools is a separate admission decision.

### Logical layers, not pre-created crates

The following dependency direction is proposed. These are responsibilities, not a promise that each becomes a separate Cargo crate or that these paths already exist.

| Layer | Responsibilities | Dependency rule |
| --- | --- | --- |
| Compiler/core substrate | `core`, target/compiler support, intrinsics, minimal runtime symbols, panic/abort and linker contract | No host libc, C helpers, OS-dependent runtime or implicit allocator |
| Architecture/platform boundary | Entry/return, traps, CPU state, barriers, page tables/TLB, clocks, interrupt controllers, firmware handoff | Depends on core; exposes reviewed narrow primitives, not generic device/business logic |
| Kernel mechanisms | Page/object allocation, references, locks, RCU, wait queues, timers, workers, usercopy, DMA and resource ownership | Owns cross-subsystem invariants; no dependency cycle through leaf drivers |
| Services | Tasks/processes, VFS/block, networking, IPC, credentials/isolation and device model | Uses shared mechanisms; stable internal abstractions only as useful, no premature general framework |
| Families and leaf implementations | Filesystems, protocols, buses/drivers, architecture-specific services, virtual machines and Rust extensions | Depend on service contracts; no bypass of raw hardware/lifetime checks without documented necessity |
| ABI façades | Syscall, ioctl/netlink, proc/sysfs, perf/eBPF/KVM and architecture compatibility entry points | Translate Linux ABI into internal types without redefining external layouts or errno |
| Host tooling | Planning audit and bounded userspace smoke runner; maintained kernel build/QEMU interfaces in [kernel tooling](kernel-tooling.md); broader configuration, packaging and qualification remain separately gated | May use `std`; never linked into the kernel; project-owned executable logic stays Rust |

Keep parsing/algorithmic code independently testable under host `std` when identical semantics can be preserved; kernel execution-context and device behavior still need kernel/hardware tests. Split crates only at independently useful dependency/unsafe/configuration boundaries. A crate per upstream file would add complexity without proving separation. Share foundational mechanisms rather than importing multiple allocator, locking, bitmap, endian or reference-count implementations.

[Upstream Rust information](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/rust/general-information.rst) establishes `no_std` and safe-abstraction layering, but its C bindings/helpers are specifically **not** an admissible runtime here. Adapt ideas and source-derived Rust logic only after dependency/provenance review. Candidate external crates and rejection reasons live in [dependencies](dependencies.md); no dependency is approved merely because it builds with `no_std`.

## Ownership and lifetime boundaries

1. **Physical memory:** allocator owns each page extent until explicitly transferred. Represent physical addresses, virtual addresses, page numbers and device bus addresses as distinct checked types; arithmetic and range-overflow checks precede mapping. Reserved/firmware/MMIO regions never become ordinary RAM by cast.
2. **Mappings:** an address-space object owns page-table roots and mapping metadata. Mapped pages outlive translations; permissions, TLB invalidation, cross-CPU shootdowns and references complete before recycling. Shared mappings have explicit accounting and reclamation ownership. Never manufacture long-lived Rust references from arbitrary user addresses.
3. **Heap and object graphs:** prefer unique ownership and borrowed access. Use shared references only when the actual process/VFS/device graph requires them; refcounts cannot wrap or resurrect dead objects. Break cycles intentionally. Intrusive collections require pinning/lifetime contracts, not assumptions about stable addresses. A reference count does not serialize mutable state.
4. **Userspace:** user pointers remain validated descriptors, not trusted `&T`. Fault-aware copy/access routines define partial progress, access checks, pinning and fault/retry behavior. Snapshot user-controlled length/metadata as required to avoid double-fetch races; preserve Linux-visible concurrent-mutation semantics rather than adding arbitrary validation.
5. **DMA:** device ownership and CPU ownership of buffers are explicit transitions. Mapping includes device mask, IOMMU isolation, coherency/synchronization, direction, alignment and teardown. Rust aliasing, volatile reads and atomic fences alone do not establish a device's DMA contract. In-flight requests must quiesce before freeing memory or detaching a driver.
6. **Devices/modules:** registration publishes only fully initialized state. Removal first stops new users, then masks/quiesces hardware and drains callbacks/work/IRQs/DMA/RCU readers before destruction. Unload must not invalidate code reachable by interrupts, function pointers or deferred work.
7. **Deferred destruction:** object release may need worker context or an RCU grace period; `Drop` cannot silently sleep from IRQ/NMI context. Separate infallible bookkeeping from context-permitted teardown. Cancellation, allocation failure and partial initialization unwind release resources in dependency-reverse order.

[Upstream RCU](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/RCU/whatisRCU.rst) explicitly separates removal from reclamation and requires old readers to finish before reclaim. The Rust abstraction must prove that lifecycle together with the actual CPU memory model; naming something `Rcu` or adding `Arc` is not proof.

## Execution contexts, locking and allocation

Every exported kernel-internal operation documents: allowed contexts; may-sleep and may-fault behavior; allocation/reclaim/IO recursion; locks and ordering; preemption/migration/IRQ state; and object lifetime/cancellation rules. Use capability/guard types where they catch real misuse without allocations or dynamic checks on hot paths; supplement with debug assertions and lock-dependency tracking.

| Context | Permitted model | Prohibited assumptions |
| --- | --- | --- |
| Early boot | Bounded reserved arenas and explicitly initialized hardware; transition ownership to mature allocators | Full scheduler, heap, worker threads, completed SMP or firmware availability |
| Sleepable task | Fallible allocation with explicit reclaim/IO policy; sleeping locks and blocking waits when safe | Sleeping while holding raw locks, within non-sleeping RCU sections, or across incompatible recursion |
| Atomic/preemption-disabled | Bounded work; raw spinlocks/atomics; explicit non-sleeping allocation or preallocation | Sleeping allocation, blocking waits, implicit task migration, unrestricted faulting usercopy |
| Hard IRQ/softirq | Context-specific synchronization, correct interrupt masking/restoration, deferred sleepable work | A task mutex or one generic critical-section wrapper is automatically safe |
| NMI/exception-critical | Minimal reentrant or specially reserved facilities with documented nesting and emergency paths | Ordinary locks, logging, allocation or per-CPU state access is necessarily safe |
| Per-CPU access | Guard pins migration/preemption/IRQ state as the data requires | Disabling local interrupts excludes another CPU or pins a task on all RT configurations |

[Linux locking rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/locking/locktypes.rst) distinguish sleeping, CPU-local and spinning locks, and PREEMPT_RT changes ordinary spinlock/local-lock behavior. The proposed APIs must distinguish strict raw spinning from RT-aware ordinary locking; final RT support is not compatible with blindly replacing every Linux lock by a generic Rust spin mutex. Guards restore the prior state, are not transferable to another task/CPU when ownership forbids it, and cannot be held across incompatible waits/callbacks. Publish a partial lock-order graph, ownership rules and IRQ nesting model before parallel subsystem implementation; model-check representative races and test contention, PI and starvation.

Kernel allocation is **fallible and context-aware**, not a global no-heap policy. Provide page, slab/object and virtually contiguous allocators with explicit accounting, locality, alignment and reclaim/no-IO/no-FS policy. Avoid an infallible allocation API in paths where Linux reports failure or must preserve forward progress. A generic global allocator cannot encode every context requirement. Non-sleeping requests have preallocation/reserves or a real tested failure path, not arbitrary retry loops. Reclaim must not re-enter locked filesystem/block paths. Untrusted allocations consume the correct resource account. See [memory](subsystems/memory.md) and [Linux's allocation guide](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/core-api/memory-allocation.rst).

## Unsafe, inline assembly and runtime purity

Most subsystem code should consume safe abstractions; the architectural boundary, allocators, concurrency primitives, DMA, usercopy and low-level intrusive ownership require reviewed unsafe internals. Each unsafe operation has a local safety argument; public unsafe interfaces state caller obligations and invalidate no safe caller's assumptions. Review all unsafe `Send`/`Sync`, aliasing, provenance, uninitialized storage, pinning, interrupt reentrancy and memory ordering. A safe wrapper around an unsound primitive is not acceptable.

Unavoidable inline assembly must record the operation and architectural source, why Rust/intrinsics cannot express it, ABI and stack state, inputs/outputs/clobbers, memory and ordering effects, interrupt/privilege assumptions, entry/exit state, reviewers, disassembly checks and a test mapping. Do not misuse `nomem`, `nostack` or `preserves_flags`. Compiler fences are not automatically hardware/device fences. [The Rust assembly reference](https://doc.rust-lang.org/reference/inline-assembly.html) distinguishes `asm!`, `naked_asm!`, and `global_asm!`. The user permits both function-local `asm!` and `naked_asm!` only when unavoidable with the documented proofs; `global_asm!` and standalone assembly escapes are prohibited. Per-operation necessity and safety review remains mandatory. Unsupported targets are blockers for toolchain work, not permission to add `.S` files.

No C/C++/Zig implementation, standalone assembly, hidden C compiler build scripts, C-backed allocator/locks, legacy binary modules or incremental C kernel coexistence. External rustc/LLVM/linker/firmware are allowed boundaries with records. `repr(C)` expresses ABI layout, not implementation language. Inspect actual undefined symbols, dependency/build graphs and disassembly as well as source extensions: the host audit's lexical checks do not prove runtime purity. The current cell selects panic-abort/no unwinding with bounded diagnostic stop and no automatic reboot as an engineering decision; broader Linux panic/crash/recovery semantics and independent review remain open. This is not proof panic can never occur.

## Build, configuration, debugging and documentation

**Current:** the workspace contains the kernel bootstrap as well as the separate host audit and bounded functional smoke tools. [Implementation evidence](implementation.md#executable-interfaces-and-evidence-status) records actual build commands, eight cell9 QEMU cases, five host production-parser tests and strict owned Clippy results; [kernel tooling](kernel-tooling.md) owns the maintained executable interface and its own run records. Neither a command description nor the manual cell9 runs establish a later harness pass. Host tools retain MSRV 1.88, separate from kernel manifest 1.101 and the runtime ABI-qualified rustc `1.101.0-nightly` commit `5c543b0b8c73c7b72bc8284ced4fb22ead15734d`/LLVM 23.1.1 with matching `rust-src` and rebuilt Rust `core`/`compiler_builtins`. The mutable nightly alias is not an immutable compiler identity. Declarative linker/layout/configuration data are not executable-language loopholes. Broader targets, configuration, instrumentation and runtime contracts still need their own qualification; [rustc platform tiers](https://doc.rust-lang.org/rustc/platform-support.html) do not establish kernel parity.

Configuration must preserve Linux feature dependencies, built-in/module distinctions and relevant userspace consequences without claiming Kconfig is a stable internal ABI. Recommended build manifests capture source commit, config and its generator, compiler/linker versions and flags, target/CPU features, lockfile, firmware/rootfs/image hashes, debug instrumentation, security mitigations and reproducibility evidence. Keep debug/instrumented and optimized qualification images separately identified; compare production profiles fairly. Pin a reference Linux build and rootfs per matrix cell; compilation settings must be controlled and comparable, with unavoidable language/tool differences explicitly documented, never hidden as a benchmark advantage.

Early debugging requires serial/diagnostic logs, deterministic QEMU replay where supported, symbolized backtraces, debugger access, exception/IRQ context dumps and a documented recovery route. Physical machines need local/remote console or a proven alternative, a known-good boot selection, crash persistence and manual recovery before candidate execution. No automatic install, reboot or boot-config edits on the user's workstation. An isolated storage-free M1 diagnostic trial may use separate user-owned recoverable media before rootfs/initramfs/userspace exist; it is not a Linux-replacement package. The approved eventual Arch/AUR-like package must satisfy the real storage, filesystem, root, initramfs, init/userspace and Limine/systemd-boot contracts without replacing the working kernel. Exact generated packaging metadata/build hooks must respect Rust-only project executable logic; see [packaging](packaging.md).

Organize design/rationale in these [indexed documents](README.md), subsystem contracts beside their plans and later code, safety obligations in rustdoc/local comments, executable test definitions in the Rust-owned suite, and raw evidence in immutable run artifacts. Documentation must identify observed facts, proposed choices and unresolved prerequisites. Generated configuration/docs must match the tested build rather than silently default to a host build.

## Performance, physical hardware and correctness together

At-least-Linux performance is a **release requirement**, not an expectation made true by Rust or a monolithic design. Per [performance](performance.md), qualify throughput, latency/tails, CPU, memory, startup and power per workload and hardware cell. Use fixed seeds/workloads/rootfs, comparable compilers/configuration, equal mitigation/security policies, controlled topology/NUMA/governors/thermals/storage/firmware, repetitions and confidence intervals. No arbitrary regression allowance, aggregate-only masking or weakening security to win. Inconclusive results are not passes. Optimize only after semantic proof, then remove demonstrated avoidable allocation/copy/locking/cache overhead without changing Linux behavior or regressions elsewhere.

Bare metal is co-developed from M1, not a late M8 exercise. Only the user's current workstation is available now, and the user will personally select/boot/test candidates and return results. Its exact qualified features, safe recovery, console and destructive-test isolation must be recorded; availability is not automatic authorization to touch disks or reboot. Missing multi-vendor, NUMA, platform, IOMMU, device, RT or architecture access remains a named blocker. VM evidence does not substitute. [Bare-metal policy](bare-metal.md) stages nondestructive checks first and requires sacrificial storage/isolated networks for separately authorized destructive/fault qualification. The actual [smoke runner](bare-metal-suite.md) is deliberately narrower: bounded sandboxed functional checks, no mounts, raw writes, elevation, configuration changes, firmware updates or reboots, explicit outcomes and privacy-preserving metadata. Its environment label is an operator assertion. A reference-host run proves neither a candidate kernel nor physical qualification.

Linux's [testing overview](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/dev-tools/testing-overview.rst) distinguishes white-box KUnit from userspace kselftest and dynamic analysis. Here, Rust unit/model/property tests exercise internal mechanisms; eligible external userspace kselftests/LTP and real applications test Linux behavior; C companion kernel modules must be ported or otherwise replaced, never loaded as an exception. Add differential traces, fuzzing, concurrency stress, OOM/fault injection, corrupt inputs, crash/recovery and security tests. Host tests do not prove privileged code, real DMA or power behavior. Actual QEMU and physical smoke execution are mandatory when kernels exist. See [verification](verification.md) and [definition of done](definition-of-done.md).

## Integration, staffing and risk ownership

No dates or sufficient headcount are invented. Work is gate-driven; roles may be combined only when review independence and lab coverage remain credible.

| Role | Required ownership |
| --- | --- |
| Architecture/integration maintainer | Shared contracts, dependency DAG, cross-subsystem changes, configuration and scope ledger |
| ABI/userspace owner | Differential reference, architecture compat ABIs, Arch/CachyOS rootfs and application regressions |
| Core/MM/concurrency owners | Allocators, scheduling, ordering, locking/RCU, reclaim, RT and NUMA |
| Storage/filesystem and network owners | Durability/protocol semantics, traffic/load/recovery tests and shared-path performance |
| Architecture/driver/firmware owners | Boot entry, CPU/platform/device families, DMA/IOMMU, lifecycle and real-platform access |
| Security/unsafe reviewers | Independent soundness and threat review, mitigations, vulnerability triage and provenance of fixes |
| Verification/performance/lab owners | Runnable test definitions, fair paired measurements, artifacts, noise analysis, hardware inventory and recovery |
| Toolchain/package/release/provenance owners | Rust-only dependency closure, reproducibility, Arch package, licensing/signatures and user-controlled rollout |
| Documentation/coverage owner | Complete source-to-workstream mapping, unresolved decisions and evidence-backed per-unit closure |

Key risks are incomplete undocumented behavior, unsafe abstraction defects, ordering/RT races, impossible-to-source legacy hardware, compiler backend gaps, firmware/license restrictions, benchmark noise, data-loss bugs, package/recovery mistakes and upstream security drift. Each must have an owner, reproducer/evidence and milestone impact. Do not solve access or staffing gaps by deleting scope. The [decisions](decisions.md) register names concrete blockers/defaults; [maintenance](maintenance.md) governs fixes and baseline changes. Approved baseline pinning is not approval to retain vulnerabilities forever, nor approval to silently claim a newer release.

## Global completion rule

A workstream is done only when its complete assigned source/facility inventory is dispositioned, actual behavior and error paths are implemented, relevant configurations/ABIs/devices have executed evidence, shared invariants and security review are complete, and correctness/performance/recovery/physical gates pass without hidden waivers. Every skip has a reason and blocks the corresponding qualification. Full-kernel completion requires all such workstreams and M8, not an average coverage number or a first server milestone. The exhaustive evidence schema belongs in [definition of done](definition-of-done.md); project implementation policy must continue while any required unit remains unported, without misrepresenting this bounded bootstrap as the completed implementation.
