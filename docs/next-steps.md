# Next steps: the day-to-day work queue

This page is the working queue. [The roadmap](roadmap.md) stays the complete M0–M8 program and inventory; this page says which concrete repair or capability comes next, what is already done, and which executable test closes each item. It does **not** lower the full-Linux scope: every architecture, driver family, filesystem, protocol and facility of the pinned 6.18.57 baseline stays mandatory ([AGENTS.md](../AGENTS.md), [definition of done](definition-of-done.md)). Choosing an order here chooses what to do first, not what to drop.

The results are in the ignored `target/audit-backlog/status-at-main.json`. Unless an item says "ran", the check was **read-only source reading**: a claim about what a non-init process triggers is a code-path deduction, not an observed failure. ## Recommended order of the open work

Dependencies, not importance:

1. **Items 1 and 6 (tooling and reproducibility).** Independent of the kernel and they gate every later "fresh machine" claim: compiler discovery (item 1), then the gate sequence as a committed `xtask` subcommand, configurable firmware paths and a CI workflow (item 6).
2. **Item 2 (comm halt).** Small and self-contained; it makes item 5.2 testable.
3. **Item 13 step 1 (inventory)** and, once the user decides the open question below, **step 2 (per-task handling)**. Items 3, 4 and 12 below remove three of the stops the inventory lists.
4. **Items 3, 4, 12 (kernel semantics)** in any order, each followed by its cross-subsystem sequence in item 5 (5.1, 5.3, 5.4).
5. **Item 9 residuals** (`execleak`, `mapleak`, `waitleak`, heap `heap_total`, `oomsweep`) and **item 5.5, 5.6**; they need no kernel fix first.
6. **Item 16** (independent review and fresh disassembly) before any further change to the entry, scheduler or paging code is called reviewed.
7. **Item 14, then 17d** (madvise lane merge, `timer_create`, `epoll`, sockets), then **17a, 17b, 17c, 17e** by chosen workload.
8. **Item 15** (module split) last, as a pure refactor.

**Open user decision (blocks item 13 step 2).** Today any `Outcome::Unimplemented` stops the whole kernel (`kernel/src/userspace.rs`, `Outcome::Unimplemented` arm). Ending only the offending task, with a loud console line and a fatal-signal-style status, is a behaviour change the v0.2.0 checkpoint recorded as needing the user's decision ([record](implementation.md#not-done-in-v020)). A success-shaped stub or broad `ENOSYS` stays forbidden whatever is decided.

## First pass: correctness and build problems

### Item 1: Compiler discovery in the build tooling

- **Audit.** `xtask/src/kernel.rs`: `verify_build_scripts`, `isolate_command`, toolchain selection. Resolve the selected Cargo and rustc explicitly, pass the compiler's absolute path as `RUSTC` to sanitized Cargo children, keep the isolation and the identity checks, and select the qualified dated toolchain instead of the mutable `nightly` alias. *Done when:* the two failing vendor tests, `xtask check` and `kernel-build` pass on a fresh rustup installation with no compiler in `/usr/bin`.
- **Status: partial.** No change since `3fe187e` (`git diff 3fe187e main` on the relevant functions is empty).
  - Done: the kernel and init builds pass the resolved compiler explicitly (`RUSTC` in `build_command`, `xtask/src/kernel.rs:2994`), and `toolchain()` (`:2647`) qualifies cargo and rustc by exact commit (`REQUIRED_RUSTC_COMMIT :122`, `REQUIRED_CARGO_COMMIT :123`) and rejects a rustc whose sysroot differs.
  - Open (a): `verify_build_scripts` (`:2405`) runs `cargo metadata` through `cargo_program()` (`:2393`) and sets no `RUSTC`; `isolate_command` (`:1335`) clears the environment and defaults `PATH` to `/usr/bin:/bin` (`:1342`; any variable the caller set explicitly, `PATH` or `RUSTC` included, is applied again, `:1346-1352`), so unless the caller sets one, cargo finds a compiler only through `/usr/bin`. Callers: `xtask check` (`main.rs:993`), `prepare_vendored_std` (`:2548`, hence `kernel-build` and `kernel-test`), and the unit tests `project_vendor_must_match_the_lock_exactly` and `cargo_decides_which_optional_vendored_targets_are_unreviewed`.
  - Open (b): selection is by alias, `rustup which --toolchain nightly` (`:2657`); the dated toolchain is only checked afterwards by commit.
  - Open (c): `KILL` and `SETPRIV` are fixed `/usr/bin` paths (`:126-127`).
- **Verified by.** Ran at `main`: the two vendor tests (2 passed) and `xtask check` (passed, 23 vendored packages) with the 1.88.0 cargo. They pass only because `/usr/bin/rustc` is a rustup proxy that resolves to the default nightly. Defect reproduction in scratch: `env -i PATH=<empty directory> cargo metadata --offline --locked --all-features ...` fails with `could not execute process rustc -vV`; the same command with `RUSTC=<absolute rustc>` succeeds. The full "no compiler in `/usr/bin`" install could not be built (no mounts or package changes), so the scenario was emulated at the `cargo metadata` call only. No test covers a compiler-free `PATH`.
- **Remaining.** Pass `RUSTC` (absolute) in `verify_build_scripts` and every isolated cargo/rustc child; derive the isolated `PATH` from the resolved toolchain instead of requiring proxies in `/usr/bin`; select the dated toolchain explicitly instead of the alias; resolve `kill`/`setpriv` through the program resolver or document them as prerequisites; document it in [toolchain](toolchain.md#compiler-selection-as-it-is-today).
- **Acceptance.** With a rustup install whose `cargo`, `rustc` and `rustup` are only under `CARGO_HOME/bin`: `cargo +1.88.0 test -p xtask` passes the two vendor tests, `xtask check` passes, `xtask kernel-build --output <new directory>` succeeds; plus a committed unit test that fails if `verify_build_scripts` runs without `RUSTC` and with a `PATH` that lacks `rustc`.

### Item 2: Process-name-dependent kernel halt

- **Audit.** `userspace.rs`, fault-report formatting in `exec/report.rs`, `PR_SET_NAME`. Pass the actual bounded process name into the diagnostics; keep logging and rate limiting separate from signal delivery, so that failing to print never blocks a handler. *Done when:* a program installs a signal handler, renames itself, takes a recoverable trap and reaches the handler, for names changed through both `prctl` and `exec`.
- **Status: open.** Unchanged since `3fe187e`; the check comes from commit `b3fed83` (blame: `68624ce`, `7e55df3`).
  - `printk_ratelimit` (`kernel/src/userspace.rs:2947-2961`) calls `crate::fail()` ("FAIL fault report names only init", `:2952`) when the task's `comm` is not `init`. `fail()` (`kernel/src/main.rs:654`) halts the CPU in the default build, exits QEMU with a failure under `qemu-self-test` and ends the group in the bare-metal suite.
  - Callers: `show_unhandled_signal` (`userspace.rs:3006`, reached from `force()` for every page fault that ends in `SIGSEGV` and every vector with a `show_signal` message) and the `rt_sigreturn` bad-frame path (`:2523`).
  - Two ways in, by source reading: (1) pid 1 renamed by `PR_SET_NAME` (`syscall/ids.rs:638-648`) or by `execve` (`exec/bprm.rs:353-358`) takes a trap: `SignalState::unhandled_signal` (`signal/state.rs:643-653`) is true for global init whatever its handler, then the `comm` check stops the kernel and the handler never runs; (2) a non-init task whose `comm` is not `init` and whose `SIGSEGV`/`SIGILL`/`SIGFPE`/`SIGBUS`/`#GP` disposition is default or ignore stops the kernel instead of dying with the signal. A renamed non-init task *with* a handler does not trip it.
  - The fault text is hard-coded to `init[...]` (`exec/report.rs:117-139, 185-203, 215-236`). `region_of` (`userspace.rs:3118-3144`) also calls `crate::fail()` for a fault in a VMA whose file is not `/init` and for an anonymous VMA after a `/dev/zero` mapping; a forked child that keeps `comm` `init` reaches both.
  - No executable evidence: no test uses `PR_SET_NAME` and then faults (`prctl-set-name` in `user/init/src/tests/ids.rs:666-682` only restores `init`; `fork.rs:374-394`, `procfs.rs:3139` set and read).
- **Verified by.** Read-only at `main`; the scenarios are deduced, not observed.
- **Remaining.** Pass the bounded NUL-trimmed `comm` to the `Segfault`/`TrapLine`/`BadFrame` formatters; take the file name for the VMA from the VMA's file; delete the two `fail()` calls; keep logging best effort and rate limited; host test for the formatters with a renamed `comm`; QEMU cases: handlers for `SIGSEGV`/`SIGILL` plus a bad `rt_sigreturn` frame after `PR_SET_NAME`; the same after `execve` of a differently named binary; in pid 1 and in a forked child; a renamed child with the default disposition dies with status 11 while the parent and the kernel keep running.
- **Acceptance.** A `kernel-test`/oracle case: a program sets a `SIGSEGV` handler, `prctl(PR_SET_NAME, "x")`, dereferences address 0, and the handler runs; the same after `execve`, once in pid 1 and once in a forked child; a renamed child without a handler is reaped by `wait4` with `WIFSIGNALED && WTERMSIG == 11`. The output matches the pinned reference `bzImage`, and a host test checks `comm` appears in the segfault, trap and bad-frame lines.

### Item 4: personality `READ_IMPLIES_EXEC`

- **Audit.** `syscall/ids.rs`, `mm/ops.rs`. Remove the assumption that a native 64-bit task cannot have `READ_IMPLIES_EXEC`; derive protections from the current personality and the pinned rules, including file and mount restrictions; never make every readable mapping executable. *Done when:* differential tests cover `personality` then `mmap` and `mprotect`, flag on and off, checking actual execution permission.
- **Status: open.** `personality` stores any value (`kernel/src/syscall/ids.rs:223-230`, as `kernel/exec_domain.c:38-46`), but nothing consumes the flag: `do_mmap` says a 64-bit task never has it (`kernel/src/mm/ops.rs:167-168`), `mprotect` likewise (`:697`), `VmFlags::DATA_DEFAULT` is a fixed non-exec constant (`mm/flags.rs:74-76`), and `Env` carries no personality. The pinned source applies the rule on x86-64 (`mm/mmap.c:356-358`, `mm/mprotect.c:868-869`; `arch/x86/kernel/process_64.c:733` (`set_personality_64bit`, every 64-bit `execve`) and `:742` (`__set_personality_x32`) clear the flag, so a 64-bit exec drops it and `personality(2)` can set it again afterwards; `fs/binfmt_elf.c:1017-1018` sets it at exec only when `elf_read_implies_exec()` is true, which is 32-bit only). The only tests query the personality (`user/init/src/tests/ids.rs:175`, host `syscall/ids.rs:796-816`). A documented gap, not a regression ([implementation](implementation.md#memory-mapping-model) lists it).
- **Verified by.** Static reading of the code and the pinned Linux sources; no test or QEMU run.
- **Remaining.** Plumb `ctx.attrs().personality` into the mm operations at each call (no cached copy); in `do_mmap` add `PROT_EXEC` for `PROT_READ` unless a file on a `noexec` mount (this needs `path_noexec` on `FileInfo`; `execve` does not check `noexec` yet either); in `mprotect` apply the `rier` rule; make brk/stack/data default flags follow `VM_DATA_DEFAULT_FLAGS`; clear the flag at a 64-bit `execve` (`set_personality_64bit`, `process_64.c:733`) and keep `personality(2)` able to set it (`exec_domain.c:38-46`), and set it for a 32-bit image only (`binfmt_elf.c:1017-1018`; the candidate has `ia32_emulation=0`, so no image reaches that path).
- **Acceptance.** An oracle group with `personality(0x0400000)` then `mmap(PROT_READ)` anonymous plus `/proc/self/maps` (`r-x` where Linux shows it, `r--` for a file on a `noexec` mount), `mprotect(PROT_READ)` on `rw-` giving `r-x`, executing a few bytes on each (success or `SIGSEGV` as the reference), and the same with the flag clear; `personality(READ_IMPLIES_EXEC)`, then `execve` of a 64-bit image, then the flag read back with `personality(0xffffffff)` is clear (and `mmap(PROT_READ)` in the new image is `r--`); rows recorded on `target/linux-reference/artifacts/bzImage` and compared by `kernel-test`; host tests in `mm/tests.rs` for both calls with and without the input; a plain `PROT_READ` mapping stays non-executable when the flag is clear.
