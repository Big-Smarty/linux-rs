# Separate Arch-style kernel packages and manual boot trials

## Status and scope

**Linux-replacement package design, with a distinct real unsigned diagnostic archive.** The Rust `no_std` x86_64 bootstrap exists; [implementation](implementation.md) records historical frozen cell9 evidence, actual maintained integrated-004 guest/artifact/visual observations and genuine diagnostic-001 ALPM archive inspection. **M1 is in progress, not complete.** The native-Limine diagnostic is not a Linux-replacement kernel package, and no package installation, physical boot/recovery or performance qualification is claimed. Do not manufacture a dummy `vmlinuz`, placeholder PKGBUILD, fake initramfs or successful install evidence. The [diagnostic handoff](diagnostic-handoff.md) preserves the real restricted recipe/BUILDINFO and inspection boundaries; the [definition of done](definition-of-done.md) distinguishes this early trial from replacement-package readiness and Linux/physical/performance qualification.

The desired replacement-kernel experience is an independently named pacman-installable kernel alongside the existing Arch/CachyOS kernel, selectable in the user's **existing** Limine or systemd-boot menu. Initial userspace is Arch/CachyOS, not CachyOS's downstream kernel patch set. The user controls installation, accepting a boot entry, selection and reboot; no agent runs host boot/install/firmware/destructive actions. Replacement-package layouts and procedures below are **not tested instructions for this workstation**. Read-only observations already record Btrfs root, UEFI visibility, active Limine 12.9.3, Secure Boot disabled and tty0 without an observed serial console; they do not establish physical qualification, exact safe media/partition layout or a tested recovery route. Reconfirm artifact-specific prerequisites before any user-operated trial.

Package the accepted **modular monolithic Rust kernel**, with fixed Linux 6.18.57 feature scope and separately recorded, reviewed security deltas. A later feature-baseline update requires its own decision. Every baseline module's functionality remains required in Rust; arbitrary third-party/proprietary out-of-tree functionality is not promised unless separately enumerated and approved.

## Two ordered trial paths, with no storage or package waiver

### Isolated storage-free M1 diagnostic trial

The current engineering path is external Limine12.9.3 loading the genuine `freestanding` diagnostic ELF through native `protocol: limine`, with UEFI64 handoff and a validated32bpp framebuffer. The separate `qemu-self-test` image includes QEMU-only COM1/debug-exit; it is not the physical artifact. [Implementation evidence](implementation.md) separately binds historical cell9 and final maintained integrated-004 hashes, exact compiler/runtime/firmware identities, both-profile code/layout inspection, eight bounded cases and independent default visual review. Its actual diagnostic-001 archive and read-only inspection are distribution evidence, not installation or Linux-replacement qualification. [Kernel tooling](kernel-tooling.md) owns those executable interfaces; later source changes require new bound runs rather than recycling these results.

An initial physical diagnostic trial can precede storage, filesystem, rootfs, initramfs, init and Linux userspace because this candidate does not operate those facilities. It must use **separate user-owned recoverable media**, preserve the existing working kernel/default/boot configuration and provide **independent known-good manual recovery**. Before the user chooses to boot, require independent review of the exact artifact, the applicable QEMU suite, compatible CPU/firmware/framebuffer/controller assumptions, observable diagnostics, a bounded observation/stop procedure and a confirmed recovery path. A framebuffer in QEMU is not a tested workstation console. No host installation, boot-entry/NVRAM modification, mounting/raw-device operation, firmware update, elevation or reboot is authorized for agents.

This remains an experimental boot diagnostic, **not a Linux-replacement package**, despite the real separate artifact-distribution archive. It must not install fake module/initramfs metadata, take a Linux `vmlinuz` identity or claim that the userspace smoke runner can execute on it. No candidate root-disk access or root-storage trial is permitted by this route. A native Limine ELF is not a Linux boot-protocol image, PE/COFF EFI application or systemd-boot payload. Physical execution/recovery has not passed; the exception to *ordering* waives no M1, storage, filesystem, userspace, Linux-replacement packaging or release gate.

### Linux-replacement package: real boot, storage and userspace prerequisites

A renamed ELF file is not a `bzImage`, and pacman cannot turn it into one. The x86_64 distribution artifact must implement the advertised [Linux/x86 boot protocol](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/arch/x86/boot.rst): correct setup/header/version/flags, image placement/alignment/relocation, entry state, boot parameters and memory map, command line, initrd placement/length and reserved memory. Advertise only actually implemented header features. BIOS real-mode versus protected/64-bit entry paths have separate obligations; no imported `.S` or C bootstrap is allowed. Implement unavoidable operations through reviewed function-local Rust `asm!`/`naked_asm!`, never `global_asm!` or standalone assembly; prove naked entry/exit/stack/ABI contracts and validate binary headers/disassembly and real handoffs.

For systemd-boot and EFI chainloading, additionally provide a correct PE/COFF executable and Rust EFI-stub equivalent: machine type/sections/relocations/entry ABI, firmware memory allocation/map, initrd delivery, command-line encoding, ACPI/DT discovery, `ExitBootServices` retry/order and post-exit state. Linux's [EFI stub documentation](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/admin-guide/efi-stub.rst) explains that its x86 bzImage masquerades as PE/COFF through the EFI stub. Merely naming a Rust feature `CONFIG_EFI_STUB` or adding `.efi` does not implement it. A UKI's external systemd stub is permitted as external boot software but does not replace the required compatible kernel payload/entry behavior. Native Limine-protocol early bring-up may be useful; success there alone does not establish `protocol: linux` or systemd-boot compatibility.

The kernel must parse the actual [initramfs buffer format](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/driver-api/early-userspace/buffer-format.rst), including required newc/crc semantics, hardlinks, archive concatenation/alignment and the compression algorithms selected by the installed generator. Early microcode ordering and supported vendor images must be explicit. A file called `initramfs-*.img` is neither a loaded driver nor a block-device filesystem by itself.

Before offering a Linux-replacement package or a trial that uses a user's root disk, qualify its entire actual path on disposable images and suitable physical test media:

- Firmware/ACPI/interrupt/timer/SMP/memory/DMA/IOMMU, console and input needed for boot/recovery.
- Actual PCI/storage controller and block transport; partition scheme; root filesystem and its enabled on-disk features; cache/flush/FUA/barrier ordering and crash recovery; device-mapper, LUKS/crypto/key entry, LVM/RAID/multipath if present. Missing any required root component is a **boot blocker**, not a reason to try the live disk anyway.
- Real ELF loader, interpreter, relocations/TLS/vDSO/auxv, syscall and compat layouts, signals/futex/threads/time, `/dev`/devtmpfs, proc/sysfs, device discovery/uevents, permissions/capabilities and namespace/cgroup behavior needed by actual initramfs, glibc, shell, systemd/udev, mount/cryptsetup/lvm/mdadm, kmod and core utilities.
- Root discovery (UUID/PARTUUID or chosen stable identifier), `root=`/mount flags, initramfs `/init`, switch-root and PID 1 behavior; emergency failure must not silently mount a wrong disk read-write.

External glibc, BusyBox or systemd programs may contain C; that is allowed existing userspace, not a C-backed kernel implementation. Their unmodified binaries must actually work against our Linux ABI. “Only Rust kernel code” cannot mean substituting a tiny Rust demo init for the promised Arch userspace boot and claiming distribution compatibility. The [compatibility](compatibility.md), [storage](subsystems/storage.md), [filesystems](subsystems/filesystems.md), [drivers](subsystems/drivers.md) and [firmware](subsystems/firmware.md) plans own these implementations.

## Proposed Linux-replacement Rust package builder

Implement this replacement-package path only after its real boot, storage/filesystem, root/initramfs/init and userspace prerequisites exist. A storage-free diagnostic artifact has a different payload and cannot satisfy this design. The following command/API names are proposed replacement-package interfaces, not current CLI promises: `package build`, `package inspect`, `package plan-install`, `package stage-boot`, `package plan-remove`; current executable interfaces are documented in [kernel tooling](kernel-tooling.md). Every output includes schema version, candidate identity, inputs, hashes, configuration, external-tool versions, command argument vectors, logs and outcome. No action invokes `sh -c`; use structured arguments and bounded output/errors. Building/inspection works unprivileged in a new staging directory. Installation, entry acceptance and reboot remain explicit user actions; no build installs to host `/boot`.

### Identity and side-by-side policy

For example **future** candidate ID `0001` could use:

| Identity | Proposed example and rule |
| --- | --- |
| Package name and pkgbase | `linux-rs-qual-0001`; reserved distinct namespace, not `linux`, `linux-lts`, `linux-cachyos` or a stock preset name. A separate candidate ID gets a separate package/pkgbase, allowing two candidate generations and stock recovery to coexist. |
| Package version/revision | `pkgver=6.18.57.r1`, `pkgrel=1`, target `arch=x86_64`; emit `linux-rs-qual-0001-6.18.57.r1-1-x86_64.pkg.tar.zst`. Package revision and kernel release are distinct fields, not inferred from each other. |
| Exact running/kernel release | `6.18.57-rs0001`, embedded consistently in the kernel's uname/proc release and all module/build manifests. Changing kernel ABI/build content gets a new release/candidate identity; never replace a different image under a trusted old release. |
| Boot identity | Unique entry token plus exact release; versioned immutable resource directory and manifest. Never rewrite a stock entry/default or an unrelated installation's token. |

Allocate IDs deterministically from reviewed release metadata; refuse collisions with existing paths/packages. A rebuild with the same declared identity must reproduce identical bytes or fail for identity reuse. Do not declare `replaces=linux`, `conflict=linux`, broad `provides=linux`, `LINUX-HEADERS`, DKMS compatibility or upstream module provisions without genuine evidence; the intended package coexists with stock kernels. Initial dependencies explicitly select the tested generator (`mkinitcpio` rather than merely an arbitrary provider), kmod and required external userspace; record any firmware package required by the qualified profile. Avoid requiring unrelated firmware globally.

### Exact package and sidecar artifacts

1. `.PKGINFO` with real name/pkgbase/version/architecture, size/build metadata, GPL/SPDX licenses with exceptions accounted for, real dependencies and no fictitious replacement/provision claims.
2. `.BUILDINFO` format 2 with actual build environment/tools/installed versions. Its mandatory `pkgbuild_sha256sum` is specifically a PKGBUILD digest: **do not place an unrelated manifest hash there**. The Rust builder will generate and consume a real **assignment-only declarative `PKGBUILD` input** (constant quoted metadata/source hashes, no functions, expansions, substitutions or control flow), retain its exact bytes in the source/evidence bundle and hash those bytes. The builder parses the restricted data grammar itself; it does not execute shell. This is a Rust-builder recipe, **not** a claim that `makepkg` can execute it. Record the additional Rust build manifest/lock/config hashes separately. Validate this representation against the adopted ALPM metadata/tool versions before distribution; it cannot be papered over with fake checksum/provenance fields.
3. `.MTREE` in the adopted ALPM format describing actual archive ownership/type/mode/size/digests/times. Deterministic safe tar paths, root ownership, appropriate image/data modes, normalized recorded timestamps, no absolute members, path traversal, special-device payloads, escaping symlinks or unrecorded executable source. Use audited Rust archive/hash/compression implementations under [dependency policy](dependencies.md), or explicitly versioned external tar/zstd tools. Do not author foreign-language packaging scripts.
4. `usr/lib/modules/<release>/vmlinuz`, a genuine validated boot image; `usr/lib/modules/<release>/pkgbase`, one exact pkgbase line. Install actual Rust loadable modules only if the profile implements them, with their complete kmod metadata. Include the built-in metadata required by the selected generator even for a built-in-only early profile; do not invent fake empty files for unimplemented features.
5. `usr/share/linux-rs/candidates/<release>/` with machine-readable build/config/boot requirements, image hashes, source provenance, exported ABI information, complete module/builtin/firmware manifest and qualification evidence references; corresponding source/license/notices distribution and debug artifacts in a separate versioned archive or explicitly named debug package. No C-oriented `-headers` facade for DKMS: a future Rust module SDK needs its own exact-release contract and real artifacts.
6. Optional **declarative-only** `etc/mkinitcpio.d/<pkgbase>.preset` and profile config, marked for appropriate pacman backup behavior. Although interpreted by external shell, generated files contain only whitelisted constant variable/array assignments; reject newline/quote/path injection. No authored shell functions, command substitutions, install hooks, `.INSTALL`, PKGBUILD build functions or shell wrappers. Existing distribution hooks execute externally maintained code; new project actions must be Rust executables invoked through declarative ALPM hook metadata, if needed.
7. Output archive SHA-256 and detached OpenPGP package signature with recorded signing identity, plus reproducibility manifest and evidence bundle. Package signature trust is separate from EFI signing/module signing. Do not embed private keys in packages/evidence.

The source/AUR experience is intentionally precise: pacman consumes binary ALPM packages independently of makepkg. AUR normally distributes executable PKGBUILDs; we do **not** claim an assignment-only recipe is an AUR-compatible build recipe or publish a misleading broken one. The Rust builder plus authenticated declarative recipe provides the requested locally buildable Arch/AUR-like experience without project-authored shell. Any later actual AUR submission must explicitly resolve the executable-PKGBUILD policy rather than silently adding a shell bridge.

## Modules, builtins and initramfs are one compatibility boundary

No legacy Linux C `.ko`, DKMS output or stock kernel module may load into this kernel. A new Rust module loader and module build pipeline must implement their chosen Linux-compatible ELF relocation, exported symbol/version, vermagic/release, dependency, alias, parameter, signature, lifetime/unload and error semantics. Internal Linux driver ABI is [not stable](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/stable-api-nonsense.rst); identical release strings do not make old modules valid.

Where ordinary external kmod/mkinitcpio is promised, use their actual naming/interface expectations: `/usr/lib/modules/<exact-release>/kernel/.../*.ko` with supported compression/signatures and authentic metadata, `modules.order`, `modules.builtin`, `modules.builtin.modinfo`, dependencies/aliases/softdeps/symbol maps and generated binary indexes as required by the selected kmod release. Derive files from the actual compiled module/builtin inventory; run versioned external `depmod` against **staged target release**, never default to the running kernel. Reject foreign ELF objects/provenance before staging. Exact required files and empty-but-valid built-in cases must be tested against chosen versions; no fake exported symbols or module successes.

An early all-built-in root-driver profile is allowed as an implementation order, not full module-scope closure. It still needs correct builtin names/aliases so `modprobe`/initramfs can distinguish present builtins from missing modules. Do not set mkinitcpio `-k none` merely to hide absent drivers. Treat any required missing module, alias, firmware, unsupported compression, kmod lookup or dependency failure as image-generation failure.

The installed stock kernel's initramfs contains **that** release's modules. It cannot supply unported root/NIC/GPU drivers to the Rust candidate. Host autodetection observes the host's drivers and can select unavailable or differently named candidate components; compare every autodetected root-stack item against the candidate's manifest and explicit profile. A fallback initramfs is broader driver inclusion, **not** permission to include C modules, nor a rescue path for a missing Rust driver. Preserve external firmware/microcode licenses and record whether early loading and trust actually work.

## Initramfs integration modes: choose exactly one owner

### Default: Arch mkinitcpio/preset flow

Prefer the distro's existing mkinitcpio ALPM integration with a distinct pkgbase/preset. If a project-generated preset is supplied, it is constant data with `PRESETS`, exact `ALL_kver`/`<preset>_kver`, config and versioned output paths, not an executable build script. A pathname `ALL_kver` destination can trigger the external helper's copy behavior; a version-string `ALL_kver` chooses the already staged target release without relying on kernel-version scanning. The implementation must choose and validate one interpretation, not assume both happen.

Proposed default here: use the exact **release string** for `ALL_kver`; target images are generated to a candidate-specific staging/boot-resource directory and the Rust staging tool explicitly copies the validated package-owned `vmlinuz`. This avoids relying on a custom image's version extractor before it has been qualified. Generate with the targeted preset or explicit `mkinitcpio -k <release> -g <staged-image> -c <qualified-config>`; do not use `-P` as a substitute for target selection or rely on `uname -r`. Existing hooks' actual paths/side effects must pass disposable-root install tests before using this custom preset on a host.

Concrete proposed generated preset for that example candidate (data illustration, not a delivered preset or working artifact):

```text
ALL_kver='6.18.57-rs0001'
ALL_config='/etc/linux-rs/6.18.57-rs0001/mkinitcpio.conf'
PRESETS=('default')
default_image='/var/lib/linux-rs/generated/6.18.57-rs0001/initramfs.img'
```

The Rust builder packages the qualified assignment-only config at the named config path and the writable generated-output directory with correct ownership, but not a pre-fabricated image. The config explicitly records actual compression, required modules/builtins, binaries/files and externally maintained hooks verified for that root stack; it does not silently inherit an arbitrary host configuration. The external generator writes outside ESP/XBOOTLDR first. The Rust staging tool then validates and copies the real kernel/initramfs into the versioned boot-resource directory before the user accepts the entry. No blanket post-hook may publish an entry prematurely. A broader fallback preset is added only after its actual Rust-module inventory and generator semantics qualify, not by promising stock drivers will fill gaps.

The package is not “ready to select” until generator exit status, image listing/decompression, required `/init`/interpreters/libraries/config, root-stack Rust modules or builtins, firmware and exact release all validate. A successful CPIO build alone is insufficient. Compare actual contents against the requirement manifest, and boot the resulting image with Arch userspace in QEMU. Prefer a separate minimal rescue userspace and a known-working **stock** recovery kernel; do not confuse the candidate's fallback image with a trusted stock rescue.

### Optional: kernel-install/UKI flow

Use only when the user has chosen and validated it. Record `kernel-install inspect <release> <image> [initrd...]`, discovered plugin names/versions, entry token, `$BOOT`, `layout=bls` or `layout=uki`, generated resources and removal behavior. Always provide exact release/image/initrd arguments: omission can default to the running kernel. Installed generator plugins may build initrds; absent/incompatible ones must block, not leave an entry pointing to missing data. Do not mutate global `/etc/kernel/install.conf` or disable stock plugins for the candidate.

A separate Rust-controlled UKI assembly may call external `ukify`/mkinitcpio/systemd-stub, but must validate payload entry requirements, architecture, `.linux`/`.initrd`/`.cmdline`/`.osrel`/release metadata, signature coverage and generator versions. Select BLS or UKI copy ownership once; do not run both stock mkinitcpio boot-copy hooks and kernel-install over the same paths. Detect duplicate entries and stale resources. Runtime Arch userspace identity in `.osrel` is not the candidate kernel release.

## systemd-boot: partition constraints and proposed entry

The authoritative [Boot Loader Specification](https://uapi-group.org/specifications/specs/boot_loader_specification/) requires XBOOTLDR on the **same disk as the ESP**; firmware-readable filesystems are required, normally VFAT, with regular files/directories rather than symlink tricks. systemd-boot cannot read arbitrary `/usr/lib/modules` files from an ordinary encrypted root or normal ext4/btrfs `/boot`. A mountpoint named `/boot` alone proves nothing: inspect partition GUIDs, mounts and actual firmware-readable paths. Never reformat/repartition as an implicit package operation.

For Type #1, the snippet lives at `$BOOT/loader/entries/<token>-<release>.conf`. The `linux` and each `initrd` path are absolute **relative to the root of the partition containing the snippet**, not host absolute filesystem paths. Put snippet and all referenced candidate resources together on that ESP/XBOOTLDR. For example, once rendered and validated for a future machine, a declarative entry could read:

```text
title Linux Rust qualification 0001
version 6.18.57-rs0001
architecture x64
linux /linux-rs/6.18.57-rs0001/vmlinuz
initrd /linux-rs/6.18.57-rs0001/initramfs.img
options <machine-specific validated root and recovery-console arguments>
```

This is syntax illustration only; the angle-bracket value must never be installed verbatim. Preserve verified early microcode ordering if supplied separately; avoid duplicating it when integrated by mkinitcpio. A directly executed image requires the EFI stub. Type #2 instead uses a real signed/validated UKI at `$BOOT/EFI/Linux/<token>-<release>.efi`, auto-discovered without pretending the UKI is a generic Linux ELF file.

Use existing `bootctl status` and `bootctl list` for inspection, not `bootctl install/update/remove`. These latter commands can alter boot binaries/fallback paths/NVRAM beyond the candidate. Retain the known-working default. User may manually select the menu item for the trial; an explicitly requested one-shot selection is separate from installation. Boot counting/fallback exists upstream but requires actual tested OS success/failure signalling; do not promise it automatically recovers a hard lockup or claim it works before our kernel/userland integration does.

## Limine: distinct entry format and resource resolution

Match the installed Limine major/version before rendering: current `trunk` syntax below is not a promise about old `limine.cfg` formats. Locate the **actually loaded** `limine.conf`, including EFI-relative search priority/shadowing, before proposing a change. Retain its stock entries/defaults and a recoverable backup; do not install a new boot loader, run `limine bios-install`, or overwrite `EFI/BOOT/BOOTX64.EFI` as part of candidate packaging.

For the Linux-boot-protocol image, a future declarative entry using current syntax could be:

```text
/Linux Rust qualification 0001
    protocol: linux
    path: boot():/linux-rs/6.18.57-rs0001/vmlinuz
    module_path: boot():/linux-rs/6.18.57-rs0001/initramfs.img
    cmdline: <machine-specific validated root and recovery-console arguments>
```

Again, the unresolved value is not an installable instruction. `boot():/` means the partition containing the config on the boot drive, **not** an unconditional synonym for the Linux `/boot` mount or the ESP. If resources are elsewhere, render a verified `guid(<partition-or-supported-filesystem-uuid>):/path` resource or another documented locator; validate filesystem support and absence of ambiguous drive numbering. Repeated `module_path` values represent initrd components for `protocol: linux`; their order/microcode semantics must match the actual image parser and loader. They are not Linux loadable `.ko` driver commands.

A native early bring-up entry with `protocol: limine` uses the implemented request/response contract and separate diagnostic ELF recorded in [implementation](implementation.md); it is not interchangeable with `linux`. The storage-free M1 route above does not qualify the illustrated Linux/rootfs entry. For a future UKI/EFI artifact, use the documented `protocol: efi` with `path:` and validate firmware/stub command-line/initrd policy. Do not assume BLS snippets are automatically consumed by Limine or that native Limine gives systemd-boot a compatible image.

## Secure Boot, signing and trust

Default to preserving the user's current security policy; never disable Secure Boot/mitigations or enroll keys silently. Record firmware trust databases, existing loader signature trust, revocations and key ownership without exporting secrets. Distinguish three independent checks:

1. **Package authenticity:** detached OpenPGP signature and pacman trust policy, plus verified source provenance. A signed tar archive is not a signed EFI executable.
2. **Boot chain:** signed EFI image/boot manager and kernel/UKI accepted by the user's trust chain. A signed UKI can cover kernel, initramfs and embedded command line; plain signed kernel plus external initramfs/options does not automatically authenticate those external resources. Verify actual secure-boot policy of the selected stub/loader, image digests and expected command-line restrictions, including negative tamper/unauthorized-key cases on a disposable test platform.
3. **Modules/firmware:** kernel-enforced module signature/lockdown and firmware/microcode provenance policy, not an assumption inherited from the stock kernel. If required security features are unimplemented, the profile is not qualified.

For current Limine, [USAGE Secure Boot](https://raw.githubusercontent.com/limine-bootloader/limine/trunk/USAGE.md) explicitly distinguishes a merely signed EFI loader from a loader with an enrolled config hash. With Secure Boot active **and** enrolled config hash, config verification and required per-resource BLAKE2b/BLAKE3 hashes are enforced, editor disabled, and EFI chainloading delegates image verification to firmware. Without enrolled config hash, a signed Limine image alone does not give config/resource integrity. Rendering a new candidate entry changes the config hash and may require a newly enrolled/re-signed loader under user control; never rewrite the currently trusted loader automatically. Verify behavior against the actual installed release, not only moving `trunk` docs. Measured boot is not by itself authorization, and changed PCRs may affect disk-unlock policies/recovery keys.

## Transaction, rollback and uninstall design

Treat pacman payload installation and boot-resource activation as separate phases, not a mythical cross-filesystem atomic transaction:

1. **Plan/read-only:** inspect package inventory/conflicts/signatures, root stack, tool versions/plugins, mounts/partition identity, Secure Boot policy and available space for candidate plus retained recovery. Produce the precise proposed changes and refusal reasons. Never auto-delete older stock resources to make space.
2. **User install:** user installs the authenticated package with pacman only after prerequisites. No global package installs or `--overwrite` conflict bypasses. Distribution post-transaction hooks may fail **after payload extraction**; capture their exact result and inspect package database/state before advising retry/removal.
3. **Generate/stage:** generate target-release initramfs/UKI and validate all bytes/manifests before any selectable entry. Use candidate-private temporary/versioned resources on the destination filesystem, fsync file/directory changes where supported and validate read-back/hashes. ESP/FAT and power-loss semantics need explicit fault tests; rename is not a universal cross-filesystem/power-fail guarantee.
4. **Activate last:** user accepts the exact entry/config change only after validated resources exist. Atomic replacement where available, manifest-backed ownership, no modification of stock default. A partial failure leaves old working entry/resources untouched and no selectable incomplete candidate. Limine config changes preserve other entries and, when relevant, satisfy its enrolled-hash signing process.
5. **Trial/report:** user selects candidate and reboots manually, with console/recovery media and known-working stock entry. Confirm exact release and artifact/entry identity, collect console logs and run the [bounded suite](bare-metal-suite.md) with explicit environment plus broader profile tests. Package installation is not physical qualification; suite labels are operator assertions, not proof of bare metal. Reboot to stock on a failure rather than attempting unsafe root repairs from an unqualified kernel.
6. **Rollback/remove:** boot the retained working kernel first. User removes only the exact candidate package/entry/resources by owned manifest; refuse removal of the running candidate or last known recovery through project tools. `kernel-install remove <release>` is only for the chosen validated layout/plugins, not a broad cleanup command. Mkinitcpio preset removal may save modified presets as `.pacsave`; preserve/report user edits. Never glob-delete `/usr/lib/modules/*`, wipe all loader entries, remove the boot manager, delete shared microcode/firmware or follow foreign symlinks. Handle already-missing resources idempotently and report leftovers without broadening deletion scope.

Exercise package aborts, missing/mis-mounted/read-only/full ESP, path collisions/case folding, wrong release/architecture, generator/depmod/signature failure, interrupted copy, repeated install/remove and edited preset/config in disposable roots/images. Retain evidence that stock image/module paths, entry, default and fallback EFI binary are unchanged. Failed pacman hooks or partial boot staging must have deterministic recoverable diagnostics; no fake success or claiming pacman rolls back external boot files automatically.
