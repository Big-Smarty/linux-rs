# Research record and unresolved evidence

## What this record establishes

Research access date: **2026-10-19**. This is a curated question-driven record of primary sources consulted for planning, not a claim to have read every Linux file, verified every architecture, run every suite, or discovered every compatibility obligation. Long documents and source files were read in relevant excerpts; their uninspected portions are not implied researched. Other workstream documents carry their own mechanism-specific citations. The complete pinned tree inventory, when audited, establishes structural scope, not behavioral understanding or implementation.

The approved baseline is Linux **6.18.57 LTS**, tag `v6.18.57`, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`. Metadata/tree/signature observations and retrieval caveats belong to [coverage](coverage.md). Links using `v6.18.57` below identify the pinned source version, not today's mainline. Live manuals, `master` README files and standards sites can change; before implementing a test/build, pin their exact revision or archive and record its digest. A link being reachable is not proof that the described feature is implemented here.

Accepted project decisions, distinct from source observations: modular monolithic Rust architecture; unavoidable function-local `asm!` and `naked_asm!` with explicit proofs, never `global_asm!` or standalone assembly; fixed 6.18.57 feature scope plus reviewed security deltas. Every in-baseline module's functionality needs a Rust replacement. Arbitrary proprietary/out-of-tree module functionality is not included without separately enumerated approval. Later feature-baseline expansion is a separate decision, not a moving research assumption.

Evidence classes used across this program:

- **Observed upstream fact:** directly supported by the cited source or an actual recorded tool result, with source version/date and scope.
- **Observed project behavior:** exact source/toolchain/artifact identity and retained execution or inspection output; claims are limited to the exercised cell, not inferred from a plan.
- **Proposed design:** this project's planned behavior, architecture, gate or workflow; not upstream policy and not an implementation result.
- **Open obligation/blocker:** unresolved implementation, missing toolchain/device, unverifiable claim, test gap or decision; not a pass and not removed from scope.

The original research delivery was planning/setup with all routes `not_started`. Current [implementation evidence](implementation.md) separates the real Rust x86_64 bootstrap's historical cell9 results, maintained integration/package checkpoint and subsequent foundation revisions. The canonical [routed-workstream table](implementation.md#routed-implementation-status) identifies current `in_progress` owners; all other rows remain `not_started`. The [planning auditor](project-audit.md) and [bounded smoke tool](bare-metal-suite.md) remain separate host/setup tools. Whole-QEMU/Linux qualification, physical platform results, performance and M1 completion remain open under the [definition of done](definition-of-done.md). Initial-cell sequencing and integration lint choices are engineering decisions, not additional detailed user approvals.

## Is upstream Rust support already a complete Rust Linux kernel?

**No.** The pinned [Linux Rust introduction](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/rust/index.rst), consulted 2026-10-19, describes support merged in v6.1 to evaluate Rust, development of abstractions/drivers/infrastructure, and experimental limitations for certain configurations. That is upstream Rust **within** Linux, not a Rust replacement for Linux's scheduler, MM, filesystems, networking, architecture code and all drivers. Its prose is an upstream statement at this tag, not independent production qualification or a forecast of later upstream releases.

The [rustc platform-support guide](https://doc.rust-lang.org/rustc/platform-support.html), consulted in introductory/tier excerpts on 2026-10-19, distinguishes tier guarantees and compiler/library/host availability. A Linux userspace target triple is not a bootable `no_std` kernel target. A target's presence does not provide entry/trap code, atomics on every CPU variant, linker/image support, kernel ABI correctness, or hardware qualification. Missing toolchain support is a blocker to solve, not grounds to delete an architecture. See [architectures](subsystems/architectures.md) and [toolchain](toolchain.md).

Generic crate/embedded/web guidance must not override the approved Rust-only/no-C-runtime kernel boundary. Crates are candidates until licenses, `no_std` features, allocation/error context, unsafe contracts, transitive native code and target behavior are reviewed. Upstream abstractions can inform the direct GPL source port, but any dependency on remaining C functionality must be removed rather than disguised as a finished Rust implementation.

## Questions deliberately left open until evidence exists

1. Which additional device IDs/revisions, topology and recovery facilities are actually available? Read-only prerequisite observations recorded x86_64, running `7.2.10-1-cachyos`, Btrfs root, UEFI visibility, active Limine 12.9.3, Secure Boot disabled and only `tty0` with no serial observed. These are observations, not physical attestation or tested recovery. Keep unobserved serial/BMC, spare media, NUMA and other machines unresolved; the privacy-limited smoke metadata is not a full hardware inventory.
2. Which baseline architectures lack a viable Rust/LLVM/kernel target path, and what compiler/runtime engineering and physical/remote hardware is needed? Resolve with real toolchain/source investigation per architecture, not target-list optimism.
3. What are the exhaustive native/compat ioctl, netlink family, pseudo-filesystem, filesystem feature and protocol obligations? Expand structural inventory using pinned source symbols/UAPI/config and actual binaries; no exhaustive behavioral ledger is claimed yet.
4. Which external tests require forbidden C kernel helpers, newer-than-baseline features, destructive media or unavailable peers? Pin revisions, classify prerequisites and implement justified Rust alternatives without losing the original obligation.
5. How will Rust KCOV-compatible coverage, target sanitizers, low-level race checking and model-to-implementation correspondence work on each target? Existing Linux capabilities and host-only tools are not automatic implementations.
6. Which workloads/metrics can demonstrate at-least-Linux performance with equivalent security, firmware/topology/storage and statistically adequate repeated results? Use the balanced server profile first; expand all final-scope workloads rather than averaging away regressions.
7. Which declared-scope handoff and recovery path is ready for the real bootstrap artifact? Follow [packaging](packaging.md) and [kernel tooling](kernel-tooling.md), distinguish their integration state from actual manual cell9 evidence, and require the full applicable QEMU cases before a user-test claim. An isolated storage-free M1 diagnostic trial may precede rootfs/initramfs/storage/userspace; a Linux-replacement package still requires them. Native Limine ELF does not imply systemd-boot EFI/PE or Linux boot compatibility. Preserve known-good boot and independent user-controlled recovery; no physical result is claimed.
8. Where are physical durability, power, other-vendor/architecture and rare-device requirements blocked by unavailable equipment? Keep each named cell open, never substitute VM results or the bounded smoke suite.

Subsequent research records must identify the question, exact source revision and inspected scope, observation versus proposed decision, unresolved conflicts, planned discriminating experiment and resulting evidence. Do not inflate a reading list into proof or silently turn a missing source into an implementation assumption.
