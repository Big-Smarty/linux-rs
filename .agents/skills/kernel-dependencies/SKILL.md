# Kernel dependencies

## Scope and required inputs

Read [dependency policy](../../../docs/dependencies.md), [toolchain](../../../docs/toolchain.md), [licensing](../../../docs/licensing.md), [architecture](../../../docs/architecture.md), [performance](../../../docs/performance.md) and [bare-metal requirements](../../../docs/bare-metal.md). Pair with [kernel-security](../kernel-security/SKILL.md) and the relevant subsystem skill. This skill is authored locally: do not install external skills, cargo subcommands or global packages as a side effect of reviewing a candidate. Review external tool source/provenance and obtain appropriate authorization before execution.

Inputs: exact requirement and Linux 6.18.57 contract, candidate name/version/source revision/checksum, intended kernel/host/build-only/test-only use, selected targets/features/configurations, expected allocation and execution contexts, dependency graph, license/source files, maintainer/update ownership, and proposed evidence plan. A suggestion is a **candidate**, not an accepted or installed dependency. The [existing bootstrap and routed status](../../../docs/implementation.md) are actual implementation, but no proposed crate is proof of support or permission to add a new dependency.

Kernel code is `no_std`; project host tools may use `std`. Kernel allocation is fallible and context-aware, not universally forbidden. Project-owned executable code is Rust only, and kernel dependencies must not smuggle in C/C++/Zig implementations, standalone assembly, prebuilt opaque code or a C kernel runtime. External compiler/linker/rustc/LLVM, bootloader, QEMU, reference Linux, existing userspace suites and explicitly recorded firmware/microcode are separate allowed external categories, not claims of Rust purity. ABI syntax such as `repr(C)` or `extern` does not by itself prove C implementation or prohibit a compatible ABI.

Use the standing [definition of done](../../../docs/definition-of-done.md). The actual [bounded smoke suite](../../../docs/bare-metal-suite.md) and metadata auditor are Rust host/guest tools, not permission to add kernel dependencies or claim kernel qualification. First userspace is Arch/CachyOS userspace without downstream CachyOS kernel patches; use the approved balanced-server performance profile. Only the current workstation is available for physical runs, leaving broader hardware coverage explicitly blocked. [Packaging](../../../docs/packaging.md) distinguishes the existing storage-free diagnostic ELF from a Linux-replacement package with real storage/durable filesystem/root/initramfs/init/userspace prerequisites. Preserve the working kernel and recovery; native Limine ELF is not direct systemd-boot EFI/PE/Linux compatibility. Generated declarative metadata and external pacman/mkinitcpio/boot tools are allowed, but project-owned packaging implementation remains Rust. User-operated installation/boot is not an action for this audit.

The [bootstrap runtime/source audit](../../../docs/implementation.md) links only the vendored `x86_64`/`raw-cpuid` graph (seven crates, two reviewed host build scripts; the host `xtask` also vendors `serde_json` and its graph; see dependencies.md admitted exact configurations). It uses exact `rustc 1.101.0-nightly` commit `5c543b0b8c73c7b72bc8284ced4fb22ead15734d`, LLVM 23.1.1 and matching installed `rust-src` to build target `core`/`compiler_builtins`; inspect actual linked providers rather than assuming the whole rebuilt archive is qualified. The required `memset` is scalar project Rust, not the avoidable assembly provider. Host MSRV 1.88 is a separate engineering metadata baseline, not a user-selected version or a result proved by nightly kernel tests. Bind runtime qualification to exact compiler and artifact identities, not a mutable toolchain alias.

Limine 12.9.3 and OVMF remain external loader/firmware trust dependencies with their own notices and hashes. The translated protocol layouts in `kernel/src/boot.rs` retain `GPL-2.0-only AND 0BSD` and the upstream 0BSD notices. Preserve the [local source-verification boundary](../../../docs/implementation.md): GPG “Good signature” with the kernel.org HTTPS/WKD-pinned fingerprint and `TRUST_UNDEFINED` / `[unknown]`, not Web-of-Trust/ultimate trust or a retroactive change to the original GitHub-only retrieval history. Local artifact use does not close redistribution, SBOM, reproducibility or physical qualification.

## Ordered audit with required outputs

1. **Specify the actual gap.** Read the pinned upstream mechanism, its ABI and invariants before searching crates. State exactly which primitive the candidate would supply and which Linux semantics remain project-owned: failure codes, partial operations, cancellation, persistence, locking, namespace identity and hardware effects. Compare reusing existing project primitives, directly porting the baseline, adapting a crate and writing a small audited implementation. Output: requirement-to-candidate map; never select a complete userspace runtime merely to obtain one data structure.
2. **Acquire identity without trusting execution.** Inspect manifest, complete source archive/tree, release provenance, checksum, source URL, repository tag/commit mapping, license files, bundled assets and generated/prebuilt content before running Cargo on untrusted code. Inspect workspace and `.cargo` configuration, patches, source replacements and symlinks. Record toolchain identity and any signature/attestation verification actually performed; a forge badge is not local verification. Output: auditable source receipt and unexplained-content list.
3. **Resolve the entire feature/target graph.** Review direct, transitive, optional, target-specific, build and dev dependencies and proc macros. Later, in an authorized isolated environment, collect the exact selected `cargo metadata` and `cargo tree -e features` graph for each intended target/profile. Cargo features unify additively; `default-features = false` on one edge does not prevent another edge enabling `std` or native code. Separate host/build execution from target linkage, but security-review both. Output: resolved feature graph with every package's role, source and enabled features, not only the top-level manifest.
4. **Prove no_std and allocator compatibility.** Inspect source under the resolved feature set for `std`, OS syscalls, threads/TLS, global allocators, hidden heap growth, panic paths, unwinding, libc assumptions and unsupported runtime symbols. Classify stack bounds, allocation failure handling, allocation context, sleeping/reclaim/reentrancy and deallocation context. `alloc` support does not imply recoverable OOM or IRQ safety; a `Vec`-based API that aborts on allocation is not accepted for a fallible kernel path without a genuine redesign. Output: API-by-API allocation/context table and a plan to validate the target artifact, not a `no_std` badge.
5. **Audit atomics, synchronization and architecture assumptions.** List atomic widths/alignment and required operations, target feature dispatch, lock-free assumptions and critical-section fallback. Check UP versus SMP, interrupt/NMI/preemption/reclaim use, weak memory ordering, 32-bit overflow, endianness, page size and pointer width. An interrupt-disabled fallback local to one CPU cannot emulate global SMP mutual exclusion. Runtime CPU detection must not depend on unavailable userspace services or execute forbidden instructions before detection; SIMD/FPU use requires kernel state/context management. Output: target/config matrix with explicit unsupported cells and adaptation obligations; rustc target existence alone is not kernel qualification.
6. **Inspect all implementation languages and build execution.** Examine `build.rs`, proc macros, `links`, linker instructions, `include_bytes!`, `global_asm!`, `asm!`, archives, object blobs, `*-sys` crates, `cc`/CMake/pkg-config invocations and generated outputs. Search transitive sources and inactive feature branches relevant to final scope. Trace compiler-builtins/runtime linkage and distinguish approved compiler toolchain behavior from bundled third-party native implementations. Build scripts and macros execute on the host and can read secrets or fetch code; sandbox with least privilege and no network unless explicitly justified. Reject any kernel-linked non-Rust implementation or standalone assembly, even if hidden behind a Rust API. Inline assembly needs unavoidable-operation justification, operand/memory/clobber/privilege contract, reviewer approval and disassembly evidence through [kernel-unsafe](../kernel-unsafe/SKILL.md). Output: language/linkage/build-execution inventory and disposition of each generated artifact.
7. **Evaluate soundness and Linux semantics.** Read unsafe blocks and public safety contracts; verify ownership, aliasing, pinning, Send/Sync, MMIO/DMA ordering, cancellation and error cleanup in the actual kernel context. General-purpose spin locks, interrupt helpers and host async runtimes do not automatically satisfy kernel lock classes or scheduling. Parsers must not construct invalid Rust references from untrusted bytes; cryptographic code needs constant-time, entropy, algorithm/API and key-lifetime review. Output: obligations that the crate proves, obligations the adapter proves, and independent tests required for each.
8. **Perform the GPLv2 provenance audit.** This is a direct source port under GPL-2.0-only as a whole. Read full applicable license texts and per-file SPDX expressions, exceptions, notices, generated inputs and embedded assets, including transitive components. Preserve upstream attribution, source paths/revisions, modifications and valid per-file exceptions; do not replace all notices with one blanket project header. Evaluate the selected branch of an `OR` expression and all terms of an `AND` expression. An Apache-2.0-only implementation is not automatically compatible with GPLv2-only; a genuine MIT alternative may be selectable after full review. UAPI syscall exceptions do not automatically apply to kernel-linked implementation. Unknown/custom/conflicting obligations block acceptance pending a competent licensing decision. Firmware has its own redistribution/license record. Output: component/file provenance and license decision, notices/source-distribution obligations and unresolved legal questions; do not pretend a scanner is legal approval.
9. **Review maintenance and advisories.** Inspect upstream maintainers, release/change history, security contact, open soundness issues, supported Rust/toolchains, abandoned/yanked status, ownership changes and the cost of carrying patches. Check RustSec and upstream advisories against the exact version, feature set and transitive native components; pin advisory database revision/retrieval date. Explain applicability rather than suppressing matches, and record that an empty scan excludes undiscovered bugs. Assign an update/backport owner and monitor upstream security changes. Output: maintenance risk, advisory dispositions and sustainable update plan, not a popularity score or unsupported freshness claim.
10. **Choose accept, adapt, reject or blocked.** Apply the decision table below and record alternatives, scope and reviewer authorization in [dependencies](../../../docs/dependencies.md); architectural trade-offs belong in [decisions](../../../docs/decisions.md). Adaptation is an owned Rust fork/port with exact delta, original notices, upstream tracking and regression coverage, not a shim that calls C. Avoid accepting a whole crate when a small attributable compatible portion is safer to maintain. Output: explicit decision and conditions; none is silently installed.
11. **Qualify accepted changes.** In authorized implementation work, build and inspect target artifacts for each promised configuration, exercise OOM/IRQ/SMP/adversarial/error paths, and compare Linux behavior. Co-develop QEMU and real hardware from M1; physical CPU vendors, NUMA, IOMMU/DMA, device reset, firmware and power/hotplug transitions expose assumptions that a host build cannot. Require reproducible per-workload/hardware throughput, latency/tails, CPU, memory, startup and power comparison with identical security and equivalent compiler/configuration conditions, repetitions/confidence intervals/noise controls. At-least-Linux performance is mandatory; unproven non-regression is not a pass, and no arbitrary tolerance or disabled mitigation excuses a dependency. Output: source/feature/artifact identities plus semantic, security, hardware and performance evidence; missing hardware is a named blocker.
12. **Keep the accepted graph controlled.** Review lockfile/source/feature/toolchain changes as code changes, record exact release artifacts and checksums, and reproduce from reviewed offline inputs where appropriate. Vendoring may improve availability but copies maintenance/licensing obligations; it is not automatically trusted or prohibited. Retire obsolete forks/adapters and update all callers in a clean cutover. Output: reproducible graph, owner and synchronized evidence, using [kernel-documentation](../kernel-documentation/SKILL.md).

## Decision rules

| Disposition | Required rationale |
| --- | --- |
| Accept for a specific role | Reviewed source/graph/license, compatible execution context and behavior, no prohibited implementation, owned maintenance, and evidence for the stated targets; approval does not extend to other features or kernel linkage. |
| Adapt in Rust | A bounded mismatch can be removed without changing required Linux behavior or breaking license obligations. Specify removed dependencies, fallible/context-aware APIs, architecture/assembly changes, semantic tests, upstream merge strategy and owner. Acceptance waits for the completed adaptation and evidence. |
| Reject | C/native-only backend, standalone assembly requirement with no compliant redesign, irreconcilable license, unsound required API, incompatible allocation/locking, irreducible semantic mismatch, unreviewable provenance, or maintenance/security burden exceeding the actual benefit. Record why a Rust wrapper cannot cure it. |
| Blocked | Exact sources, license rights, soundness proof, hardware, backend/toolchain support or required evidence is unavailable. Name what is missing and the owner; do not rebrand a blocker as rejection of the entire Linux feature or silently narrow final scope. |

A dependency can be rejected for kernel linkage while accepted as an external test/reference tool under the project contract. Distinguish that from allowing non-Rust project-owned tools or transitive C implementations. Optional future architectures cannot be dropped to make today's crate look portable.

## Five design checks

- **Crate:** Does a small candidate actually implement the needed contract with fewer risks than the pinned source port? Separate reusable primitive from subsystem implementation and record candidates rejected as well as selected.
- **Bundle:** Reuse reviewed endian decoding, bitfields, intrusive collections, crypto primitives and synchronization boundaries where contracts match. Unify versions/features deliberately; avoid duplicate copies of security-sensitive algorithms or a mega-crate that couples unrelated contexts.
- **Simplify:** Prefer no dependency for a small boring mechanism when ownership/tests are cheaper, but do not hand-roll cryptography casually. Disable unnecessary default features only after checking graph-wide unification. Do not use fixed-capacity containers to invent Linux resource limits merely to avoid allocator integration.
- **Security:** Treat source retrieval, build scripts, proc macros, tool installers, updates and opaque generated artifacts as supply-chain attack surfaces. Keep signing/provenance evidence distinct from correctness and enforce private handling of embargoed advisories.
- **Improve:** Measure code size, memory, stack, copies, allocations, lock contention and hardware throughput/tails before and after integration. Delete needless layers rather than retaining compatibility aliases, and feed sound fixes upstream where appropriate.

## Gate and output contract

Return candidate identity and purpose; exact dependency/features/roles; no_std/allocation/context and atomic/architecture matrix; unsafe/assembly/native/build-script inventory; license/provenance decision; advisories/maintenance owner; accept/adapt/reject/blocked rationale; required and actually observed semantic/security/hardware/performance evidence; and unresolved blockers. Integration is blocked until required audit/adaptation evidence exists. Release qualification cannot be inferred from Cargo success or a clean advisory scan. During planning or no-gates work, cite retained evidence without claiming new execution or unreviewed/benchmarked kernel dependencies; host-tool audit success is not a kernel dependency proof.

## Primary evidence

- [Cargo features](https://doc.rust-lang.org/cargo/reference/features.html): feature unification and default-feature caveats.
- [Cargo build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html): host execution, target-versus-host cfg, native linking and generated output behavior.
- [Rust atomic target configuration](https://doc.rust-lang.org/reference/conditional-compilation.html#target_has_atomic): supported atomic widths and alignment properties; pin compiler documentation for actual qualification.
- [Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html): target tiers have distinct build/test guarantees, not kernel-support guarantees.
- [Linux 6.18.57 license rules](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/license-rules.rst): whole-kernel GPLv2, per-file compatible licenses, SPDX expressions and UAPI exceptions.
- [RustSec](https://rustsec.org/): crate advisory database and available audit tooling; external tools require separate review, not automatic installation.
