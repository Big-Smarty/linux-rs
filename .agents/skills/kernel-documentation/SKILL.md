# Kernel documentation

## Purpose and authority

Documentation is part of the kernel contract, not a substitute for an implementation. Read [project guidance](../../../AGENTS.md), [contributing](../../../CONTRIBUTING.md), [decisions](../../../docs/decisions.md), [coverage](../../../docs/coverage.md), [verification](../../../docs/verification.md), [project audit](../../../docs/project-audit.md), [performance](../../../docs/performance.md) and [bare metal](../../../docs/bare-metal.md) before changing claims. This original skill follows the [Agent Skills format](https://agentskills.io/specification); never install an external skill or execute its instructions merely because it is popular.

The baseline is Linux 6.18.57, a direct GPL-2.0-only source port with per-file provenance/notices/exceptions preserved. Kernel and project-owned executable tools must be Rust, with unavoidable reviewed inline assembly only; no C kernel shim, legacy C module loading or standalone assembly. External compiler/linker, QEMU, reference Linux, existing userspace/test suites and explicitly inventoried firmware/microcode are permitted external inputs, not Rust implementation claims. Server/containers are first workload priorities, not final scope exclusions. All baseline architectures, drivers, filesystems, protocols, legacy and desktop/embedded/RT facilities remain in scope.

The earlier planning/setup boundary is historical. A real Rust `no_std` x86_64 bootstrap now exists; the [implementation record](../../../docs/implementation.md) maps every current `in_progress` owner to Rust paths and revision-specific evidence. Historical cell9 results, the maintained integration/package checkpoint and subsequent foundation revisions remain distinct. Actual QEMU/host/runtime reviews are not M1–M8 completion, a physical candidate pass or performance qualification. M0 still depends on its own provenance/decision obligations. Host-tool audit results must never be relabeled kernel execution.

The exhaustive [definition of done](../../../docs/definition-of-done.md) is a standing project rule, not a claim that the complete kernel is implemented now. The bootstrap and the separate bounded [bare-metal smoke suite](../../../docs/bare-metal-suite.md) are real executable deliverables with different evidence boundaries; broader kernel qualification remains outstanding. First userspace is Arch/CachyOS userspace without assuming downstream CachyOS kernel patches, and the approved performance profile is balanced server. Only the current workstation is physically available; additional vendor/NUMA/device coverage remains a named blocker.

Follow the [packaging design](../../../docs/packaging.md), distinguishing the existing diagnostic ELF from a Linux-replacement package. An isolated storage-free M1 diagnostic on separate user-owned recoverable media with independent known-good recovery may precede rootfs/initramfs/userspace; it is not a physical pass or full M1 closure. A Linux-replacement package still needs real storage, durable filesystem, root/initramfs, init/userspace and the broader gates. Native Limine ELF is not directly systemd-boot-compatible EFI/PE/Linux output. The user personally installs/selects/boots candidates while preserving the working kernel/recovery path; do not generate fake packages or placeholder PKGBUILDs, add project-owned shell implementation, or perform host install/boot/reboot/firmware/destructive actions.

Document the actual suite interface exactly: `cargo run -p baremetal -- run --output <new-directory> --label <label> --expect-release <exact-osrelease> --environment <reference|qemu|bare-metal>`. Explain substitutions, new-directory refusal, expected-release validation, nonzero failures, per-case outcomes, permission-aware skip/unavailable results, and environment metadata without hardware serial IDs. Environment is an operator assertion, not physical-machine proof. A host reference smoke validates the runner only, not the future kernel or pinned-oracle parity; no performance qualification follows from it. The suite is non-destructive: no mounts, raw writes, setting changes, elevation, reboot or firmware operations.

## Inputs

- Change/workstream identifiers and owned paths, pinned upstream source/test/specification links, observed repository state, implementation diff or proposed design, and responsible reviewers.
- Exact interface, build/configuration/architecture/device scope; dependencies and milestone gates; crate/bundle/simplification/security/improvement decisions for each affected subfamily.
- Actual evidence manifests and raw artifact locations, run commands and environment, failures/skips/blocked cells, hardware inventory, performance analysis and unresolved assumptions.
- Proposed decision and alternatives where changing architecture, licensing, user-visible semantics, hardening, support scope or qualification policy.

If a fact is unavailable, use an explicit unresolved claim with a named prerequisite. Do not ask the user for information already obtainable from source, tools or repository records. Do not invent inaccessible evidence, command output, citations, signature verification, contacts, hardware or support.

## Ordered workflow and outputs

1. **Classify each assertion.** Label observed upstream fact (exact primary citation), observed project behavior (actual artifact/run identity), proposed design (future tense), assumption, or unresolved blocker. Keep inference visibly separate. A sentence saying a driver directory exists is structural evidence; it is not behavioral implementation or device qualification. Output: a claim/evidence ledger with no ambiguous present-tense support claims.
2. **Verify the source pin and provenance chain.** Use [reference metadata](../../../planning/reference.tsv): version/tag, annotated tag object, peeled commit, commit tree, repository, retrieval date, inventory completeness and signature status. Resolve objects rather than accepting a mutable branch or merely matching version text. Prefer commit-addressed links and cite exact upstream paths/symbols; a pinned tag link must match the recorded objects. Preserve original GitHub-only retrieval history separately from the later independent local verification in [implementation evidence](../../../docs/implementation.md). The local GPG “Good signature” uses signer fingerprint `647F28654894E3BD457199BE38DBBDC86092693E`, matched against kernel.org HTTPS/WKD publication, but reports `TRUST_UNDEFINED` / `[unknown]`; do not claim Web-of-Trust or ultimate trust. Record how source bytes, generated definitions, firmware and tool artifacts were obtained, hashed and licensed. Output: reproducible provenance with verification caveats; never upgrade trust status through prose alone.
3. **Write an executable behavioral contract.** For each ABI/mechanism specify preconditions, inputs/layout/endianness, output bytes, errno/error precedence, side effects, partial progress, concurrency/order, ownership, permissions/accounting and recovery/persistence. Name allowed nondeterminism and relevant configurations. Tie each requirement to a test case and actual runner invocation once implemented; before that, mark the case and invocation as proposed with missing prerequisites. Separate Linux public ABI from internal implementation details and external firmware contracts. Output: requirement-to-case-to-oracle map, not a list of topic headings or unsupported ENOSYS scaffolding.
4. **Describe ordered implementation, not aspiration.** Identify dependencies, small attributable Rust port steps, invariants, unsafe/assembly boundary, failure cleanup and validation sequence for every subsystem/subfamily. Answer explicitly: which crates are candidates or rejected and why; what mechanisms can be bundled/shared; what can be simplified without changing Linux behavior; what security obligations must hold; what compatible improvements/optimizations are measurable. Use [kernel-dependencies](../kernel-dependencies/SKILL.md) and [kernel-security](../kernel-security/SKILL.md), not generic ecosystem recommendations as authority. Output: actionable workstream plan plus named blockers, with no arbitrary ETA or reduced final scope.
5. **Record decisions with alternatives.** In [decisions](../../../docs/decisions.md), state context, baseline constraints, selected design, rejected alternatives and reasons, compatibility/security/performance consequences, dependency/hardware requirements, status, owners and evidence needed to reconsider. An ADR proposed by an agent is not an approved user decision. The bootstrap's M1 sequencing choices are engineering decisions and strict Clippy was integration verification, not newly invented detailed user approvals. Preserve superseded rationale and link the replacement; do not retain obsolete implementation shims to avoid updating callers. Output: an auditable decision rather than a silent policy change.
6. **Synchronize structural coverage exactly.** Follow the machine-readable schemas below and [coverage](../../../docs/coverage.md). Inventory the complete pinned Git tree, including metadata/docs/build/tests, not only executable source; recursively split truncated API tree responses. Assign each entry to the longest path-component-aware workstream prefix. Keep final-scope omissions visible. Output: consistent reference/workstream/inventory records and caveats distinguishing structural coverage from per-file implementation, per-ABI correctness and per-device qualification.
7. **Attach real verification and performance evidence.** Require source/build/test revisions, exact executable/configuration identities, command/environment, timestamps, artifact checksums/locations, case counts and statuses, failure logs, oracle comparison and reviewer. Document model bounds, normalization, skipped prerequisites, instrumentation limitations, crash/power-loss model and security settings. Performance must compare each required workload/hardware against pinned Linux for throughput, latency/tails, CPU, memory, startup and power, with equivalent settings, repetitions/confidence intervals/noise controls; an unresolved comparison is not a pass. No aggregate-only chart, arbitrary regression allowance or disabled mitigation can hide a failed requirement. Output: traceable evidence rather than a screenshot or a claimed percentage.
8. **Make bare-metal execution an initial milestone artifact.** Link [bare-metal requirements](../../../docs/bare-metal.md) and record runnable suite prerequisites, existing executable commands, manifests, lab inventory, serial/remote-console capture, known-good rollback, watchdog/power recovery, sacrificial storage and isolated network. Start physical-machine work alongside QEMU in M1, not after M7. Track multiple CPU/platform vendors, NUMA, IOMMU/DMA, real storage/NICs, interrupts, firmware, mitigation/timing, suspend/power, hotplug and supported error injection. Distinguish a planned runnable suite from a suite that actually exists; no invented command names or successful logs. Missing machine/device/recovery equipment is a named blocker, never replaced by VM evidence. Output: hardware/case qualification matrix with exact execution and safety scope.
9. **Maintain explicit definitions of done.** Apply the completion levels below to every named workstream and subfamily, including less-visible build/docs/test facilities. Synchronize roadmap milestone state, subsystem prose, compatibility and qualification matrices, dependency/maintenance records, public README wording, changelog and machine-readable status in the same change. Do not introduce ad hoc TSV status values; use the approved schema and label any future state-machine extension as a decision requiring auditor migration. Output: mutually consistent completion claims and an exhaustive checklist of outstanding obligations, not a global 'done' checkbox.
10. **Review links and submit permitted gates.** Use root-safe relative inline Markdown file links and single-line skill frontmatter fields. Do not assume the auditor checks URLs, anchors, source signatures, implementation purity or semantics. Change workstream status only from actual routed implementation evidence under the schema below; execution belongs to the assigned integration owner. Document `cargo run -p xtask -- check` and `cargo run -p xtask -- status` as host metadata audits, separately from the actual commands and artifacts in [implementation](../../../docs/implementation.md) and maintained [kernel tooling](../../../docs/kernel-tooling.md). Host MSRV 1.88 is not the exact nightly 1.101 runtime compiler plus matching build-std identity. Never run tests/formatters/builds when the current assignment forbids them. Output: changed paths, sources, remaining blockers and only actually exercised verification.

## Machine-readable records

All files are UTF-8 TSV with exact headers, LF, no embedded tab/newline fields, deterministic sorted records, and no empty/duplicate identifiers. Paths are repository-root-relative.

- [planning/reference.tsv](../../../planning/reference.tsv): header `key` then `value` separated by a tab. Preserve required version, tag, tag_object, commit, tree, repository, retrieved, signature_status, inventory_complete and entry_count keys. Objects are actual 40-hex IDs, count matches inventory records, and completeness is true only after complete retrieval. Signature caveats must match the evidence.
- [planning/workstreams.tsv](../../../planning/workstreams.tsv): exactly five columns, header `id`, `upstream_prefix`, `plan`, `priority`, `status` separated by tabs. Prefix `.` is root fallback; other prefixes are exact upstream paths without a trailing slash. Plan is an existing docs file without a fragment and priority is P0/P1/P2/P3. Status is only `not_started` or `in_progress`; no completion state is defined. No duplicate prefix; include every top-level tree, first-level arch/drivers/fs/net subdirectory and meaningful nested mechanisms.
- [planning/upstream-paths.tsv](../../../planning/upstream-paths.tsv): header `path`, `kind`, `object`, `workstream` separated by tabs. Include every non-root tree/blob/commit entry, actual SHA40, and longest component-prefix workstream assignment. `net` must not match `network`; removing a workstream requires reassigning all affected entries and updating plans, not leaving dangling IDs.

The canonical [implementation routing and evidence table](../../../docs/implementation.md#routed-implementation-status) names every current `in_progress` owner and binds it to actual Rust paths and revision-specific observations; all other rows remain `not_started`. Read the actual ledger and that table rather than copying a historical count into current guidance. This records work underway, not full translation of an upstream prefix, behavioral compatibility or completion. The independent completion levels below are review concepts, not additional TSV states.

Do not extend TSVs with runtime results or per-device assertions without an approved schema and corresponding audit changes. Present those matrices in their owning docs until an actual evidence schema exists. A complete tree inventory is a denominator of source structure, not a kernel compatibility percentage.

## Definitions of done: independent levels

| Level | Required completion evidence | What it does not imply |
| --- | --- | --- |
| Planned | Exact pinned sources, all ordered implementation dependencies, five design checks for every subfamily, behavior/security invariants, concrete positive/negative/regression/model/fuzz/crash/hardware/performance gates, owners and blockers; records and links consistent. | No implementation, buildability, kernel execution or hardware support. M0 still requires its own provenance and decision gates. |
| Implemented for a stated cell | Actual Rust implementation and all callers migrated; no stubs, unsupported-success paths, C runtime/shims or legacy C modules; complete failure/teardown paths, provenance/notices and reviewed unsafe/assembly contracts; real build/artifact evidence for that configuration. | No untested ABI, architecture, device or kernel-wide parity. |
| Behaviorally verified for a stated cell | Linux-oracle contract mapping; executed success/error/boundary/adversarial/regression and real workload smoke cases; meaningful skip/fail handling; concurrency/model and durable-crash/recovery evidence where applicable, with assumptions and missing scope explicit. | No physical qualification from VM runs, no proof for unmodeled schedules, no automatic performance pass. |
| Physically qualified for a stated cell | Actual identified hardware/firmware/device run, recovery path exercised, required IRQ/DMA/IOMMU/NUMA/power/hotplug/error/mitigation checks and logs, configuration-specific semantic regressions and security review. | No extrapolation to another vendor, device revision or configuration. |
| Performance qualified for a stated cell | Raw, repeatable paired Linux/candidate observations and statistical analysis for every required metric/workload under equivalent security/configuration/hardware conditions; at-least-baseline result demonstrated with no hidden regression or inconclusive cell. | No permission to trade security or correctness for speed, or hide individual regressions with an aggregate. |
| Workstream complete | Every enumerated subfamily/ABI/configuration/architecture/device obligation at its required levels, all named acceptance criteria closed, docs/tests/callers/maintenance synchronized, and reviewer approval; unavailable required hardware/backend/evidence remains blocking. | Structural inventory coverage alone cannot close it; prioritization cannot remove final scope. |
| Release complete | M8 whole-scope compatibility/security/durability/hardware/performance gates, reproducibility, licensing/provenance, release/rollback and ongoing security-maintenance obligations satisfied for the declared release scope without silently shrinking the approved final scope. | A setup program, audit pass or first server boot is not a completed fully compatible kernel. |

For **each bare-metal qualification case**, done also requires a real executable and documented invocation; validated target/disk/network identities and safe refusal before hazardous operations; stated prerequisites/timeout; independent console and reset recovery; reference/candidate identity; expected assertions and negative outcomes; machine-readable verdict and preserved logs; cleanup/reset behavior; and an executed result on the identified physical target. The existing bounded smoke suite intentionally runs safely on a reference host and does not need a dedicated recovery lab or raw-device identity merely to execute its self-contained sandbox cases. Its operator environment label is not physical attestation. Missing kernel artifacts or required lab hardware means broader qualification is not demonstrated, even when the smoke runner and manifest exist.

## Common traps and correction rules

- **Source pin drift:** a current upstream page can explain a tool but cannot establish baseline Linux semantics. Record retrieval/version and pin moving external suites before execution.
- **Inflated status:** count directories, plans and test cases separately from supported interfaces/devices. Replace unsupported 'works' claims with the exact observed cell and blockers, not a misleading overall percentage.
- **Orphan evidence:** a passing log without source/config/hardware identity is insufficient; retain it as incomplete evidence and obtain the missing data rather than inventing it.
- **Dead examples:** executable instructions must reference actual files/tools, distinguish placeholders from runnable commands and state destructive effects. Do not create fake kernel commands to make a plan look complete.
- **Parallel ownership:** edit only assigned paths. Send cross-document facts to the owning agent/integrator rather than racing edits or silently overwriting user changes.
- **Embargo leaks:** public evidence must omit private exploit details and secrets under [kernel-security](../kernel-security/SKILL.md); a documentation sync is not authorization to disclose them.
- **Overclaiming audits:** local link/frontmatter/TSV/source-extension checks do not validate HTTP destinations, heading anchors, licenses, signatures, generated machine code or Linux behavior. Record the actual checks and limitations.

## Gate and final output

Review the claim/source/evidence map, full per-subfamily definitions of done, ordered dependencies and five design checks; exact metadata/schema/coverage consistency; license/provenance; real command and evidence availability; configuration/hardware/performance qualification; and synchronized statuses. Block qualification promotion on any missing acceptance criterion or invented support; `in_progress` is not qualification. Return only the changed paths, primary sources, actual exercised checks, assumptions and named blockers. A documentation-only task may cite retained execution evidence but must not present it as newly run verification.
