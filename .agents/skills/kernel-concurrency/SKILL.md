# Kernel concurrency and memory ordering

## Scope and authority

Use this skill for shared state, publication/reclamation, locks, wait/wakeup protocols, per-CPU data, interrupt exclusion, lock-free algorithms and scheduler-visible concurrency. Read [project instructions](../../../AGENTS.md), [core](../../../docs/subsystems/core.md), [memory](../../../docs/subsystems/memory.md), [process](../../../docs/subsystems/process.md), and [architecture](../../../docs/subsystems/architectures.md) plans. The [current bootstrap](../../../docs/implementation.md) still has one executing BSP. Its subsequent consumed raw-lock/IRQ-save revision uses native atomics and packed root-IF/depth ownership, not a scheduler, complete Linux locking, RCU or RT implementation. Independent saved-state guards must not assume LIFO destruction: `!Send` does not prevent dropping an outer guard first. Require actual IF0/IF1 out-of-order checks, compiler ordering before STI, real pending-IRQ observations across STI's shadow, and explicit NMI/fault exclusion from blocking locks/nesting domains. Old cell9/integrated-005 proof cannot qualify changed guard source, nested NMI, weak-memory, SMP or physical execution; every revision needs its own evidence.

Kernel `no_std` concurrency is not a choice between Tokio and `std::sync`. A plain userspace mutex, generic spinning crate or reference count does not implement IRQ/preemption rules, priority inheritance, RCU, CPU hotplug or Linux wait semantics. Project runtime code is Rust only, with no C locking shim or legacy C modules. Read the unsafe skill for memory-model and aliasing boundaries.

Use the [standing definition of done](../../../docs/definition-of-done.md) for complete implementation/qualification, not merely source translation or stress survival. The actual [bounded smoke suite](../../../docs/bare-metal-suite.md) provides executable memory/thread, sandbox-filesystem, loopback-socket, process and visibility checks with expected-release validation and fresh reports. Its thread smoke is not an IRQ/NMI/RT/RCU model, deadlock proof, full qualification or performance benchmark. Preserve failures/skips/unavailable cases; a reference-host run validates only the runner, and an environment label does not attest real hardware.

Only the current workstation is available for physical execution today; other vendors, topologies and weakly ordered architectures remain named blockers, not assumed coverage. The user installs/selects/boots real candidates following [packaging/recovery design](../../../docs/packaging.md). Do not alter the host bootloader, reboot, change firmware or perform destructive disk operations to collect concurrency evidence.

## Required inputs

For each shared object supply:

- Pinned Linux implementation/API and configuration, owning [workstream](../../../planning/workstreams.tsv), architecture memory model/atomic capabilities, and PREEMPT/preemption/RT variants.
- Every reader, writer, waiter, reclaimer and callback, including task, workqueue, timer, softirq, hardirq, NMI, other CPUs, firmware and devices. Device DMA additionally needs the unsafe/driver protocol; CPU locks alone do not synchronize a device.
- Per-field protection and ownership, legal allocation/block/fault behavior, lifetime/refcount/pinning, lock classes/order, publication event, linearization points or allowed outcomes, and progress/fairness assumptions.
- Wait conditions and wake sources, cancellation/signal/timeout/exit behavior, hotplug and idle transitions, plus a failure schedule for the race being addressed.
- Evidence targets: relevant Linux tests, host model scope, target code-generation checks, QEMU SMP cases and real physical CPU/platform cases from [bare-metal policy](../../../docs/bare-metal.md).

## Ordered design procedure

1. **Write the actor/context matrix.** For every operation state whether it may sleep, allocate with reclaim, fault on userspace, migrate, be preempted, be interrupted/reentered, or execute with IRQs masked. List NMI explicitly: local IRQ masking does not exclude NMI. List all CPUs: preemption/IRQ disabling is local control, not inter-CPU exclusion. Model emergency logging, panic and tracing callbacks rather than assuming instrumentation is non-reentrant.
2. **Define invariants and lifetime before choosing a lock.** Identify data protected by each mechanism and when a pointer can be acquired, published, removed and reclaimed. Separate mutual exclusion, memory visibility, lifetime protection, CPU affinity and progress; one guard rarely proves all five. Refcount acquisition from an unprotected pointer can race with free, and arithmetic overflow or resurrection from zero needs an explicit safe contract.
3. **Choose context-correct primitives.** Sleeping locks require appropriate preemptible task context; raw spinning is for contexts that cannot sleep and short bounded critical sections. For a lock shared with hardirq, use a protocol preventing same-CPU interrupt acquisition while its owner holds it, with saved-state restoration. A lock shared with NMI needs a proven NMI-compatible protocol; blocking or spinning on a lock held by the interrupted context deadlocks. Do not solve this by an unreviewed “try and drop data” behavior change.
4. **Specify preemption and RT behavior.** Distinguish raw spinlock semantics from `spinlock_t`-like semantics: pinned Linux maps the latter differently under PREEMPT_RT and IRQ suffixes do not imply the same physical IRQ state. Pin/migration guards protect per-CPU identity, not against another context accessing the same CPU-local field. Decide which APIs are valid in RT, threaded interrupts and softirq contexts, then implement both applicable semantics deliberately. Do not emulate RT by simply replacing every mutex with a spinlock.
5. **Build the lock dependency graph.** Assign classes, establish an acyclic order, annotate legal nested-object hierarchy and record IRQ/softirq safe/unsafe usage. Include callbacks, allocator/reclaim, filesystem writeback, scheduler operations, teardown and tracing. A local rule such as “never take B under A here” is insufficient if indirect paths create the reverse edge. Implement debug assertions/lockdep-style state and class tracking without changing public semantics. Document which edges and contexts tests actually exercise.
6. **Derive publication ordering.** For each shared state transition write events and required happens-before edges, specifying which load observes which release store or release sequence. Choose Rust atomic operations/orderings legal for the object and target. Explain successful and failed CAS ordering separately. Acquire on an unrelated variable, a fence without a matching protocol, and `Relaxed` payload access do not magically publish initialized data. Account for pointer ABA, counter wraparound, mixed-size access and alignment. Unsupported atomic widths require a valid kernel-context implementation, not an unnoticed runtime helper.
7. **Translate LKMM mechanisms, not syntax.** Linux `READ_ONCE`, dependencies, barriers, refcounts, seqcounts and RCU accesses are defined within Linux's compiler/architecture/model contracts. Plain or volatile Rust accesses racing with writes are not justified by an LKMM example. Map each operation to a supported Rust synchronization contract and compiler lowering; document any required architecture primitive and its proof. Rust `SeqCst` is not a proof of lifecycle correctness, device ordering or equivalence to every Linux barrier. Avoid dependence on compiler-preserved control/address dependencies without a documented supported contract.
8. **Specify waits as state machines.** Define condition check, waiter registration, task-state publication, releasing protection, sleep, wakeup, reacquisition/recheck and waiter removal. Close the check-versus-enqueue lost-wakeup window with the correct lock/atomic protocol. Include spurious wakeups, exclusive wake rules, close/exit, signals, timeout boundaries, nonblocking behavior and memory ordering. Preserve Linux's restart and partial-progress semantics; generic channel cancellation is not automatically equivalent.
9. **Separate removal from reclamation.** For RCU define flavor, read-side entry/exit/context rules, publication/dereference contract, grace-period tracking, preexisting-reader set, callbacks and legal callback context. Include preempted readers, idle/nohz, CPU offline/online and teardown. Do not free on pointer replacement, confuse grace period with callback-drain barrier, or wait for a grace period while holding a lock needed by readers. References derived under RCU must not escape the read-side guard unless a separate lifetime mechanism is safely acquired. SRCU/ordinary RCU/tasks variants are not interchangeable. Bound deferred reclaim backlog and update rate to resist memory-exhaustion attacks.
10. **Check seqlock and lock-free special cases.** Retrying a plain Rust non-atomic read after a concurrent write does not undo UB; use a proven representation/access protocol. Seqcounts do not protect pointer lifetime and can livelock if a reader spins while its writer cannot run. Lock-free does not mean wait-free, bounded latency, starvation-free, or correct under NMI interruption. State reclamation and progress assumptions for every algorithm.
11. **Integrate context-safe ownership.** Make IRQ/migration/preemption guards obey CPU-local acquisition/restoration and nesting rules; do not make them transferable just because an underlying crate guard is `Send`. Audit guard leaks, destruction, early errors, cancellation and prohibited scheduling. Migrate every caller and remove obsolete internal synchronization paths. Record changed invariants and dependencies in owning plans and [decisions](../../../docs/decisions.md).
12. **Optimize only after semantic proof.** Profile contention and protected work, then consider per-CPU batching/sharding, shorter critical sections, read-mostly publication and cacheline separation. Prove cross-shard ordering, hotplug drain, bounded backlog and fairness. Avoid extra allocations, copies, barriers and locking, but never omit required ordering or IRQ protection to win a benchmark.

## Reuse, bundling, simplification, security and improvement

| Question | Required answer for this object/protocol |
| --- | --- |
| Reuse a crate? | Prefer `core::sync::atomic` where its contracts suffice. [Spin](https://docs.rs/spin/latest/spin/) is a candidate algorithm reference or narrowly reviewed component, not a kernel lock subsystem: IRQ/preemption/RT/lockdep/owner rules and transferable/leakable guards need explicit evaluation. [Loom](https://docs.rs/loom/latest/loom/) is host verification infrastructure only. Review exact versions/features, native/runtime code, licensing, unsafe, target atomics/fallbacks, advisories and allocation/context behavior under [dependency policy](../../../docs/dependencies.md). Never accept userspace epoch reclamation as kernel RCU by name alone. |
| Bundle shared mechanisms? | Use one architecture IRQ-state interface, scheduler wait/wakeup contract, lock-class instrumentation, refcount policy, per-CPU lifecycle and RCU core across subsystems. Keep lock domains and policy-specific wake/ordering rules distinct. A global mutex is not a maintainable bundle for unrelated data. |
| Simplify? | Use a conventional lock instead of a bespoke lock-free algorithm only if legal contexts, lifetime/progress semantics and required performance remain satisfied. A temporary UP boot gate is not SMP completion. Do not delete RT, NMI, hotplug, fairness or namespace-visible behavior to make the proof easier. |
| Secure? | Analyze attacker-controlled contention, priority inversion, refcount overflow, callback backlog, repeated wakeups, CPU removal, teardown and object reuse. Prevent denial of service without changing externally mandated semantics. Synchronization does not replace credentials/capability checks or IOMMU isolation. |
| Improve? | Name workload and counters: wait/hold time, acquisitions, cacheline traffic, cross-NUMA transfers, migrations, wakeup/IPI rate, grace-period latency/backlog and IRQ-off duration. Optimize the demonstrated bottleneck and record throughput plus tail/progress/memory/power counter-metrics, not just faster uncontended locking. |

## Model tools and their limits

Use several forms of evidence, and name exactly what each covers:

- **LKMM/herd litmus:** useful for the pinned Linux protocol and allowed/forbidden outcomes. LKMM is not the Rust language memory model, a Rust aliasing proof, an MMIO/DMA model, or a proof that the compiler emitted the intended protocol. Record model revision and litmus assumptions. Reference Linux litmus files may be external non-Rust fixtures, not project kernel implementation.
- **Loom:** all relevant shared accesses and synchronization must use modeled replacements. Hidden atomics/locks are invisible. Record threads, state-space/preemption/branch bounds and modeled allocation/reclamation. Its docs explicitly list relaxed-memory limitations; bounded completion is not exhaustive system correctness. No IRQ/NMI, device, RT scheduler, fairness, clock or hotplug behavior is covered unless explicitly represented, and those representations are abstractions rather than actual execution.
- **Miri/sanitizers/static analysis:** can catch selected UB/races in supported environments; unsupported primitives, instrumentation gaps and allocator/device behavior limit conclusions. Instrumentation can change timing. A clean run does not prove absence of races.
- **Lockdep-style runtime validation:** checks dependency/class/context usage represented and exercised. Correctly annotate hierarchy; unobserved chains, non-lock resource cycles and missing instrumentation remain outside a passing observation. Do not present lockdep's qualified closure claims as proof of all kernel liveness.
- **Target disassembly and real stress:** check instruction widths/barriers, features and ABI; do not treat one compiler's current output as a language guarantee. QEMU scheduling and x86 ordering do not qualify weakly ordered physical architectures.

## Runnable qualification suite and definition of done

Follow [verification](../../../docs/verification.md), [performance](../../../docs/performance.md), and [bare metal](../../../docs/bare-metal.md). Execute gates only with the actual kernel/harness, authorized safe equipment and an assignment permitting execution. The [retained cell9 results](../../../docs/implementation.md) establish only the exercised BSP interrupt/publication subset; broader tests below remain required, not implicitly passed.

For each affected primitive supply runnable Rust harness/test entries, named independently of a particular shell script, covering:

| Gate | Required executable cases and oracles |
| --- | --- |
| M1 local exclusion/entry | Nested save/restore of IRQ state, allowed exception/NMI entry, guard CPU affinity, fault containment and supported emergency console path; expected mask/context transitions and safe recovery. Run in QEMU and on initial physical bring-up hardware. Distinguish QEMU serial from the existing diagnostic framebuffer; neither supplies unexecuted physical evidence. |
| M2 SMP/scheduler | Mutual exclusion/publication, CAS failure paths, contention, recursive/IRQ lock misuse caught by debug checks, wait registration versus wakeup, spurious wakes, timeout/signal/cancel, CPU migration and offline/online with in-flight work; invariant assertions and bounded liveness oracles. |
| M2 onward RCU/lifetime | Reader held across update, preempted reader, concurrent removals, repeated address reuse/ABA, grace-period/callback-drain distinction, offline CPU, callback backlog pressure and shutdown; no early free, lost callback or stale access. |
| Consuming M3–M7 | Real process/IPC/VFS/network/driver workloads under IRQ storms, memory pressure, RT/preemption configurations, cross-NUMA contention, reset/hotplug, suspend/resume and fault injection where supported. Include crash/recovery and observable Linux semantic comparisons. |
| M8/performance | Pinned Linux versus Rust on each required physical topology/vendor/architecture/configuration cell, including weakly ordered machines as implemented. Measure throughput, latency/tails, CPU, memory, startup, relevant power, IRQ-off duration, starvation and reclaim backlog under identical mitigations/firmware/load. |

Every runnable case needs an actual harness invocation once implemented, fixture prerequisites, CPU/device/configuration identity, expected outcome, timeout/failure classification, raw log capture, revision and recovery/cleanup procedure. Use remote/serial recovery, isolated networks and sacrificial storage where applicable. An unavailable device/platform is a named blocked cell, never replaced by a VM result. Test emergency paths without risking the development host.

Done means the invariants are reviewed; every affected context/caller/configuration is integrated; required runnable model, regression and hardware cases exist and their required executions have recorded outcomes; and no unresolved race, deadlock, lifetime, liveness or qualification blocker remains. Performance must be demonstrably at least the pinned baseline per workload/hardware cell with repetitions, confidence intervals and noise control; aggregate wins, arbitrary slowdown allowances, unproven non-inferiority or disabling security are not passes. Report unrun gates honestly and retain unsupported cells in scope.

## Stop and escalation

Stop when a legal calling context cannot be established, a lock is reachable from its interrupted owner, blocking occurs under non-sleepable protection, a Rust race/aliasing rule is violated, reclamation has no proof, model results disagree with assumptions, or required hardware/liveness/performance evidence is unavailable. Escalate with actor matrix, minimal failing schedule/litmus, source/model/compiler revision and precise missing mechanism. Do not “fix” a failure with volatile, blanket `SeqCst`, a global lock, ignored wakeups, lockdep suppression, or dropped functionality without a new complete proof and compatible design.

## Deliverable checklist

- [ ] Actor/context/field-protection matrix, lock graph, memory-order edges, linearization and progress assumptions.
- [ ] Wait/restart, refcount/reclamation, RCU flavor/grace-period/callback, RT and CPU-hotplug contracts.
- [ ] Five design answers, context-safe API/guard review and complete consumer cutover.
- [ ] Runnable regression/model/hardware cases, explicit model bounds and missing behaviors, raw results or unrun blockers.
- [ ] Per-cell bare-metal/performance qualification, security preserved, no completion claim inferred from UP/QEMU success.
