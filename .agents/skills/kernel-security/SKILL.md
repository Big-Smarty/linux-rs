# Kernel security

## Authority and inputs

Read [security](../../../docs/subsystems/security.md), [compatibility](../../../docs/compatibility.md), [licensing](../../../docs/licensing.md), [maintenance](../../../docs/maintenance.md), [bare metal](../../../docs/bare-metal.md) and [performance](../../../docs/performance.md). Use [kernel-unsafe](../kernel-unsafe/SKILL.md), [kernel-concurrency](../kernel-concurrency/SKILL.md) and [kernel-verification](../kernel-verification/SKILL.md) for detailed proofs and execution evidence. This original local skill never authorizes installing unreviewed external skills or running their instructions.

Inputs are the change/workstream ID; pinned Linux 6.18.57 source paths and applicable security updates; exposed ABIs and configurations; trust boundaries; attacker capabilities; allocation/locking/lifetime context; CPU/device/firmware identities; proposed dependency graph; test and recovery environment. Record whether the actor is an unprivileged local user, container administrator, host administrator, remote network peer, guest, malicious peripheral, storage-image author or firmware supplier. Distinguish intended policy from claimed protection against that actor.

The project is a direct GPL-2.0-only port, not a clean-room replacement. Safe Rust helps memory safety but does not prove authorization, DMA isolation, side-channel safety or protocol correctness. No legacy C module loading, C shim or non-Rust project-owned executable implementation is permitted. External firmware/microcode is a separate provenance/licensing/trust boundary, never advertised as Rust. The [existing bootstrap](../../../docs/implementation.md) has checked firmware/range parsing, owned W^X mappings, guard/fault tests and raw-before-reference initialization in its narrow BSP cell. Its trusted loader/immutable-firmware assumptions do not protect against malicious firmware or DMA; credentials, Linux isolation, CPU mitigations, entropy, physical security evidence and independent review remain open.

Apply the standing [definition of done](../../../docs/definition-of-done.md). First userspace is Arch/CachyOS userspace, not a port of CachyOS kernel patches; performance uses the approved balanced-server profile. Only the current workstation is available, so additional vendor/device/NUMA evidence remains blocked until obtained. The [bounded smoke suite](../../../docs/bare-metal-suite.md) is non-destructive host/guest Rust tooling, not a kernel security certification; its environment label is an operator assertion. Never elevate, mount, raw-write, reboot, change firmware or change settings through that suite. Future [Arch-style packaging and boot selection](../../../docs/packaging.md) is user-operated with a known-good kernel/recovery path preserved, not permission to install or boot anything during this task.

## Ordered review procedure

1. **Identify assets and entry points.** Enumerate secrets, executable code, credentials, persistent data, availability and accounting. Trace user-controlled data from syscalls/ioctls, procfs/sysfs/netlink, sockets, mounted images, firmware tables, device descriptors, DMA rings, BPF/perf/trace, module/extension and guest entry paths to privileged effects. Include compat paths, teardown, error paths and debug facilities. Output: trust-boundary/data-flow map, attacker assumptions and reachable-surface list mapped to pinned source.
2. **Write invariants before mechanisms.** Specify user/kernel address separation, W^X and read-only-after-init policy, no uninitialized output/padding, no reference-count overflow, checked sizes, revocation semantics, IRQ-safe locking, DMA lifetime, authority checks and bounded resource consumption. For each invariant name the responsible primitive, bypass routes and negative test. Output: a security contract and obligation owner; a generic claim of memory safety is insufficient.
3. **Review each applicable surface using the table below.** Follow ownership from acquisition through async completion, cancellation, revocation and reuse. Confirm authorization uses the correct namespace/object/credential snapshot and is repeated when state can change. Output: concrete defects or evidence-backed reviewed invariants, with upstream compatibility implications.
4. **Audit unsafe and external code.** Inventory unsafe functions/blocks, Send/Sync implementations, raw user pointers, assembly, JIT/code-patching, MMIO and DMA. Require validity/alignment/initialization/aliasing/lifetime and synchronization proofs and explicit safe-wrapper contracts. Inline assembly is allowed only when unavoidable: record why Rust/intrinsics cannot implement the operation, registers, memory effects, clobbers, privilege, reviewers and required disassembly inspection. No standalone assembly is allowed. Review dependency build scripts/proc macros as executable supply-chain inputs through [kernel-dependencies](../kernel-dependencies/SKILL.md). Output: complete unsafe/assembly/dependency review, not just a count of `unsafe` tokens.
5. **Preserve behavior without reproducing vulnerabilities blindly.** Compare permission failures, errno precedence, namespace identity mappings, credential transitions and interface visibility against the pinned oracle. Where the baseline contains a confirmed defect, propose an explicit security/compatibility decision and regression, not an undocumented divergence or a copied exploit. Keep obscure APIs in final scope; configurable hardening is not permission to claim a removed ABI works. Output: compatibility decision and any ADR required in [decisions](../../../docs/decisions.md).
6. **Exercise hostile transitions.** Test malformed/oversized/truncated inputs, cross-page usercopy faults, concurrent mutation/unmap, failed allocations, reference exhaustion, privilege drop/revoke, fork/exec races, namespace escape, malformed storage/network/firmware data, device reset/remove during DMA and corrupted completions. Fuzz reachable parsers and syscall sequences; model security-sensitive publication/revocation races; replay regressions in production-equivalent configurations as well as instrumented ones. Output: attack-to-invariant-to-case mapping with reproducible manifests and failures, not an assurance based on a clean compile.
7. **Validate hardware defenses from initial bring-up.** Co-develop QEMU and physical-machine review from M1: recoverable serial/remote console, known-good boot media, isolated lab networks and sacrificial disks. Confirm page permissions, privilege transitions, IOMMU mappings, DMA confinement, interrupt state, firmware handoff and CPU mitigation selection on actual CPU/platform vendors. Cover SMP/SMT, NUMA, migration, suspend/resume, hotplug and reset because defenses can be lost there. Read back relevant control state where safe and inspect generated code. Unavailable hardware is a named blocker; emulated features cannot qualify physical devices or timings. Output: per-platform mitigation/firmware records and adversarial evidence.
8. **Measure, then optimize without weakening defenses.** Use equivalent Linux/candidate mitigation settings, security policies, compiler settings and physical configurations. Measure per-workload throughput, tail latency, CPU, memory, startup and power with repetitions, confidence intervals and noise controls. Optimize redundant allocation/copy/serialization only after correctness and side-channel review. Disabling checks, reducing entropy, bypassing IOMMU or suppressing mitigations to beat Linux is a failure. Unproved non-regression remains inconclusive. Output: security/performance trade-off analysis consistent with the mandatory at-least-baseline release requirement.
9. **Publish the appropriate report.** Public routine review lists scope, assumptions, findings, severity rationale, fixes and evidence. Security findings follow the private procedure below. Synchronize documented protection and support claims with actual evidence through [kernel-documentation](../kernel-documentation/SKILL.md). Output: approved review, unresolved blockers and exact qualification scope; never invent a security contact, key, CVE or test pass.

## Surface-specific obligations

| Surface | Concrete review and negative evidence |
| --- | --- |
| Syscalls, ioctls and user memory | Decode compat layouts/endianness/flags explicitly; bound counts before multiplication; treat every user access as fallible and concurrently mutable. Reject double-fetch assumptions; choose validated copied metadata or reviewed pinning while preserving Linux race/fault semantics. Verify partial-copy behavior, no leaked padding or kernel addresses, and failure precedence. |
| Network, filesystem and other data parsers | Validate lengths, offsets, alignment, nesting, checksums and arithmetic before creating references. Preserve protocol state on duplicate/reordered input; bound work, memory and amplification. Test hostile images, decompression bombs, fragment reassembly exhaustion, replay and partial persistence. Parsing into a Rust type is not proof the bytes satisfy its validity rules. |
| Drivers, DMA and firmware | Separate MMIO volatility from ordering; validate device-owned indices, descriptors and completion lengths. Pin/map buffers only for their true device lifetime; account for noncoherent caches, stale DMA after reset, IOMMU invalidation and bounce-buffer initialization. Revoke bus mastering/isolate before freeing where required by hardware. Exercise malformed descriptors, surprise removal and interrupt storms. |
| Credentials and authorization | Trace real/effective/saved IDs, fsuid, capabilities, groups, exec/set-id/file capabilities, securebits and no_new_privs. Respect user-namespace mappings and object-relative capability checks. Review credential publication/RCU lifetime, fd passing, ptrace, `/proc`, key access and policy hooks for stale authority or confused deputies. |
| Containers, guests and policy isolation | Check mount/PID/user/network/IPC namespaces, cgroup ownership/accounting/limits, seccomp, LSM hooks and cross-boundary handles. A namespace is not by itself a security boundary. For virtualization validate guest memory translation, host mappings, nested exits and device passthrough; test denial of service as well as confidentiality/integrity. |
| Speculation and CPU state | Review syscall/interrupt/exception entry and exit, indirect control flow/JIT, user-controlled indexing, context switches and VM/firmware transitions. Select mitigations from actual CPU/microcode capabilities; verify generated sequences and SMT policy. Check all architectural extended state for leakage, including lazy-save hazards. Memory-safe bounds checks do not automatically stop transient execution. |
| Cryptography, entropy and keys | Audit algorithm/mode/parameter compatibility, constant-time behavior on the actual architecture, entropy readiness/blocking semantics, nonce uniqueness, authenticated-decryption failure, key lifetime/zeroization and async request ownership. Check algorithm selection names/priorities and sync/async completion semantics. Use known-answer, differential and invalid-tag/key/length tests; a primitive crate is not the Linux crypto API, FIPS validation or entropy proof. |
| Debug, logging and extensions | Enforce capability/policy boundaries on perf, tracing, dumps, firmware updates, BPF, module/extension loading and executable mappings. Restrict raw addresses/secrets in errors and traces; preserve necessary audit information without exposing embargoed data. Verify module signature/policy semantics for Rust replacements rather than loading C modules. |

## Crate, bundle, simplify and improve decisions

- **Crates:** Consider narrowly scoped reviewed Rust cryptographic/parser primitives only after no_std, allocation, assembly, target-feature, constant-time, licensing, transitive-code and maintenance audit. An ecosystem audit badge or popular package is not evidence for the selected version or CPU. Reject native C wrappers and unaudited fallback code; adaptation needs its own owned review and update path.
- **Bundle:** Share credential/capability checks, validated usercopy boundaries, checked size arithmetic, DMA lifetime and key-handling primitives where the contracts genuinely match. Keep policy selection distinct from enforcement and avoid a universal helper that loses namespace or execution-context information.
- **Simplify:** Prefer narrow APIs, immutable publication and explicit state machines to implicit authority. Reduce internal writable state and duplicate parsers without dropping baseline interfaces or legacy algorithms from final compatibility scope. Do not replace a privilege check with an unchecked assumption for a fast path.
- **Improve:** Turn findings into type-level obligations and regression cases; remove redundant copies/locks only with measured evidence and preserved isolation. Stronger defaults or new hardening require explicit compatibility and performance analysis, not unsupported claims of being universally more secure.

## Vulnerability and embargo procedure

1. Stop public dissemination of a suspected nonpublic vulnerability. Do not put exploit inputs, secrets, full traces or revealing patches in public issues, CI logs, shared corpora or generated planning documents. Keep a private minimal report with source/config/hardware versions, impact, prerequisites, reproducer, mitigations, proposed fix and affected releases; sanitize credentials and personal data.
2. Use the established project private reporting channel if one actually exists. If no owner/contact/infrastructure exists, record that operational blocker and request a trusted private channel from the maintainer without posting the exploit. Never invent a project security mailbox or assume private storage from a filename.
3. For shared Linux defects coordinate with `security@kernel.org` under the pinned [Linux security-bug process](https://raw.githubusercontent.com/gregkh/linux/v6.18.57/Documentation/process/security-bugs.rst). Be available for reproduction and fix review. That process is not a promise this project has an equivalent team; do not contact distro coordination lists casually or conflate their rules.
4. Agree affected parties, access list, embargo clock, fix readiness, rollback, release coordination and reporter consent. Linux's documented ordinary maximum deferral is seven calendar days from the start of the release process, exceptionally fourteen by agreement; do not misstate that as seven days from initial report or a universal project policy. Original reports/discussions/exploits remain confidential absent permission even after a fix is public.
5. Validate the fix and affected branches privately; coordinate advisories and CVE handling with the appropriate authority without requiring a CVE before fixing. Publish only approved material when authorized; then add sanitized permanent regression coverage and update dependency/maintenance records. Output: private evidence and disclosure authorization, followed by a truthful public advisory, never a fabricated identifier.

## Gates and traps

Block integration for missing authorization, unsafe/DMA lifetime proof, uninitialized disclosure, unresolved exploitable defect, incompatible native dependency, or absent required negative evidence. Block protection/support claims on missing hardware/mitigation evidence; block release on failed/inconclusive required performance or incomplete security scope. A Rust type, sanitizer-clean run, QEMU pass, timing t-test, signature badge or empty advisory scan cannot independently prove security. Write remaining risk and tool limitations explicitly. Planning audit success never means these kernel gates executed.
