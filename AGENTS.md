## Non-negotiable implementation boundaries

1. Kernel code and project-owned executable tools MUST be implemented in Rust. The kernel uses `no_std`; host tools may use `std`. Do not add C/C++, Zig, standalone assembly, shell/Python/JavaScript implementation scripts, a C kernel shim, C-backed Rust bridges, `-sys` wrappers around C functionality, or legacy C kernel modules. Port every required **in-baseline** module's functionality to Rust. Arbitrary third-party/proprietary out-of-tree module functionality is not implicitly promised; additions require separately enumerated, approved scope. `repr(C)` and `extern` ABI declarations are not themselves C implementation, but they MUST NOT conceal calls into a C-backed kernel runtime.
2. External rustc/LLVM/linker tools, QEMU, reference Linux, existing userspace programs, and external test suites may be non-Rust. They are development/reference inputs, not Rust kernel implementation. Firmware and microcode require the provenance, license, integrity, and trust records in [firmware](docs/subsystems/firmware.md) and [licensing](docs/licensing.md); never describe them as Rust. Inspect generated code, compiler builtins, linked objects, dependencies, and build steps rather than treating file extensions as proof of a Rust-only executable.
3. Inline assembly is permitted **only where unavoidable** for a documented operation. Each site MUST state why safe Rust, ordinary Rust, and supported intrinsics cannot express it; architecture/CPU prerequisites; input/output registers; clobbers; flags; stack/alignment; memory effects and ordering; privilege/interrupt/preemption requirements; control-flow and unwind contract. Require an architecture reviewer, unsafe reviewer, and compiler/disassembly evidence for each supported configuration. Prefer the smallest Rust-scoped `asm!` or necessary `naked_asm!` boundary; do not move implementation into `.S`, `.s`, `.asm`, included assembly blobs, or a `global_asm!` escape hatch. Unsupported compiler/architecture capability is a named blocker, not permission to add another implementation language. See the [Rust assembly rules](https://doc.rust-lang.org/reference/inline-assembly.html) and [architecture plan](docs/subsystems/architectures.md).
4. Exact Linux-facing ABI **and observable semantics** are required: syscall numbers and calling conventions, layouts, compat ABIs, errors and precedence, partial results, restart/signal behavior, faults, readiness, timing contracts, resource accounting, filesystem formats, network protocols, ioctl/netlink/procfs/sysfs behavior, and privilege boundaries. Stable internal Linux C driver ABI is not a goal; Rust internals may differ. See [compatibility](docs/compatibility.md). Do not replace functionality with success-shaped no-ops, broad `ENOSYS`, fake devices, unsupported panics, stubs, or undocumented special cases. Linux-defined unsupported behavior must be reproduced only with source and differential evidence.
5. The complete pinned scope remains in scope: every architecture, driver family, filesystem, protocol, security facility, test/build/documentation area, and obscure or legacy interface. x86_64 QEMU and server/container workloads are sequencing priorities, not exclusions. Do not delete inventory rows or lower scope to make a gate pass.

### Allocation, execution contexts, and unsafe boundaries

- Kernel allocations MUST be fallible and context-aware: define sleep/reclaim/I/O/filesystem-reentry permissions, accounting/quotas, NUMA/zone/alignment/DMA constraints, reserve use, failure cleanup, and Linux-visible errors. No infallible collection growth, unchecked allocation assumptions, or user-triggered panic/abort. A heap is permitted; avoidable allocations/copies/computation are not. Never substitute a blanket no-heap rule for Linux memory semantics. See [memory](docs/subsystems/memory.md).
- Before using a blocking operation or destructor, document whether the context is task, hardirq, softirq, NMI, preemption-disabled, or reclaim-sensitive. Do not sleep or perform reclaim/I/O under an incompatible spinlock/context. Teardown and error paths obey the same rules as success paths.
- Minimize unsafe boundaries behind narrow safe interfaces. Every unsafe operation needs a local `SAFETY` justification establishing actual preconditions; every unsafe API needs caller obligations. Prove pointer origin/provenance, lifetime, alignment, initialization, aliasing, valid bit patterns, layout, bounds, synchronization, and teardown. An unsafe `Send`/`Sync` implementation needs its own argument. A comment restating the operation is not proof; a successful test is not a soundness proof.
- Never directly trust or dereference a userspace address. Use the reviewed fault-aware access/copy/pinning mechanism, checked lengths/arithmetic, permission checks, short-copy/error semantics, and TOCTOU/lifetime handling. Treat disk/network/firmware/device data as untrusted too. Do not turn mutable DMA or userspace memory into an ordinary Rust reference with an unjustified exclusive/stable-memory promise.
- Keep CPU virtual, CPU physical, and DMA/bus addresses distinct. DMA ownership transfers, mapping errors, masks, coherency/cache maintenance, barriers, IOMMU isolation, pinning, completion, reset, and unmap/free order MUST be explicit. No unchecked DMA, guessed identity mapping, or freeing live device buffers. See [drivers](docs/subsystems/drivers.md) and [security](docs/subsystems/security.md).

### SMP, per-CPU state, RCU, and locking

For every shared object record its ownership/lifetime, synchronization domain, reader/writer contexts, publication/reclamation protocol, and invariants. Per-CPU access requires a proved CPU-pinning/migration/preemption rule; local interrupt masking does not protect against other CPUs. Include CPU hotplug and offline teardown. Atomics need an explicit happens-before argument and justified memory order; do not translate the Linux memory model mechanically into Rust atomics or replace RCU with reference counting without semantic/performance proof.

Every lock class MUST have a documented order in the owning plan: permitted predecessor/successor classes, nesting/subclass rules, IRQ/NMI/reclaim interactions, sleeping restrictions, and callback/reentry edges. Cross-subsystem acquisition adds an edge to both owners' shared lock-order DAG before implementation; reject cycles, recursive acquisition, and unproved exceptions. There is no invented universal lock list in this planning tree. Runtime lock-order diagnostics and adversarial SMP tests are future gates, not substitutes for the design argument. RCU requires correct flavor/read-side conditions, publication ordering, grace-period progress, callback context, and delayed reclamation through teardown and hotplug. See [core](docs/subsystems/core.md) and [process](docs/subsystems/process.md).

## Evidence, review, performance, and physical hardware

- Follow [verification](docs/verification.md) and [security](docs/subsystems/security.md): semantic differential tests against the pin, boundary/negative cases, fuzz/adversarial inputs, allocation/fault injection, SMP stress, recovery/crash consistency, and regressions. Name the exact configuration, artifacts, commands, results, and remaining blind spots. External test code may remain external; repository-owned harness logic must be Rust.
- Review MUST cover correctness, Linux compatibility, unsafe contracts, locking/order, resource exhaustion, access control, attack surface, dependencies/licenses, and operational recovery. An author/agent cannot substitute self-assertion for the required independent subsystem/security/architecture review. A discovered security issue follows [maintenance](docs/maintenance.md); do not expose secrets or execute weaponized tests on a normal host.
- Performance **at least the pinned real Linux baseline** is a release requirement, not a demonstrated property. Follow [performance](docs/performance.md): per-workload/per-hardware throughput, latency/tails, CPU, memory, startup, and power; matched configurations/security mitigations/compiler settings/topology/storage/firmware; repetitions, confidence intervals, and noise controls. No geometric-mean-only masking, arbitrary tolerated regression, or disabling security to win. Inconclusive comparisons are not passes. Optimize only while preserving correctness/security/semantics, and remove avoidable allocation, copying, and locking with measured evidence.
- QEMU is the first debugging target, **not a replacement for physical hardware**. Co-develop bare metal from M1, using the [bare-metal plan](docs/bare-metal.md): serial/remote console and recovery, sacrificial media, isolated networks, multiple CPU/platform vendors, NUMA, IOMMU/DMA, real storage/network, interrupts, firmware, power/suspend, hotplug, fault handling, security mitigations, and timing. Unavailable hardware is a named qualification blocker. Never perform destructive tests against a contributor's host or production devices.
- Never fabricate a pass, log, benchmark, signature verification, review, supported-device claim, or test execution. Distinguish observed fact, proposed design, inference, and blocker. A structural inventory/audit does not prove semantic completeness, security, code purity, or bootability. Publish only exercised checks, including failures and skips.

Before implementation, write an exhaustive, task-specific definition of done tracing every named pinned mechanism and Linux-visible success/error/security/recovery behavior to the relevant architecture/configuration, actual executable tests, review, and retained evidence. Answer exactly: **Can I use a preexisting crate? Can I bundle functionality together? Can I simplify things? Is this secure? See [contributor acceptance definitions](CONTRIBUTING.md) and the cross-project [definition of done](docs/definition-of-done.md). The standing full-completion rule remains in force during implementation; a bounded bootstrap or runnable smoke tool does not satisfy it.

A runnable suite requires real Rust-owned runner/harness code, documented executable commands/case IDs, bounded operations, new-output-directory protection, timeouts, per-case failures/skips/unavailable states, and retained results. The current [bare-metal smoke suite](docs/bare-metal-suite.md) runs bounded non-destructive functional checks on an existing Linux environment; its explicit environment label is an operator assertion, not proof of physical execution or candidate origin. It must not mount, raw-write devices, change system settings, elevate, reboot, or update firmware. Full kernel/hardware qualification additionally requires exhaustive hardware/firmware/configuration coverage, serial/remote-console recovery, safe separately authorized destructive cases where required, actual candidate physical execution, differential behavior, stress/recovery, and baseline performance evidence. The smoke suite, structural auditor, prose plan, or QEMU alone cannot establish that qualification. Do not mark a task, milestone, target, performance gate, or full parity release done while any required item remains uncovered or blocked.

Only the current workstation is presently available; additional vendor/platform/device coverage is a named blocker, not an assumption of support. The user personally installs/selects/boots physical candidates. Agents MUST NOT perform host package installation, bootloader/boot-entry changes, reboot, firmware changes, mounts, raw-device/destructive-disk operations or elevation. Read-only workstation observations are not physical attestation or proof of recovery.
